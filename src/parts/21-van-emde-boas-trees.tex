\chapter{van Emde Boas Trees}

In Chapter~20, Fibonacci heaps drove insertion and decrease-key down to $\Oh(1)$ amortized time, yet extracting the minimum still took $\Om(\lg n)$ comparisons, where $n$ is the number of stored keys (recall from Chapter~14 that $\lg$ means $\log_2$). Every data structure that orders keys solely by comparing pairs (``is $a < b$?''), including balanced binary search trees (BSTs), red-black trees, B-trees, and heaps, must spend $\Om(\lg n)$ comparisons in the worst case to locate or extract a key, because each yes/no comparison can at best halve the remaining possibilities.

What happens if keys are not abstract objects, but integers drawn from a known, bounded range $\{0, 1, \dots, u-1\}$, such as $32$-bit network addresses, millisecond timestamps within a day, or byte positions in memory? Then we can bypass pairwise comparisons altogether: we can \emph{look at the bits} of a key and use them as array indices. Once key bits become memory addresses, an exponential speedup becomes possible. The van Emde Boas tree (written vEB) supports
\textsc{Insert}, \textsc{Delete}, \textsc{Member}, \textsc{Minimum},
\textsc{Maximum}, \textsc{Successor}, and \textsc{Predecessor} all in
\[
  \Oh(\lg \lg u)
\]
worst-case time, where $u$ is the size of the \emph{universe} of possible keys rather than the
number $n$ of keys currently stored. For a $32$-bit universe,
$u = 2^{32}$ and $\lg\lg u = \lg 32 = 5$. At most five levels of descent
suffice for any query, whether the structure holds ten keys or ten
million, and regardless of how keys are distributed.

We build the structure step by step from an array of bits. Each refinement removes the bottleneck of the previous design until every operation runs in $\Oh(\lg\lg u)$ time.

\section{The problem, stated carefully}

Fix a universe size $u = 2^k$, so each key fits in $k = \lg u$ bits. To avoid floors and ceilings when we repeatedly take square roots of $u$, we assume throughout this chapter that the bit-length $k$ is itself a power of two ($u \in \{2, 4, 16, 256, 2^{16}, 2^{32}, \dots\}$), so $\sqrt{u} = 2^{k/2}$ stays an integer all the way down to $2$. (When $k$ is odd, splitting $k$ bits into $\lceil k/2 \rceil$ and $\lfloor k/2 \rfloor$ bits achieves the same time bounds; see Exercise~\ref{ch21:ex-space}.) The keys we store are integers from
$\{0, 1, 2, \dots, u-1\}$. We want a \emph{dynamic set} $S \subseteq
\{0,\dots,u-1\}$ supporting these operations:

\begin{itemize}
  \item $\textsc{Member}(S, x)$: is $x \in S$?
  \item $\textsc{Insert}(S, x)$, $\textsc{Delete}(S, x)$: add or remove a key $x$.
  \item $\textsc{Minimum}(S)$, $\textsc{Maximum}(S)$: the smallest or largest key in $S$,
        or $\textsc{nil}$ if $S$ is empty.
  \item $\textsc{Successor}(S, x)$: the smallest key in $S$ strictly greater
        than $x$ (or $\textsc{nil}$ if none exists). Note that $x$ itself need not be in $S$.
  \item $\textsc{Predecessor}(S, x)$: the largest key in $S$ strictly less than $x$ (or $\textsc{nil}$).
\end{itemize}

The hard operations are \textsc{Successor} and \textsc{Predecessor}. Membership
and min/max are easy to make fast in isolation; the difficulty is making
\emph{successor} fast \emph{at the same time}. A hash table (Chapter~11) achieves
\textsc{Member} and \textsc{Insert} in $\Oh(1)$ expected time, but keys are
scattered across buckets, so locating the next key above $x$
requires scanning. A balanced BST (Chapters~12--13) supports successor in $\Oh(\lg n)$ time
but pays $\Oh(\lg n)$ for every operation. We want all operations to be fast
simultaneously by using the integer structure of the universe.

\begin{focusbox}
The cost is measured against $u$, the \emph{universe size}, not $n$, the number
of stored keys. We trade a dependence on key count
$n$ for a double-logarithmic dependence on the universe size $u$.
\end{focusbox}

\begin{aestheticbox}
Where does a bounded-integer universe with fast successor show up?
Network routers perform longest-prefix matching on $32$- or $128$-bit Internet Protocol (IP)
addresses (finding the most specific routing rule that fits a destination), which reduces to repeated successor and predecessor queries on integer
keys. Event simulators and operating system schedulers keep queues of integer
timestamps and repeatedly ask ``what is the next scheduled event?'' Memory
allocators track free blocks by integer addresses. In each case, $n$ can be
large while $u$ is fixed by the machine word size (the number of bits the processor handles at once, such as $32$ or $64$ bits), and cutting $\lg n$ down to
$\lg\lg u$ keeps query times small.
\end{aestheticbox}

\section{Idea zero: the bit vector}

The simplest structure that stores a subset $S \subseteq \{0,\dots,u-1\}$ is a
\emph{bit vector}: an array $A[0\,..\,u-1]$ of $u$ bits with $A[i] = 1$ if $i \in S$ and $A[i] = 0$ otherwise.

\begin{intuitionbox}
Picture a row of $u$ light switches, one per possible key, all initially
off. Inserting $x$ flips switch $x$ on; deleting flips it off; membership asks
``is switch $x$ on?'' To find the successor of $x$, you stand at switch $x$ and
walk right until you hit the next lit switch.
\end{intuitionbox}

\textsc{Member}, \textsc{Insert}, and \textsc{Delete} run in $\Oh(1)$
time by indexing straight to bit $x$. Figure~\ref{ch21:bit-vector} shows why \textsc{Successor} is slow: to find the
next key after $x$, we must scan $A[x+1], A[x+2], \dots$ sequentially until we
encounter a $1$ or reach the end. In the worst case, such as $S = \{0, u-1\}$ when
we ask for $\textsc{Successor}(S, 0)$, we scan nearly all $u$ bits.

\textbf{Bit vector.}
\textsc{Member}/\textsc{Insert}/\textsc{Delete}: $\Oh(1)$.

Eliminating that $\Oh(u)$ successor scan is the goal of the rest of the chapter.

\section{Idea one: a tree of summaries (the layered approach)}

The bit vector's weakness is that successor scans a flat row with no
shortcuts. To add shortcuts, lay a complete binary tree over the $u$ bits, with the
bits as leaves. Each internal node stores the logical OR of its two children ($1$ if at least one child is $1$, and $0$ otherwise), so a node holds
$1$ exactly when its subtree contains at least one key.
Figure~\ref{ch21:summary-tree} traces a successor query on such a tree for $u = 8$.

How does this help successor? Start at leaf $x$ and
\emph{climb}. At each step along the upward path, whenever you come up from a left child, check whether its right sibling holds a $1$. The first time that right sibling is $1$, cross into it and
\emph{descend}, taking the left child if it is $1$ and the right child otherwise, until you reach a
leaf. That leaf is the successor of $x$. Climbing takes $\Oh(\lg u)$ steps and descending takes
$\Oh(\lg u)$ steps, so successor runs in $\Oh(\lg u)$ time (and insertions and deletions also update the $\lg u$ ancestors along one root-to-leaf path in $\Oh(\lg u)$ time).

That matches a balanced BST on $u$ slots without pairwise key comparisons, yet
$\Oh(\lg u)$ is still slower than our $\Oh(\lg\lg u)$ target. The binary summary tree has
$\lg u$ levels and we walk up and down them. To go faster we need a tree that is
much shallower, which means giving each node many children instead of two.

\begin{walkbox}
The binary summary tree has branching
factor $2$ (each internal node has two children) and height $\lg u$. If instead each node had $\sqrt{u}$ children at the top, $\sqrt{\sqrt{u}} = u^{1/4}$ at the next level, and so on down to $2$,
how tall would the tree be? Work out the number of levels for $u = 2^{16}$ under branching
factor $2$ versus square-root branching ($\sqrt{u}=2^8$, then $2^4$, $2^2$, $2^1$).
\end{walkbox}

\section{Idea two: split the key, build proto-vEB}

To reach a tree depth of $\lg\lg u$, we branch by $\sqrt{u}$ instead of $2$. Take a key
$x \in \{0,\dots,u-1\}$ written in binary using $k = \lg u$ bits, and split its bits
into two equal halves. The \emph{high half} (the upper, most significant
$k/2$ bits) selects one of $\sqrt{u}$ \emph{clusters}. The
\emph{low half} (the lower, least significant $k/2$ bits) selects a relative offset \emph{within} that
cluster, out of $\sqrt{u}$ slots.

Formally, with $u = 2^k$ and $\sqrt{u} = 2^{k/2}$, for any key $x$, cluster number $h \in \{0,\dots,\sqrt{u}-1\}$, and within-cluster offset $\ell \in \{0,\dots,\sqrt{u}-1\}$, define
\[
  \mathrm{high}(x) = \left\lfloor \frac{x}{\sqrt{u}} \right\rfloor,
  \qquad
  \mathrm{low}(x) = x \bmod \sqrt{u},
  \qquad
  \mathrm{index}(h,\ell) = h\sqrt{u} + \ell .
\]
Because $\sqrt{u} = 2^{k/2}$ is a power of two, hardware and programming languages compute these without division or multiplication, using single-instruction bit operations:
\[
  \mathrm{high}(x) = x \gg (k/2), \qquad
  \mathrm{low}(x) = x \,\&\, (2^{k/2} - 1), \qquad
  \mathrm{index}(h, \ell) = (h \ll (k/2)) \mid \ell .
\]
Here $x \gg (k/2)$ shifts the bits of $x$ right by $k/2$ places, discarding the low half; $\,\&\,$ is bitwise AND with the bitmask $2^{k/2} - 1$ (whose binary form is $k/2$ consecutive ones, zeroing out the high half and keeping the low half); $h \ll (k/2)$ shifts $h$ left by $k/2$ places, filling the bottom $k/2$ bits with zeros; and $\mid$ is bitwise OR, placing $\ell$ into those zero bits.
The $\mathrm{index}$ function reassembles the two halves into the original
integer, so $x = \mathrm{index}(\mathrm{high}(x), \mathrm{low}(x))$ for every $x$, in $\Oh(1)$ time.

\begin{example}[Splitting a key]
Let $u = 16$, so $\sqrt{u} = 4$ and keys are $4$-bit numbers. Take $x = 13$,
which in base~$2$ is $1101_2$ (the subscript $2$ marks binary notation). The high two bits are $11_2 = 3$ and the low two bits
are $01_2 = 1$:
\begin{align*}
  \mathrm{high}(13) &= \lfloor 13/4 \rfloor = 3, \\
  \mathrm{low}(13) &= 13 \bmod 4 = 1, \\
  \mathrm{index}(3,1) &= 3\cdot 4 + 1 = 13. \quad\checkmark
\end{align*}
Key $13$ sits in cluster $3$ at internal offset $1$ (Figure~\ref{ch21:bit-split}).
\end{example}

We now build a preliminary recursive structure called \emph{proto-vEB} (short for \emph{prototype van Emde Boas}). A structure of
size $u$, written $\text{proto-vEB}(u)$, contains:

\begin{itemize}
  \item if $u = 2$ (the base case), a $2$-bit array $A[0\,..\,1]$ holding the
        set directly;
  \item otherwise ($u > 2$), an array $\mathit{cluster}[0\,..\,\sqrt{u}-1]$ of
        $\sqrt{u}$ pointers, each to a $\text{proto-vEB}(\sqrt{u})$ holding one
        cluster's keys, plus one extra
        $\text{proto-vEB}(\sqrt{u})$ called $\mathit{summary}$.
\end{itemize}

The $\mathit{summary}$ plays the role of the binary summary tree's OR-nodes:
$\mathit{summary}$ records \emph{which clusters are nonempty}, holding index $i \in \{0,\dots,\sqrt{u}-1\}$
whenever $\mathit{cluster}[i]$ contains at
least one key. Because $\mathit{summary}$ is itself a $\text{proto-vEB}(\sqrt{u})$ with one slot per cluster, it answers ``which is the next
nonempty cluster?'' through its \emph{own} recursive successor query.
Figure~\ref{ch21:proto-structure} shows two levels of this recursion.

\subsection{How tall is this recursion?}

Each level shrinks the universe from $u$ to $\sqrt{u}$, producing the sequence
\[
  u,\quad u^{1/2},\quad u^{1/4},\quad u^{1/8},\quad \dots,\quad 2.
\]
How many square roots drive $u = 2^k$ down to $2$? Taking a square root maps $2^k$ to
$2^{k/2}$, which \emph{halves the exponent} $k$. The recursion reaches $2 = 2^1$ when the
exponent hits $1$. Halving $k$ down to $1$ takes $\lg k = \lg \lg u$ steps.

\begin{focusbox}
The depth of the recursion is $\lg \lg u$, not $\lg u$. Taking the square root of
the universe at each level halves the \emph{exponent}, and halving an exponent $k = \lg u$ down to $1$ takes $\lg k = \lg\lg u$ steps.
\end{focusbox}

\begin{example}[Counting the levels]
Let $u = 2^{32}$, so $k = 32$. The universe sizes down the recursion are
\[
  2^{32} \to 2^{16} \to 2^{8} \to 2^{4} \to 2^{2} \to 2^{1}=2.
\]
That is $5$ square roots, matching $\lg\lg u = \lg 32 = 5$. Figure~\ref{ch21:depth} contrasts this five-step descent
with a binary tree over the same universe, which is $32$ levels deep.
\end{example}

\section{Proto-vEB operations, and why they are not yet fast enough}

Writing out the operations on proto-vEB shows where the time goes. \textsc{Member} achieves $\Oh(\lg\lg u)$, whereas \textsc{Successor} and \textsc{Minimum} degrade to $\Th(\lg u)$. Seeing why reveals how to fix the structure.

\subsection{Member}

\begin{algorithm}[H]
\caption{\textsc{proto-vEB-Member}($V, x$)}
\KwIn{A proto-vEB $V$ of size $u$, key $x$.}
\KwOut{\textsc{true} if and only if $x \in S$.}
\If{$V.u = 2$}{
  \Return $V.A[x]$ \tcp*{base case: read the bit directly}
}
\Return $\textsc{proto-vEB-Member}(V.\mathit{cluster}[\mathrm{high}(x)],\ \mathrm{low}(x))$\;
\end{algorithm}

Testing membership peels off the high half to pick the cluster and recurses on
the low half. Each call descends one level and performs $\Oh(1)$ work, so if $M(u)$ is the running time on universe size $u$,
\[
  M(u) = M(\sqrt{u}) + \Oh(1).
\]
Writing $m = \lg u$ (so $\lg\sqrt{u} = m/2$) turns this into $M(2^m) = M(2^{m/2}) + \Oh(1)$: a recurrence that halves $m$ at each step and adds a constant, matching binary search (Chapter~4) and solving to $\Oh(\lg m) = \Oh(\lg\lg u)$ (proved in full in Section~\ref{ch21:sec-recurrence}). \textsc{Member} already meets our target.

\subsection{Minimum and Maximum: why two calls per level is slow}

To find the minimum, we locate the first nonempty cluster via the summary,
then recurse into that cluster to find its minimum.

\begin{algorithm}[H]
\caption{\textsc{proto-vEB-Minimum}($V$)}
\KwIn{A proto-vEB $V$ of size $u$.}
\KwOut{The smallest stored key, or \textsc{nil} if $V$ is empty.}
\If{$V.u = 2$}{
  \lIf{$V.A[0]=1$}{\Return $0$}
  \lElseIf{$V.A[1]=1$}{\Return $1$}
  \lElse{\Return \textsc{nil}}
}
$c \leftarrow \textsc{proto-vEB-Minimum}(V.\mathit{summary})$
  \tcp*{first nonempty cluster}
\lIf{$c = \textsc{nil}$}{\Return \textsc{nil}}
$o \leftarrow \textsc{proto-vEB-Minimum}(V.\mathit{cluster}[c])$
  \tcp*{min within it}
\Return $\mathrm{index}(c, o)$\;
\end{algorithm}

This routine makes \emph{two} recursive calls of size
$\sqrt{u}$ on a nonempty tree: one into $\mathit{summary}$ and one into $\mathit{cluster}[c]$.
Its worst-case time $T(u)$ satisfies
\[
  T(u) = 2\,T(\sqrt{u}) + \Oh(1).
\]
Setting $m = \lg u$ and $S(m) = T(2^m)$ gives
\begin{align*}
  S(m) &= T(2^m) \\
       &= 2\,T(2^{m/2}) + \Oh(1) \\
       &= 2\,S(m/2) + \Oh(1),
\end{align*}
which by the master theorem (Chapter~4) solves to $S(m) = \Th(m)$, so $T(u) = \Th(\lg u)$. Figure~\ref{ch21:branching-blowup} shows why: two calls per level across $\lg\lg u$ levels produce a binary recursion tree with $2^{\lg\lg u} = \lg u$ leaves, canceling out the shallow height.

call into a $\sqrt{u}$-sized substructure per level.}
\end{trapbox}

\subsection{Successor: the bottleneck diagnosed}

Successor suffers from the same branching recursion. Tracing its call
path shows why we need to store the smallest and largest keys directly at each node. To find
the successor of $x$:

\begin{enumerate}
  \item Look \emph{within $x$'s own cluster} for a key larger than
        $\mathrm{low}(x)$. If found, recombine it with $\mathrm{high}(x)$ and
        return (one recursive call).
  \item Otherwise the answer lies in a \emph{later} cluster. Query the summary for
        the next nonempty cluster $c$ after $\mathrm{high}(x)$ (a second recursive
        call), then find the \emph{minimum} of cluster $c$ (a \emph{third}
        recursive call).
\end{enumerate}

\begin{algorithm}[H]
\caption{\textsc{proto-vEB-Successor}($V, x$)}
\KwIn{A proto-vEB $V$ of size $u$, key $x$.}
\KwOut{Smallest stored key $> x$, or \textsc{nil}.}
\If{$V.u = 2$}{
  \lIf{$x = 0$ \textbf{and} $V.A[1]=1$}{\Return $1$}
  \lElse{\Return \textsc{nil}}
}
$o \leftarrow \textsc{proto-vEB-Successor}(V.\mathit{cluster}[\mathrm{high}(x)],\ \mathrm{low}(x))$\;
\If{$o \ne \textsc{nil}$}{
  \Return $\mathrm{index}(\mathrm{high}(x), o)$ \tcp*{found in same cluster}
}
$c \leftarrow \textsc{proto-vEB-Successor}(V.\mathit{summary},\ \mathrm{high}(x))$\;
\lIf{$c = \textsc{nil}$}{\Return \textsc{nil}}
$o' \leftarrow \textsc{proto-vEB-Minimum}(V.\mathit{cluster}[c])$\;
\Return $\mathrm{index}(c, o')$\;
\end{algorithm}

When the first recursive call returns $\textsc{nil}$, it has already spent $\Th(\lg\sqrt{u})$ time exploring empty branches (since any failed \textsc{proto-vEB-Successor} call makes two recursive calls at each level), and the procedure then recurses into $\mathit{summary}$ and calls \textsc{proto-vEB-Minimum} for another $\Th(\lg\sqrt{u})$. That yields $T(u) = T(\sqrt{u}) + \Th(\lg u) = \Th(\lg u)$ in the worst case, still no faster than a balanced BST.

\begin{complexitybox}
\textbf{proto-vEB.}
\textsc{Member}: $\Oh(\lg\lg u)$.
\textsc{Minimum}/\textsc{Maximum}: $\Th(\lg u)$ (two calls per level).
\textsc{Successor}/\textsc{Predecessor}: $\Th(\lg u)$.
\textsc{Insert}/\textsc{Delete}: $\Th(\lg u)$ (they recurse
into a cluster \emph{and} update the summary).
Diagnosis: multiple recursive calls per level.
\end{complexitybox}

\section{Two fixes: cached extremes and a floating minimum}

Where did the extra recursive calls come from? \textsc{Minimum} made recursive
calls to compute its answer; \textsc{Successor} called \textsc{Minimum} and searched empty clusters blindly; and
\textsc{Insert} recursed into a cluster \emph{and} into the
summary. If \textsc{Minimum} and \textsc{Maximum} cost $\Oh(1)$, and
\textsc{Insert} never had to recurse into both a cluster and the summary at the same level, every operation would stay within the budget of one recursive call per level. Two
changes achieve this.

\textbf{Fix 1: store the minimum and maximum explicitly.} Give every vEB node two
fields, $V.\mathit{min}$ and $V.\mathit{max}$, holding the smallest and
largest keys stored in that node. Reading \textsc{Minimum} or \textsc{Maximum} now takes
$\Oh(1)$ time with no recursion.

\textbf{Fix 2: the minimum does not live in any cluster.} Adopt the convention that the key stored in
$V.\mathit{min}$ is \emph{not} also stored down in $V$'s clusters. It sits at the
top in $V.\mathit{min}$ alone. (The maximum \emph{is} stored in
its cluster whenever the node holds at least two keys; only $\mathit{min}$ is excluded from the clusters.)

Why exclude $\mathit{min}$ from the clusters? First, inserting into an \emph{empty} vEB node now finishes in $\Oh(1)$ time by setting $V.\mathit{min} = V.\mathit{max} = x$ without touching any cluster or summary. Second, whenever
\textsc{Insert} does recurse into a cluster, that cluster was either empty (so initializing its $\mathit{min}$ field takes $\Oh(1)$ while only $\mathit{summary}$ recurses) or already nonempty (so $\mathit{summary}$ already records it and only the cluster recurses). For \textsc{Successor}, caching both $\mathit{min}$ and $\mathit{max}$ lets us test in $\Oh(1)$ time whether the answer lies inside $x$'s cluster before recursing.

\begin{intuitionbox}
Think of $\mathit{min}$ as a doorman standing at the entrance of each vEB node.
Inserting into an empty node? The doorman holds the key, and the clusters and summary inside stay untouched.
Inserting a second key? The doorman is already occupied, so the second key goes inside; and once a cluster has a key at its door, the summary already marks that cluster as nonempty, so later insertions into that cluster skip the summary update.
\end{intuitionbox}

\begin{formalbox}
\textbf{The vEB tree.} A $\text{vEB}(u)$ structure stores a set
$S \subseteq \{0,\dots,u-1\}$. It has fields $\mathit{min}$ and $\mathit{max}$
(each a key or \textsc{nil}). If $u > 2$, it also has
$\mathit{cluster}[0\,..\,\sqrt{u}-1]$, each a $\text{vEB}(\sqrt{u})$, and
$\mathit{summary}$, also a $\text{vEB}(\sqrt{u})$. Invariants:
\begin{itemize}
  \item $\mathit{min}$ holds the smallest key of $S$ and is \emph{not} stored in
        any cluster.
  \item $\mathit{max}$ holds the largest key of $S$ (and, whenever $\mathit{max} \ne \mathit{min}$ and $u > 2$, $\mathrm{low}(\mathit{max})$ \emph{is} stored in $\mathit{cluster}[\mathrm{high}(\mathit{max})]$).
  \item $\mathit{cluster}[i]$ stores $\{\mathrm{low}(x) : x \in S,\ \mathrm{high}(x)=i,\ x \ne \mathit{min}\}$.
  \item $\mathit{summary}$ stores $\{i : \mathit{cluster}[i] \text{ is nonempty}\}$.
  \item An empty set $S = \emptyset$ has $\mathit{min}=\mathit{max}=\textsc{nil}$. A one-element set (singleton)
        $S=\{x\}$ has $\mathit{min}=\mathit{max}=x$ and \emph{all clusters
        empty}.
\end{itemize}
When $u=2$, there are no clusters or summary; $\mathit{min}$ and $\mathit{max}$ over $\{0,1\}$ represent $S$ completely.
\end{formalbox}

\section{The fast operations}

Each operation below does as much work as possible with $\mathit{min}$ and $\mathit{max}$ in $\Oh(1)$ time and makes at most one non-$\Oh(1)$ recursive call.

\subsection{Minimum, Maximum, Member}

\textsc{Minimum} and \textsc{Maximum} return $V.\mathit{min}$ and
$V.\mathit{max}$ directly in $\Oh(1)$ time. \textsc{Member} first checks $x$ against $V.\mathit{min}$ and $V.\mathit{max}$: checking $V.\mathit{min}$ is required because the minimum lives in no cluster, and checking $V.\mathit{max}$ handles the base case $V.u = 2$ (where there are no clusters) in one line.

\begin{algorithm}[H]
\caption{\textsc{vEB-Member}($V, x$)}
\KwIn{A vEB $V$ of size $u$, key $x$.}
\KwOut{\textsc{true} if and only if $x \in S$.}
\If{$x = V.\mathit{min}$ \textbf{or} $x = V.\mathit{max}$}{\Return \textsc{true}}
\lElseIf{$V.u = 2$}{\Return \textsc{false}}
\lElse{\Return $\textsc{vEB-Member}(V.\mathit{cluster}[\mathrm{high}(x)],\ \mathrm{low}(x))$}
\end{algorithm}

Because \textsc{vEB-Member} makes at most one recursive call per level, it runs in $\Oh(\lg\lg u)$ time.

\subsection{Successor: the centerpiece}

\begin{algorithm}[H]
\caption{\textsc{vEB-Successor}($V, x$)}
\KwIn{A vEB $V$ of size $u$, key $x$ (need not be in $S$).}
\KwOut{Smallest key in $S$ strictly greater than $x$, or \textsc{nil}.}
\If{$V.u = 2$}{
  \lIf{$x = 0$ \textbf{and} $V.\mathit{max}=1$}{\Return $1$}
  \lElse{\Return \textsc{nil}}
}
\If{$V.\mathit{min} \ne \textsc{nil}$ \textbf{and} $x < V.\mathit{min}$}{
  \Return $V.\mathit{min}$ \tcp*{the floating min is the answer}
}
$\mathit{maxlow} \leftarrow \textsc{vEB-Maximum}(V.\mathit{cluster}[\mathrm{high}(x)])$\;
\If{$\mathit{maxlow} \ne \textsc{nil}$ \textbf{and} $\mathrm{low}(x) < \mathit{maxlow}$}{
  $o \leftarrow \textsc{vEB-Successor}(V.\mathit{cluster}[\mathrm{high}(x)],\ \mathrm{low}(x))$\;
  \Return $\mathrm{index}(\mathrm{high}(x), o)$ \tcp*{successor is in same cluster}
}
\Else{
  $c \leftarrow \textsc{vEB-Successor}(V.\mathit{summary},\ \mathrm{high}(x))$\;
  \lIf{$c = \textsc{nil}$}{\Return \textsc{nil}}
  \Return $\mathrm{index}(c,\ \textsc{vEB-Minimum}(V.\mathit{cluster}[c]))$\;
}
\end{algorithm}

For $V.u > 2$, Figure~\ref{ch21:successor-exits} shows the three mutually exclusive exits, none of which makes more than one recursive call:

\begin{enumerate}
  \item \emph{Shortcut via $\mathit{min}$.} If $x < V.\mathit{min}$, then $V.\mathit{min}$ itself is the smallest stored key above $x$. Return it in $\Oh(1)$ time with zero recursive calls.
  \item \emph{Same cluster.} Read the cached maximum $\mathit{maxlow}$ of $x$'s cluster in $\Oh(1)$ time. If $\mathrm{low}(x) < \mathit{maxlow}$, then $x$'s cluster definitely contains a key above $x$, so one recursive \textsc{vEB-Successor} call into that cluster finds it.
  \item \emph{Later cluster.} Otherwise no key above $x$ exists in $x$'s cluster. Make one recursive \textsc{vEB-Successor} call into $\mathit{summary}$ to find the next nonempty cluster $c$, then read $V.\mathit{cluster}[c].\mathit{min}$ in $\Oh(1)$ time.
\end{enumerate}

Caching $\mathit{max}$ avoids searching an empty or exhausted cluster in Exit~2, and caching $\mathit{min}$ avoids a second recursion in Exit~3. Every exit makes at most one recursive call into a $\sqrt{u}$-sized substructure, giving
\[
  T(u) = T(\sqrt{u}) + \Oh(1) = \Oh(\lg\lg u).
\]
\textsc{Predecessor} is symmetric (with one extra boundary check for the floating $\mathit{min}$; see Exercise~\ref{ch21:ex-pred}) and runs in $\Oh(\lg\lg u)$ time as well.

The remaining keys $\{3,4,5,7,14,15\}$ go to clusters by their high

\[

0 & 3 & \{3\}\ (\text{since } \mathrm{low}(3)=3)\\
1 & 4,5,7 & \{0,1,3\}\\
3 & 14,15 & \{2,3\}
\end{array}

Cluster $2$ is empty. The summary stores $\{0,1,3\}$ (the nonempty clusters),
with its own floating $\mathit{min}=0$.

Now run $\textsc{vEB-Successor}(V, 5)$:
\begin{enumerate}
  \item $u=16 \ne 2$. Is $5 < V.\mathit{min}=2$? No.
  \item $\mathrm{high}(5)=1$, $\mathrm{low}(5)=1$. Read
        $\textsc{vEB-Maximum}(\mathit{cluster}[1])$. Cluster $1$ holds lows

\end{enumerate}

is $14$.
\begin{enumerate}
  \item Is $7 < 2$? No. Compute $\mathrm{high}(7)=1$ and $\mathrm{low}(7)=3$.
  \item $\textsc{vEB-Maximum}(\mathit{cluster}[1]) = 3$. Is $\mathrm{low}(7)=3 < 3$?

  \item Read $\textsc{vEB-Minimum}(\mathit{cluster}[3]) = 2$ in $\Oh(1)$ time, and reassemble:
        $\mathrm{index}(3, 2) = 3\cdot 4 + 2 = 14$.
\end{enumerate}
Answer: $14$. $\checkmark$
\end{labbox}

\subsection{Insert: one recursion via the doorman}

\begin{algorithm}[H]
\caption{\textsc{vEB-Insert}($V, x$)}
\KwIn{A vEB $V$ of size $u$, key $x \in \{0,\dots,u-1\}$.}
\KwOut{$V$ with $x$ inserted into $S$.}
\If{$V.\mathit{min} = \textsc{nil}$}{
  $V.\mathit{min} \leftarrow V.\mathit{max} \leftarrow x$
  \tcp*{empty: seat the doorman in $\Oh(1)$ and stop}
  \Return
}
\If{$x = V.\mathit{min}$ \textbf{or} $x = V.\mathit{max}$}{
  \Return \tcp*{already present: no-op}
}
\If{$x < V.\mathit{min}$}{
  swap $x \leftrightarrow V.\mathit{min}$
  \tcp*{new smallest: push old min down into clusters}
}
\If{$V.u > 2$}{
  \eIf{$\textsc{vEB-Minimum}(V.\mathit{cluster}[\mathrm{high}(x)]) = \textsc{nil}$}{
    $\textsc{vEB-Insert}(V.\mathit{summary},\ \mathrm{high}(x))$
      \tcp*{cluster was empty: update summary}
    $V.\mathit{cluster}[\mathrm{high}(x)].\mathit{min} \leftarrow
        V.\mathit{cluster}[\mathrm{high}(x)].\mathit{max} \leftarrow \mathrm{low}(x)$\;
  }{
    $\textsc{vEB-Insert}(V.\mathit{cluster}[\mathrm{high}(x)],\ \mathrm{low}(x))$
      \tcp*{cluster nonempty: recurse into it}
  }
}
\lIf{$x > V.\mathit{max}$}{$V.\mathit{max} \leftarrow x$}
\end{algorithm}

Mutual exclusion between the summary update and the cluster descent is what
makes the floating-minimum convention pay off. The two recursive
calls (one into $\mathit{summary}$, one into $\mathit{cluster}[\mathrm{high}(x)]$) sit in \emph{opposite}
branches of an \texttt{if/else}, so they never both run at the same level:

\begin{itemize}
  \item If the target cluster is \emph{empty}, we recurse into $\mathit{summary}$ to
        record that it became nonempty, and we initialize the cluster's $\mathit{min}$ and $\mathit{max}$ fields directly in $\Oh(1)$ time \emph{without} recursing into the cluster.
  \item If the target cluster is \emph{nonempty}, $\mathit{summary}$ already contains $\mathrm{high}(x)$, so we skip the summary and recurse only into the cluster (where duplicate keys are also caught if they match a cached $\mathit{min}$ or $\mathit{max}$ down the path).
\end{itemize}

Figure~\ref{ch21:fig-insert-cases} contrasts the two branches: in each case, at most one $\sqrt{u}$-sized recursive call is made.

\begin{trapbox}
A common misreading of the pseudocode is: ``\textsc{vEB-Insert} contains two recursive calls, so it must take
$\Th(\lg u)$ time like proto-vEB.'' Those two calls sit in opposite
branches of an \texttt{if/else}, and the branch that recurses into $\mathit{summary}$ initializes the empty cluster in $\Oh(1)$ time without a second recursive call. Count how many recursive calls can fire \emph{together on one execution path}, not how many appear in the listing.
\end{trapbox}

\begin{algorithm}[H]
\caption{\textsc{vEB-Delete}($V, x$)}
\KwIn{A vEB $V$ of size $u$, key $x \in S$.}
\KwOut{$V$ with $x$ removed from $S$.}
\If{$V.\mathit{min} = V.\mathit{max}$}{
  $V.\mathit{min} \leftarrow V.\mathit{max} \leftarrow \textsc{nil}$
  \tcp*{only one element; now empty}
  \Return
}
\If{$V.u = 2$}{
  \lIf{$x=0$}{$V.\mathit{min}\leftarrow 1$}\lElse{$V.\mathit{min}\leftarrow 0$}
  $V.\mathit{max}\leftarrow V.\mathit{min}$\; \Return
}

  $c \leftarrow \textsc{vEB-Minimum}(V.\mathit{summary})$
    \tcp*{first nonempty cluster}
  $x \leftarrow \mathrm{index}(c,\ \textsc{vEB-Minimum}(V.\mathit{cluster}[c]))$\;
  $V.\mathit{min} \leftarrow x$
    \tcp*{promote: remove $x$ from its cluster below}
}
$\textsc{vEB-Delete}(V.\mathit{cluster}[\mathrm{high}(x)],\ \mathrm{low}(x))$\;
\If{$\textsc{vEB-Minimum}(V.\mathit{cluster}[\mathrm{high}(x)]) = \textsc{nil}$}{
  $\textsc{vEB-Delete}(V.\mathit{summary},\ \mathrm{high}(x))$
    \tcp*{cluster emptied: clear its summary entry}
  \If{$x = V.\mathit{max}$}{
    $s \leftarrow \textsc{vEB-Maximum}(V.\mathit{summary})$
      \tcp*{last nonempty cluster, if any}
    \eIf{$s = \textsc{nil}$}{
      $V.\mathit{max} \leftarrow V.\mathit{min}$\tcp*{only the floating min is left}
    }{
      $V.\mathit{max} \leftarrow \mathrm{index}(s,\ \textsc{vEB-Maximum}(V.\mathit{cluster}[s]))$\;
    }
  }
}
\lElseIf{$x = V.\mathit{max}$}{
  $V.\mathit{max} \leftarrow \mathrm{index}(\mathrm{high}(x),\ \textsc{vEB-Maximum}(V.\mathit{cluster}[\mathrm{high}(x)]))$
}
\end{algorithm}

The listing contains two \textsc{vEB-Delete} calls (first on the cluster, then conditionally on $\mathit{summary}$), yet they never both descend recursively on the same execution path. The second call runs only when $\mathit{cluster}[\mathrm{high}(x)]$ became \emph{empty} after the first deletion. For that cluster to become empty, it must have held only a single key beforehand ($\mathit{min} = \mathit{max}$), which means the first \textsc{vEB-Delete} hit line~1 and returned in $\Oh(1)$ time without recursing deeper. Thus a recursive descent occurs in \emph{either} the cluster \emph{or} the summary, never both, giving $T(u) = T(\sqrt{u}) + \Oh(1) = \Oh(\lg\lg u)$.

\begin{complexitybox}
\textbf{vEB (final).} \textsc{Minimum} and \textsc{Maximum} run in $\Oh(1)$ worst-case time, and \textsc{Member}, \textsc{Insert},
\textsc{Delete}, \textsc{Successor}, and
\textsc{Predecessor} all run in $\Oh(\lg\lg u)$ worst-case time via
$T(u) = T(\sqrt{u}) + \Oh(1)$. The tradeoff is $\Th(u)$ space (next
section) and a fixed integer universe.
\end{complexitybox}

\section{Solving the recurrence, once and for all}
\label{ch21:sec-recurrence}

Every recursive vEB operation satisfies $T(u) = T(\sqrt{u}) + \Oh(1)$. A change of
variables turns the square root into halving. Let
\[
  m = \lg u, \qquad\text{so that}\qquad u = 2^m.
\]
Then $\sqrt{u} = u^{1/2} = 2^{m/2}$, whose base-$2$ logarithm is $m/2$. Define
$S(m) = T(2^m)$. Substituting $u = 2^m$ into $T(u) = T(\sqrt{u}) + \Oh(1)$ gives
\begin{align*}
  S(m) &= T(2^m) \\
       &= T(2^{m/2}) + \Oh(1) && \text{(by the recurrence)} \\
       &= S(m/2) + \Oh(1) && \text{(by definition of $S$).}
\end{align*}
This recurrence \emph{halves $m$} and adds a constant, the same
recurrence as binary search. By the master theorem (Chapter~4, Case~2 with
$a=1$, $b=2$, and $f(m)=\Oh(1)$),
\[
  S(m) = \Oh(\lg m).
\]
Substituting back $m = \lg u$ gives
\[
  T(u) = S(\lg u) = \Oh(\lg \lg u).
\]

\begin{walkbox}
Prove $S(m) = \Oh(\lg m)$ directly by unrolling, without the master
theorem. Writing $c > 0$ for the constant hidden in $\Oh(1)$,
\begin{align*}
  S(m) &\le S(m/2)+c \\
       &\le S(m/4)+2c \\
       &\le S(m/8)+3c \\
       &\le \cdots
\end{align*}
After $t$
steps, the argument is $m/2^t$ and the accumulated cost is $tc$. The recursion
reaches the base case $S(1)$ when $m/2^t = 1$, so $t = \lg m$ and
$S(m) \le S(1) + c\lg m = \Oh(\lg m)$. Substituting $m = \lg u$ recovers
$T(u) = \Oh(\lg\lg u)$.
\end{walkbox}

\section{The cost of all this: space}

A $\text{vEB}(u)$ node with $u > 2$ contains $\sqrt{u}$ cluster
substructures plus one summary substructure, each a $\text{vEB}(\sqrt{u})$, and
all of them are \emph{allocated up front}, including clusters that hold no keys.
Let $P(u)$ be the number of memory words used by a $\text{vEB}(u)$ structure. Then for $u > 2$,
\[
  P(u) = (\sqrt{u} + 1)\,P(\sqrt{u}) + \Oh(1).
\]
We prove $P(u) = \Th(u)$ by bounding $P(u)$ from above and below. For the
upper bound, write $c > 0$ for the constant in $\Oh(1)$ and suppose by induction on smaller universes that $P(\sqrt{u}) \le C\sqrt{u} - D$ for constants $C, D > 0$ to be chosen:
\begin{align*}
  P(u) &\le (\sqrt{u} + 1)(C\sqrt{u} - D) + c \\
       &= Cu - D + (C - D)\sqrt{u} + c \\
       &\le Cu - D
\end{align*}
provided we choose $D = C + c$ (so $(C-D)\sqrt{u} + c = -c\sqrt{u} + c \le -c < 0$ since $\sqrt{u} \ge 2$) and $C = P(2) + c$ (so the base case $P(2) \le 2C - D = C - c = P(2)$ holds). For the lower bound, write $u = 2^k$ (where $k$ is a power of two) and drop the $+1$ and $+\Oh(1)$ terms at each level:
\begin{align*}
  P(u) &\ge \sqrt{u}\,P(\sqrt{u}) \\
       &\ge u^{1/2}\cdot u^{1/4}\,P(u^{1/4}) \\
       &\ge \cdots \\
       &\ge u^{1/2 + 1/4 + \cdots + 1/k}\,P(2)
        = u^{1 - 1/k}\,P(2)
        = \frac{u}{2}\,P(2),
\end{align*}
since $u^{1/k} = (2^k)^{1/k} = 2$. Combining both bounds gives $P(u) = \Th(u)$: the structure uses memory proportional to the
\emph{entire universe}, whether it stores one key or a million.

\begin{trapbox}
$\Th(u)$ space restricts where a plain vEB tree is practical. For $u=2^{32}$, allocating $\Th(u)$ words requires gigabytes of memory even to store ten keys. In
practice, one replaces each node's array of $\sqrt{u}$ cluster pointers with a
\emph{hash table} (Chapter~11) keyed by cluster number, allocating a cluster only
when its first key arrives. That lowers space to $\Oh(n)$ (or $\Oh(n \lg\lg u)$ without further pruning) while keeping $\Oh(\lg\lg u)$ \emph{expected} query and update time. A related structure, the \emph{$y$-fast trie} (where a \emph{trie}, or prefix tree, branches along the bits of a key), combines a hashed prefix tree with small balanced BSTs to achieve $\Oh(n)$ space and $\Oh(\lg\lg u)$ expected time; see CLRS's chapter notes.
\end{trapbox}

\begin{aestheticbox}
When keys are integers rather than opaque objects, their bit representations carry structure we can use. The $\Om(\lg n)$ comparison lower bound applies only
when an algorithm's sole access to keys is asking ``is $a < b$?'' Once an algorithm can
use a key (or slices of its bits) directly as an array index, faster bounds open up. That is the same principle behind counting sort and radix sort (Chapter~8) and
direct-address tables (Chapter~11). A vEB tree applies direct indexing \emph{recursively}, slicing off half the remaining bits at each level.
\end{aestheticbox}

\begin{historybox}
Peter van Emde Boas presented the first version of this data structure in 1975 at the Institute of Electrical and Electronics Engineers (IEEE) Symposium on Foundations of Computer Science, followed by a journal paper with R.~Kaas and E.~Zijlstra in 1977. His question was whether an integer priority queue could beat the $\Om(\lg n)$ comparison bound on a random-access machine. By splitting each key into a high half and a low half ($\sqrt{u}$ clusters of size $\sqrt{u}$), caching each node's minimum and maximum, and indexing clusters with constant-time bit operations, he showed that every priority-queue and predecessor operation runs in $\Oh(\lg \lg u)$ time.

Memory remained the obstacle: $\Th(u)$ words rules out $64$-bit universes. In 1983 Dan Willard introduced $x$-fast and $y$-fast tries, combining bitwise prefix trees with hash tables and balanced BSTs to cut space to $\Oh(n)$ while keeping $\Oh(\lg \lg u)$ expected time. Michael Fredman and Willard's fusion trees (1990) pack multiple keys into a single $w$-bit word on a word random-access machine (word RAM, a processor model with $\Oh(1)$-time arithmetic and bitwise operations on $w$-bit integers) to reach $\Oh(\lg n / \lg w)$ time per operation, independent of $u$.

Mihai P\v{a}tra\c{s}cu and Mikkel Thorup (2006) proved matching lower bounds in the \emph{cell-probe model} (which counts only how many memory words an algorithm reads or writes and treats all computation on them as free), showing that with near-linear space and across a broad range of universe sizes, $\Th(\lg\lg u)$ query time is optimal. CLRS (3rd edition, Chapter~20) develops the structure through the same four stages used here: bit vector, binary summary tree, proto-vEB, and full vEB.
\end{historybox}

\section{Recap: the chain of ideas}

Each stage below fixes the bottleneck of the stage before it.

\begin{focusbox}
\begin{enumerate}
  \item \textbf{Bit vector} ($\Oh(u)$ successor): $\Oh(1)$ membership, insert, and delete, but
        successor scans a flat array.
  \item \textbf{Binary summary tree} ($\Oh(\lg u)$): logical-OR internal nodes provide
        shortcuts, but the tree has height $\lg u$.
  \item \textbf{Square-root split / proto-vEB} (depth $\lg\lg u$, time $\Th(\lg u)$): branch by
        $\sqrt{u}$ so the recursion is $\lg\lg u$ levels deep, though making two recursive calls per level still costs $\Th(\lg u)$.
  \item \textbf{Cached $\mathit{min}/\mathit{max}$ + floating $\mathit{min}$} ($\Oh(\lg\lg
        u)$): store $\mathit{min}$ and $\mathit{max}$ for $\Oh(1)$ access, and keep $\mathit{min}$ out of the
        clusters so every operation makes \emph{at most one} recursive call per
        level, satisfying $T(u)=T(\sqrt u)+\Oh(1)=\Oh(\lg\lg u)$.
\end{enumerate}
The invariant driving the final design is: \emph{at most one recursive call into a
$\sqrt{u}$-sized substructure per level.}
\end{focusbox}

This chapter concludes Part~5 on advanced data structures; Part~6 begins our study of graphs and network algorithms.

\section{Exercises}

\begin{exercise}[Counting the levels]
For each universe size $u \in \{4,\ 16,\ 256,\ 2^{16},\ 2^{64}\}$, write out the
sequence of universe sizes down the vEB recursion ($u \to \sqrt u \to \cdots \to
2$) and confirm the number of levels equals $\lg\lg u$. Which of these would have
operations costing more than $6$ levels of work? (Warmup.)
\end{exercise}

\begin{exercise}[Splitting keys]
Let $u = 256$, so $\sqrt u = 16$. Compute $\mathrm{high}(x)$, $\mathrm{low}(x)$,
and verify $\mathrm{index}(\mathrm{high}(x),\mathrm{low}(x)) = x$ for
$x \in \{0, 17, 200, 255\}$. Express $\mathrm{high}(x)$ and $\mathrm{low}(x)$ as bit-shift and bitmask operations on the $8$-bit value $x$. (Warmup.)
\end{exercise}

\begin{exercise}[Why two calls per level is fatal]
Solve each recurrence by the $m=\lg u$ substitution and state its asymptotic bound:
(a) $T(u)=T(\sqrt u)+\Oh(1)$; (b) $T(u)=2\,T(\sqrt u)+\Oh(1)$;
(c) $T(u)=\sqrt u\,T(\sqrt u)+\Oh(1)$. Match each to one of the quantities analyzed in the
chapter (final vEB time, proto-vEB minimum time, total space). (Medium.)
\end{exercise}

\begin{exercise}[Trace Successor]
Let $u=16$ and $S=\{1,2,6,9,13\}$. Lay out the clusters and the summary
(remembering that the floating minimum is not stored in any cluster). Trace
\textsc{vEB-Successor}$(V, x)$ for $x = 2$, $x = 6$, and $x = 9$, naming which of
the three exits fires each time and how many recursive descents occur.
(Medium.)
\end{exercise}

\begin{exercise}[Trace Insert]
Starting from an empty $\text{vEB}(16)$, insert the keys $5, 2, 8, 5, 0$ in that
order (the second $5$ is a no-op; explain why). After each insertion, write down
$\mathit{min}$, $\mathit{max}$, the contents of each cluster, and the summary.
Identify every recursive or top-level call that finished in $\Oh(1)$ time because it hit the empty-node
fast path. (Medium.)
\end{exercise}

\begin{exercise}[The floating minimum, examined]
Explain in your own words why \textsc{vEB-Insert} into an \emph{empty} node takes
$\Oh(1)$ time, and why this fact keeps \textsc{vEB-Insert}'s recurrence at
$T(u)=T(\sqrt u)+\Oh(1)$ rather than $T(u)=2\,T(\sqrt u)+\Oh(1)$. What would
go wrong if we also stored $\mathit{min}$ down in its cluster like every other
key? (Medium.)
\end{exercise}

\begin{exercise}[Predecessor by mirror]
\label{ch21:ex-pred}
\textsc{vEB-Predecessor} mirrors \textsc{vEB-Successor}, except for one
asymmetry involving
$\mathit{min}$. Write \textsc{vEB-Predecessor} in full pseudocode and explain the
extra case. Hint: because the floating $\mathit{min}$ is not stored in any
cluster, if no earlier nonempty cluster exists in $\mathit{summary}$, you must still check whether $x > V.\mathit{min}$. (Medium-hard.)
\end{exercise}

\begin{exercise}[Trace Delete, including a promotion]
Take $u=16$ and $S=\{0,3,4,11\}$ with the $\text{vEB}(16)$ structure built. Trace
$\textsc{vEB-Delete}(V, 0)$. Since $0$ is the floating minimum, follow the
promotion: which key becomes the new $\mathit{min}$, and from which cluster is it
removed? Show the clusters and summary before and after. (Hard.)
\end{exercise}

\begin{exercise}[Space recurrence]
\label{ch21:ex-space}
Set up and solve the space recurrence $P(u) = (\sqrt u + 1)\,P(\sqrt u)+\Oh(1)$ to
show $P(u)=\Th(u)$. Then estimate the space, in memory words, for $u = 2^{20}$ holding a
set of $3$ keys, and compare it with a balanced BST holding the same $3$ keys.
(Since $20$ is not a power of two, split any $b$-bit universe into
$2^{\lceil b/2 \rceil}$ clusters of size $2^{\lfloor b/2 \rfloor}$ whenever $b$ is
odd, as CLRS does; an order-of-magnitude estimate suffices.)
When is a vEB tree worth its memory cost? (Hard.)
\end{exercise}

\begin{exercise}[From $\Th(u)$ space to near-linear space]
Sketch how replacing each node's $\mathit{cluster}$ array of length $\sqrt{u}$ with a hash
table (Chapter~11), allocating a cluster only on its first insertion,
reduces space from $\Th(u)$ to $\Oh(n \lg\lg u)$ (and how storing small clusters directly reduces it further to $\Oh(n)$). Which time bounds become \emph{expected} rather than
worst-case, and why? (Challenge.)
\end{exercise}

\begin{exercise}[Successor without stored max]
Suppose you kept the floating $\mathit{min}$ convention but did \emph{not} store
$\mathit{max}$, computing a cluster's maximum by a recursive
call instead. Show that \textsc{vEB-Successor} would then make two recursive calls in its
``same cluster'' branch (the maximum query plus the successor query), degrading its
running time to $\Th(\lg u)$. This shows why caching
$\mathit{max}$ alongside $\mathit{min}$ is necessary. (Challenge.)
\end{exercise}
