\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

Every backend engineer eventually meets the day when the database stops pretending to be an infinite hash map.

Perhaps a query that ran in four milliseconds on Friday suddenly takes nineteen seconds on Monday morning. Nobody deployed code over the weekend. Perhaps two concurrent requests (requests running at the same time) check that a customer has 100 dollars available, and both pass inside separate \texttt{BEGIN ... COMMIT} blocks. Both deduct 80 dollars, and the account settles at $-60$ dollars (Figure~\ref{fig:race_condition}). Or perhaps someone adds a harmless-looking \texttt{WHERE id NOT IN (SELECT blocked\_id FROM blocks)} filter. One row in \texttt{blocks} happens to have \texttt{blocked\_id = NULL} (a special marker for missing data), and the entire query returns zero rows without a warning.

A database is a deterministic machine built out of concrete data structures. Rows live inside fixed 8,192-byte pages (blocks of memory or disk). Indexes form trees whose sibling pointers let readers keep moving while pages split. Crash safety rests on append-only log segments, and concurrency rests on 32-bit transaction IDs.

Academic textbooks teach relational algebra (the mathematics of tables) and serializability graphs (the mathematics of concurrent transactions), yet rarely open an actual 8~KB page on disk. They seldom show why hardware alignment rules pad a row header or why a 4~KB operating system write can tear an 8~KB database page in half. Operational manuals list settings like \texttt{shared\_buffers}, \texttt{work\_mem}, and \texttt{autovacuum\_vacuum\_scale\_factor}, yet seldom derive from first principles what breaks when they are misconfigured. This book keeps the math, the byte-level PostgreSQL layout, and production engineering together.

\section*{What this book is, and who it is for}

This book assumes you know Java~6 (classes, \texttt{null}, \texttt{synchronized}, \texttt{ArrayList}, \texttt{HashMap}, and garbage collection) and basic C (structs, pointers, \texttt{malloc}, \texttt{write}, and \texttt{fsync}). You may have written SQL through JDBC or Hibernate, or you may be meeting SQL seriously for the first time. We assume no prior knowledge of database internals. Each new mechanism is first tied to the Java or C construct it resembles: an object graph, a \texttt{TreeMap}, a padded C struct, or an unsynced file stream. Then we show where PostgreSQL differs and why.

By the end of these eight chapters, you will be able to trace PostgreSQL from the query parser down to flash storage:

\begin{itemize}
  \item Read a SQL query in the ten-stage order the engine logically evaluates it, from \texttt{FROM} through \texttt{LIMIT}, and spot \texttt{NULL} traps.
  \item Inspect a raw 8~KB PostgreSQL table page, trace slot pointers growing downward while rows grow upward, and compute exact row sizes with alignment padding.
  \item Choose between index types based on their physical geometry, and trace how readers traverse splitting pages without blocking. Match specialized workloads to indexes built for arrays, full-text, geometry, and append-only tables.
  \item Follow a transaction commit through memory buffers, the write-ahead log, and disk synchronization, and replay crash recovery by hand.
  \item Predict which row versions a snapshot can see, why updates leave dead versions behind, when updates avoid index bloat, and why old transaction identifiers must be frozen.
  \item Build timelines for concurrent anomalies (like lost updates), pick the right lock, and read every performance counter in an execution plan.
  \item Design schemas for financial ledgers backed by replication and connection pooling.
\end{itemize}

\section*{How to read this book}

Every major mechanism in this book follows the same four-step rhythm: a concrete problem, a small paper-and-pencil trace, the exact PostgreSQL data structure, and a hands-on inspection query.

We always start with \emph{the failure or bottleneck that forced the design}. Why not store disk pointers from a customer record directly to their order records? Why not overwrite an updated integer in place inside its 8~KB page? Why not flush modified table pages straight to disk at \texttt{COMMIT}?

Next we work through \emph{tiny numbers by hand}. We pack three rows into a miniature page and watch byte offsets move when the middle row is deleted. We split a four-key search tree node while a concurrent reader is halfway down the tree. We replay crash recovery across six log records and check the log position stamped on each page.

Then we open \emph{PostgreSQL's real C structures and inspection extensions}. Built-in extensions such as \texttt{pageinspect}, \texttt{pg\_walinspect}, \texttt{pg\_buffercache}, and \texttt{pg\_stat\_statements} let you inspect live pages and log records from an ordinary \texttt{psql} prompt. In each chapter we explain what a field does in everyday words first, and then give its real PostgreSQL name so the documentation and source tree feel familiar.

\section*{One end-to-end trace}

We trace one SQL statement from text to disk.

Suppose a ledger table \texttt{accounts} holds rows with \texttt{(id BIGINT, balance\_cents BIGINT)}. Account \texttt{7} sits on page \texttt{0} at slot \texttt{1} with a balance of \texttt{25000} cents (250.00~USD). A session runs:

\begin{lstlisting}[language=SQL]
BEGIN;
UPDATE accounts
   SET balance_cents = balance_cents - 5000
 WHERE id = 7;
COMMIT;
\end{lstlisting}

A naive mental model imagines PostgreSQL seeking to byte offset $8160$ of the table file, overwriting \texttt{25000} with \texttt{20000}, and returning \texttt{UPDATE 1}. PostgreSQL does not overwrite those eight bytes in place, because that would break two promises:

\begin{enumerate}
  \item \textbf{Concurrent readers without read locks:} Another session running a report that started ten milliseconds ago must still see \texttt{25000}. It should neither block your \texttt{UPDATE} nor wait behind it.
  \item \textbf{Atomic rollback and crash safety:} Atomic rollback reverts all changes if a transaction fails. If your transaction aborts on the next statement or the server loses power, \texttt{25000} must still be intact.
\end{enumerate}

Instead, suppose your transaction gets transaction ID \texttt{502}, while the original row was inserted earlier by committed transaction \texttt{480}. Here is what PostgreSQL actually does in RAM (memory) and on disk:

\begin{enumerate}
  \item \textbf{Index lookup and buffer pin:} The database engine walks the primary-key search tree on \texttt{id} down to a leaf entry mapping \texttt{id = 7} to physical slot \texttt{(0, 1)} (page \texttt{0}, slot \texttt{1}). It finds page \texttt{0} in PostgreSQL's shared RAM cache (\texttt{shared\_buffers}) and pins the 8~KB frame (marking it so it is not discarded). Slot \texttt{1} points to byte offset \texttt{8152} inside that page.
  \item \textbf{Multi-version row creation in RAM:} Rather than overwriting \texttt{25000}, PostgreSQL marks the old row version as superseded by stamping its expiration field (\texttt{t\_xmax}) with \texttt{502}. Next it carves out a brand-new row version in the page's free space at byte offset \texttt{8104}, pointed to by slot \texttt{2}. That new version records birth transaction \texttt{t\_xmin = 502}, expiration \texttt{t\_xmax = 0}, and \texttt{balance\_cents = 20000}. Finally, the old row's forward link (\texttt{t\_ctid}) is updated from \texttt{(0, 1)} to \texttt{(0, 2)} so readers can follow the chain.
  \item \textbf{Write-Ahead Logging before page flush:} Modifying page \texttt{0} in RAM marks the buffer dirty (modified but not yet saved to disk), yet PostgreSQL does \emph{not} write that 8~KB table page to disk at commit time. Instead, it appends a short change record to the sequential Write-Ahead Log (WAL) buffer at byte position (Log Sequence Number, or LSN) \texttt{0/16B3748}. It also stamps that position at the start of page \texttt{0} (\texttt{pd\_lsn = 0/16B3748}). When \texttt{COMMIT} runs, PostgreSQL appends a tiny commit record at \texttt{0/16B3780} and calls \texttt{fdatasync} (a command to flush data to disk) on the sequential log file \emph{only}. Once those few dozen bytes reach flash, your transaction is durable---even while dirty page \texttt{0} rests in RAM for minutes until a checkpoint flushes it.
\end{enumerate}

\section*{How the book is organized}

\textbf{Part~I --- Relations, Storage Pages, and Access Methods (Chapters~1--3).} Chapter~1 explains relational algebra and SQL. Chapter~2 explains how rows are stored on disk pages and in memory. Chapter~3 explains search trees and specialized indexes.

\textbf{Part~II --- Durability, Concurrency, and MVCC Internals (Chapters~4--6).} Chapter~4 explains crash recovery and the write-ahead log. Chapter~5 explains how PostgreSQL keeps multiple versions of rows for concurrent readers. Chapter~6 explains transaction isolation levels and row locks.

\textbf{Part~III --- Query Execution and Production PostgreSQL (Chapters~7--8).} Chapter~7 explains the query planner and execution plans. Chapter~8 explains schema design, replication, and connection pooling.

\section*{Exercises}

Every chapter closes with concrete exercises. These five require nothing beyond what we just traced.

\begin{exercise}[Counting rows per 8~KB page]
An empty PostgreSQL heap page is $8{,}192$ bytes long and begins with a $24$-byte page header. Each row added to the page consumes one $4$-byte slot pointer at the front of the page plus the padded row bytes at the back. Suppose each row in a narrow ledger table occupies $40$ bytes (a $24$-byte row header plus two $8$-byte \texttt{BIGINT} columns). What is the maximum number of live rows that fit on a single $8{,}192$-byte page? How many bytes of free space remain unused?
\end{exercise}

\begin{exercise}[Why in-place overwrite breaks crash atomicity]
Suppose a naive storage engine has no Write-Ahead Log and updates rows by overwriting bytes directly inside table pages on disk. A transaction transfers 50~USD from Account~A (stored on page~$12$) to Account~B (stored on page~$904$). Describe the disk state if power fails halfway between flushing page~$12$ and flushing page~$904$. Why can the restarted server not tell whether to undo page~$12$ or finish page~$904$?
\end{exercise}

\begin{exercise}[Log Sequence Number byte arithmetic]
PostgreSQL writes a 64-bit Log Sequence Number as \texttt{X/YYYYYYYY}, where \texttt{X} is the upper 32 bits in hexadecimal and \texttt{YYYYYYYY} is the lower 32 bits in hexadecimal. In our trace above, the heap update record began at \texttt{0/16B3748} and the commit record began at \texttt{0/16B3780}. How many bytes long was the heap update WAL record?
\end{exercise}

\begin{exercise}[Reading through a version chain]
Look back at the 8~KB heap-page diagram in this preface, where Row Version \texttt{(0, 1)} has \texttt{xmin = 480, xmax = 502} and Row Version \texttt{(0, 2)} has \texttt{xmin = 502, xmax = 0}. Suppose Transaction~\texttt{501} started \emph{before} Transaction~\texttt{502} committed, while Transaction~\texttt{505} started \emph{after} Transaction~\texttt{502} committed. Which row version should Transaction~\texttt{501} read, which row version should Transaction~\texttt{505} read, and why can neither transaction safely delete \texttt{(0, 1)} while Transaction~\texttt{501} is still running?
\end{exercise}

\begin{exercise}[Sequential WAL versus random heap I/O]
A busy payment checkout inserts one row into an \texttt{orders} table that has four secondary indexes (on \texttt{customer\_id}, \texttt{merchant\_id}, \texttt{created\_at}, and \texttt{status}). How many distinct 8~KB pages in \texttt{shared\_buffers} may be dirtied by this single \texttt{INSERT}? Compare the I/O cost of calling \texttt{fdatasync} on five scattered files across a 2~TB table space at \texttt{COMMIT} versus appending roughly 300 bytes to one sequential \texttt{pg\_wal} file.
\end{exercise}
