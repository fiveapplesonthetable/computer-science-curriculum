\chapter{Isolation Anomalies, Row Locking, and Serializable Snapshot Isolation}

In Chapter~5 we built PostgreSQL's snapshot engine: every query receives a frozen list of completed transactions, so readers and writers glide past each other without read locks. At first glance, snapshots look like the whole answer to concurrency. Every query sees a self-consistent photograph of the database, nobody reads half-written bytes, and rollbacks vanish cleanly.

Now try running a bank on snapshots alone.

Suppose Alice holds two sub-accounts under one margin agreement: \texttt{Checking = 80~USD} and \texttt{Savings = 80~USD}. Firm policy says \emph{her combined balance across both accounts may never drop below 0~USD}. At 10:00:00.000~AM, Alice submits two 100~USD withdrawals from two browser tabs at the same millisecond---one from Checking, one from Savings. Both workers run at \texttt{REPEATABLE READ}:
\begin{itemize}
  \item Worker~1 reads its snapshot: \texttt{Checking = 80, Savings = 80} (total 160~USD). Withdrawing 100~USD leaves $60 \ge 0$, so Worker~1 sets \texttt{Checking} to $-20$ and commits.
  \item Worker~2 reads its identical 10:00:00.000~AM snapshot: \texttt{Checking = 80, Savings = 80} (total 160~USD). Withdrawing 100~USD leaves $60 \ge 0$, so Worker~2 sets \texttt{Savings} to $-20$ and commits.
\end{itemize}
Neither worker read an uncommitted byte. Neither worker touched the row the other modified. Both finished under \texttt{REPEATABLE READ} without a single error or lock wait---yet Alice just withdrew 200~USD against 160~USD of collateral, leaving a $-40$~USD balance.

\begin{focusbox}
By the end of this chapter, you will be able to answer five questions from first principles:
\begin{itemize}
  \item Why does wrapping two \texttt{SELECT} queries in \texttt{BEGIN ... COMMIT} at PostgreSQL's default isolation level still allow inconsistent totals?
  \item Why does subtracting a balance in application code lose money under concurrency, while \texttt{SET bal = bal - 8000 WHERE bal >= 8000} stays safe?
  \item How can two \texttt{REPEATABLE READ} transactions break a multi-row business rule without ever touching the same row?
  \item How does PostgreSQL's \texttt{SERIALIZABLE} mode catch every multi-row race condition without placing blocking locks on readers?
  \item Why does PostgreSQL split row locks into four strengths, and how do \texttt{SKIP LOCKED} and \texttt{ORDER BY id ASC} eliminate queue bottlenecks and deadlocks?
\end{itemize}
\end{focusbox}

\section{What ``Isolation'' Actually Promises (and Why ANSI SQL-92 Missed Half the Story)}
\label{ch06:isolation-contract}

The ``I'' in ACID stands for \emph{Isolation}: even when hundreds of transactions overlap across CPU cores, each should behave \emph{as if it had the database to itself}. Database theory calls that gold standard \textbf{serializability}.

\begin{definition}[Serializable Execution]
\label{ch06:def-serializable}
A concurrent execution of committed transactions $T_1, T_2, \dots, T_k$ is \emph{serializable} if its final state and query results match running those same transactions \textbf{strictly one after another with zero overlap} in some order $T_{\pi(1)} \to T_{\pi(2)} \to \dots \to T_{\pi(k)}$.
\end{definition}

Check Alice's two withdrawals against Definition~\ref{ch06:def-serializable}. Only two one-at-a-time orders exist for $T_1$ (withdraw 100~USD from Checking) and $T_2$ (withdraw 100~USD from Savings):
\begin{itemize}
  \item \textbf{$T_1$ then $T_2$:} $T_1$ sees $80 + 80 = 160$, sets Checking to $-20$, and commits. Next, $T_2$ sees $-20 + 80 = 60 < 100$ and \emph{rejects} the second withdrawal. Final total: $+60$~USD.
  \item \textbf{$T_2$ then $T_1$:} Symmetrically, $T_2$ sets Savings to $-20$, and $T_1$ sees $80 + (-20) = 60 < 100$ and \emph{rejects} the first withdrawal. Final total: $+60$~USD.
\end{itemize}
In \emph{every} serial execution, at most one withdrawal commits and $+60$~USD remains. Any schedule leaving $-40$~USD violates serializability: no one-at-a-time history could ever produce that state.

\subsection{The ANSI SQL-92 Table vs.\ PostgreSQL Reality}

When ANSI SQL-92 defined isolation levels (\texttt{READ UNCOMMITTED}, \texttt{READ COMMITTED}, \texttt{REPEATABLE READ}, \texttt{SERIALIZABLE}), the standard had two famous blind spots exposed in 1995 by Berenson, Bernstein, Gray, Melton, and the O'Neils:
\begin{enumerate}
  \item It assumed 1980s lock-based engines rather than MVCC snapshots; and
  \item It defined levels using only \emph{three read phenomena} (Dirty Reads, Non-Repeatable Reads, Phantom Reads), omitting \textbf{Lost Updates} and \textbf{Write Skew}.
\end{enumerate}

In PostgreSQL, MVCC snapshots reshape that matrix in ways every backend engineer must know:

\begin{center}
\footnotesize
\begin{tabular}{@{}lcccc@{}}
\toprule
\textbf{PostgreSQL Level} & \textbf{Dirty} & \textbf{Non-Repeatable} & \textbf{Phantom} & \textbf{Lost Update / Write Skew} \\
\midrule
\texttt{READ UNCOMMITTED}$^{\dagger}$ & Impossible & Possible & Possible & Possible / Possible \\
\texttt{READ COMMITTED} (default) & Impossible & Possible & Possible & \textbf{Possible} / Possible \\
\texttt{REPEATABLE READ} (SI) & Impossible & Impossible & \textbf{Impossible} & Impossible$^{\ddagger}$ / \textbf{Possible} \\
\texttt{SERIALIZABLE} (SSI) & Impossible & Impossible & Impossible & Impossible / Impossible \\
\bottomrule
\end{tabular}
\end{center}
{\footnotesize $^{\dagger}$PostgreSQL accepts \texttt{READ UNCOMMITTED} for SQL compatibility and maps it directly to \texttt{READ COMMITTED}. $^{\ddagger}$Blocked via automatic \texttt{40001} conflict abort.}

Two facts jump right out of that table:
\begin{itemize}
  \item \textbf{Dirty reads never happen in PostgreSQL} at any level, because Chapter~5's visibility check rejects uncommitted \texttt{t\_xmin} values unconditionally.
  \item \textbf{PostgreSQL's \texttt{REPEATABLE READ} already blocks phantom reads}, yet it is \emph{not} serializable: it implements pure \emph{Snapshot Isolation} (\emph{SI}), which still allows \textbf{Write Skew}.
\end{itemize}

Let us trace each anomaly on concrete two-session timelines.

\section{Read Anomalies: Dirty Reads, Read Skew, and Phantoms}
\label{ch06:read-anomalies}

\subsection{Dirty Read ($P_1$): Reading Uncommitted Bytes}

A \emph{dirty read} happens when session~$T_2$ reads bytes written by concurrent session~$T_1$ \emph{before} $T_1$ commits. If $T_1$ then runs \texttt{ROLLBACK}, $T_2$ acted on money that never existed:

\begin{lstlisting}[language=SQL]
-- T1                                  -- T2
BEGIN;                                 BEGIN;
UPDATE accounts SET bal = 99999900
 WHERE id = 1;
                                       -- Under true READ UNCOMMITTED:
                                       SELECT bal FROM accounts WHERE id = 1;
                                       -- Sees 99999900 and wires cash out!
ROLLBACK; -- T1 aborts!
\end{lstlisting}

In PostgreSQL, when $T_1$ updates the row, old version \texttt{(0,1)} gets \texttt{t\_xmax = xid(T1)} and new version \texttt{(0,2)} gets \texttt{t\_xmin = xid(T1)}. While \texttt{xid(T1)} is still running in \texttt{pg\_xact}, $T_2$ sees that \texttt{(0,1)}'s deleter has not committed (so \texttt{(0,1)} stays visible) and \texttt{(0,2)}'s creator has not committed (so \texttt{(0,2)} stays hidden). Dirty reads cannot happen.

If $T_2$ instead re-read \texttt{id = 1} in its second query, it would see \texttt{5000} first and \texttt{1000} second---a \emph{non-repeatable read}. Seeing an inconsistent cut across two related rows is its multi-row twin, \textbf{read skew}.

\subsection{Phantom Reads ($P_3$)}

A \emph{phantom read} is the set-level twin of a non-repeatable read: concurrent session~$T_1$ \textbf{\texttt{INSERT}s a new row} (or \texttt{DELETE}s one) matching $T_2$'s \texttt{WHERE} filter between two queries in $T_2$. Under \texttt{READ COMMITTED}:
\begin{enumerate}
  \item $T_2$ runs \texttt{SELECT COUNT(*) FROM postings WHERE entry\_id = 500;} and gets \texttt{2}.
  \item $T_1$ inserts a third fee leg into \texttt{entry\_id = 500} and commits.
  \item $T_2$ runs \texttt{SELECT amount\_minor FROM postings WHERE entry\_id = 500;} expecting two rows---and gets \textbf{three} rows.
\end{enumerate}

Switch $T_2$ to \texttt{BEGIN ISOLATION LEVEL REPEATABLE READ;} and both non-repeatable reads and phantom reads disappear. The third posting's \texttt{t\_xmin} belongs to $T_1$ ($\ge \mathrm{xmax}_{S_1}$ or in $\mathrm{xip}_{S_1}$), so $S_1$ hides the inserted row cleanly.

\begin{trapbox}
Many developers assume wrapping two \texttt{SELECT} queries in \texttt{BEGIN; ... COMMIT;} freezes a shared snapshot automatically. \textbf{At default \texttt{READ COMMITTED}, \texttt{BEGIN ... COMMIT} around plain \texttt{SELECT}s does not freeze your snapshot across statements.} Every \texttt{SELECT} still grabs a new snapshot. Multi-query reports or reconciliations \emph{must} run \texttt{BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;} (or combine both reads into one SQL query).
\end{trapbox}

\section{Lost Updates and \texttt{EvalPlanQual} Re-Evaluation}
\label{ch06:lost-updates-epq}

Now let both concurrent sessions \emph{write} to the same account row \texttt{id = 1}, starting at \texttt{bal = 10000} (100.00~USD). Two payment workers simultaneously process two 80.00~USD (\texttt{8000}-cent) ATM withdrawals. What happens depends on \emph{how} you write the SQL and \emph{which} isolation level you pick.

\subsection{Case 1: Read-Modify-Write in Application Code Under \texttt{READ COMMITTED}}

In ORM-heavy codebases, developers often fetch a row into app memory, subtract in code, and write back the literal result:

\begin{lstlisting}[language=SQL]
-- Worker 1 (READ COMMITTED)           -- Worker 2 (READ COMMITTED)
BEGIN;                                 BEGIN;
SELECT bal FROM accounts WHERE id = 1; SELECT bal FROM accounts WHERE id = 1;
-- App computes: 10000 - 8000 = 2000   -- App computes: 10000 - 8000 = 2000

UPDATE accounts SET bal = 2000
 WHERE id = 1;
                                       UPDATE accounts SET bal = 2000
                                        WHERE id = 1;
                                       -- Blocks waiting on Worker 1's XID!
COMMIT;
                                       -- Unblocks, writes 2000, and COMMITS!
\end{lstlisting}

The ATM handed out 80.00~USD \emph{twice} (160.00~USD total), yet \texttt{accounts.bal} ends at \texttt{2000} (20.00~USD). Worker~2 overwrote Worker~1's debit using a stale read: a \textbf{Lost Update}. It is the exact same bug as two Java threads running \texttt{balance = balance - 80} without synchronization.

\subsection{Case 2: Atomic SQL \texttt{SET bal = bal - 8000} and \texttt{EvalPlanQual} (\texttt{EPQ})}

Now push the subtraction into a single atomic SQL \texttt{UPDATE} with a balance guard under \texttt{READ COMMITTED}:

\begin{lstlisting}[language=SQL]
UPDATE accounts
   SET bal = bal - 8000
 WHERE id = 1 AND bal >= 8000
RETURNING bal;
\end{lstlisting}

Trace what PostgreSQL's update executor does when Worker~1 and Worker~2 run this statement at the same microsecond under \texttt{READ COMMITTED}:
\begin{enumerate}
  \item Both workers take a snapshot seeing version \texttt{(0,1)} with \texttt{bal = 10000}, where \texttt{10000 >= 8000} is \texttt{true}.
  \item Worker~1 reaches the row first, stamps its XID into \texttt{(0,1)}'s \texttt{t\_xmax}, inserts \texttt{(0,2)} with \texttt{bal = 2000}, and commits.
  \item Worker~2 arrives a microsecond behind, sees Worker~1's active \texttt{t\_xmax} on \texttt{(0,1)}, and \textbf{waits for Worker~1 to finish}.
  \item Once Worker~1 commits, Worker~2 wakes up facing a dilemma. Using old \texttt{(0,1)} (\texttt{10000}) would lose Worker~1's debit; blindly subtracting \texttt{8000} from new \texttt{(0,2)} (\texttt{2000}) would write \texttt{-6000} and violate \texttt{WHERE bal >= 8000}.
\end{enumerate}

To handle concurrent row updates safely under \texttt{READ COMMITTED}, PostgreSQL walks forward to the newest committed row version and re-runs both the \texttt{WHERE} filter and the \texttt{SET} expression against it. Internally, this re-check step is called \textbf{\texttt{EvalPlanQual}} (\textbf{\texttt{EPQ}}):
\begin{itemize}
  \item Worker~2 follows \texttt{(0,1)}'s \texttt{t\_ctid} link to committed version \texttt{(0,2)} (\texttt{bal = 2000}) and locks it.
  \item \texttt{EvalPlanQual} plugs \texttt{(0,2)} into the query plan and \textbf{re-checks \texttt{WHERE} and \texttt{SET} on \texttt{(0,2)}}.
  \item On \texttt{bal = 2000}, \texttt{bal >= 8000} is \textbf{false}. Worker~2 skips the row, returns \texttt{UPDATE 0}, and declines the second ATM withdrawal.
\end{itemize}

\begin{trapbox}
\textbf{Even \texttt{EvalPlanQual} has a sharp edge on multi-table \texttt{UPDATE ... FROM} queries.}
Under \texttt{READ COMMITTED}, \texttt{EvalPlanQual} reloads only \emph{locked target rows}; unlocked joined tables in \texttt{FROM} or subqueries keep the rows from the statement's original snapshot. For single-row debits, \texttt{SET bal = bal - p\_amt WHERE bal >= p\_amt} is safe. For multi-statement read-modify-write code without explicit locks, \texttt{REPEATABLE READ} catches every same-row collision automatically via \textbf{First-Updater-Wins} (\texttt{SQLSTATE 40001}).
\end{trapbox}

\section{Write Skew: Why \texttt{REPEATABLE READ} Still Breaks Multi-Row Invariants}
\label{ch06:write-skew}

Look back at Panel~3 of Figure~\ref{ch06:fig-lost-update-epq}. Why did \texttt{REPEATABLE READ} catch that lost update? Because $T_1$ and $T_2$ modified \textbf{the exact same row} (\texttt{id = 1}). When $T_2$ tried to stamp \texttt{t\_xmax} on \texttt{id = 1}, it saw $T_1$'s committed \texttt{t\_xmax} and raised \texttt{40001}.

Now return to Alice's two sub-accounts from our opening page, or the classic hospital on-call rule (``at least one night-shift doctor must stay \texttt{on\_call = true}''). Watch Worker~1 and Worker~2 run under \texttt{REPEATABLE READ}:

\begin{lstlisting}[language=SQL]
-- Worker 1 (REPEATABLE READ)           -- Worker 2 (REPEATABLE READ)
BEGIN ISOLATION LEVEL REPEATABLE READ;  BEGIN ISOLATION LEVEL REPEATABLE READ;

SELECT SUM(bal) FROM sub_accounts       SELECT SUM(bal) FROM sub_accounts
 WHERE user_id = 7;  -- returns 16000    WHERE user_id = 7;  -- returns 16000

-- 16000 - 10000 = 6000 >= 0 (OK!)      -- 16000 - 10000 = 6000 >= 0 (OK!)
UPDATE sub_accounts                     UPDATE sub_accounts
   SET bal = bal - 10000                   SET bal = bal - 10000
 WHERE user_id = 7 AND kind = 'chk';     WHERE user_id = 7 AND kind = 'sav';

COMMIT; -- Succeeds!                    COMMIT; -- ALSO SUCCEEDS!
-- Combined balance is now -2000 + (-2000) = -4000 (< 0)!
\end{lstlisting}

Database researchers call this bug \textbf{Write Skew}:
\begin{enumerate}
  \item $T_1$ and $T_2$ read \emph{overlapping} rows ($R(T_1) = \{\texttt{chk}, \texttt{sav}\}$ and $R(T_2) = \{\texttt{chk}, \texttt{sav}\}$).
  \item Using what they read, $T_1$ and $T_2$ write to \emph{disjoint} rows ($W(T_1) = \{\texttt{chk}\}$, $W(T_2) = \{\texttt{sav}\}$, so $W(T_1) \cap W(T_2) = \emptyset$).
  \item Because their write sets never touch the same row, First-Updater-Wins never fires, and the multi-row rule ($\texttt{chk} + \texttt{sav} \ge 0$) breaks silently.
\end{enumerate}

Write skew strikes \textbf{\texttt{INSERT}s} too (\emph{insert write skew}):
\begin{itemize}
  \item \textbf{Room double-booking} (without an exclusion constraint): Worker~1 checks \texttt{COUNT(*) = 0} for Room~4 from 2--3~PM and inserts booking~A; Worker~2 sees \texttt{COUNT(*) = 0} too and inserts booking~B. Neither updated an existing row, so both commit under \texttt{REPEATABLE READ}.
  \item \textbf{Daily payout cap}: Two concurrent payouts check that Merchant~99's daily wires total under 50,000~USD, and each inserts a 40,000~USD wire. Both commit under \texttt{REPEATABLE READ}, sending 80,000~USD.
\end{itemize}

\section{Serializable Snapshot Isolation (SSI): True \texttt{SERIALIZABLE} Without Read Locks}
\label{ch06:ssi}

For thirty years after System~R, textbooks taught a painful tradeoff: preventing write skew required \textbf{Strict Two-Phase Locking (S2PL)}, where every \texttt{SELECT} took shared read and index-gap locks that blocked writers. Because read locks hurt throughput, PostgreSQL before version~9.1 mapped \texttt{SERIALIZABLE} silently to \texttt{REPEATABLE READ}.

In 2008, Michael Cahill, Uwe R\"ohm, and Alan Fekete proved a breakthrough result, shipped in PostgreSQL~9.1 by Kevin Grittner and Dan Ports. You can keep \textbf{100\% non-blocking MVCC reads} and still guarantee full serializability by watching lightweight read-before-write conflict links in RAM. PostgreSQL calls this engine \textbf{Serializable Snapshot Isolation} (\textbf{SSI}).

\subsection{Conflict Edges and the ``Dangerous Structure'' Theorem}

When two transactions $T_1$ and $T_2$ touch the same row or index range $x$, three ordering links can form:
\begin{enumerate}
  \item \textbf{Write-Read ($T_1 \xrightarrow{\mathrm{wr}} T_2$):} $T_1$ writes $x$ and commits; $T_2$'s snapshot reads that version. Thus $T_1$ comes before $T_2$.
  \item \textbf{Write-Write ($T_1 \xrightarrow{\mathrm{ww}} T_2$):} $T_1$ writes $x$ and commits; $T_2$ overwrites $T_1$'s version. Again $T_1$ comes before $T_2$.
  \item \textbf{Read-Write Antidependency ($T_1 \xrightarrow{\mathrm{rw}} T_2$):} $T_1$ reads an \emph{older} version of $x$, while concurrent $T_2$ writes a \emph{newer} version of $x$ (or inserts a row matching $T_1$'s \texttt{WHERE} filter). In any matching one-at-a-time history, \textbf{$T_1$ must come before $T_2$}: had $T_2$ run first, $T_1$ would have seen $T_2$'s write.
\end{enumerate}

Now trace those links on Alice's Checking/Savings overdraft:
\begin{itemize}
  \item $T_1$ read old \texttt{sav} (\texttt{8000}) while concurrent $T_2$ updated \texttt{sav} to \texttt{-2000}: $T_1 \xrightarrow{\mathrm{rw}} T_2$.
  \item $T_2$ read old \texttt{chk} (\texttt{8000}) while concurrent $T_1$ updated \texttt{chk} to \texttt{-2000}: $T_2 \xrightarrow{\mathrm{rw}} T_1$.
\end{itemize}
Together they form a cycle:
\[
  T_1 \;\xrightarrow{\;\mathrm{rw}\;}\; T_2 \;\xrightarrow{\;\mathrm{rw}\;}\; T_1.
\]
$T_1$ must run before $T_2$, and $T_2$ must run before $T_1$---no valid serial order exists. Fekete et al.\ proved that \emph{every} Snapshot Isolation anomaly leaves one telltale two-step footprint:

\begin{theorem}[Dangerous Structure Under Snapshot Isolation]
\label{ch06:thm-ssi}
In any non-serializable Snapshot Isolation schedule, the dependency graph has a cycle, and \textbf{every minimal cycle contains two consecutive $\mathrm{rw}$-antidependency edges}:
\[
  T_{\mathrm{in}} \;\xrightarrow{\;\mathrm{rw}\;}\; T_{\mathrm{pivot}} \;\xrightarrow{\;\mathrm{rw}\;}\; T_{\mathrm{out}},
\]
where each adjacent pair overlapped in time and $T_{\mathrm{out}}$ commits first ($T_{\mathrm{in}} = T_{\mathrm{out}}$ in 2-party write skew).
\end{theorem}

\begin{intuitionbox}
Why does Theorem~\ref{ch06:thm-ssi} keep SSI fast? Searching a huge graph for arbitrary cycles on every query would be slow. Theorem~\ref{ch06:thm-ssi} says PostgreSQL never needs full cycle search. It merely watches for any \textbf{pivot transaction} $T_{\mathrm{pivot}}$ with both an incoming $\mathrm{rw}$-link and an outgoing $\mathrm{rw}$-link whose target $T_{\mathrm{out}}$ commits first. One local two-hop check in shared memory catches every anomaly.
\end{intuitionbox}

\subsection{How \texttt{SIRead} Predicate Locks Work Inside PostgreSQL}

To spot when $T_2$ writes data that $T_1$ already read---even an empty gap where no row existed yet---PostgreSQL records passive read markers in shared memory called \textbf{\texttt{SIRead} predicate locks} (\texttt{predicate.c}):
\begin{enumerate}
  \item \textbf{\texttt{SIRead} markers never block anyone:} Despite the name, an \texttt{SIRead} lock is just a passive sticky note in RAM saying ``serializable session~$T_1$ read this row, index page, or table.'' Readers never wait on writers, and writers never wait on \texttt{SIRead} markers.
  \item \textbf{Index leaf tags catch phantom inserts:} When $T_1$ runs an index scan \texttt{WHERE room = 4 AND ...} and finds zero rows, PostgreSQL tags the \textbf{B-tree leaf page} where \texttt{room = 4} belongs. When concurrent $T_2$ inserts a booking onto that leaf page, it trips $T_1$'s marker and records $T_1 \xrightarrow{\mathrm{rw}} T_2$. (Without an index, a \texttt{Seq Scan} must tag the whole table---so always index columns filtered inside \texttt{SERIALIZABLE} transactions to avoid false-positive retries.)
  \item \textbf{Bounded RAM via promotion:} If a query reads thousands of rows on one page, PostgreSQL merges their row markers into one page-level (or table-level) marker governed by \texttt{max\_pred\_locks\_per\_transaction}. Merging never misses a real conflict; at worst it causes an extra \texttt{40001} retry.
  \item \textbf{Retained briefly past \texttt{COMMIT}:} In Alice's example, $T_1$ commits \emph{first}, and the cycle completes only when $T_2$ commits second. PostgreSQL therefore keeps a committed transaction's \texttt{SIRead} summary until all overlapping serializable transactions finish.
\end{enumerate}

\begin{recoverybox}
\textbf{Pause and compare the three MVCC isolation levels.} \texttt{READ COMMITTED} takes a new snapshot per statement. \texttt{REPEATABLE READ} keeps one snapshot per transaction and aborts same-row write collisions. \texttt{SERIALIZABLE} adds non-blocking \texttt{SIRead} markers to abort multi-row write-skew cycles with \texttt{40001} so your app can retry cleanly.
\end{recoverybox}

\begin{applicationbox}
\textbf{Two rules every \texttt{SERIALIZABLE} production service lives by:}
\begin{enumerate}
  \item \textbf{Wrap every \texttt{REPEATABLE READ} or \texttt{SERIALIZABLE} transaction in a retry loop} catching \texttt{SQLSTATE 40001} and \texttt{40P01}, rolling back, and re-running from \texttt{BEGIN} with brief jitter. Never fire irreversible side effects (like charging a card or sending an email) inside a retryable transaction; write a transactional \texttt{outbox} row instead.
  \item \textbf{Mark long read-only reports \texttt{SERIALIZABLE READ ONLY DEFERRABLE}:} Plain \texttt{SERIALIZABLE} on a 30-second report places \texttt{SIRead} markers that can trigger \texttt{40001} retries. Starting with:
\begin{lstlisting}[language=SQL]
BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE;
\end{lstlisting}
  waits briefly at \texttt{BEGIN} for a safe snapshot isolated from active writers, then runs the entire 30-second report with \textbf{zero \texttt{SIRead} markers and zero \texttt{40001} errors}.
\end{enumerate}
\end{applicationbox}

\section{Explicit Row Locks, Work Queues, Deadlocks, and Advisory Locks}
\label{ch06:explicit-locks}

SSI is optimistic: sessions run without waiting and retry if \texttt{40001} fires. Under heavy contention on one hot row---say, 200 checkout workers debiting the same flash-sale SKU---re-running 199 aborted transactions wastes CPU. On hot rows, \textbf{pessimistic locking} (queuing writers cleanly on the first pass) wins.

\subsection{PostgreSQL's Four Row-Level Lock Strengths}

Why does PostgreSQL offer \emph{four} \texttt{SELECT ... FOR ...} row-lock modes instead of just ``shared'' and ``exclusive''? Because of \textbf{foreign keys}.

Suppose \texttt{postings.account\_id} references \texttt{accounts(id)}. Inserting a posting for Account~42 must stop anyone from deleting Account~42 or changing its \texttt{id} before commit. Before PostgreSQL~9.3, that child insert took \texttt{FOR SHARE} on \texttt{accounts(id = 42)}, \textbf{blocking every concurrent balance \texttt{UPDATE} on Account~42} even though \texttt{id} never changed.

PostgreSQL fixed that bottleneck by splitting row locks into four strengths:
\begin{enumerate}
  \item \textbf{\texttt{FOR KEY SHARE}:} Weakest lock, taken automatically on parent rows during foreign-key checks. Conflicts \emph{only} with \texttt{DELETE} and key-changing updates (\texttt{FOR UPDATE}).
  \item \textbf{\texttt{FOR SHARE}:} Shared lock freezing the whole row until commit. Blocks \texttt{FOR NO KEY UPDATE} and \texttt{FOR UPDATE}, while allowing other \texttt{FOR SHARE} readers.
  \item \textbf{\texttt{FOR NO KEY UPDATE}:} Taken automatically by any \texttt{UPDATE} that leaves \texttt{PRIMARY KEY} / \texttt{UNIQUE} columns untouched. \textbf{Compatible with \texttt{FOR KEY SHARE}}, so child inserts and parent balance updates run side by side without blocking.
  \item \textbf{\texttt{FOR UPDATE}:} Strongest row lock (taken by \texttt{DELETE} or key-changing updates). Blocks all four row-lock modes, while still never blocking plain MVCC \texttt{SELECT}s.
\end{enumerate}

To prevent Alice's Checking/Savings overdraft pessimistically under default \texttt{READ COMMITTED}, lock \textbf{both} rows in ID order before summing:

\begin{lstlisting}[language=SQL]
BEGIN;
-- Locks BOTH sub-accounts in deterministic ID order before summing!
SELECT id, kind, bal
  FROM sub_accounts
 WHERE user_id = 7
 ORDER BY id ASC
   FOR NO KEY UPDATE;
-- Worker 2 sleeps right here until Worker 1 commits, then sees bal = 6000!
\end{lstlisting}

\subsection{Non-Blocking Modifiers: \texttt{NOWAIT} and \texttt{SKIP LOCKED} Job Queues}

By default, \texttt{FOR UPDATE} waits until the lock holder finishes. Two clauses change that wait behavior:
\begin{itemize}
  \item \textbf{\texttt{FOR UPDATE NOWAIT}:} Fails \emph{immediately} with \texttt{SQLSTATE 55P03} if the row is locked instead of parking an HTTP thread. In user-facing APIs, always use \texttt{NOWAIT} or \texttt{SET LOCAL lock\_timeout = '2s';} so one stuck lock cannot drain your connection pool.
  \item \textbf{\texttt{FOR UPDATE SKIP LOCKED}:} Quietly skips rows already locked by other workers. Six lines of SQL turn an ordinary table into an ACID work queue where fifty workers claim disjoint batches with zero lock waits:
\end{itemize}

\begin{lstlisting}[language=SQL]
WITH claimed AS (
    SELECT id
      FROM webhook_outbox
     WHERE status = 'pending' AND next_attempt_at <= now()
     ORDER BY next_attempt_at ASC
     LIMIT 25
       FOR UPDATE SKIP LOCKED
)
UPDATE webhook_outbox w
   SET status = 'processing', attempts = attempts + 1
  FROM claimed c
 WHERE w.id = c.id
RETURNING w.id, w.endpoint_url, w.payload_json;
\end{lstlisting}

\subsection{Deadlocks (\texttt{deadlock\_timeout}) and Deterministic Lock Ordering}

Whenever transactions lock multiple rows one by one, opposite lock orders can form a wait cycle:
\begin{itemize}
  \item $T_1$ transfers 10~USD from Account~10 to Account~20: locks row~\texttt{10}, then waits on row~\texttt{20}.
  \item Simultaneously, $T_2$ transfers 15~USD from Account~20 to Account~10: locks row~\texttt{20}, then waits on row~\texttt{10}.
\end{itemize}
Now $T_1$ waits on $T_2$ and $T_2$ waits on $T_1$; neither can move forward.

PostgreSQL checks for deadlocks lazily. Building a global wait graph on every microsecond lock wait would waste CPU when 99.99\% of row locks clear in under a millisecond. Instead, a waiting backend sets a timer for \textbf{\texttt{deadlock\_timeout}} (default \texttt{1s}). Only if it is still waiting after 1,000~ms does it scan the wait graph, spot $T_1 \to T_2 \to T_1$, and abort one victim with \texttt{SQLSTATE 40P01: deadlock detected}.

The proof behind Figure~\ref{ch06:fig-locks-deadlock} takes two lines. If every session locks accounts in strictly increasing \texttt{id} order, any session holding $k_1$ while waiting for $k_2$ satisfies $k_1 < k_2$. A cycle $k_1 < k_2 < \dots < k_m < k_1$ would imply $k_1 < k_1$, which is impossible. Sorting account IDs before locking eliminates transfer deadlocks completely.

\subsection{Transactional Advisory Locks (\texttt{pg\_advisory\_xact\_lock})}

One puzzle remains: how do you lock a resource \textbf{whose row does not exist yet}? Suppose two requests concurrently onboard merchant \texttt{tax\_id = 'US-98-7654321'} and run validation checks before inserting the first row. \texttt{SELECT ... FOR UPDATE WHERE tax\_id = ...} finds zero rows and locks nothing.

PostgreSQL solves this with \textbf{advisory locks}---application-defined 64-bit integer keys held purely in shared memory, generating zero heap writes, zero dead rows, and zero WAL:

\begin{lstlisting}[language=SQL]
BEGIN;
-- Hash a namespace + business key to a 64-bit BIGINT lock ID;
-- automatically released at COMMIT or ROLLBACK!
SELECT pg_advisory_xact_lock(
    hashtextextended('onboard_tax_id:' || $1, 0)
);
-- Now strictly one worker per tax_id executes this critical section at a time!
COMMIT;
\end{lstlisting}

Always prefer transaction-scoped \texttt{pg\_advisory\_xact\_lock} over session-scoped \texttt{pg\_advisory\_lock}. Behind a transaction-mode pooler like \texttt{PgBouncer} (Chapter~8), an unreleased session lock stays stuck on the pooled backend connection and blocks unrelated tenants.

We now know how PostgreSQL keeps concurrent transactions fast and isolated. Yet before any query can lock or read a row, PostgreSQL must choose \emph{how} to find it across billions of rows and dozens of tables---sequential scan, index scan, bitmap scan, nested loop, hash join, or merge join. Chapter~7 opens the query planner and reads \texttt{EXPLAIN (ANALYZE, BUFFERS)} line by line.

\section{Exercises}
\label{ch06:exercises}

\begin{exercise}[Testing serializability by hand]
Accounts start at \texttt{A = 100} and \texttt{B = 100}. Consider two committed transactions:
\begin{itemize}
  \item $T_1$: reads \texttt{A}, then sets \texttt{B = A + 50}.
  \item $T_2$: reads \texttt{B}, then sets \texttt{A = B * 2}.
\end{itemize}
(a) Find the final $(\texttt{A}, \texttt{B})$ pair for both serial orders ($T_1 \to T_2$ and $T_2 \to T_1$).
(b) Find the final $(\texttt{A}, \texttt{B})$ pair when $T_1$ and $T_2$ run concurrently from the same initial snapshot under \texttt{REPEATABLE READ}. Does \texttt{REPEATABLE READ} raise an error, and is the result serializable?
(c) Trace what changes under \texttt{ISOLATION LEVEL SERIALIZABLE}.
\end{exercise}

\begin{exercise}[Read skew in pagination and reporting]
At default \texttt{READ COMMITTED}, an API wraps two queries in \texttt{BEGIN; ... COMMIT;}. First it runs \texttt{SELECT COUNT(*) FROM invoices WHERE user\_id = 99 AND status = 'unpaid';} for a badge, and 5~ms later it fetches \texttt{SELECT id, amount\_minor FROM invoices} with the same filter. Show an interleaving with a concurrent payment where the badge says ``1 unpaid invoice'' while the list is empty. Give two ways to fix the mismatch without blocking the writer.
\end{exercise}

\begin{exercise}[Tracing \texttt{EvalPlanQual} step by step]
