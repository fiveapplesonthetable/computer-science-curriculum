\chapter{MVCC, Snapshots, \texttt{VACUUM}, and Transaction ID Wraparound}

In Chapter~4, Write-Ahead Logging solved crash survival: if power fails mid-transaction, the redo log guarantees that committed bytes survive and torn 8~KB pages heal on restart. Now suppose the server stays up, the SSDs are healthy, and five hundred clients connect at once.

Picture a payment platform at 4:00~PM. Four hundred checkout workers are running small transfers---subtracting 50~USD from one row of \texttt{accounts} and adding 50~USD to another---while an analyst audits all ten million accounts:

\begin{lstlisting}[language=SQL]
SELECT SUM(balance_minor) FROM accounts;
\end{lstlisting}

Suppose a transfer moves 5,000 cents from Account~A (on block~12) to Account~Z (on block~98,400) while the scan sits at block~40,000. If the scan reads Account~A \emph{before} the debit and reaches block~98,400 \emph{after} the credit commits, it counts those 5,000 cents twice. Flip the block order and 5,000 cents vanish from the audit, even though every single transfer balanced.

Early databases prevented that miscount with two-phase read/write locks. The \texttt{SELECT} locked every page it read, blocking writers until all ten million rows finished scanning, while write locks stalled the scan right back. Throughput collapsed whenever analytics and live payments shared a table.

PostgreSQL takes a different path: \emph{Multi-Version Concurrency Control} (\emph{MVCC}). Under MVCC, \textbf{readers never block writers, and writers never block readers}. Instead of overwriting a row in place while another query might still be reading it, every update writes a fresh version alongside the old one. Transaction IDs stamped on each version tell every reader which copy belongs to its moment in time.

If you have used Java's \texttt{CopyOnWriteArrayList}, you already know this pattern. An iterator keeps walking the array it started with, even while a writer builds a modified copy and swaps the list pointer. Readers take zero locks, and the garbage collector frees the old array once no iterator needs it. PostgreSQL applies that same idea one row at a time, with background \texttt{VACUUM} acting as the garbage collector.

\begin{focusbox}
By the end of this chapter, you will be able to answer five questions from first principles:
\begin{itemize}
  \item Why does PostgreSQL write new row versions right into table pages instead of using a separate undo log, and why does that make a ten-million-row \texttt{ROLLBACK} instant?
  \item How can a 100\% read-only \texttt{SELECT} query dirty thousands of buffer pages and emit megabytes of Write-Ahead Log?
  \item How does a three-number snapshot string like \texttt{740:748:742,745} let an audit query read a frozen point in time while payments commit around it?
  \item Why does indexing a frequently updated column slow down \emph{every} other index on the table, and how do same-page (HOT) updates avoid that trap?
  \item How can 32-bit transaction counter wraparound make committed rows vanish without touching a byte on disk---and how does tuple freezing prevent it?
\end{itemize}
\end{focusbox}

\section{Two Ways to Build a Time Machine: Undo Logs vs.\ In-Heap Versions}
\label{ch05:undo-vs-heap}

Once you decide that an \texttt{UPDATE} must not destroy the bytes an older reader still needs, there are only two places in the storage engine where the multiple versions of a row can live. Every major relational database picks one of these two designs, and nearly every operational quirk of Oracle, MySQL/InnoDB, and PostgreSQL flows from that single choice.

\paragraph{Design A: Overwrite in place and push old bytes to an undo log (Oracle, InnoDB).}
In InnoDB and Oracle, the main table page holds \emph{only the newest version} of each row. When transaction~$T_2$ changes a balance from \texttt{10000} to \texttt{5000}, the engine writes \texttt{5000} straight into the table page. First, though, it copies the displaced value (``balance was \texttt{10000}'') into a separate \emph{undo log} and links the row header backward to that undo record.

Look at what Design~A optimizes and what it penalizes:
\begin{itemize}
  \item \textbf{Fast in-place updates for unindexed columns:} If an \texttt{UPDATE} leaves secondary index columns untouched, secondary indexes need no new entries because the row's slot or primary key stayed put.
  \item \textbf{Slow \texttt{ROLLBACK} on big writes:} If a batch \texttt{UPDATE} modifies five million rows and aborts at the end, the engine must walk five million undo records and copy old bytes back into table pages.
  \item \textbf{Undo-chain walks for older snapshots:} A five-minute-old report query cannot read table pages at face value. Whenever it hits a recently changed row, it must chase undo links backward to rebuild an older version. If the undo log recycles space first, Oracle raises \texttt{ORA-01555: snapshot too old}.
\end{itemize}

\paragraph{Design B: Append new tuple versions directly into the heap (PostgreSQL).}
Michael Stonebraker originally built Postgres around an archival idea: never overwrite rows at all, so queries could ask for a table ``as of last Tuesday.'' Modern PostgreSQL replaced infinite history with garbage collection, yet kept that physical layout. When transaction~$T_2$ updates a row, the old version stays right where it sits on its 8~KB page. PostgreSQL stamps an expiration ID onto the old version, writes the complete new version into a free slot (on the same page if room permits), and links the old version forward to the new one.

\begin{intuitionbox}
In PostgreSQL, an \texttt{UPDATE} is physically a \texttt{DELETE} (stamping an expiration transaction ID onto the existing tuple) paired with an \texttt{INSERT} (appending a brand-new tuple version). Because the old bytes were never overwritten, a \texttt{ROLLBACK} of a ten-million-row update takes less than a millisecond: PostgreSQL flips two status bits in the commit log to \texttt{ABORTED} and walks away. Future readers see the aborted transaction ID on the new tuples and ignore them on sight.
\end{intuitionbox}

Every strength and operational quirk of PostgreSQL comes back to Figure~\ref{ch05:undo-vs-inheap}. Rollbacks run in $O(1)$ time, historical reads inspect table pages directly, and queries never fail with ``undo segment full.'' The price is \emph{dead tuples}: once every active query moves past \texttt{742}, versions \texttt{(0,1)} and \texttt{(0,2)} sit on the page taking up space until pruning or \texttt{VACUUM} reclaims them.

\section{Inside \texttt{HeapTupleHeaderData}: \texttt{xmin}, \texttt{xmax}, \texttt{cid}, and \texttt{ctid}}
\label{ch05:tuple-header}

To tell row versions apart without an undo log, every physical row version needs four small stamps on its front: which transaction created it, which transaction retired or locked it, which command inside a multi-step transaction wrote it, and where its next version lives. Chapter~2 showed that every row begins with a 23-byte header (\texttt{HeapTupleHeaderData} in \texttt{src/include/access/htup\_details.h}), padded to 24~bytes. Here are those exact fields:

\begin{lstlisting}[language=C]
/* Simplified from src/include/access/htup_details.h */
typedef struct HeapTupleFields {
    TransactionId t_xmin;        /* 4 bytes: inserting XID */
    TransactionId t_xmax;        /* 4 bytes: deleting / locking XID, or 0 */
    union {
        CommandId t_cid;         /* 4 bytes: command ID within transaction */
        TransactionId t_xvac;    /* legacy VACUUM FULL xid */
    } t_field3;
} HeapTupleFields;               /* 12 bytes */

typedef struct HeapTupleHeaderData {
    union {
        HeapTupleFields t_heap;  /* 12 bytes: MVCC transaction fields */
        DatumTupleFields t_datum;/* used only for in-memory composite datums */
    } t_choice;
    ItemPointerData t_ctid;      /* 6 bytes: (block_hi, block_lo, offset) */
    uint16 t_infomask2;          /* 2 bytes: natts + HOT / keys-updated flags */
    uint16 t_infomask;           /* 2 bytes: hint bits, null-bitmap, lock flags */
    uint8  t_hoff;               /* 1 byte: offset to user data */
    /* optional null bitmap follows, then aligned user columns */
} HeapTupleHeaderData;           /* 23 bytes fixed */
\end{lstlisting}

Let us trace each of the four MVCC fields, because PostgreSQL packs a lot of state into these 20 bytes.

\subsection{\texttt{t\_xmin} and Lazy Transaction ID Assignment}

Every writing transaction receives an increasing 32-bit XID (\texttt{TransactionId}), such as \texttt{740}. When transaction \texttt{740} runs an \texttt{INSERT}, it stamps \texttt{t\_xmin = 740} and \texttt{t\_xmax = 0} (signaling ``no deleter yet'') into the new tuple's header.

Notice the qualifier: \emph{every writing transaction}. What if your app runs five thousand read-only \texttt{SELECT} queries per second? Spending a 32-bit \texttt{xid} on every read would burn through four billion IDs in days. Instead, PostgreSQL assigns 32-bit XIDs \emph{lazily}. At \texttt{BEGIN}, a session gets only a cheap, backend-local virtual XID. PostgreSQL allocates a permanent 32-bit \texttt{xid} from shared memory only when the session runs its first \texttt{INSERT}, \texttt{UPDATE}, \texttt{DELETE}, \texttt{SELECT FOR UPDATE}, or \texttt{pg\_current\_xact\_id()}.

\subsection{\texttt{t\_xmax}: Deletion, Update Chains, and Row Locks}

On a freshly inserted row, \texttt{t\_xmax = 0}. Three events write a non-zero ID into \texttt{t\_xmax}:
\begin{enumerate}
  \item \textbf{A \texttt{DELETE}:} Transaction \texttt{741} deletes the row by setting \texttt{t\_xmax = 741}. Its \texttt{t\_ctid} still points to its own slot, say \texttt{(0,1)}, meaning ``no newer version follows me.''
  \item \textbf{An \texttt{UPDATE}:} Transaction \texttt{741} sets \texttt{t\_xmax = 741} on old version \texttt{(0,1)}, inserts a new version at \texttt{(0,2)} with \texttt{t\_xmin = 741, t\_xmax = 0}, and points the old version's \texttt{t\_ctid} to \texttt{(0,2)}.
  \item \textbf{A row lock (\texttt{SELECT ... FOR SHARE / FOR UPDATE}):} Suppose transaction \texttt{741} locks a row without editing it. Keeping a shared-memory lock entry per row in a million-row job would exhaust RAM. Instead, PostgreSQL writes \texttt{t\_xmax = 741} right onto the row and sets \texttt{HEAP\_XMAX\_LOCK\_ONLY} (\texttt{0x0080}) in \texttt{t\_infomask}, telling readers the row was \emph{not} deleted. If transactions \texttt{741} and \texttt{743} both share-lock the same row, PostgreSQL allocates one \emph{MultiXactId} for $\{741, 743\}$, stores it in \texttt{t\_xmax}, and sets \texttt{HEAP\_XMAX\_IS\_MULTI} (\texttt{0x1000}).
\end{enumerate}

\subsection{\texttt{t\_cid} and the Halloween Problem}

Why spend 4 header bytes on \texttt{t\_cid} (Command ID)? Suppose one transaction runs two SQL statements back to back:

\begin{lstlisting}[language=SQL]
BEGIN;
-- Command 0: give every underpaid account a 1,000-cent bonus
UPDATE accounts SET balance_minor = balance_minor + 1000
 WHERE balance_minor < 50000;

-- Command 1: inspect our own uncommitted change
SELECT balance_minor FROM accounts WHERE id = 42;
COMMIT;
\end{lstlisting}

Both commands share the \emph{same} \texttt{xid}, say \texttt{740}. Look at the two opposite visibility needs inside transaction \texttt{740}:
\begin{itemize}
  \item In Command~1 (\texttt{SELECT}), transaction \texttt{740} \emph{must} see the new version written by Command~0, and \emph{must not} see the retired old version.
  \item During Command~0 (\texttt{UPDATE}) itself, as the scan walks blocks~0 to~500, a new version with \texttt{balance\_minor + 1000} might land on block~420 ahead of the scan. If Command~0 could see its own new versions, it would visit that row again, add \emph{another} 1,000 cents, and loop until every account hit 50,000 cents. Engineers call this the \textbf{Halloween Problem}. IBM's System~R team hit it on Halloween 1976, when a 10\% raise query for employees under 25,000~USD kept re-updating rows until everyone earned at least 25,000~USD.
\end{itemize}

PostgreSQL prevents the Halloween Problem with a 32-bit \texttt{CommandId} counter inside each transaction. It starts at \texttt{0} and increments before each row-modifying command. Command~0 stamps \texttt{cmin = 0} on every version it writes. While Command~0 runs, its snapshot requires \texttt{cmin < 0} for its own \texttt{xid}, hiding rows created during Command~0 from Command~0's own scan. Once Command~0 finishes, the counter ticks to \texttt{1}, so Command~1 checks \texttt{cmin < 1} and sees Command~0's updates cleanly. (If one transaction both inserts and deletes the same tuple, a backend-local \emph{combo CID} packs both \texttt{cmin} and \texttt{cmax} into the 4-byte \texttt{t\_cid} slot.)

\begin{labbox}
With PostgreSQL's \texttt{pageinspect} extension you can inspect the live 8~KB page and check every claim in this section yourself. Run this sequence on a scratch database:

\begin{lstlisting}[language=SQL]
CREATE EXTENSION IF NOT EXISTS pageinspect;
CREATE TABLE demo_mvcc (id INT PRIMARY KEY, bal BIGINT);

INSERT INTO demo_mvcc VALUES (1, 10000);
UPDATE demo_mvcc SET bal = 8000 WHERE id = 1;

BEGIN;
UPDATE demo_mvcc SET bal = 5000 WHERE id = 1;
ROLLBACK;

SELECT lp, t_xmin, t_xmax, t_ctid,
       t_infomask::bit(16) AS infomask
  FROM heap_page_items(get_raw_page('demo_mvcc', 0));
\end{lstlisting}

You will see \emph{three} physical tuples on page~0 (the XID numbers on your machine will differ; we use 740, 741, 742):
\begin{itemize}
  \item \texttt{lp = 1}: \texttt{t\_xmin = 740}, \texttt{t\_xmax = 741}, \texttt{t\_ctid = (0,2)} (retired by the committed \texttt{UPDATE}).
  \item \texttt{lp = 2}: \texttt{t\_xmin = 741}, \texttt{t\_xmax = 742}, \texttt{t\_ctid = (0,3)} (still the live row. Its \texttt{t\_xmax = 742} belongs to an \emph{aborted} transaction, so readers ignore \texttt{t\_xmax} and keep \texttt{bal = 8000}).
  \item \texttt{lp = 3}: \texttt{t\_xmin = 742}, \texttt{t\_xmax = 0}, \texttt{t\_ctid = (0,3)} (dead on arrival because transaction \texttt{742} rolled back).
\end{itemize}
\end{labbox}

\section{Commit Status (\texttt{pg\_xact}) and Why a \texttt{SELECT} Can Dirty Disk Pages}
\label{ch05:clog-hint-bits}

Pause on \texttt{lp = 2} in the lab above: its header says \texttt{t\_xmin = 741} and \texttt{t\_xmax = 742}. Nowhere inside those 23 bytes did transaction \texttt{742} come back during \texttt{ROLLBACK} to erase \texttt{t\_xmax = 742}; doing so across a million touched pages would make \texttt{ROLLBACK} slow again. So how does a subsequent \texttt{SELECT} discover that \texttt{741} committed whereas \texttt{742} aborted?

\subsection{The Commit Log (\texttt{pg\_xact}): Two Bits per Transaction}

To answer that question in $O(1)$ time, PostgreSQL keeps a compact commit-status bitmap on disk under \texttt{PGDATA/pg\_xact/} (formerly \texttt{pg\_clog}), cached in shared memory via a Simple LRU (\emph{SLRU}) pool. Because every transaction ends in one of four states, \texttt{pg\_xact} needs just \textbf{2 bits per \texttt{TransactionId}}:

\begin{center}
\small
\begin{tabular}{@{}llp{6.2cm}@{}}
\toprule
\textbf{Bits} & \textbf{C constant} & \textbf{Meaning} \\
\midrule
\texttt{00} & \texttt{STATUS\_IN\_PROGRESS} & Started (or unassigned); neither committed nor aborted \\
\texttt{01} & \texttt{STATUS\_COMMITTED} & Committed (either synchronously or asynchronously) \\
\texttt{10} & \texttt{STATUS\_ABORTED} & Rolled back explicitly or crashed before commit \\
\texttt{11} & \texttt{STATUS\_SUB\_COMMITTED} & Subtransaction (\texttt{SAVEPOINT}) committed; check parent XID \\
\bottomrule
\end{tabular}
\end{center}

Check the packing math. Four transactions fit in 1~byte ($4 \times 2 = 8$~bits), so one 8,192-byte page of \texttt{pg\_xact} records:
\[
  8{,}192 \text{ bytes} \times 4 \frac{\text{transactions}}{\text{byte}} = 32{,}768 \text{ transactions.}
\]
Ten million transactions take barely $2.5\text{ MB}$ of cache. Finding the exact bit-pair for \texttt{xid} needs zero tree lookups: divide by $32{,}768$ for the page, take $(\texttt{xid} \bmod 32{,}768) / 4$ for the byte, and shift by $(\texttt{xid} \bmod 4) \times 2$. At \texttt{COMMIT} or \texttt{ROLLBACK}, PostgreSQL logs the outcome to WAL and flips those 2~bits.

\subsection{Tuple Hint Bits: Caching Commit Status on the Heap Tuple}

If \texttt{pg\_xact} is tiny and $O(1)$, why not check it every time a query visits a row?

Because \texttt{pg\_xact} sits in shared memory shared across every CPU core. If sixty-four cores scan 100~million rows per second, hammering shared SLRU locks two hundred million times per second would stall the CPU interconnect.

PostgreSQL skips repeat lookups by caching four \textbf{hint bits} right inside each row's 16-bit \texttt{t\_infomask} flag word:
\begin{itemize}
  \item \texttt{HEAP\_XMIN\_COMMITTED} (\texttt{0x0100}): \texttt{t\_xmin} committed.
  \item \texttt{HEAP\_XMIN\_INVALID} (\texttt{0x0200}): \texttt{t\_xmin} aborted (the version never existed).
  \item \texttt{HEAP\_XMAX\_COMMITTED} (\texttt{0x0400}): \texttt{t\_xmax} committed.
  \item \texttt{HEAP\_XMAX\_INVALID} (\texttt{0x0800}): \texttt{t\_xmax} is \texttt{0} or aborted.
\end{itemize}

Watch how a newly inserted row gets its hint bit:
\begin{enumerate}
  \item Transaction \texttt{740} inserts the row on page~0. Because \texttt{740} has \emph{not} committed yet, neither \texttt{HEAP\_XMIN\_COMMITTED} nor \texttt{HEAP\_XMIN\_INVALID} is set.
  \item Transaction \texttt{740} runs \texttt{COMMIT}. PostgreSQL syncs the commit WAL record and sets \texttt{pg\_xact[740] = 01}. It does \emph{not} go back to page~0.
  \item Ten seconds later, the first reader (even a plain \texttt{SELECT}) visits page~0 and sees \texttt{t\_xmin = 740} with no hint bit. That reader checks \texttt{pg\_xact}, confirms \texttt{740}'s commit WAL record is already flushed to disk, sets \texttt{HEAP\_XMIN\_COMMITTED} inside the 8~KB buffer, and \textbf{marks the buffer dirty}.
  \item Every later \texttt{SELECT} checks \texttt{t\_infomask \& HEAP\_XMIN\_COMMITTED} in one CPU instruction and never touches \texttt{pg\_xact}.
\end{enumerate}

\begin{trapbox}
Operators are often surprised when a read-only \texttt{SELECT COUNT(*) FROM ledger\_events;} right after a bulk load triggers gigabytes of disk writes and \texttt{EXPLAIN (ANALYZE, BUFFERS)} prints \texttt{Buffers: shared hit=120000 dirtied=120000}.

Nothing is broken: your \texttt{SELECT} is the first visitor after the bulk commit, stamping \texttt{HEAP\_XMIN\_COMMITTED} onto every page. With data checksums (\texttt{initdb --data-checksums}) or \texttt{wal\_log\_hints = on}, the first hint-bit update on a page after a checkpoint also writes a full-page WAL image (\texttt{FPI\_FOR\_HINT}) so a torn write cannot break the checksum. After any bulk \texttt{COPY}, run \texttt{VACUUM ANALYZE table\_name;} right away to set hint bits, Visibility Map bits, and statistics in one predictable pass.
\end{trapbox}

\section{Snapshots and the Exact Visibility Formula}
\label{ch05:snapshot-visibility}

Hint bits tell us \emph{whether} transaction \texttt{740} committed, yet that alone is not enough. Recall our 4:00~PM audit query: if the audit started at 4:00:00~PM and transfer \texttt{746} committed at 4:00:01~PM, \texttt{746} is committed, yet the 4:00:00~PM audit \emph{must ignore it}.

To freeze a consistent view of the database, a query takes a \textbf{snapshot} (\texttt{SnapshotData} in \texttt{src/include/utils/snapshot.h}) by scanning \texttt{ProcArray}---the shared-memory array listing each connected backend's active \texttt{xid}. Run \texttt{SELECT pg\_current\_snapshot();} at any time to see your own snapshot string:
\[
  \texttt{xmin:xmax:xip\_list}, \qquad \text{for example:} \quad \texttt{740:748:742,745}.
\]

Watch out for one naming quirk in PostgreSQL's C code: \texttt{xmin} and \texttt{xmax} inside a \emph{snapshot} describe active transaction bounds, not row birth and death:

\begin{definition}[MVCC Snapshot Triple]
\label{ch05:def-snapshot}
A PostgreSQL MVCC snapshot $S = (\mathrm{xmin}_S,\; \mathrm{xmax}_S,\; \mathrm{xip}_S)$ captured from \texttt{ProcArray} consists of:
\begin{enumerate}
  \item $\mathrm{xmin}_S$: the \textbf{lowest still-active} transaction ID across the system at snapshot creation (or $\mathrm{xmax}_S$ if none are active). Every transaction $x < \mathrm{xmin}_S$ has already finished---it either committed before $S$ was taken or aborted.
  \item $\mathrm{xmax}_S$: \textbf{one past the highest completed} (or allocated) transaction ID at snapshot creation. Every transaction $x \ge \mathrm{xmax}_S$ had not even finished (or started) when $S$ was taken, so its effects are unconditionally \emph{invisible} to $S$.
  \item $\mathrm{xip}_S$ (\emph{transactions in progress}): the sorted list of transaction IDs in the half-open interval $[\mathrm{xmin}_S, \mathrm{xmax}_S)$ that were still actively running at the instant $S$ was captured. Even if $x \in \mathrm{xip}_S$ commits one microsecond later, $x$ remains \emph{invisible} to $S$.
\end{enumerate}
\end{definition}

Look how cleanly $(\mathrm{xmin}_S, \mathrm{xmax}_S, \mathrm{xip}_S) = (740, 748, \{742, 745\})$ partitions the entire timeline of transactions (Figure~\ref{ch05:fig-snapshot}):
\begin{itemize}
  \item Any $x < 740$ (such as \texttt{738}, \texttt{739}): finished before our snapshot. Visible if committed; invisible if aborted.
  \item $x \in [740, 748)$:
    \begin{itemize}
      \item $x \in \{742, 745\}$: was still running when our snapshot snapped the shutter. \textbf{Invisible}, even if it commits later.
      \item $x \in \{740, 741, 743, 744, 746, 747\}$: already finished before our snapshot. Visible if committed; invisible if aborted.
    \end{itemize}
  \item Any $x \ge 748$ (such as \texttt{748}, \texttt{749}): started or finished after our snapshot. \textbf{Invisible}, even if already committed.
\end{itemize}

Before writing out the exact logic, state the visibility test in two plain questions. First, \emph{was this row version already born when my snapshot started?} Its creator (\texttt{t\_xmin}) must have committed before $\mathrm{xmax}_S$ and must not appear in the still-running list $\mathrm{xip}_S$ (or must come from an earlier command of my own transaction). Second, \emph{was this row version still alive when my snapshot started?} Either nobody has deleted it ($\texttt{t\_xmax} = 0$ or lock-only), or its deleter (\texttt{t\_xmax}) aborted or committed \emph{after} my snapshot took effect. Inside \texttt{src/backend/access/heap/heapam\_visibility.c}, \texttt{HeapTupleSatisfiesMVCC()} encodes both checks (with $x_{\text{self}}$ as our own XID and $c_{\text{cur}}$ as our current command ID):

\begin{formalbox}
\textbf{Exact MVCC Tuple Visibility Rule (\texttt{HeapTupleSatisfiesMVCC}).}
First define when another transaction $x \ne x_{\text{self}}$ is visible to snapshot $S = (\mathrm{xmin}_S, \mathrm{xmax}_S, \mathrm{xip}_S)$:
\begin{itemize}
  \item Transaction $x$'s writes are visible to $S$ when:
  \[
    \operatorname{Vis}(x, S) \;\iff\; \big(\operatorname{Status}(x) = \texttt{COMMITTED}\big) \;\land\; \big(x < \mathrm{xmax}_S\big) \;\land\; \big(x \notin \mathrm{xip}_S\big).
  \]
  (Whenever $x < \mathrm{xmin}_S$, $x \notin \mathrm{xip}_S$ holds automatically without searching $\mathrm{xip}_S$.)
\end{itemize}
A physical row version $T$ with header $(\texttt{t\_xmin}, \texttt{t\_xmax}, c_{\min}, c_{\max}, \texttt{t\_infomask})$ is \textbf{visible} to snapshot $S$ if and only if \emph{both} its birth condition (\textbf{B}) and its non-death condition (\textbf{D}) hold:
\begin{enumerate}
  \item \textbf{Birth condition (B):} Either ($\texttt{t\_xmin} = x_{\text{self}}$ and $c_{\min} < c_{\text{cur}}$), or ($\texttt{t\_xmin} \ne x_{\text{self}}$ and $\operatorname{Vis}(\texttt{t\_xmin}, S)$ holds, or \texttt{HEAP\_XMIN\_FROZEN} is set).
  \item \textbf{Non-death condition (D):} At least one of the following holds:
  \begin{enumerate}
    \item $\texttt{t\_xmax} = 0$, or \texttt{HEAP\_XMAX\_INVALID} is set (deleter aborted), or \texttt{HEAP\_XMAX\_LOCK\_ONLY} is set (locked, not deleted);
    \item $\texttt{t\_xmax} = x_{\text{self}}$ and $c_{\max} \ge c_{\text{cur}}$ (deleted by our own current or later command, so this command still sees it);
    \item $\texttt{t\_xmax} \ne x_{\text{self}}$ and $\neg \operatorname{Vis}(\texttt{t\_xmax}, S)$ (deleter is still running, aborted, listed in $\mathrm{xip}_S$, or has $\texttt{t\_xmax} \ge \mathrm{xmax}_S$).
  \end{enumerate}
\end{enumerate}
\end{formalbox}

\label{ch05:ex-visibility}
Suppose a read-only audit query captures snapshot $S = \texttt{740:748:742,745}$ ($x_{\text{self}}$ unassigned). Every completed transaction committed except \texttt{744} (which rolled back), and \texttt{742} commits \emph{after} our snapshot was taken. Which of these five versions on page~0 does our query emit?

Look closely at \texttt{(0,1)}, \texttt{(0,2)}, and \texttt{(0,3)}. They are three physical versions of \emph{one} logical row updated by \texttt{741} and then \texttt{742}. Version \texttt{(0,1)} died before our snapshot, and \texttt{(0,3)} was born in \texttt{742}, which was still running when our snapshot froze. \textbf{Exactly one version}---\texttt{(0,2)}---passes both (B) and (D). That single-visible-version rule lets our 4:00~PM audit scan ten million rows while live payments fly past.

\begin{recoverybox}
\textbf{Pause and check the two-question rule.} A row version is visible to snapshot $S$ when (1) its creator \texttt{t\_xmin} committed before $S$ froze, and (2) its deleter \texttt{t\_xmax} had \emph{not} visibly committed when $S$ froze. Every version chain produces either zero or one visible version per snapshot.
\end{recoverybox}

\begin{walkbox}
When is a snapshot taken? That single timing choice is the sole difference between PostgreSQL's first two transaction isolation levels (Chapter~6):
\begin{itemize}
  \item Under \texttt{READ COMMITTED} (PostgreSQL's default), PostgreSQL takes a \textbf{fresh snapshot at the start of every individual SQL statement} inside the transaction.
  \item Under \texttt{REPEATABLE READ} (and \texttt{SERIALIZABLE}), PostgreSQL takes \textbf{one snapshot at the start of the first non-control SQL statement} in the transaction and reuses that identical $(\mathrm{xmin}_S, \mathrm{xmax}_S, \mathrm{xip}_S)$ triple until \texttt{COMMIT} or \texttt{ROLLBACK}.
\end{itemize}
\end{walkbox}

\section{Write Amplification and \texttt{HOT} (Heap-Only Tuple) Updates}
\label{ch05:hot-updates}

Now flip from the reader's perspective to the B-tree indexes we studied in Chapter~3, and watch a painful consequence of Design~B emerge.

Suppose your \texttt{accounts} table has four B-tree indexes:
\begin{enumerate}
  \item \texttt{accounts\_pkey} on \texttt{(id)},
  \item \texttt{idx\_accounts\_owner} on \texttt{(owner\_id)},
  \item \texttt{idx\_accounts\_currency} on \texttt{(currency)},
  \item \texttt{idx\_accounts\_updated} on \texttt{(updated\_at)}.
\end{enumerate}
Remember from Chapter~3 that PostgreSQL secondary indexes do \emph{not} point to primary keys (unlike InnoDB); every PostgreSQL B-tree leaf entry points directly to a physical heap \texttt{ctid = (block, offset)}. Now run a tiny balance update that also bumps \texttt{updated\_at}:

\begin{lstlisting}[language=SQL]
UPDATE accounts
   SET balance_minor = balance_minor - 5000,
       updated_at    = now()
 WHERE id = 42;
\end{lstlisting}

Old version \texttt{(0,1)} stays put; new version \texttt{(0,2)} lands on the table. Because \texttt{updated\_at} is indexed, \texttt{idx\_accounts\_updated} obviously needs a new entry pointing to \texttt{(0,2)}. What about the other three indexes---\texttt{id}, \texttt{owner\_id}, and \texttt{currency}---whose values \emph{did not change}? Those three indexes currently point only to \texttt{(0,1)}. Without an index update, a future lookup on \texttt{owner\_id = 99} would land on dead \texttt{(0,1)} and miss the row. Consequently, naive in-heap MVCC must insert a new entry into \textbf{every index on the table} pointing to \texttt{(0,2)}.

Updating one 8-byte integer just dirtied one table page \emph{plus four B-tree leaf pages}, emitted five WAL records, and bloated all four indexes. Before PostgreSQL~8.3, that write amplification punished every write-heavy table.

\subsection{How \texttt{HOT} Decouples B-Trees from Unindexed Updates}

PostgreSQL~8.3 solved that common case with \textbf{Heap-Only Tuples} (\textbf{HOT}). Suppose we drop \texttt{idx\_accounts\_updated} (updating \emph{only} unindexed \texttt{balance\_minor}), and suppose page~0 still has free space for new version \texttt{(0,2)}.

Look at what already sits inside page~0: a forward link \texttt{t\_ctid = (0,2)} from \texttt{(0,1)} to \texttt{(0,2)}. Chasing \texttt{t\_ctid} across \emph{different} blocks during an index scan would cost extra random disk reads. Chasing \texttt{t\_ctid} \textbf{inside the same 8~KB page already pinned in \texttt{shared\_buffers}}, by contrast, costs zero extra I/O and just a few nanoseconds.

PostgreSQL therefore runs a \textbf{HOT update} whenever \emph{both} rules hold:
\begin{enumerate}
  \item \textbf{Zero indexed columns change} (checked against all columns used by any index, including expression and partial indexes); and
  \item \textbf{The new version fits on the exact same 8~KB page} as the old version.
\end{enumerate}

When a HOT update fires:
\begin{itemize}
  \item \textbf{Zero B-tree indexes are touched.} Every index keeps its single leaf entry pointing to root slot \texttt{(0,1)}.
  \item Old version \texttt{(0,1)} gets \texttt{HEAP\_HOT\_UPDATED} (\texttt{0x4000}) in \texttt{t\_infomask2}.
  \item New version \texttt{(0,2)} gets \texttt{HEAP\_ONLY\_TUPLE} (\texttt{0x8000}) in \texttt{t\_infomask2}, meaning no index points straight to \texttt{(0,2)}.
  \item When an index scan visits \texttt{(0,1)}, it sees \texttt{HEAP\_HOT\_UPDATED} and walks \texttt{(0,1) $\to$ (0,2) $\to$ (0,3)} inside the pinned buffer to find the version matching its snapshot.
\end{itemize}

\subsection{Single-Page Pruning (On-the-Fly Defragmentation Without \texttt{VACUUM})}

HOT brings a second big win alongside skipping index writes: \textbf{single-page HOT pruning}.

Think about why full \texttt{VACUUM} normally has to scan every index before freeing a dead slot \texttt{(0,1)}. If an index still points to \texttt{(0,1)} and you reuse slot~1 for Customer~B, a lookup for Customer~A returns Customer~B's account.

Now look at \texttt{(0,2)} inside a HOT chain \texttt{(0,1) $\to$ (0,2) $\to$ (0,3)} once \texttt{(0,1)} and \texttt{(0,2)} are older than every active snapshot (\texttt{OldestXmin}):
\begin{itemize}
  \item \emph{No index anywhere} points to \texttt{(0,2)} or \texttt{(0,3)}.
  \item Every index points \emph{only} to root slot \texttt{ItemId[1]}.
\end{itemize}
Thus the very next query touching this 8~KB page---even a plain \texttt{SELECT} or \texttt{UPDATE} when free space runs low---can clean up the chain \textbf{locally on this one page in microseconds, touching zero indexes}:
\begin{enumerate}
  \item It deletes the dead bytes of \texttt{v1} and \texttt{v2}, sliding live \texttt{v3} upward to compact free space.
  \item It turns root slot \texttt{ItemId[1]} into a 4-byte redirect (\textbf{\texttt{LP\_REDIRECT}}) pointing straight to slot~3.
  \item It marks \texttt{ItemId[2]} as \textbf{\texttt{LP\_UNUSED}}, ready for the very next \texttt{UPDATE}.
\end{enumerate}

\begin{applicationbox}
On a busy \texttt{accounts} table handling 15,000 balance updates per second, two small DDL rules prevent runaway bloat:
\begin{enumerate}
  \item \textbf{Keep fast-changing counters out of secondary indexes} unless queries truly filter or sort on them. Indexing \texttt{updated\_at} or \texttt{balance\_minor} disables HOT on every balance change. Check your HOT ratio in \texttt{pg\_stat\_user\_tables} (\texttt{n\_tup\_hot\_upd} vs.\ \texttt{n\_tup\_upd}); on a healthy balance table, $>95\%$ of updates are HOT.
  \item \textbf{Reserve same-page headroom with \texttt{fillfactor}:} Heap tables default to \texttt{fillfactor = 100}, packing new pages 100\% full so the \emph{first} \texttt{UPDATE} spills to another block. Running \texttt{ALTER TABLE accounts SET (fillfactor = 85);} leaves 15\% ($\approx 1.2\text{ KB}$) free during inserts so HOT chains fit and self-prune on the same page.
\end{enumerate}
\end{applicationbox}

\section{Table Bloat, \texttt{VACUUM}, \texttt{autovacuum}, and \texttt{VACUUM FULL}}
\label{ch05:vacuum}

When a row is \texttt{DELETE}d, or when an \texttt{UPDATE} cannot use HOT, single-page pruning can free the dead row bytes, yet it \textbf{must leave a 4-byte \texttt{LP\_DEAD} stub in the slot array} and \textbf{must leave dead entries inside every B-tree index}. Clearing both requires \texttt{VACUUM}.

\subsection{The Three Phases of Concurrent (``Lazy'') \texttt{VACUUM}}

Plain \texttt{VACUUM} (``lazy vacuum'' in \texttt{src/backend/access/heap/vacuumlazy.c}) takes only a \texttt{SHARE UPDATE EXCLUSIVE} lock---\textbf{never blocking \texttt{SELECT}, \texttt{INSERT}, \texttt{UPDATE}, or \texttt{DELETE}}. It runs in three phases:
\begin{enumerate}
  \item \textbf{Phase 1 --- Heap Scan:} \texttt{VACUUM} finds \texttt{OldestXmin}, the oldest active snapshot across all sessions, replication slots, and prepared transactions. It scans the table sequentially while \emph{skipping} pages marked \texttt{ALL\_VISIBLE} in the \textbf{Visibility Map} (\texttt{\_vm}). Along the way, it prunes dead row payloads and collects dead 6-byte \texttt{(block, offset)} TIDs in RAM up to \texttt{autovacuum\_work\_mem}. PostgreSQL~17 replaced the old 1~GB flat TID array with a compact radix tree that holds far more TIDs per megabyte.
  \item \textbf{Phase 2 --- Index Vacuuming:} Whenever the dead-TID buffer fills (or Phase~1 ends), \texttt{VACUUM} scans every index on the table and deletes entries matching the dead-TID set. Memory sizing matters hugely here. If your dead-TID buffer holds only one-tenth of a bloated table's dead TIDs across 8 indexes, \texttt{VACUUM} must scan all 8 indexes \emph{ten times}. Sizing memory to fit all dead TIDs at once collapses ten passes into one.
  \item \textbf{Phase 3 --- Slot Cleanup, FSM, and VM:} Once no index points to those TIDs, \texttt{VACUUM} revisits the table pages and flips \texttt{LP\_DEAD} slots to reusable \texttt{LP\_UNUSED}. It then logs the freed space in the \textbf{Free Space Map} (\texttt{\_fsm}) for future writes and sets \texttt{ALL\_VISIBLE} / \texttt{ALL\_FROZEN} bits in the Visibility Map.
\end{enumerate}

\subsection{Why \texttt{VACUUM} Does Not Shrink Disk Usage (vs.\ \texttt{VACUUM FULL})}

Suppose you insert 50~million test rows (8~GB on disk), run \texttt{DELETE FROM ledger\_test;}, and run \texttt{VACUUM ledger\_test;}. Checking \texttt{pg\_relation\_size('ledger\_test')} can still show 8~GB if even one live row sits near the end of the file.

Why? Plain \texttt{VACUUM} frees space \emph{inside} existing 8~KB pages and lists it in the Free Space Map for future inserts. It truncates OS file blocks only at the \emph{trailing end} of the file when those tail pages are 100\% empty. Moving a live row from block~999,999 down to block~0 would change its \texttt{ctid}, breaking open scans and indexes unless the whole table were locked.

\textbf{\texttt{VACUUM FULL}}, by contrast, rewrites the entire table and rebuilds every index into brand-new files before deleting the old ones. It shrinks an 8~GB bloated file with 1,000 live rows down to 64~KB, at two steep costs:
\begin{itemize}
  \item \texttt{VACUUM FULL} holds an \textbf{\texttt{ACCESS EXCLUSIVE} lock} across the entire rewrite, blocking \emph{every \texttt{SELECT} and write} on the table.
  \item Because old and new files coexist until commit, \texttt{VACUUM FULL} needs enough free disk space to hold a full second copy of the table and its indexes.
\end{itemize}
On 24/7 systems, engineers avoid \texttt{VACUUM FULL} during live traffic and use online tools like \texttt{pg\_repack}. Those build a clean shadow table in the background, replay concurrent writes from a log table, and take \texttt{ACCESS EXCLUSIVE} only for a brief catalog swap at the end.

\begin{trapbox}
\textbf{Two production traps that silently paralyze \texttt{autovacuum}:}
\begin{enumerate}
  \item \textbf{One \texttt{idle in transaction} session:} Suppose someone opens \texttt{psql}, runs \texttt{BEGIN; SELECT * FROM accounts LIMIT 1;}, and leaves for a four-hour lunch. If that session holds an open snapshot or uncommitted write, global \texttt{OldestXmin} stays pinned at noon. Even if \texttt{autovacuum} runs every minute, it \textbf{cannot reclaim a single dead version created anywhere in the database after noon}. Always set \texttt{idle\_in\_transaction\_session\_timeout = '60s'} and alert on abandoned replication slots in \texttt{pg\_replication\_slots}.
  \item \textbf{The 20\% default scale factor on big tables:} By default, \texttt{autovacuum} wakes when dead rows pass $\tau = 50$ plus $s = 0.20$ times table size:
  \[
    \texttt{n\_dead\_tup} \;>\; \tau \;+\; s \times \texttt{reltuples}.
  \]
  On a 200-million-row \texttt{postings} table, $50 + 0.20 \times N$ waits for \textbf{40,000,050 dead rows} before starting. Lower the scale factor per large hot table:
\begin{lstlisting}[language=SQL]
ALTER TABLE accounts SET (
    autovacuum_vacuum_scale_factor = 0.01,
    autovacuum_vacuum_cost_delay   = 2,
    autovacuum_vacuum_cost_limit   = 2000
);
\end{lstlisting}
\end{enumerate}
\end{trapbox}

\section{32-Bit Transaction ID Wraparound and Tuple Freezing}
\label{ch05:xid-wraparound}

The final consequence of in-heap MVCC can halt writes across an entire cluster. Check \texttt{HeapTupleHeaderData} in Section~\ref{ch05:tuple-header}: \texttt{t\_xmin} and \texttt{t\_xmax} are 32-bit unsigned integers (\texttt{uint32}). Why hasn't PostgreSQL widened them to 64 bits on disk?

Storage cost. Widening \texttt{t\_xmin} and \texttt{t\_xmax} to 8~bytes each adds \textbf{8~bytes of fixed header to every row in every table}. On a 10-billion-row postings table with 48-byte rows, 8 extra bytes per row adds 80~GB of disk and RAM ($\approx 17\%$). PostgreSQL tracks a 64-bit \texttt{FullTransactionId} in memory (returned by \texttt{pg\_current\_xact\_id()}), while on-disk row headers store only the low 32~bits.

With 32 bits there are $2^{32} = 4{,}294{,}967{,}296$ distinct values. PostgreSQL reserves the first three:
\begin{itemize}
  \item \texttt{0} = \texttt{InvalidTransactionId} (used for empty \texttt{t\_xmax}),
  \item \texttt{1} = \texttt{BootstrapTransactionId} (used during \texttt{initdb} catalog creation; always visible),
  \item \texttt{2} = \texttt{FrozenTransactionId} (legacy sentinel for frozen tuples; always visible),
  \item \texttt{3..}$(2^{32}-1)$ = normal circular \texttt{TransactionId} space (\texttt{FirstNormalTransactionId = 3}).
\end{itemize}
Whenever the 32-bit counter increments past $4{,}294{,}967{,}295$ (\texttt{0xFFFFFFFF}), it wraps right around to \texttt{3} (skipping \texttt{0}, \texttt{1}, \texttt{2}).

\subsection{Modular Circle Comparison (\texttt{TransactionIdPrecedes})}

If \texttt{xid} wraps around a finite circle of size $\approx 2^{32}$, you cannot compare two transaction IDs $a$ and $b$ with ordinary integer inequality \texttt{a < b}. Right after wraparound from \texttt{4,294,967,295} to \texttt{3}, transaction \texttt{3} happened \emph{after} \texttt{4,294,967,295}, even though $3 < 4{,}294{,}967{,}295$ as unsigned integers.

Instead, PostgreSQL defines ordering on the modular circle $\Z / 2^{32}\Z$ using signed 32-bit modular subtraction (\texttt{src/backend/access/transam/transam.c}):

\begin{lstlisting}[language=C]
/* Normal XID comparison in PostgreSQL: true if id1 logically precedes id2 */
bool NormalTransactionIdPrecedes(TransactionId id1, TransactionId id2) {
    int32 diff = (int32) (id1 - id2);
    return (diff < 0);
}
\end{lstlisting}

Look at the geometry of \texttt{(int32)(id1 - id2) < 0} on the $2^{32}$ clock dial (Figure~\ref{ch05:fig-wraparound}):
\begin{itemize}
  \item Stand at the current transaction counter $x_{\text{now}}$.
  \item Looking counterclockwise up to $2^{31} \approx 2.147\text{ billion}$ steps behind $x_{\text{now}}$, \texttt{(int32)(t\_xmin - x\_now) < 0}: all of those $2^{31}$ XIDs lie in the \textbf{visible Past}.
  \item Looking clockwise up to $2^{31} - 1 \approx 2.147\text{ billion}$ steps ahead of $x_{\text{now}}$, \texttt{(int32)(t\_xmin - x\_now) > 0}: all of those $2^{31}$ XIDs lie in the \textbf{invisible Future}.
\end{itemize}

Here is what would happen if a row were never frozen:
\begin{enumerate}
  \item In January, transaction \texttt{100} inserts a founding-capital row into \texttt{journal\_entries}, so the tuple has \texttt{t\_xmin = 100}. It is an immutable historical record; nobody ever updates or deletes it again.
  \item Over the next eight months or so, your payment service runs 100 write transactions per second, advancing $x_{\text{now}}$ past $2{,}147{,}483{,}748$ ($= 2^{31} + 100$).
  \item Now an auditor runs \texttt{SELECT * FROM journal\_entries WHERE id = 1;}. PostgreSQL compares \texttt{t\_xmin = 100} against $x_{\text{now}} = 2{,}147{,}483{,}749$:
  \[
    \texttt{(int32)(100 - 2147483749)} \;=\; +2{,}147{,}483{,}647 \;>\; 0 \quad (\text{so } 100 \text{ is in the future}).
  \]
  \item No byte on disk has changed, yet \textbf{that committed row disappears from every query}, because \texttt{t\_xmin = 100} moved across the antipode from ``2.1 billion transactions ago'' to ``2.1 billion transactions in the future.''
\end{enumerate}

\subsection{The Cure: Tuple Freezing, \texttt{relfrozenxid}, and the Safety Shutdown}

PostgreSQL prevents wraparound loss through \textbf{tuple freezing}. Once a committed tuple's \texttt{t\_xmin} is older than \texttt{OldestXmin} and older than \texttt{vacuum\_freeze\_min\_age} (default 50~million XIDs), \texttt{VACUUM} marks it frozen by setting \emph{both} \texttt{xmin} hint bits at once:
\[
  \texttt{HEAP\_XMIN\_FROZEN} \;=\; \texttt{HEAP\_XMIN\_COMMITTED} \;\mid\; \texttt{HEAP\_XMIN\_INVALID} \;=\; \texttt{0x0300}.
\]
(Since PostgreSQL~16, \texttt{VACUUM} also freezes younger tuples opportunistically when it is already writing a full-page image of that page, because the extra freezing then costs almost nothing.) Before PostgreSQL~9.4, freezing overwrote \texttt{t\_xmin} with \texttt{2}, which destroyed forensic history. Setting \texttt{0x0300} instead keeps the original \texttt{t\_xmin} readable in \texttt{pageinspect} while telling every visibility check to treat the tuple as committed infinitely long ago.

Once every tuple on an 8~KB page is frozen, \texttt{VACUUM} also sets the page's \textbf{all-frozen bit} in the Visibility Map (\texttt{\_vm} fork). Later anti-wraparound vacuums skip those pages entirely, so a 50~TB archive table whose old pages are all frozen costs almost nothing to keep safe.

PostgreSQL tracks each table's oldest unfrozen XID in \texttt{pg\_class.relfrozenxid} and the database-wide oldest in \texttt{pg\_database.datfrozenxid}. Three guardrails protect your cluster:
\begin{enumerate}
  \item \textbf{Routine freeze threshold (\texttt{autovacuum\_freeze\_max\_age = 200,000,000}, $\approx 9.3\%$ of $2^{31}$):} Once \texttt{age(relfrozenxid)} passes 200~million XIDs---even if \texttt{autovacuum = off}---PostgreSQL launches a mandatory anti-wraparound \texttt{autovacuum}. It uses all-frozen bits in \texttt{\_vm} to skip frozen pages and then deletes old \texttt{pg\_xact} segments.
  \item \textbf{Client warning zone ($\approx 40\text{ million}$ XIDs before $2^{31}$):} Every XID-allocating command emits \texttt{WARNING: database "prod" must be vacuumed within N transactions}.
  \item \textbf{Hard safety stop (3~million XIDs before $2^{31}$):} Before wraparound can hide committed rows, PostgreSQL \textbf{refuses new XIDs}, failing writes with:
\begin{lstlisting}[language=Plain]
ERROR: database is not accepting commands that assign new
       transaction IDs to avoid wraparound data loss in
       database "prod"
HINT:  Execute a database-wide VACUUM in that database.
\end{lstlisting}
  Read queries still work, and \texttt{VACUUM} needs no XID, so a superuser can connect normally and run \texttt{VACUUM (FREEZE, INDEX\_CLEANUP OFF, TRUNCATE OFF) worst\_table;}. Skipping index cleanup advances \texttt{relfrozenxid} fastest.
\end{enumerate}

\begin{labbox}
Monitor XID wraparound health in every production database before it ever reaches 50\% of the $2^{31}$ ceiling. Add this exact query to your operational runbook and Prometheus exporter:

\begin{lstlisting}[language=SQL]
SELECT c.oid::regclass                       AS table_name,
       age(c.relfrozenxid)                   AS xid_age,
       ROUND(100.0 * age(c.relfrozenxid)
             / 2147483647.0, 2)              AS pct_toward_wraparound,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
  FROM pg_class c
  JOIN pg_namespace n ON n.oid = c.relnamespace
 WHERE c.relkind IN ('r', 'm', 't')
   AND n.nspname NOT IN ('pg_catalog', 'information_schema')
 ORDER BY age(c.relfrozenxid) DESC
 LIMIT 10;
\end{lstlisting}

Notice \texttt{'t'} in \texttt{relkind IN ('r', 'm', 't')}. TOAST tables (Chapter~2) track their \emph{own} \texttt{relfrozenxid} separate from their parent table, and a slow vacuum on a bloated TOAST table has surprised many experienced teams.
\end{labbox}

MVCC snapshots let readers and writers run concurrently without read locks. Still, one big concurrency question remains. What happens when two sessions both read a consistent snapshot and write back based on what they saw---either colliding on the same row, or modifying \emph{two different rows} whose combined balance must stay positive? That brings us to isolation levels, concurrency anomalies, row locks, and Serializable Snapshot Isolation in Chapter~6.

\section{Exercises}
\label{ch05:exercises}

\begin{exercise}[Storage design tradeoffs]
A batch job runs \texttt{UPDATE ledger\_staging SET fee\_minor = fee\_minor + 10;} across 8,000,000 rows, hits a constraint error on the last row, and runs \texttt{ROLLBACK}. Compare step by step what InnoDB (in-place update + undo log) and PostgreSQL (in-heap versions + \texttt{pg\_xact}) do during (a) the 7,999,999 updates, (b) the \texttt{ROLLBACK} itself, and (c) the next hour.
\end{exercise}

\begin{exercise}[Commit log byte and bit offsets]
Recall that \texttt{pg\_xact} packs 2 status bits per \texttt{TransactionId} into 8,192-byte SLRU pages.
(a) For \texttt{xid = 1,000,005}, compute the 0-indexed \texttt{pg\_xact} page number, the byte offset inside that page, and the bit-shift (\texttt{0}, \texttt{2}, \texttt{4}, or \texttt{6}) inside that byte.
(b) At 5,000 write transactions per second for 24 hours, how many megabytes of \texttt{pg\_xact} do those transactions occupy before truncation?
\end{exercise}

\begin{exercise}[Tracing snapshot visibility by hand]
A \texttt{REPEATABLE READ} transaction has $x_{\text{self}} = 912$, $c_{\text{cur}} = 2$, and snapshot $S = \texttt{905:915:907,910}$. Every other transaction $< 915$ committed except \texttt{909}, which aborted. Meanwhile, \texttt{907} committed two seconds \emph{after} $S$ froze, \texttt{910} is still running, and \texttt{916} committed five seconds after $S$ froze.
State whether each row version below is \textbf{visible} or \textbf{invisible}, naming the exact clause of \texttt{HeapTupleSatisfiesMVCC}:
\begin{enumerate}
  \item \texttt{t\_xmin = 902, t\_xmax = 907} (normal delete).
  \item \texttt{t\_xmin = 907, t\_xmax = 0}.
  \item \texttt{t\_xmin = 908, t\_xmax = 909} (normal delete).
  \item \texttt{t\_xmin = 908, t\_xmax = 911, infomask = HEAP\_XMAX\_LOCK\_ONLY}.
  \item \texttt{t\_xmin = 912, cmin = 1, t\_xmax = 0}.
  \item \texttt{t\_xmin = 912, cmin = 2, t\_xmax = 0}.
\end{enumerate}
\end{exercise}

\begin{exercise}[The Halloween Problem]
Create \texttt{nums(x INT)} with rows \texttt{1}, \texttt{2}, \texttt{3} and an index on \texttt{(x)}. Suppose PostgreSQL skipped checking \texttt{cmin < curcid} during \texttt{UPDATE nums SET x = x + 1 WHERE x > 0;}. Trace an ascending index scan step by step, and explain how \texttt{t\_cid} stops the infinite loop without hiding the updated rows from the \emph{next} statement in the same transaction.
\end{exercise}

\begin{exercise}[Why a read-only query dirties buffers and emits WAL]
Right after a checkpoint finishes, a loader inserts 500,000 rows into \texttt{events} across 4,000 pages and runs \texttt{COMMIT}. Next, on a server with data checksums enabled, an analyst runs \texttt{SELECT COUNT(*) FROM events;}.
(a) Why does \texttt{EXPLAIN (ANALYZE, BUFFERS)} on that \texttt{SELECT} report roughly \texttt{dirtied=4000}?
(b) Why does that first \texttt{SELECT} emit $\approx 32\text{ MB}$ of WAL, whereas running the same \texttt{SELECT} one second later reports \texttt{dirtied=0} and emits zero WAL?
\end{exercise}

\begin{exercise}[Designing for HOT updates]
A \texttt{sessions} table has columns \texttt{id}, \texttt{user\_id}, \texttt{seen\_at}, and \texttt{hits}, with secondary B-tree indexes on \texttt{(user\_id)} and \texttt{(seen\_at)}. Every HTTP request runs:
\begin{lstlisting}[language=SQL]
UPDATE sessions
   SET seen_at = now(), hits = hits + 1
 WHERE id = $1;
\end{lstlisting}
(a) What fraction of these updates can use HOT today, and how many index leaf entries are inserted per 1,000 requests?
(b) Product reads \texttt{seen\_at} only once an hour to purge sessions older than 30 days. Redesign the index or update threshold (plus \texttt{fillfactor}) so $>98\%$ of requests become HOT updates while keeping the hourly purge fast.
\end{exercise}

\begin{exercise}[Autovacuum trigger math]
A \texttt{ledger\_postings} table holds $N = 150{,}000{,}000$ rows and receives 2,000 non-HOT updates per second.
(a) Under default threshold \texttt{50} and scale factor \texttt{0.20}, how many hours pass between autovacuums, and how many dead rows build up first?
(b) Pick per-table \texttt{autovacuum} settings so cleanup starts every $\approx 500{,}000$ dead rows ($\approx 4$~minutes).
\end{exercise}

\begin{exercise}[Wraparound modular arithmetic]
Test PostgreSQL's modular XID check $(\text{int32})(\mathrm{id}_1 - \mathrm{id}_2) < 0$ on each pair below:
\begin{enumerate}
  \item \texttt{id1 = 4294967290} (\texttt{0xFFFFFFFA}) and \texttt{id2 = 10} (\texttt{0x0000000A}).
  \item \texttt{id1 = 100} and \texttt{id2 = 2147483747} ($= 100 + 2^{31} - 1$).
  \item \texttt{id1 = 100} and \texttt{id2 = 2147483749} ($= 100 + 2^{31} + 1$). What happens to an unfrozen committed row with \texttt{t\_xmin = 100} between (2) and (3)?
\end{enumerate}
\end{exercise}

\begin{exercise}[Emergency wraparound triage]
At 2:00~AM, a database has 8~million XIDs left before wraparound shutdown (\texttt{age(datfrozenxid) = 2,139,000,000}) and burns 1,500 XIDs/s ($\approx 88$~minutes left).
(a) Write queries on \texttt{pg\_stat\_activity}, \texttt{pg\_prepared\_xacts}, and \texttt{pg\_replication\_slots} to find what is pinning \texttt{OldestXmin}.
(b) Once cleared, why must you run \texttt{VACUUM (FREEZE, INDEX\_CLEANUP OFF, TRUNCATE OFF)} on the oldest table instead of \texttt{VACUUM FULL}?
\end{exercise}
