\chapter{Financial Schemas, Replication, and Connection Pooling}
\label{ch08:capstone}

For seven chapters we have worked inside the PostgreSQL engine room. Chapter~2
walked 8~KB slotted heap pages and shared buffer descriptors. Chapter~3 split
B-trees and generalized search trees. Chapter~4 flushed write-ahead log records
and full-page images to survive power loss. Chapter~5 traced multiversion
snapshots and \texttt{VACUUM}. Chapter~6 separated concurrent transactions with
row-level locks and serializable conflict tracking, and Chapter~7 priced execution
plans from column statistics. Now we sit at the architect's desk and put all seven
layers to work on a system where every bug has a price tag: a production
double-entry financial ledger served by an asynchronous Rust (\texttt{Axum} and
\texttt{SQLx}) API over PostgreSQL.

Financial systems punish vague thinking because every shortcut fails in a
predictable, expensive way. Store balances in binary floating point and sums of fee
postings stop matching the books to the cent. Store wall-clock timestamps without a
UTC reference and the autumn daylight-saving fallback folds two distinct hours onto
the same nominal minute. Choose random UUID primary keys and a sixty-gigabyte
B-tree turns tiny inserts into a storm of 8~KB full-page writes across cold NVMe
blocks. Check balances only in Rust handlers and a single concurrent retry creates
money out of thin air. Leave replication asynchronous and a primary disk failure
erases transfers you already confirmed to customers. Point five thousand Tokio
tasks straight at PostgreSQL and shared-memory snapshot scans bring a
thirty-two-core server to its knees.

In this final chapter, we motivate every design rule with the exact production
failure it prevents. Then we trace how PostgreSQL's storage, indexing, WAL,
locking, and wire-protocol internals enforce the guarantee.

\begin{focusbox}
By the end of this chapter you will be able to answer five practical engineering questions:
\begin{itemize}
  \item Why does \texttt{0.1 + 0.2 = 0.3} evaluate to \texttt{false} in floating-point columns, and how do banks store money and timestamps without ever losing a cent or repeating an hour?
  \item Why do random UUID primary keys run fast at five million rows and then choke disk bandwidth at two billion rows?
  \item How can the database itself refuse any payment transfer whose debits and credits fail to sum to zero, even if a bug slips into application code?
  \item How do you store ten billion historical ledger rows while keeping queries fast and archiving old months in milliseconds?
  \item How can a PostgreSQL cluster survive a data-center outage without losing confirmed transfers, and serve five thousand concurrent Rust tasks using only forty-eight database processes?
\end{itemize}
\end{focusbox}

\section{Data Types That Never Lie About Money, Time, or Identity}
\label{ch08:types}

A relational schema is a physical contract about the bit patterns allowed onto
8~KB heap pages. If a column's type rounds fractions, discards UTC context, or
scatters keys uniformly across disk, no amount of application-layer discipline can
undo the damage downstream.

\subsection{Money: Why Binary Floats Fail, and \texttt{BIGINT} vs.\ \texttt{NUMERIC}}
\label{ch08:money-types}

Suppose a payment platform stores account adjustments in PostgreSQL's 8-byte
\texttt{DOUBLE PRECISION} type (\texttt{float8}, matching \texttt{f64} in Rust and
\texttt{double} in Java or C++). A merchant collects a $0.10\text{ USD}$ platform
fee and a $0.20\text{ USD}$ network fee, expecting a $0.30\text{ USD}$ total. Ask
PostgreSQL whether the two sides match:

\begin{lstlisting}[language=SQL]
SELECT (0.1::float8 + 0.2::float8) = 0.3::float8 AS exact_match,
       (0.1::float8 + 0.2::float8) - 0.3::float8 AS drift;
-- exact_match: false | drift: 5.551115123125783e-17
\end{lstlisting}

The comparison returns \texttt{false}. Why? IEEE~754 binary floating point writes
every number in base~2 as $(-1)^s \times m \times 2^e$ using a 53-bit binary
significand $m$. Just as $1/3 = 0.333\ldots_{10}$ never terminates in base~10, one
tenth never terminates in base~2: $0.1_{10} = 0.0001100110011\overline{0011}_2$.
Chopping that infinite bit pattern at bit~53 introduces a tiny rounding error of
roughly $10^{-17}$ on a single addition. Worse, parallel \texttt{HashAggregate}
workers (Chapter~7) sum rows in whatever order chunks arrive. Across ten million
fee postings, two runs of the exact same reconciliation query can disagree by
whole cents. Binary floats (\texttt{REAL} and \texttt{DOUBLE PRECISION}) never
belong in monetary columns.

PostgreSQL gives you two exact alternatives, each suited to a clear job:

\begin{enumerate}
  \item \textbf{\texttt{BIGINT} (\texttt{int8}) minor units.} Instead of storing
    currency as decimal fractions, store integer counts of the asset's smallest
    indivisible unit. Use cents ($10^{-2}\text{ USD}$) for retail payments,
    micro-dollars ($10^{-6}\text{ USD}$) for sub-cent API billing, or satoshis
    ($10^{-8}\text{ BTC}$). On disk, \texttt{BIGINT} takes a fixed 8~bytes on the
    heap page, maps directly to \texttt{i64} in Rust or \texttt{long} in Java, and
    adds in a single CPU integer instruction. Its signed range reaches
    $\pm(2^{63}-1) \approx \pm 9.22 \times 10^{18}$. In USD cents that exceeds
    $92\text{ quadrillion USD}$; in micro-dollars it exceeds $9.22\text{ trillion USD}$.
    Always store the asset's ISO currency code or scale alongside the integer so
    application code never adds Japanese yen ($10^{0}$) to US cents ($10^{-2}$) or
    Kuwaiti dinar fils ($10^{-3}$).
  \item \textbf{\texttt{NUMERIC(p, s)} (equivalently \texttt{DECIMAL(p, s)}).}
    Foreign-exchange rates (\texttt{1.08437525}), fractional equity shares
    (\texttt{0.00418275} shares), and bond accruals mix many decimal scales $s$
    with total precision $p$ past twenty digits. Multiplying two such figures can
    also overflow a 64-bit integer intermediate. To store decimal fractions without
    binary rounding, PostgreSQL packs \emph{four base-10 digits into each 16-bit
    integer word} (working in base~$10{,}000$), preceded by a short variable-length
    header (\texttt{NumericVar} in \texttt{numeric.c}) recording the weight, sign,
    and display scale. Because every decimal fraction terminates cleanly in
    base~$10{,}000$, \texttt{0.1::numeric + 0.2::numeric = 0.3::numeric} is exact
    to every declared digit. The tradeoff is CPU and space. \texttt{NUMERIC} uses a
    variable-length (\texttt{varlena}) header---typically 8--16~bytes on disk---and
    loops over digit words in software rather than running one hardware instruction.
    Heavy \texttt{SUM(amount)} scans therefore spend roughly $5\times$ to $15\times$
    more CPU than \texttt{SUM(amount\_minor)} on \texttt{BIGINT}. In Rust
    \texttt{SQLx}, \texttt{NUMERIC} maps cleanly to \texttt{rust\_decimal::Decimal}
    or \texttt{bigdecimal::BigDecimal}.
\end{enumerate}

The rule of thumb is straightforward. Use \texttt{BIGINT} minor units for
single-scale ledger postings and account balances. Use \texttt{NUMERIC(p, s)} for
FX rates, unit prices, and interest multipliers where mixed scales or wide
intermediates arise.

\subsection{Time: \texttt{TIMESTAMPTZ} and the Daylight-Saving Trap}
\label{ch08:time-types}

At 01:59:59 Eastern Daylight Time on the first Sunday of November, clocks in New
York jump backward to 01:00:00 Eastern Standard Time. Suppose a ledger table uses
\texttt{TIMESTAMP WITHOUT TIME ZONE} (which SQL abbreviates as plain
\texttt{TIMESTAMP}). A customer wires funds at 01:15~EDT (\texttt{05:15 UTC}).
Fifty minutes later, she wires a second payment at 01:05~EST (\texttt{06:05 UTC}).
Stored as wall-clock New York \texttt{TIMESTAMP} values, the second transfer
appears to happen \emph{ten minutes before} the first: \texttt{'2026-11-01
01:05:00'} sorts ahead of \texttt{'2026-11-01 01:15:00'}. Worse still,
\texttt{TIMESTAMP WITHOUT TIME ZONE} silently discards timezone offsets on input.
If one API pod connects with \texttt{TimeZone = 'UTC'} and an admin script connects
with \texttt{TimeZone = 'America/Chicago'}, both write incompatible local clocks
into the same column with zero warning.

\begin{intuitionbox}
Despite its verbose SQL name, \texttt{TIMESTAMP WITH TIME ZONE}
(\texttt{TIMESTAMPTZ}) stores \textbf{zero timezone string or UTC offset on disk}.
Both \texttt{TIMESTAMP} and \texttt{TIMESTAMPTZ} occupy the exact same 8~bytes in
a heap tuple: a signed 64-bit integer counting microseconds since PostgreSQL's
epoch, \texttt{2000-01-01 00:00:00 UTC}. The sole difference happens at the input
and output boundary. When you insert \texttt{'2026-11-01 01:15:00-04'} into a
\texttt{TIMESTAMPTZ} column, PostgreSQL immediately converts that instant into UTC
microseconds and stores that single universal point on the physical timeline. On
\texttt{SELECT}, it formats those UTC microseconds into whatever session
\texttt{TimeZone} the reader requested.
\end{intuitionbox}

The rule for financial schemas has only two cases:
\begin{itemize}
  \item Use \texttt{TIMESTAMPTZ} for every physical instant when an event occurred
    (\texttt{created\_at}, \texttt{posted\_at}, \texttt{expires\_at}). In Rust
    \texttt{SQLx}, bind it to \texttt{chrono::DateTime<Utc>} or
    \texttt{time::OffsetDateTime} with the session \texttt{TimeZone} pinned to
    \texttt{'UTC'}.
  \item Use 4-byte \texttt{DATE} for calendar dates defined by legal contract, such
    as a wire's settlement \texttt{value\_date = '2026-11-02'} or a monthly
    statement date. Never store a contract date as midnight timestamp, which shifts
    to the previous day whenever a reader views it from a western timezone.
\end{itemize}

\subsection{Primary Keys at Scale: Why \texttt{UUIDv4} Keys Thrash B-Trees and \texttt{UUIDv7} Flies}
\label{ch08:uuid-types}

An 8-byte \texttt{BIGINT GENERATED ALWAYS AS IDENTITY} sequence appends strictly
to the right edge of its primary-key B-tree, keeping inserts fast and compact. Yet
distributed financial systems rarely expose sequential integers as public IDs.
Sequential IDs leak transfer volume to competitors (\texttt{entry\_id = 1042}
versus \texttt{1089} an hour later). They also force Rust services or mobile apps
to make a database round-trip before knowing a new resource's ID. That pushes teams
toward 128-bit \texttt{UUID} keys, stored natively in PostgreSQL's 16-byte
\texttt{uuid} type rather than 36-byte ASCII \texttt{TEXT}.

Here is the trap that catches growing ledgers six months after launch. You pick
random \texttt{UUIDv4}, which fills 122 of its 128~bits from a cryptographic random
generator. At five million rows, the primary-key B-tree is roughly 150~MB. It fits
easily inside an 8~GB \texttt{shared\_buffers} pool (Chapter~2) and sustains
$35{,}000$ inserts per second. A year later, \texttt{postings} reaches two billion
rows and its primary B-tree spans 65~GB on a server with 32~GB of RAM. Insert
throughput drops tenfold while NVMe write bandwidth pins at $100\%$, even though
each new row is barely 100~bytes. Three mechanisms from Chapters~2--4 combine to
cause this collapse:

\begin{enumerate}
  \item \textbf{Buffer-pool cache misses.} Every \texttt{UUIDv4} lands at a uniform
    random spot across $[0, 2^{128})$. Once the 65~GB leaf layer outgrows
    \texttt{shared\_buffers}, almost every \texttt{INSERT} targets a cold leaf page
    on disk, stalling on a random 8~KB read and evicting another cached page.
  \item \textbf{Midpoint page-split bloat.} As Chapter~3 showed, random B-tree
    inserts split full leaf pages 50/50, leaving average occupancy near $70\%$.
    Monotonically increasing right-edge inserts split at the insertion point and
    keep leaves $90\%$ full.
  \item \textbf{WAL \texttt{full\_page\_writes} amplification.} Chapter~4 showed
    that the first change to \emph{any} 8~KB page after a \texttt{CHECKPOINT} must
    log the entire 8~KB Full Page Image (FPI) into WAL to survive torn writes. Right
    after a checkpoint, ten thousand random \texttt{UUIDv4} inserts dirty roughly
    ten thousand distinct leaf pages. A few hundred kilobytes of new keys explode
    into $10{,}000 \times 8\text{ KB} \approx 80\text{ MB}$ of WAL.
\end{enumerate}

Time-ordered \textbf{\texttt{UUIDv7}} (standardized in RFC~9562, built into
PostgreSQL~18 as \texttt{uuidv7()}, and available in Rust via
\texttt{uuid::Uuid::now\_v7()}) eliminates all three penalties without central
sequence locks. How? It places a 48-bit big-endian Unix millisecond timestamp at
the very front of the 128-bit value. Next come a 4-bit version tag (\texttt{0111}),
12~bits of sub-millisecond counter or random data (\texttt{rand\_a}), a 2-bit
variant (\texttt{10}), and 62~bits of cryptographic randomness (\texttt{rand\_b}).
PostgreSQL compares 16-byte \texttt{uuid} values from most-significant byte to
least. Every \texttt{UUIDv7} minted during the current millisecond therefore sorts
to the \emph{far right} of the entire historical B-tree
(Figure~\ref{ch08:fig-uuidv4-vs-v7}). Concurrent Rust pods still generate
collision-free IDs offline, yet all inserts land on a few hot rightmost leaf pages
pinned in \texttt{shared\_buffers}.

\section{Encoding Domain Invariants Directly in the Schema}
\label{ch08:invariants}

``Our Rust service validates every request struct before calling SQL, so the
database only needs plain columns.'' That sentence precedes nearly every silent
data-corruption postmortem. Application code is only one doorway into a database.
Settlement batch jobs, emergency \texttt{psql} backfills, schema migrations, and
concurrent network retries all write to the same tables. Worse, under \texttt{READ
COMMITTED} isolation (Chapter~6), two Rust handlers can each read a valid snapshot
and still commit a combined state that breaks business rules. Pushing invariants
into PostgreSQL turns application bugs from silent ledger corruption into loud,
rolled-back \texttt{ERROR} responses.

\subsection{\texttt{NOT NULL}, \texttt{CHECK}, Domains, and Atomic Idempotency Keys}
\label{ch08:scalar-invariants}

Recall from Chapter~1 how three-valued logic treats \texttt{NULL} inside a
\texttt{CHECK} constraint. A row passes \texttt{CHECK (expr)} whenever
\texttt{expr} evaluates to \texttt{TRUE} \emph{or} \texttt{UNKNOWN}. If you declare
\texttt{amount\_minor BIGINT CHECK (amount\_minor > 0)} without \texttt{NOT NULL},
inserting \texttt{NULL} evaluates \texttt{NULL > 0} to \texttt{UNKNOWN} and lands
cleanly on the heap page. Always pair \texttt{NOT NULL} with \texttt{CHECK}.

For constrained text categories, choose deliberately among three tools:
\begin{itemize}
  \item \textbf{\texttt{CREATE TYPE ... AS ENUM}} stores each label as a compact
    4-byte OID on disk. It fits closed state machines whose values match fixed code
    branches (\texttt{'pending'}, \texttt{'posted'}, \texttt{'voided'}). Keep in
    mind that PostgreSQL enums cannot drop old labels without recreating the type.
  \item \textbf{\texttt{DOMAIN}s or \texttt{CHECK}-constrained \texttt{TEXT}}
    validate text format across dozens of tables while letting you add new values
    without DDL locks. For example, \texttt{CHAR(3)} checked against a three-letter
    uppercase pattern enforces ISO currency codes cleanly. When each currency needs
    metadata such as its minor-unit scale ($2$ for \texttt{USD}, $0$ for
    \texttt{JPY}), point a foreign key at a tiny \texttt{assets} table; its single
    8~KB page stays permanently cached in \texttt{shared\_buffers}.
  \item \textbf{Storage-enforced idempotency keys.} Suppose a mobile app sends
    \texttt{POST /v1/transfers} and its network socket times out before the HTTP
    reply arrives. The client cannot tell whether the commit succeeded, so it must
    retry with the same client-generated \texttt{idempotency\_key}. Running a
    \texttt{SELECT} check in Rust before \texttt{INSERT} creates a classic
    time-of-check to time-of-use race if two retries arrive together. Declaring
    \texttt{UNIQUE (client\_id, idempotency\_key)} closes that race inside the
    storage engine. PostgreSQL's B-tree uniqueness check (\texttt{\_bt\_check\_unique})
    inspects even uncommitted in-flight index entries, blocks the second retry on
    the first transaction's lock, and resolves cleanly via
    \texttt{ON CONFLICT DO NOTHING}.
\end{itemize}

\subsection{Temporal Non-Overlapping Invariants with \texttt{EXCLUDE USING gist}}
\label{ch08:gist-exclude}

Suppose each savings account has a tiered interest-rate schedule valid over a time
window. Two admin jobs concurrently insert schedules for account~$A$: one sets
$4.50\%$ over $[\text{Jun~1}, \text{Dec~1})$ and the other sets $5.00\%$ over
$[\text{Sep~1}, \text{Mar~1})$. A nightly accrual query joins \texttt{accounts} to
\texttt{account\_rate\_schedules WHERE now() <@ effective\_during}. Throughout
autumn it matches \emph{both} rows and pays $9.50\%$ interest. No \texttt{UNIQUE}
constraint on \texttt{(account\_id, effective\_from)} can catch partial overlap
because the two start timestamps differ.

Chapter~3 introduced Generalized Search Trees (GiST) as balanced trees over
bounding predicates such as box or range overlap (\texttt{\&\&}). Pair GiST with the
bundled \texttt{btree\_gist} extension, which adds plain scalar equality
(\texttt{=}) to GiST keys. PostgreSQL's \textbf{exclusion constraint} then rejects
any two rows where \emph{all} listed operator comparisons return true at once:

\begin{lstlisting}[language=SQL]
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE account_rate_schedules (
    schedule_id      UUID PRIMARY KEY DEFAULT uuidv7(),
    account_id       UUID NOT NULL,
    annual_bps       INTEGER NOT NULL CHECK (annual_bps BETWEEN 0 AND 10000),
    effective_during TSTZRANGE NOT NULL,
    CONSTRAINT non_empty_window CHECK (NOT isempty(effective_during)),
    CONSTRAINT no_overlapping_rates EXCLUDE USING gist (
        account_id       WITH =,
        effective_during WITH &&
    )
);
\end{lstlisting}

Notice the range type \texttt{TSTZRANGE} and PostgreSQL's half-open convention
\texttt{'[)'} (closed lower bound, open upper bound). Suppose an old rate schedule
\texttt{[2026-01-01Z, 2026-06-01Z)} ends at midnight June~1 and its replacement
\texttt{[2026-06-01Z, infinity)} starts at that exact microsecond. The two windows
touch with zero gap yet share zero instants, so \texttt{\&\&} evaluates to
\texttt{false}. Even under \texttt{READ COMMITTED}, two concurrent transactions
inserting overlapping windows for the same \texttt{account\_id} collide inside the
GiST index just like a duplicate primary key. One commits; the other aborts with
SQLSTATE \texttt{23P01} (\texttt{exclusion\_violation}).

\section{A Double-Entry Financial Ledger in PostgreSQL and Rust}
\label{ch08:ledger}

Beginners often model money with a single mutable column: subtract $5{,}000$ from
Alice's \texttt{balance} row with one \texttt{UPDATE}, then add $5{,}000$ to Bob's
row with a second \texttt{UPDATE}. Three production hazards make that design
unacceptable for a real ledger:
\begin{enumerate}
  \item \textbf{Destroyed history.} Overwriting \texttt{balance} in place erases
    \emph{why} the balance changed. Once \texttt{VACUUM} reclaims old tuple
    versions (Chapter~5), regulatory audits, dispute reversals, and historical
    reconstructions become impossible.
  \item \textbf{Unchecked money creation.} Nothing in the schema ties the two
    \texttt{UPDATE} statements together. A bug in a new promo-credit handler that
    runs one \texttt{UPDATE} without its counterparty silently alters total
    customer funds.
  \item \textbf{No separation between immutable facts and fast balance reads.}
    Recording append-only ledger legs separately from cached account balances lets
    the database enforce conservation of money while keeping balance lookups $O(1)$.
\end{enumerate}

\subsection{Conservation of Value and \texttt{DEFERRABLE INITIALLY DEFERRED} Triggers}
\label{ch08:deferred-triggers}

Luca Pacioli codified the cure in Venice in 1494: \textbf{double-entry
bookkeeping}. Every financial event is recorded as an immutable
\texttt{journal\_entry} header paired with two or more immutable \texttt{postings}
(legs) in the same currency whose signed minor-unit amounts sum to zero:
\[
  \forall\, e \in \text{journal\_entries}:\qquad
  \abs{P(e)} \ge 2
  \quad\text{and}\quad
  \sum_{p \in P(e)} p.\texttt{signed\_amount\_minor} = 0.
\]
When Alice sends $50.00\text{ USD}$ ($5{,}000$ cents) to Bob, we never invent
$5{,}000$ cents in Bob's row. Instead we append one leg of $-5000$ against Alice's
account and one leg of $+5000$ against Bob's account under the same
\texttt{entry\_id}. If a $1\%$ platform fee applies, the entry has three legs:
$-5000$ (Alice), $+4950$ (Bob), and $+50$ (Platform Fee Revenue), summing cleanly
to $-5000 + 4950 + 50 = 0$.

How do we force PostgreSQL itself to reject any transaction that breaks this
zero-sum balance law? A table-level \texttt{CHECK} constraint can inspect only a
\emph{single} row. And an ordinary \texttt{AFTER INSERT} trigger fires too early:
the moment you insert Alice's $-5000$ leg (before inserting Bob's $+5000$ leg), the
running sum for \texttt{entry\_id} is $-5000 \ne 0$.

What we want is a check that waits until all legs of the transfer are in place,
then runs right as the transaction asks to commit. PostgreSQL provides exactly that
mechanism: a \textbf{\texttt{CONSTRAINT TRIGGER}} declared
\textbf{\texttt{DEFERRABLE INITIALLY DEFERRED}}. Instead of firing after each
\texttt{INSERT}, PostgreSQL queues a small trigger event in backend memory and runs
the verification function \emph{when the client issues \texttt{COMMIT}}, right
before flushing the commit record to WAL (Figure~\ref{ch08:fig-gist-and-deferred}).
Let us write out the complete ledger schema, including an immutability trigger on
\texttt{postings} and a cached balance on \texttt{accounts} guarded against
unauthorized overdrafts:

\begin{lstlisting}[language=SQL]
CREATE TABLE accounts (
    account_id           UUID PRIMARY KEY DEFAULT uuidv7(),
    currency             CHAR(3) NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    cached_balance_minor BIGINT NOT NULL DEFAULT 0,
    allow_overdraft      BOOLEAN NOT NULL DEFAULT FALSE,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT non_negative_unless_overdraft
        CHECK (allow_overdraft OR cached_balance_minor >= 0)
);

CREATE TABLE journal_entries (
    entry_id        UUID PRIMARY KEY DEFAULT uuidv7(),
    client_id       UUID NOT NULL,
    idempotency_key TEXT NOT NULL CHECK (length(idempotency_key) <= 128),
    currency        CHAR(3) NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    description     TEXT NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_client_idempotency UNIQUE (client_id, idempotency_key)
);

CREATE TABLE postings (
    posting_id          UUID PRIMARY KEY DEFAULT uuidv7(),
    entry_id            UUID NOT NULL REFERENCES journal_entries(entry_id),
    account_id          UUID NOT NULL REFERENCES accounts(account_id),
    signed_amount_minor BIGINT NOT NULL CHECK (signed_amount_minor <> 0),
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_postings_entry   ON postings (entry_id);
CREATE INDEX idx_postings_account ON postings (account_id, created_at DESC);

CREATE OR REPLACE FUNCTION forbid_posting_mutation()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'postings are append-only; post a reversing entry';
END;
$$;

CREATE TRIGGER trg_postings_immutable
BEFORE UPDATE OR DELETE ON postings
FOR EACH ROW EXECUTE FUNCTION forbid_posting_mutation();

CREATE OR REPLACE FUNCTION verify_entry_zero_sum()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
DECLARE
    v_entry_id UUID := COALESCE(NEW.entry_id, OLD.entry_id);
    v_legs     BIGINT;
    v_net_sum  BIGINT;
    v_bad_ccy  BIGINT;
BEGIN
    SELECT COUNT(*), COALESCE(SUM(p.signed_amount_minor), 0),
           COUNT(*) FILTER (WHERE a.currency <> je.currency)
      INTO v_legs, v_net_sum, v_bad_ccy
      FROM journal_entries je
      LEFT JOIN postings p ON p.entry_id = je.entry_id
      LEFT JOIN accounts a ON a.account_id = p.account_id
     WHERE je.entry_id = v_entry_id;

    IF v_legs < 2 OR v_net_sum <> 0 OR v_bad_ccy > 0 THEN
        RAISE EXCEPTION USING
            ERRCODE = '23514',
            MESSAGE = 'unbalanced entry ' || v_entry_id
                   || ': legs=' || v_legs || ', sum=' || v_net_sum
                   || ', ccy_mismatch=' || v_bad_ccy;
    END IF;
    RETURN NULL;
END;
$$;

CREATE CONSTRAINT TRIGGER trg_verify_entry_zero_sum
AFTER INSERT OR UPDATE OR DELETE ON postings
DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION verify_entry_zero_sum();
\end{lstlisting}

\begin{trapbox}
\texttt{verify\_entry\_zero\_sum} checks \emph{three} things
together: \texttt{v\_legs < 2}, \texttt{v\_net\_sum <> 0}, and
\texttt{v\_bad\_ccy > 0}. Without \texttt{LEFT JOIN} and \texttt{v\_legs < 2}, an
entry whose postings were somehow deleted (if someone disabled the immutability
trigger during maintenance) would return \texttt{SUM(...) = NULL}, which naive
\texttt{IF v\_net\_sum <> 0} evaluates to \texttt{UNKNOWN} and lets slip past. And
without checking \texttt{a.currency <> je.currency}, a buggy handler could debit
5000~JPY from a yen account and credit 5000~USD cents to a dollar account while
still summing to zero numerically. Finally, attach a second deferred check on
\texttt{journal\_entries} (or always insert postings in the same helper) so an
empty header with zero postings cannot commit alone.
\end{trapbox}

\subsection{Deadlock-Free Transfers in Rust (\texttt{Axum} + \texttt{SQLx})}
\label{ch08:rust-ledger}

Now let us wire our schema to a Rust \texttt{Axum} service using \texttt{SQLx}. Two
concurrency traps await careless transfer code even when the schema is sound:

\begin{enumerate}
  \item \textbf{Opposite-order deadlocks (Chapter~6).} Suppose Task~1 transfers
    $10\text{ USD}$ from Alice to Bob while Task~2 transfers $5\text{ USD}$ from
    Bob to Alice. If each handler locks \texttt{from\_account} first and
    \texttt{to\_account} second, Task~1 holds Alice's lock and waits on Bob, while
    Task~2 holds Bob's lock and waits on Alice. Neither can move until PostgreSQL's
    \texttt{deadlock\_timeout} aborts one of them. Sorting the account UUIDs in
    ascending order (\texttt{ORDER BY account\_id}) before locking makes two-account
    deadlocks impossible, because a strict total order contains no cycles.
  \item \textbf{Over-strong row locks blocking foreign keys.} Recall from Chapter~6
    that \texttt{INSERT INTO postings} takes a lightweight \texttt{FOR KEY SHARE}
    lock on the referenced \texttt{accounts} row so nobody deletes that account
    mid-transfer. Locking \texttt{accounts} with \texttt{SELECT ... FOR UPDATE}
    tells PostgreSQL you might change the primary key \texttt{account\_id} itself,
    which blocks \texttt{FOR KEY SHARE}. Use \textbf{\texttt{FOR NO KEY UPDATE}}
    instead. It still serializes concurrent balance updates on the same account,
    while staying compatible with foreign-key checks.
\end{enumerate}

Listing~\ref{ch08:lst-rust-transfer} puts every piece together: input checks,
atomic idempotency claim, sorted \texttt{FOR NO KEY UPDATE} locking, double-entry
leg insertion, cached balance updates, and commit-time verification.

\begin{lstlisting}[language=Rust, caption={Idempotent, deadlock-free double-entry transfer in Rust with \texttt{SQLx}.}, label={ch08:lst-rust-transfer}]
use sqlx::{PgPool, Postgres, Transaction};
use uuid::Uuid;

#[derive(Debug)]
pub struct TransferCmd {
    pub client_id: Uuid,
    pub idempotency_key: String,
    pub from_account: Uuid,
    pub to_account: Uuid,
    pub currency: String,
    pub amount_minor: i64,
    pub description: String,
}

#[derive(Debug, thiserror::Error)]
pub enum LedgerError {
    #[error("invalid transfer parameters")]
    InvalidInput,
    #[error("account missing or currency mismatch")]
    AccountMismatch,
    #[error("insufficient funds")]
    InsufficientFunds,
    #[error("database error: {0}")]
    Db(#[from] sqlx::Error),
}

#[derive(sqlx::FromRow)]
struct LockedAccount {
    account_id: Uuid,
    currency: String,
    cached_balance_minor: i64,
    allow_overdraft: bool,
}

pub async fn execute_transfer(
    pool: &PgPool,
    cmd: &TransferCmd,
) -> Result<Uuid, LedgerError> {
    if cmd.amount_minor <= 0 || cmd.from_account == cmd.to_account {
        return Err(LedgerError::InvalidInput);
    }

    let mut tx: Transaction<'_, Postgres> = pool.begin().await?;

    // 1. Atomic idempotency claim via UNIQUE (client_id, idempotency_key).
    let claimed: Option<Uuid> = sqlx::query_scalar(
        "INSERT INTO journal_entries \
            (client_id, idempotency_key, currency, description) \
         VALUES ($1, $2, $3, $4) \
         ON CONFLICT (client_id, idempotency_key) DO NOTHING \
         RETURNING entry_id",
    )
    .bind(cmd.client_id)
    .bind(&cmd.idempotency_key)
    .bind(&cmd.currency)
    .bind(&cmd.description)
    .fetch_optional(&mut *tx)
    .await?;

    let Some(entry_id) = claimed else {
        // Retry detected: return the committed entry_id cleanly.
        let existing: Uuid = sqlx::query_scalar(
            "SELECT entry_id FROM journal_entries \
             WHERE client_id = $1 AND idempotency_key = $2",
        )
        .bind(cmd.client_id)
        .bind(&cmd.idempotency_key)
        .fetch_one(&mut *tx)
        .await?;
        tx.rollback().await?;
        return Ok(existing);
    };

    // 2. Canonical lock order prevents A->B vs B->A deadlocks.
    let mut ids = [cmd.from_account, cmd.to_account];
    ids.sort_unstable();

    let locked: Vec<LockedAccount> = sqlx::query_as(
        "SELECT account_id, currency, cached_balance_minor, \
                allow_overdraft \
         FROM accounts \
         WHERE account_id = ANY($1) \
         ORDER BY account_id \
         FOR NO KEY UPDATE",
    )
    .bind(&ids[..])
    .fetch_all(&mut *tx)
    .await?;

    if locked.len() != 2
        || locked.iter().any(|a| a.currency.trim() != cmd.currency)
    {
        return Err(LedgerError::AccountMismatch);
    }

    let sender = locked
        .iter()
        .find(|a| a.account_id == cmd.from_account)
        .ok_or(LedgerError::AccountMismatch)?;

    if !sender.allow_overdraft
        && sender.cached_balance_minor < cmd.amount_minor
    {
        return Err(LedgerError::InsufficientFunds);
    }

    // 3. Append both immutable postings in a single multi-row INSERT.
    sqlx::query(
        "INSERT INTO postings \
            (entry_id, account_id, signed_amount_minor) \
         VALUES ($1, $2, $3), ($1, $4, $5)",
    )
    .bind(entry_id)
    .bind(cmd.from_account)
    .bind(-cmd.amount_minor)
    .bind(cmd.to_account)
    .bind(cmd.amount_minor)
    .execute(&mut *tx)
    .await?;

    // 4. Update cached balances while holding FOR NO KEY UPDATE locks.
    sqlx::query(
        "UPDATE accounts \
         SET cached_balance_minor = cached_balance_minor + CASE \
             WHEN account_id = $1 THEN -$3 \
             WHEN account_id = $2 THEN  $3 \
         END \
         WHERE account_id IN ($1, $2)",
    )
    .bind(cmd.from_account)
    .bind(cmd.to_account)
    .bind(cmd.amount_minor)
    .execute(&mut *tx)
    .await?;

    // 5. Commit fires trg_verify_entry_zero_sum inside PostgreSQL!
    tx.commit().await?;
    Ok(entry_id)
}
\end{lstlisting}

\begin{recoverybox}
\textbf{Pause and check: four independent safety nets on every transfer.}
Trace what happens if a bug or network glitch hits Listing~\ref{ch08:lst-rust-transfer}:
\begin{enumerate}
  \item \textbf{Duplicate retry:} \texttt{UNIQUE (client\_id, idempotency\_key)} catches the retry atomically and returns the original \texttt{entry\_id}.
  \item \textbf{Opposite-direction race:} sorting \texttt{ids} before \texttt{FOR NO KEY UPDATE} prevents $A \to B$ versus $B \to A$ deadlocks while serializing concurrent debits on the same sender.
  \item \textbf{Overdraft race:} \texttt{CHECK (allow\_overdraft OR cached\_balance\_minor >= 0)} rejects negative balances on the heap tuple itself.
  \item \textbf{Unbalanced legs:} \texttt{trg\_verify\_entry\_zero\_sum} runs at \texttt{COMMIT} and aborts the transaction before WAL flush if the postings do not sum to zero in a single currency.
\end{enumerate}
\end{recoverybox}

\section{Declarative Partitioning for Billion-Row Ledgers}
\label{ch08:partitioning}

Imagine our ledger sustains $150$ transfers ($300$ postings) per second around the
clock. That adds $300 \times 86{,}400 \times 365 \approx 9.5\text{ billion}$ new
\texttt{postings} rows a year. At roughly 100~bytes per row, the heap alone grows
by nearly a terabyte a year before indexes. Keeping years of history inside one
giant physical table causes three operational headaches:

\begin{enumerate}
  \item \textbf{Cold secondary indexes.} Even with \texttt{UUIDv7} keeping primary
    key inserts hot, secondary indexes such as \texttt{(account\_id, created\_at
    DESC)} span years of history across hundreds of gigabytes and push active pages
    out of \texttt{shared\_buffers}.
  \item \textbf{Multi-hour \texttt{VACUUM} freeze passes.} Chapter~5 showed that
    even an append-only table needs periodic \texttt{autovacuum} freeze scans to
    mark pages all-frozen in the Visibility Map before the 32-bit transaction ID
    horizon wraps around. Scanning a half-terabyte single heap file saturates disk
    reads for hours.
  \item \textbf{Retention archival via \texttt{DELETE} bloats disk.} Suppose
    compliance policy moves postings older than seven years to cold object storage.
    Running \texttt{DELETE} on $250\text{ million}$ old rows does \emph{not} shrink
    the file on disk: it marks $250\text{ million}$ dead tuples, writes tens of
    gigabytes of WAL, and leaves half-empty pages behind.
\end{enumerate}

PostgreSQL's \textbf{declarative range partitioning} solves all three problems. SQL
queries still address one logical parent table (\texttt{postings}), while storage
splits cleanly into monthly physical child tables (\texttt{postings\_2026\_11},
\texttt{postings\_2026\_12}, and so on). Each child owns its own heap files,
Visibility Map, and local B-tree indexes:

\begin{lstlisting}[language=SQL]
CREATE TABLE postings (
    posting_id          UUID NOT NULL DEFAULT uuidv7(),
    entry_id            UUID NOT NULL,
    account_id          UUID NOT NULL,
    signed_amount_minor BIGINT NOT NULL CHECK (signed_amount_minor <> 0),
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (posting_id, created_at)
) PARTITION BY RANGE (created_at);

CREATE TABLE postings_2026_11 PARTITION OF postings
    FOR VALUES FROM ('2026-11-01 00:00:00+00')
                 TO ('2026-12-01 00:00:00+00');

CREATE TABLE postings_2026_12 PARTITION OF postings
    FOR VALUES FROM ('2026-12-01 00:00:00+00')
                 TO ('2027-01-01 00:00:00+00');

CREATE INDEX idx_postings_acct_time
    ON postings (account_id, created_at DESC);
\end{lstlisting}

Look at what changes inside the engine:
\begin{itemize}
  \item \textbf{Plan-time and runtime partition pruning.} When a customer loads a
    November statement (filtering \texttt{account\_id} and November
    \texttt{created\_at} bounds), the planner (Chapter~7) checks each child's
    \texttt{FOR VALUES} range and skips $83$ out of $84$ monthly partitions before
    reading a single index page. Even when date bounds come from join keys or
    prepared parameters at runtime, the executor's \texttt{Append} node prunes
    non-matching partitions on the fly. Only the current month's indexes need to fit
    in \texttt{shared\_buffers}.
  \item \textbf{Localized \texttt{autovacuum}.} Once November ends, \texttt{VACUUM}
    freezes \texttt{postings\_2026\_11} once in its Visibility Map and never scans
    those pages again.
  \item \textbf{Millisecond, zero-bloat archival.} Retiring the oldest month never
    runs \texttt{DELETE}:
\begin{lstlisting}[language=SQL]
ALTER TABLE postings DETACH PARTITION postings_2019_10 CONCURRENTLY;
-- Export standalone table postings_2019_10 to Parquet/archive, then:
DROP TABLE postings_2019_10;
\end{lstlisting}
    \texttt{DETACH PARTITION CONCURRENTLY} unhooks the child from the parent catalog
    without blocking live reads or inserts. After archiving, \texttt{DROP TABLE}
    unlinks its 1~GB OS segment files in milliseconds with zero dead tuples.
\end{itemize}

\begin{trapbox}
Notice that our partitioned table declared \texttt{PRIMARY KEY (posting\_id,
created\_at)} rather than \texttt{PRIMARY KEY (posting\_id)}. PostgreSQL rejects
any \texttt{UNIQUE} or \texttt{PRIMARY KEY} constraint on a partitioned table
unless \emph{every column of the partition key appears inside the constraint}.
From Chapter~3 you can see why: each monthly partition owns a separate local
B-tree, and enforcing global uniqueness on \texttt{posting\_id} alone would force
every single \texttt{INSERT} to probe all $84$ monthly B-trees. Keep
\texttt{journal\_entries} unpartitioned (or partitioned with \texttt{created\_at}
included in the idempotency window) if you need a single global B-tree on
\texttt{(client\_id, idempotency\_key)}.
\end{trapbox}

\section{High Availability: Physical Streaming and Logical Replication}
\label{ch08:replication}

A RAID array or cloud block volume protects one server against a single drive
failure. It cannot save you from a kernel panic, a motherboard fault, or a
data-center power loss. Yet simply standing up a standby server is not enough
either. Depending on two configuration settings, an automatic failover can still
erase the last few milliseconds of confirmed customer deposits, or a read replica
can report a stale balance right after a transfer succeeds.

\subsection{Physical Streaming WAL Replication and Standby Conflicts}
\label{ch08:physical-replication}

Recall from Chapter~4 that PostgreSQL's Write-Ahead Log records physical page
edits ordered by a rising 64-bit byte offset called the Log Sequence Number (LSN,
represented internally as \texttt{XLogRecPtr}). \textbf{Physical streaming
replication} turns that local crash-recovery log into a live network stream:

\begin{enumerate}
  \item On the primary, a background sender process (\texttt{walsender}) reads
    newly written WAL bytes straight from memory or \texttt{pg\_wal} and streams
    them over TCP to each standby. Attaching a \textbf{physical replication slot}
    tracks how far each standby has caught up so the primary never deletes a 16~MB
    WAL file that a temporarily disconnected replica still needs. Always alert on
    slot lag in \texttt{pg\_replication\_slots}: an abandoned slot for a dead
    standby holds onto WAL forever until the primary's disk fills $100\%$.
  \item On the standby, a receiver process (\texttt{walreceiver}) writes incoming
    WAL bytes to the standby's own \texttt{pg\_wal} directory and flushes them to
    disk. Alongside it, the standby's \texttt{startup} process continuously replays
    those records onto the standby's 8~KB heap and index pages.
\end{enumerate}

Because physical replication ships exact page changes, a physical standby is a
\textbf{byte-for-byte clone} of the primary. Every 8~KB slotted page, every
\texttt{xmin}/\texttt{xmax} stamp, and every B-tree leaf matches across the
cluster. With \texttt{hot\_standby = on}, read-only queries can run directly on the
standby while replay continues underneath them.

That concurrent reading creates a subtle clash with Chapter~5's \texttt{VACUUM}.
Suppose a slow reporting query runs for forty seconds on the standby using snapshot
\texttt{xmin = 50000}. Meanwhile on the primary, no old query is active, so
\texttt{VACUUM} reclaims dead rows from transaction \texttt{50010} and logs a
cleanup record (\texttt{HEAP2\_PRUNE}). When the standby's replay process reaches
that record, applying it right away would erase rows that the standby's running
query still needs to see. PostgreSQL resolves this \textbf{recovery conflict} with
\texttt{max\_standby\_streaming\_delay} (default \texttt{30s}). The standby pauses
WAL replay up to that limit so the query can finish. If the timer expires first,
PostgreSQL cancels the standby query with \texttt{ERROR: canceling statement due to
conflict with recovery}. Turning on \texttt{hot\_standby\_feedback = on} tells the
standby to report its oldest active \texttt{xmin} back to the primary's snapshot
table (\texttt{ProcArray}). That prevents standby query cancellations, at the price
of holding back dead-row cleanup on the primary while long replica queries run.

\subsection{The \texttt{synchronous\_commit} Durability and Visibility Ladder}
\label{ch08:sync-commit-ladder}

When a Rust handler calls \texttt{tx.commit().await}, how far through the
replication pipeline must the commit LSN travel before the primary tells the client
``success''? PostgreSQL lets you pick the exact rung on the latency-versus-safety
ladder, either globally in \texttt{postgresql.conf} or per transaction with
\texttt{SET LOCAL}. Two settings work together: \texttt{synchronous\_commit} chooses
the rung, and \texttt{synchronous\_standby\_names} names which standbys count---for
example, \texttt{ANY 1 (az2\_standby, az3\_standby)} across three availability
zones.

Each standby continuously reports three LSN watermarks back to the primary, all
visible in \texttt{pg\_stat\_replication}:
\begin{itemize}
  \item \texttt{write\_lsn}: WAL bytes copied into the standby's OS page cache;
  \item \texttt{flush\_lsn}: WAL bytes flushed with \texttt{fsync} onto the
    standby's NVMe drive;
  \item \texttt{replay\_lsn}: WAL bytes applied to the standby's shared buffers,
    making the commit visible to standby readers.
\end{itemize}

\subsection{Logical Replication for Zero-Downtime Upgrades and Event Streaming}
\label{ch08:logical-replication}

Physical replication requires the primary and standby to run the \emph{exact} same
major PostgreSQL version and CPU architecture, because 8~KB page layouts change
across major releases. How, then, do you upgrade a live financial ledger from
PostgreSQL~16 to PostgreSQL~18 without downtime, or stream committed
\texttt{postings} rows into an analytics warehouse?

Setting \texttt{wal\_level = logical} turns on \textbf{logical decoding}. Instead
of shipping raw 8~KB page diffs, the primary decodes WAL back into logical row
changes. Because concurrent transactions write interleaved WAL records, a per-slot
staging area called the \textbf{Reorder Buffer} gathers each transaction's records
by transaction ID (spilling huge transactions to disk if needed). Rolled-back
transactions are discarded. The moment a transaction commits, an output plugin
(\texttt{pgoutput}) emits structured \texttt{INSERT}, \texttt{UPDATE}, and
\texttt{DELETE} row events:

\begin{lstlisting}[language=SQL]
-- On the primary (or PG 16 source cluster):
CREATE PUBLICATION ledger_pub
    FOR TABLE accounts, journal_entries, postings
    WITH (publish_via_partition_root = true);

-- On the PG 18 target cluster:
CREATE SUBSCRIPTION ledger_sub
    CONNECTION 'host=pg16-primary dbname=ledger user=repl_role'
    PUBLICATION ledger_pub;
\end{lstlisting}

Notice \texttt{publish\_via\_partition\_root = true}. Subscribers receive row
events tagged under the parent table \texttt{postings}, so the target cluster can
use a fresh partitioning layout or new indexes. Keep two limits in mind during
logical upgrades: schema changes (\texttt{ALTER TABLE}) do not replicate
automatically, and \texttt{SEQUENCE} counters are not copied in real time. Using
time-ordered \texttt{UUIDv7} keys avoids the sequence-cutover headache altogether.

\section{Connection Pooling at Scale: Process Architecture and PgBouncer}
\label{ch08:pooling}

Our Rust \texttt{Axum} service runs on Tokio's async runtime, where one pod juggles
ten thousand open HTTP sockets in a few dozen megabytes of RAM. Suppose you scale
out to $50$ Kubernetes pods, set each pod's \texttt{sqlx::PgPool} limit to $100$,
and raise PostgreSQL's \texttt{max\_connections = 5500} on a 32-core server so all
$5{,}000$ sockets connect directly. Everything looks calm in staging. Then Monday
morning traffic arrives. Database CPU hits $100\%$ inside kernel spinlocks, free
RAM disappears, and 99th-percentile transfer latency jumps from $3\text{ ms}$ to
four seconds.

\subsection{Why Five Thousand Backend Processes Melt PostgreSQL}
\label{ch08:process-model}

Unlike Tokio's lightweight tasks, PostgreSQL uses a
\textbf{one-OS-process-per-connection} model. Whenever a client opens a TCP
connection, the main supervisor process (\texttt{postmaster}) forks a dedicated
\texttt{postgres} OS process for that client. Keeping $5{,}000$ backend processes
open hurts throughput in three physical ways:

\begin{enumerate}
  \item \textbf{Per-backend private memory.} Although \texttt{shared\_buffers} is
    shared, every \texttt{postgres} process keeps its own private table and catalog
    caches (\texttt{relcache} and \texttt{catcache}, which grow large on
    partitioned schemas), cached plans, and \texttt{work\_mem} buffers (Chapter~7).
    At $10$--$16\text{ MB}$ of resident RAM per active process, $5{,}000$ backends
    eat $50$--$80\text{ GB}$ before caching a single table page.
  \item \textbf{Snapshot scans across \texttt{ProcArray}.} Chapter~5 showed that
    every \texttt{READ COMMITTED} query builds a fresh snapshot
    (\texttt{GetSnapshotData()}) by scanning the shared-memory array of connected
    backends (\texttt{ProcArray}) to list active transaction IDs. Scanning $5{,}000$
    slots hundreds of thousands of times per second causes fierce CPU cache-line
    contention around \texttt{ProcArrayLock}.
  \item \textbf{OS scheduler preemption inside locks.} When $600$ processes wake up
    at once on $32$ CPU cores, the Linux scheduler constantly preempts them,
    flushing CPU caches. Worse, whenever the OS deschedules a backend \emph{while
    it holds a lightweight buffer latch or spinlock}, dozens of other backends pile
    up waiting behind that sleeping process.
\end{enumerate}

Always benchmark your own hardware, but a reliable starting rule on NVMe servers
with $N_{\text{cores}}$ cores is to keep active \texttt{postgres} processes near
$1.5 \times N_{\text{cores}}$ to $3 \times N_{\text{cores}}$. On a 32-core primary,
that is \textbf{$48$ to $96$ backends}. Adding more connections past that point adds
wait time, not throughput.

\subsection{\texttt{PgBouncer} Transaction Multiplexing and the Prepared Statement Trap}
\label{ch08:pgbouncer}

How can $50$ Rust pods holding $2{,}500$ client sockets share just $48$ physical
\texttt{postgres} processes? Place \textbf{\texttt{PgBouncer}} in front of the
database (Figure~\ref{ch08:fig-pgbouncer}). \texttt{PgBouncer} is a small,
event-driven C proxy that speaks the PostgreSQL wire protocol using roughly
$2\text{ KB}$ of RAM per client socket. It offers three pooling modes:

\begin{itemize}
  \item \textbf{\texttt{session} mode} ties one \texttt{postgres} process to a
    client socket from connect until disconnect. Because \texttt{sqlx::PgPool}
    keeps long-lived TCP sockets open, \texttt{session} mode provides \emph{zero}
    multiplexing: $2{,}500$ client sockets still require $2{,}500$ backends.
  \item \textbf{\texttt{transaction} mode} (the production standard) lends a
    \texttt{postgres} process to a client \emph{only from \texttt{BEGIN} until
    \texttt{COMMIT} or \texttt{ROLLBACK}} (or for a single standalone query). The
    instant \texttt{COMMIT} finishes, \texttt{PgBouncer} hands that warm backend to
    the next waiting request. While an \texttt{Axum} task parses JSON, verifies
    signatures, or writes HTTP replies, it holds \emph{zero} database processes.
  \item \textbf{\texttt{statement} mode} reclaims the backend after every single
    SQL command and rejects multi-statement \texttt{BEGIN ... COMMIT} blocks, so
    ledger transactions cannot use it.
\end{itemize}

Flipping \texttt{pool\_mode = transaction} without knowing how PostgreSQL's wire
protocol prepares queries triggers an outage within seconds:
\texttt{ERROR: prepared statement "sqlx\_s\_1" does not exist} (or
\texttt{already exists}). Here is why that happens on the wire:

\begin{enumerate}
  \item To avoid re-parsing SQL text on every call, \texttt{SQLx} uses PostgreSQL's
    two-step extended query protocol and caches up to $100$ named prepared
    statements per TCP socket. In Transaction~A, Client~1 lands on Backend~\#4. It
    sends a \texttt{Parse} message saving statement \texttt{sqlx\_s\_1} inside
    Backend~\#4's private memory, runs it, and commits.
  \item A millisecond later, Client~1 begins Transaction~B, and \texttt{PgBouncer}
    assigns Backend~\#19. Because Client~1 is still using the same TCP socket to
    \texttt{PgBouncer}, \texttt{SQLx} assumes \texttt{sqlx\_s\_1} already exists. It
    skips \texttt{Parse} and sends a \texttt{Bind} packet asking for
    \texttt{sqlx\_s\_1}. Backend~\#19 has never heard of \texttt{sqlx\_s\_1} and
    aborts the transaction.
\end{enumerate}

The same backend-hopping behavior breaks any feature that stores state for an
entire \emph{session} rather than a single \emph{transaction}:
\begin{itemize}
  \item Never run bare \texttt{SET synchronous\_commit = 'remote\_apply'} or
    \texttt{SET statement\_timeout = '2s'} in transaction mode; that setting leaks
    onto whichever unrelated request borrows the backend next. Always write
    \textbf{\texttt{SET LOCAL ...}}, which resets automatically at \texttt{COMMIT}
    or \texttt{ROLLBACK}.
  \item Never call session-scoped \texttt{pg\_advisory\_lock}, which stays locked
    after your transaction finishes. Always call the transaction-scoped
    \textbf{\texttt{pg\_advisory\_xact\_lock}} instead.
  \item \texttt{LISTEN / NOTIFY} channels need a separate direct or
    \texttt{session}-mode connection outside the transaction pool.
\end{itemize}

For prepared statements, you have two clean fixes. Modern \textbf{\texttt{PgBouncer}
($\ge 1.21$)} supports protocol-level prepared-statement multiplexing when you set
\texttt{max\_prepared\_statements = 200} in \texttt{pgbouncer.ini}. \texttt{PgBouncer}
remembers each client's \texttt{Parse} query, maps client names
(\texttt{sqlx\_s\_1}) onto shared server names (\texttt{PGBOUNCER\_7}), and
automatically prepares missing statements on whichever backend runs the
transaction. That keeps Chapter~7's plan-cache speedups intact. If you run behind
an older pooler that lacks protocol tracking, set
\texttt{statement\_cache\_capacity(0)} on \texttt{PgConnectOptions} so \texttt{SQLx}
sends unnamed single-use statements:

\begin{lstlisting}[language=Rust]
use sqlx::postgres::{PgConnectOptions, PgPoolOptions};
use std::str::FromStr;
use std::time::Duration;

pub async fn build_ledger_pool(
    db_url: &str,
    pgbouncer_tracks_stmts: bool,
) -> Result<sqlx::PgPool, sqlx::Error> {
    let mut opts = PgConnectOptions::from_str(db_url)?;
    if !pgbouncer_tracks_stmts {
        // Fallback for stateless transaction poolers: unnamed statements.
        opts = opts.statement_cache_capacity(0);
    }

    PgPoolOptions::new()
        .max_connections(50)
        .acquire_timeout(Duration::from_secs(2))
        .idle_timeout(Duration::from_secs(300))
        .connect_with(opts)
        .await
}
\end{lstlisting}

\begin{recoverybox}
\textbf{Pause and check: three rules for safe \texttt{PgBouncer} transaction pooling.}
Before switching any service to \texttt{pool\_mode = transaction}, verify three items:
\begin{enumerate}
  \item Enable \texttt{max\_prepared\_statements = 200} on \texttt{PgBouncer} ($\ge 1.21$), or disable client statement caching (\texttt{statement\_cache\_capacity(0)}).
  \item Replace every session \texttt{SET} with \texttt{SET LOCAL} inside a transaction block.
  \item Replace every \texttt{pg\_advisory\_lock} with \texttt{pg\_advisory\_xact\_lock}, and move \texttt{LISTEN / NOTIFY} onto a dedicated unpooled connection.
\end{enumerate}
\end{recoverybox}

Here is the whole path of one $50.00\text{ USD}$ transfer through the machinery of
this book. An \texttt{Axum} task borrows a pooled connection through
\texttt{PgBouncer} and lands on one of $48$ warm backends, keeping
\texttt{ProcArray} snapshot scans tiny (Chapter~5). It generates \texttt{UUIDv7}
keys, which append cleanly to the rightmost B-tree leaf already cached in
\texttt{shared\_buffers} (Chapters~2 and~3). It claims its idempotency key via a
\texttt{UNIQUE} index, locks both accounts in sorted order with
\texttt{FOR NO KEY UPDATE} (Chapter~6), and appends two \texttt{BIGINT} postings
into the current month's partition. At \texttt{COMMIT}, the deferred trigger
confirms that the legs sum to zero. With \texttt{synchronous\_commit = on}, WAL
flushes onto NVMe drives in two availability zones before the client hears success
(Chapter~4).

\begin{exercise}[IEEE 754 Drift vs.\ Exact Ledger Representations]

SELECT SUM(val::float8) AS float_sum, SUM(val::numeric) AS num_sum

\begin{exercise}[Sizing \texttt{synchronous\_commit} Across Three Availability Zones]
A ledger cluster spans \texttt{az1} (primary), \texttt{az2} (standby), and
\texttt{az3} (standby). Local NVMe \texttt{fsync} takes $0.25\text{ ms}$, network
