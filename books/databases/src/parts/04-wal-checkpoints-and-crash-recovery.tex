\chapter{Write-Ahead Logging, Checkpoints, and Crash Recovery}
\label{ch:wal-recovery}

In Chapters~2 and~3 we built fast 8,192-byte table pages and B-tree index blocks inside PostgreSQL's RAM cache (\texttt{shared\_buffers}). As long as power flows steadily into DRAM, updates fly: inserting a row updates the page in memory, tweaks each index leaf, and marks those buffers dirty in microseconds. Now pull the server's power cord out of the wall. Every byte in \texttt{shared\_buffers} vanishes. Every byte in the Linux kernel page cache vanishes too. Worse, any 8~KB page caught mid-flight to the SSD lands split into two mismatched 4~KB halves. How does PostgreSQL return \texttt{COMMIT} in under a millisecond while guaranteeing that a power cut never loses a committed row or leaves a broken index?

\begin{focusbox}
By the end of this chapter, you will be able to answer five questions from first principles:
\begin{itemize}
  \item Why does an ordinary \texttt{write()} call leave your data in volatile RAM, and how can power loss slice an 8~KB database page into two mismatched 4~KB disk sectors?
  \item How does appending tiny change records to one sequential Write-Ahead Log (WAL) let PostgreSQL commit transactions without waiting on scattered table and index writes?
  \item Why does replaying a tiny change record fail on a half-written disk page, and how does saving one full page snapshot after each checkpoint heal torn writes?
  \item When forty clients hit \texttt{COMMIT} at the same instant, how does one leader thread sync all forty commits in a single disk flush?
  \item When power returns after a crash, how does PostgreSQL recover in one forward pass---with zero undo rollback work, even if a crashed batch job modified ten million rows?
\end{itemize}
\end{focusbox}

\section{The Physics of \texttt{write()}, \texttt{fsync()}, and Torn 8 KB Pages}
\label{ch04:physics}

Before reading any PostgreSQL recovery code, picture what happens physically when a Linux program writes to a file. Engineers casually say ``we wrote the buffer to disk'' when \texttt{write(fd, buf, 8192)} returns \texttt{8192}. Physically, nothing reached the drive. Those 8,192 bytes merely copied from one region of volatile RAM into another region of volatile RAM.

Trace a modified 8~KB page from PostgreSQL's RAM pool all the way into non-volatile NAND flash cells:

\begin{enumerate}
  \item \textbf{PostgreSQL \texttt{shared\_buffers} (user-space RAM):} When an \texttt{INSERT} or \texttt{UPDATE} changes block~7, it edits an 8,192-byte frame in shared memory and flips its dirty bit (\texttt{BM\_DIRTY}). If \texttt{postgres} crashes with \texttt{SIGSEGV} or \texttt{kill -9} and resets shared memory, every dirty frame here disappears.
  \item \textbf{Linux kernel page cache (OS RAM):} To hand a page to the operating system, PostgreSQL calls the positional write syscall \texttt{pwrite(fd, page, 8192, offset)}. The kernel copies those 8,192 bytes into two 4,096-byte kernel memory buffers (\texttt{struct folio}), marks them dirty, and returns \texttt{8192} right away. Notice the gap between process death and power loss. If \texttt{postgres} dies via \texttt{kill -9} right after \texttt{pwrite()}, Linux is still running and flushes those kernel buffers seconds later. If the kernel panics or building power fails, the entire OS page cache evaporates.
  \item \textbf{NVMe controller DRAM cache (on-drive RAM):} Even when Linux transfers 4~KB blocks over PCIe to an SSD, the drive does not program slow NAND flash right away. Most SSDs carry 512~MB to 4~GB of onboard DDR4 DRAM to absorb bursts and hold Flash Translation Layer (FTL) maps. Without backup power on the drive, bytes sitting in controller DRAM still vanish when voltage drops.
  \item \textbf{Non-volatile NAND flash (\texttt{fsync} / \texttt{fdatasync}):} To demand true persistence, a program calls \texttt{fdatasync(fd)} (or opens its log file with \texttt{O\_DSYNC}, which syncs every write automatically). Linux pushes dirty kernel buffers to the drive \emph{and} sends an NVMe \texttt{Flush} command (or sets the hardware Force Unit Access bit, \texttt{FUA}, which bypasses volatile drive cache). A compliant SSD does not complete \texttt{fdatasync()} until every byte sits in NAND flash or behind backup capacitors.
\end{enumerate}

Java~6 hides the same tiers behind \texttt{FileOutputStream.write()}, which returns as soon as the bytes reach tier~2, the kernel page cache. A Java program that needs durability must call \texttt{fos.getFD().sync()} or \texttt{FileChannel.force(true)}, and both end in \texttt{fsync(2)}. In C the pair is explicit:
\begin{lstlisting}[language=C]
ssize_t n = pwrite(fd, page, 8192, off); /* returns once bytes sit in the page cache */
if (n != 8192)
    report_error();
if (fdatasync(fd) != 0)                  /* returns once the device reports durable */
    abort();                             /* PostgreSQL PANICs here instead           */
\end{lstlisting}
Why abort instead of retrying? In 2018 PostgreSQL engineers discovered a nasty Linux kernel trap: after a failed \texttt{fsync}, Linux can mark the dirty kernel pages clean and discard them. A second \texttt{fsync} then returns success even though the bytes never reached disk. Since February 2019, any data-file \texttt{fsync} error during a checkpoint halts PostgreSQL immediately so restart replays cleanly from the Write-Ahead Log:
\begin{lstlisting}[language=Plain]
PANIC:  could not fsync file "base/16384/16391": Input/output error
\end{lstlisting}

\begin{attackbox}
\textbf{Lying consumer drives vs.\ enterprise Power-Loss Protection (PLP).}
Enterprise NVMe SSDs carry a row of tantalum or supercapacitors on their circuit boards. When 12~V power drops, those capacitors power the drive for a few milliseconds to drain onboard DRAM into NAND flash, letting the drive honor \texttt{NVMe Flush} fast and honestly. Cheap consumer SSDs omit those capacitors to save two dollars. Worse, some consumer firmware lies and reports \texttt{Flush} complete before programming NAND just to win benchmarks. Pull the plug on a lying drive mid-load and bytes that \texttt{fdatasync()} promised were safe vanish, corrupting any database engine.
\end{attackbox}

\subsection{Why Direct Heap Flushing on \texttt{COMMIT} Fails Twice}

Suppose we had no write-ahead log and tried to make \texttt{COMMIT} durable the direct way. On every \texttt{COMMIT}, we would find each 8~KB table and index page dirtied by that transaction, call \texttt{pwrite()}, and run \texttt{fdatasync()} on each file before replying to the client.

That design fails twice: first on \emph{speed}, then on \emph{correctness}.

First, count the random I/O cost. Inserting one row into \texttt{orders} with four B-tree indexes dirties five separate 8~KB blocks across five files in \texttt{PGDATA/base/16384/}. If an index leaf splits, that single index dirties three more blocks (left leaf, new right leaf, parent). Syncing five to eight random 8~KB blocks on every one-row commit turns sequential flash bandwidth into random-write thrashing and wears out SSD erase blocks. It also stops you from keeping hot pages in RAM across thousands of updates.

Second, and worse: even if you paid that $100\times$ latency tax, \textbf{a power cut mid-flush destroys the page}. Compare the block sizes across the stack:
\[
  \text{PostgreSQL page} = 8{,}192\text{ bytes}
  \qquad\text{vs.}\qquad
  \text{Linux VM page / NVMe 4Kn sector} = 4{,}096\text{ bytes}.
\]
Standard filesystems (\texttt{ext4}, \texttt{XFS}) and NVMe drives write atomically in 4,096-byte sectors, never 8,192-byte pages. Every 8~KB PostgreSQL page spans two adjacent 4~KB sectors: bytes \texttt{0..4095} in sector~$2k$ and bytes \texttt{4096..8191} in sector~$2k+1$. Recall Chapter~2's slotted page layout. The 24-byte page header and 4-byte slot pointers grow \emph{downward} from byte~\texttt{0} in sector~$2k$, while row bytes grow \emph{upward} from byte~\texttt{8192} in sector~$2k+1$.

Figure~\ref{ch04:fig-write-stack}(b) shows this \emph{torn page} (or \emph{fractured write}) in action. Before our insert, block~7 held three rows in bytes \texttt{7968..8191} (\texttt{pd\_upper = 7968}). Inserting a 56-byte fourth row lowers \texttt{pd\_upper} to \texttt{7912}, writes the row into bytes \texttt{7912..7967} (Sector~$2k+1$), and writes \texttt{ItemId[4] = (off=7912, len=56)} at byte~\texttt{36} (Sector~$2k$). Now suppose power dies right after Sector~$2k$ lands in NAND flash, before Sector~$2k+1$ arrives. On reboot, block~7 on disk is half new and half old: \texttt{ItemId[4]} points to offset~\texttt{7912}, where stale bytes or zeroes sit. With data checksums enabled (\texttt{initdb --data-checksums}), the 16-bit \texttt{pd\_checksum} catches the mismatch and aborts the query with \texttt{ERROR: invalid page in block 7}---detecting corruption, though unable to heal it. Without checksums, PostgreSQL decodes garbage bytes as customer balances.

Solving both problems at once---avoiding scattered \texttt{fdatasync()} calls at \texttt{COMMIT} \emph{and} healing any torn 8~KB page---is the job of Write-Ahead Logging.

\section{Write-Ahead Logging (\texttt{pg\_wal}), LSNs, and the Fundamental WAL Invariant}
\label{ch04:wal-invariant}

\begin{intuitionbox}
Separate \emph{recording} a change from \emph{applying} it. Recording is one sequential append to a single file. Applying touches scattered 8~KB pages in many files. \texttt{COMMIT} waits only for the append to become durable; the scattered pages are written later, in batches. If power fails before they are written, restart reads the appended records and applies them again. One rule makes this safe: \textbf{a data page may not reach disk before the log records describing its changes are durable.}
\end{intuitionbox}

PostgreSQL's Write-Ahead Log (implemented in \texttt{src/backend/access/transam/xlog.c}) turns that idea into one append-only byte stream. That logical stream starts at byte~\texttt{0} when \texttt{initdb} creates a cluster and grows upward for the life of the database.

\subsection{Segment Files in \texttt{PGDATA/pg\_wal/} and \texttt{pg\_lsn} Byte Arithmetic}

Keeping a multi-terabyte log in one giant file would make deleting old history painful. Instead, PostgreSQL slices the byte stream into fixed \textbf{16~MB} ($16{,}777{,}216 = \texttt{0x01000000}$ byte) segment files inside \texttt{PGDATA/pg\_wal/}. Internally, each 16~MB segment is split into 2,048 pages of 8,192 bytes, each starting with a small header (\texttt{XLogPageHeaderData}) so recovery can verify alignment every 8~KB.

Every byte position in this stream has a 64-bit address called a \textbf{Log Sequence Number} (\texttt{XLogRecPtr} in C, or \texttt{pg\_lsn} in SQL). PostgreSQL prints a 64-bit LSN as two hex numbers separated by a slash:
\[
  \texttt{X/YYYYYYYY} \quad\Longleftrightarrow\quad (\texttt{0xX} \ll 32) \;\mid\; \texttt{0xYYYYYYYY}.
\]
Read that format in plain terms: \texttt{X} counts how many 4~GB ($2^{32}$-byte) chunks have passed, and \texttt{YYYYYYYY} gives the hex byte offset inside the current 4~GB chunk (dropping leading zeros, so \texttt{0/016B3748} prints as \texttt{0/16B3748}). To compare two LSNs or measure the WAL bytes between them, treat both as plain 64-bit integers and subtract.

\begin{definition}[Log Sequence Number and Segment Mapping]
\label{ch04:def-lsn}
A \emph{Log Sequence Number} $L \in [0, 2^{64})$ is a byte offset into PostgreSQL's WAL stream. With segment size $S = 2^{24} = 16{,}777{,}216$~bytes (\texttt{0x01000000}) and a 32-bit timeline ID $T \ge 1$ (starting at $T = 1$ and incremented on point-in-time recovery promotion), $L$ maps to:
\begin{align*}
  \mathrm{segno}(L) &= \floor{L / S} = L \gg 24, &
  \mathrm{offset}(L) &= L \bmod S = L \mathbin{\&} \texttt{0x00FFFFFF}.
\end{align*}
Because each 4~GB chunk ($2^{32}$ bytes) holds $2^{32} / 2^{24} = 256 = \texttt{0x100}$ segments of 16~MB, the 24-character hex filename in \texttt{PGDATA/pg\_wal/} concatenates three 8-digit hex fields:
\[
  \underbrace{\texttt{TTTTTTTT}}_{\text{timeline } T}
  \;\underbrace{\texttt{XXXXXXXX}}_{\floor{\mathrm{segno}/256} = (L \gg 32)}
  \;\underbrace{\texttt{000000SS}}_{\mathrm{segno} \bmod 256}.
\]
\end{definition}

That third group \texttt{000000SS} explains a classic surprise when listing \texttt{PGDATA/pg\_wal/}: file \texttt{0000000100000000000000FF} rolls straight over to \texttt{000000010000000100000000} instead of \texttt{...00000100}. Because $256 \times 16\text{ MB} = 4\text{ GB}$, the middle eight digits count 4~GB chunks, while the last eight digits only ever run from \texttt{00} to \texttt{FF}.

\begin{example}[Concrete \texttt{pg\_lsn} Arithmetic by Hand]
\label{ch04:ex-lsn-math}
Suppose \texttt{pg\_current\_wal\_lsn()} returns $L_1 = \texttt{0/16B3748}$ before a batch insert and $L_2 = \texttt{0/16B3A90}$ right after, on timeline $T = 1$:
\begin{enumerate}
  \item \textbf{Which 16~MB file holds $L_1$, and at what byte offset?}
    Pad the right half to eight hex digits: $L_1 = \texttt{0x00000000\_016B3748}$. Dropping the last six hex digits ($\gg 24$) gives $\mathrm{segno}(L_1) = \texttt{0x01} = 1$. Keeping the last six hex digits gives $\mathrm{offset}(L_1) = \texttt{0x6B3748} = 7{,}026{,}504$~bytes ($\approx 6.70$~MB into file \texttt{000000010000000000000001}).
  \item \textbf{How many WAL bytes did the batch generate?}
    Subtract directly in base~16:
    \[
      L_2 - L_1 = \texttt{0x016B3A90} - \texttt{0x016B3748} = \texttt{0x348}
      = 3 \times 256 + 4 \times 16 + 8 = 840\text{ bytes}.
    \]
  \item \textbf{Cross-epoch subtraction:} Suppose $L_3 = \texttt{0/FFFFFC00}$ and $L_4 = \texttt{1/400}$ (short for \texttt{1/00000400}, or \texttt{0x00000001\_00000400}). Then
    \[
      L_4 - L_3 = \texttt{0x100000400} - \texttt{0x0FFFFFC00} = \texttt{0x800} = 2{,}048\text{ bytes},
    \]
    matching \texttt{SELECT pg\_wal\_lsn\_diff('1/400', '0/FFFFFC00');} $\to$ \texttt{2048}.
\end{enumerate}
\end{example}

\subsection{Inside an \texttt{XLogRecord} and Resource Managers}

What actually sits at offset \texttt{0/16B3748} inside that file? Every logged event---a row insert, a B-tree split, a \texttt{COMMIT}, or a checkpoint---starts with a fixed 24-byte envelope recording its length, 32-bit transaction ID (XID), previous record address, subsystem owner, and checksum. In C (\texttt{src/include/access/xlogrecord.h}), that envelope is \texttt{XLogRecord}:

\begin{lstlisting}[language=C]
/* Fixed 24-byte header at the front of every WAL record (xlogrecord.h) */
typedef struct XLogRecord
{
    uint32          xl_tot_len;   /* total byte length of entire record       */
    TransactionId   xl_xid;       /* 32-bit XID that wrote record (or 0)      */
    XLogRecPtr      xl_prev;      /* start LSN of previous record in WAL      */
    uint8           xl_info;      /* opcode flags specific to resource mgr    */
    RmgrId          xl_rmid;      /* resource manager ID (heap, btree, xact)  */
    /* 2 bytes of struct alignment padding here -> 20 bytes so far            */
    pg_crc32c       xl_crc;       /* CRC32C over payload + bytes 0..19        */
} XLogRecord;                     /* sizeof(XLogRecord) == 24 bytes           */
\end{lstlisting}

Right after those 24~bytes come zero or more \textbf{block headers} (\texttt{XLogRecordBlockHeader}). Each block header names a touched page by its physical file triple (\texttt{RelFileLocator}), fork, and 32-bit block number, followed by per-block change bytes (or a Full Page Image) and the record's main payload.

Three fields in \texttt{XLogRecord} keep recovery modular and safe:
\begin{itemize}
  \item \textbf{\texttt{xl\_rmid} and \texttt{xl\_info} (Resource Managers):} Instead of one giant recovery \texttt{switch}, PostgreSQL splits WAL replay across two dozen \textbf{Resource Managers} (\texttt{RmgrTable} in \texttt{rmgr.c}), each supplying an \texttt{rm\_redo} replay routine:
    \begin{itemize}
      \item \texttt{RM\_XLOG\_ID} (\texttt{XLOG}): checkpoints, settings changes, standalone full-page writes.
      \item \texttt{RM\_XACT\_ID} (\texttt{Transaction}): \texttt{COMMIT}, \texttt{ABORT}, and two-phase records.
      \item \texttt{RM\_HEAP\_ID} / \texttt{RM\_HEAP2\_ID}: \texttt{INSERT}, \texttt{UPDATE}, \texttt{HOT\_UPDATE}, \texttt{DELETE}, in-page pruning, and freeze records.
      \item \texttt{RM\_BTREE\_ID} (\texttt{Btree}): leaf inserts, page splits, and page deletions.
    \end{itemize}
  \item \textbf{\texttt{xl\_prev} (Back-pointer check):} Every record points to the start LSN of the record right before it. To save I/O, PostgreSQL recycles old 16~MB WAL files by renaming them to future segment numbers without zeroing their old bytes. As a result, bytes \emph{past} the crash point in a recycled file often hold old \texttt{XLogRecord} headers from days ago. Checking the page header LSN and \texttt{xl\_prev} stops recovery from replaying stale leftovers.
  \item \textbf{\texttt{xl\_crc} (Hardware CRC32C):} Computed with CPU instructions (\texttt{crc32q} on x86, CRC32C on ARM) over the whole record. If power dies halfway through writing a 200-byte record, \texttt{xl\_crc} fails to match, marking the exact end of valid WAL.
\end{itemize}

\subsection{\texttt{pd\_lsn} and the Fundamental WAL Invariant}

How does an 8~KB page on disk remember how much of the WAL stream it already includes? Every table, index, and visibility-map page stores an 8-byte LSN stamp right at bytes \texttt{0..7} of its header (\texttt{pd\_lsn} in \texttt{PageHeaderData}):
\begin{lstlisting}[language=C]
typedef struct PageHeaderData
{
    PageXLogRecPtr pd_lsn;        /* bytes 0..7: LSN of last modifying record */
    uint16         pd_checksum;   /* bytes 8..9: 16-bit FNV-1a page checksum  */
    uint16         pd_flags;      /* bytes 10..11: header flag bits           */
    LocationIndex  pd_lower;      /* bytes 12..13: start of free space        */
    LocationIndex  pd_upper;      /* bytes 14..15: end of free space          */
    /* ... */
} PageHeaderData;
\end{lstlisting}
Whenever a backend edits buffer~$P$ in \texttt{shared\_buffers} under an exclusive page lock, it builds an \texttt{XLogRecord} and appends it into \texttt{wal\_buffers}. That append returns the record's \emph{ending} LSN~$L$. The backend stamps \texttt{pd\_lsn = L} into bytes \texttt{0..7} of~$P$ and marks~$P$ dirty.

At that moment, both \texttt{wal\_buffers} and~$P$ still sit in volatile RAM. Neither has touched NAND flash yet. One rule governs which one must reach flash first.

\begin{theorem}[The Write-Ahead Logging Invariant]
\label{ch04:thm-wal-rule}
Let $P$ be a dirty buffer in \texttt{shared\_buffers} stamped with $\texttt{pd\_lsn}(P) = L$, and let $\mathrm{FlushLSN}$ be the highest WAL byte offset synced (\texttt{fdatasync}) to disk inside \texttt{PGDATA/pg\_wal/}. PostgreSQL's buffer manager (\texttt{FlushBuffer} in \texttt{bufmgr.c}) enforces:
\[
  P \text{ may be written to the OS via \texttt{pwrite(2)}} \quad\Longrightarrow\quad \mathrm{FlushLSN} \ge \texttt{pd\_lsn}(P) = L.
\]
Whenever $\mathrm{FlushLSN} < L$, \texttt{FlushBuffer} blocks and calls \texttt{XLogFlush(L)} before calling \texttt{pwrite(2)}. Together with torn-page protection (Section~\ref{ch04:fpw}) and commit flushing, this rule guarantees that every committed write survives crashes and no disk page holds an unlogged change.
\end{theorem}

\begin{proof}
In Haerder and Reuter's buffer taxonomy, PostgreSQL is a \textbf{\textsc{Steal} / \textsc{No-Force}} engine:
\begin{itemize}
  \item \textbf{\textsc{No-Force}:} When transaction~$T_1$ commits at $L_{\text{commit}}$, PostgreSQL syncs only the sequential WAL stream up to $\mathrm{FlushLSN} \ge L_{\text{commit}}$. Dirty 8~KB pages touched by~$T_1$ stay in RAM. Because all of $T_1$'s edits sit at LSNs $L_i < L_{\text{commit}} \le \mathrm{FlushLSN}$, every log record needed to rebuild $T_1$'s work is already safe on flash before the client hears \texttt{COMMIT}.
  \item \textbf{\textsc{Steal}:} Conversely, if \texttt{shared\_buffers} needs room, PostgreSQL may \emph{steal} frame~$P$ dirtied by an uncommitted transaction~$T_2$ at LSN~$L$ and write~$P$ to its table file early. Because \texttt{FlushBuffer} forces $\mathrm{FlushLSN} \ge L$ before \texttt{pwrite(2)}, the log record at~$L$ (plus its full-page image if~$P$ tears) is already safe on flash. Recovery can rebuild a valid page~$P$ and let transaction commit status govern row visibility. \qedhere
\end{itemize}
\end{proof}

\end{recoverybox}

\begin{attackbox}
\textbf{What breaks if \texttt{bgwriter} violates the WAL Invariant?}
Trace a concrete violation. Transaction~$T_1$ splits B-tree leaf block~19: it allocates right-sibling block~44 and moves half of block~19's keys there at LSN \texttt{0/1A40}. Because $T_1$ has not committed yet, \texttt{0/1A40} sits only in volatile \texttt{wal\_buffers} (\texttt{FlushLSN = 0/1980}). Now suppose a buggy writer pushes block~19 to disk without calling \texttt{XLogFlush(0/1A40)}, and power fails before \texttt{0/1A40} or block~44 reaches flash. On reboot, recovery stops at \texttt{0/1980}. Block~44 does not exist on disk, while block~19 has permanently lost half its index entries \emph{for already committed rows} and points to a missing page.
\end{attackbox}

\section{Torn Pages Solved: \texttt{full\_page\_writes} After a Checkpoint}
\label{ch04:fpw}

Test your intuition with one question before reading on.

\begin{walkbox}
Suppose PostgreSQL obeys the WAL Invariant (Theorem~\ref{ch04:thm-wal-rule}): before dirty block~7 (\texttt{pd\_lsn = 0/1140}) writes to its table file, its WAL record at \texttt{0/1140} is already \texttt{fdatasync}ed in \texttt{pg\_wal}. A millisecond later, \texttt{bgwriter} calls \texttt{pwrite()} on block~7, and power fails mid-write, tearing block~7 across its two 4~KB sectors as in Figure~\ref{ch04:fig-write-stack}(b). Since record \texttt{0/1140} is safe on disk, why can't recovery simply replay \texttt{0/1140} onto block~7 to fix the tear?
\end{walkbox}

Trace the exact byte offsets and you will see naive delta replay fail in \emph{two separate ways}.

Normally, WAL records use \textbf{physiological logging}: physical as to \emph{which} 8~KB block changed (``table 16384, block 7''), logical inside that block's layout (``lower \texttt{pd\_upper} by 56, write these 56 row bytes there, and point \texttt{ItemId[4]} at \texttt{pd\_upper}''). Those compact deltas take only 55 to 80 bytes instead of 8,192 bytes. To avoid inserting the same row twice during replay, recovery compares the disk page's \texttt{pd\_lsn} against the record's end LSN:
\begin{align*}
  \texttt{page.pd\_lsn} \ge \texttt{record.end\_lsn} &\implies \text{skip replay (\texttt{BLK\_DONE});}\\
  \texttt{page.pd\_lsn} < \texttt{record.end\_lsn} &\implies \text{apply delta and set } \texttt{page.pd\_lsn} \gets \texttt{record.end\_lsn}.
\end{align*}

Now watch both halves of a torn 8~KB write break that check:

\begin{enumerate}
  \item \textbf{Failure Case A (Sector~$2k$ lands, Sector~$2k+1$ is lost):}
    Where does \texttt{pd\_lsn} sit inside an 8,192-byte page? At bytes \texttt{0..7}, right at the start of Sector~$2k$. When Sector~$2k$ lands on flash and power cuts before Sector~$2k+1$ arrives, the torn page carries the \emph{new} \texttt{pd\_lsn = 0/1140} in Sector~$2k$, while Sector~$2k+1$ still misses the 56-byte row. On reboot, recovery reads block~7, sees $\texttt{page.pd\_lsn} = \texttt{0/1140} \ge \texttt{0/1140}$, and concludes block~7 was already fully written. It \textbf{skips record \texttt{0/1140}}, leaving the page permanently broken.
  \item \textbf{Failure Case B (Sector~$2k+1$ lands first, Sector~$2k$ is lost):}
    NVMe queues freely reorder unbarriered 4~KB sector writes. Suppose Sector~$2k+1$ (row bytes) hits flash while Sector~$2k$ (header and slot pointers) stays at old \texttt{pd\_lsn = 0/1080}. Worse, suppose record \texttt{0/1140} compacted the page (\texttt{PageRepairFragmentation}), shifting twenty rows upward in Sector~$2k+1$ and updating twenty slot offsets in Sector~$2k$. Replaying physiological deltas onto a half-shifted, half-unshifted 8~KB page reads misaligned offsets and scrambles the block.
\end{enumerate}

\begin{whybox}
Physiological delta replay works only when the 8~KB page on disk is a \textbf{clean snapshot from one real instant in time}---either wholly before a WAL record or wholly after it. A torn 8~KB page never existed in RAM; no chain of deltas can build safely on two mismatched 4~KB halves.
\end{whybox}

\subsection{Hole-Stripped Full Page Images (FPIs) vs.\ Doublewrite Buffers}

Storage engines solve torn pages in two main ways. MySQL's InnoDB uses a \textbf{doublewrite buffer}: before scattering dirty 16~KB pages to table files, InnoDB writes full 16~KB copies sequentially into a staging area and calls \texttt{fsync()}, doubling every background page write.

PostgreSQL takes a lighter path governed by \texttt{full\_page\_writes = on} (enabled by default). Instead of writing every evicted page twice, PostgreSQL ties torn-page protection to checkpoints. Whenever a checkpoint starts, PostgreSQL records that starting WAL offset in a shared pointer called $\mathrm{RedoRecPtr}$:

\begin{formalbox}
\textbf{The \texttt{full\_page\_writes} Rule (\texttt{XLogCheckBufferNeedsBackup}).}
Let $\mathrm{RedoRecPtr}$ be the WAL LSN where the latest checkpoint \emph{began}. When a backend edits buffer~$P$ and logs a WAL record, it checks $P$'s \emph{previous} \texttt{pd\_lsn} (before stamping the new LSN):
\begin{itemize}
  \item If $\texttt{pd\_lsn}_{\text{prior}}(P) \le \mathrm{RedoRecPtr}$, this is the \textbf{first edit to page~$P$ since the checkpoint began}. PostgreSQL embeds a complete \textbf{Full Page Image (FPI)} of the 8~KB page inside this WAL record (\texttt{BKPBLOCK\_HAS\_IMAGE | BKPIMAGE\_APPLY}).
  \item If $\texttt{pd\_lsn}_{\text{prior}}(P) > \mathrm{RedoRecPtr}$, an earlier record after $\mathrm{RedoRecPtr}$ already saved an FPI for page~$P$. Every 2nd, 3rd, $\dots$, $10{,}000$th edit to page~$P$ until the next checkpoint writes \textbf{only a compact 55--80 byte delta}.
\end{itemize}
\end{formalbox}

Trace how this heals both Case~A and Case~B at once. A checkpoint starts at $\mathrm{RedoRecPtr} = \texttt{0/1000}$. Block~7 (previously at \texttt{0/0E20}) is touched first at \texttt{0/1080} (which saves an FPI), updated by deltas at \texttt{0/1140} and \texttt{0/1190}, and then torn on disk when power fails.

On reboot, recovery scans forward from $\mathrm{RedoRecPtr} = \texttt{0/1000}$. The first record touching block~7 is \texttt{0/1080}, which carries an FPI. When recovery (\texttt{XLogReadBufferForRedoExtended}) sees an FPI, it \textbf{never reads or trusts the torn disk page's \texttt{pd\_lsn}}. It zeroes an 8~KB buffer in RAM, copies the clean FPI straight from WAL, sets \texttt{pd\_lsn = 0/1080}, and returns \texttt{BLK\_RESTORED}. Even if Sector~$2k$ on disk claimed \texttt{0/1190}, the FPI overwrites all 8~KB in RAM back to the intact \texttt{0/1080} state. Next, recovery applies the 64-byte delta at \texttt{0/1140} and the 58-byte delta at \texttt{0/1190} cleanly in RAM.

Better still, an FPI rarely writes all 8,192 bytes to WAL. Between \texttt{pd\_lower} (end of slot pointers) and \texttt{pd\_upper} (start of rows) sits an empty \textbf{free-space hole}. PostgreSQL strips that hole (\texttt{BKPIMAGE\_HAS\_HOLE}), storing only its start offset and length in a 4-byte header:
\[
  \text{Raw FPI bytes} = 8{,}192 - (\texttt{pd\_upper} - \texttt{pd\_lower}).
\]
If block~7 holds ten rows totaling 2,000~bytes (\texttt{pd\_lower = 64}, \texttt{pd\_upper = 6192}), the hole is $6{,}128$~bytes, so the raw FPI takes only $64 + 2{,}000 = 2{,}064$~bytes. Turning on \texttt{wal\_compression = lz4} (or \texttt{zstd} in PG~15+) shrinks those 2,064~bytes further to \textbf{650--900~bytes}.

\begin{applicationbox}
\textbf{Diagnosing and taming the ``Checkpoint WAL Storm'' in production.}
Starting a checkpoint advances $\mathrm{RedoRecPtr}$. Right away, \emph{every hot page in \texttt{shared\_buffers}} satisfies $\texttt{pd\_lsn} \le \mathrm{RedoRecPtr}$ again. Over the next 30 to 90 seconds, the first update to each active page emits a Full Page Image. That burst spikes WAL volume (\texttt{wal\_fpi} and \texttt{wal\_bytes} in \texttt{pg\_stat\_wal}), disk sync load, and replication traffic by $3\times$ to $10\times$. Two settings flatten that sawtooth wave on busy OLTP clusters:
\begin{enumerate}
  \item Raise \texttt{checkpoint\_timeout} from \texttt{5min} to \texttt{15min}--\texttt{30min} (raising \texttt{max\_wal\_size} to \texttt{16GB}--\texttt{64GB} to match), so hot buffers pay the FPI cost three to six times less often.
  \item Set \texttt{wal\_compression = lz4} (or \texttt{zstd}), which cuts FPI bytes by $60\%$--$75\%$ and often \emph{raises} commit throughput on cloud block volumes.
\end{enumerate}
Never set \texttt{full\_page\_writes = off} on \texttt{ext4} or \texttt{XFS}. It is safe only on Copy-on-Write filesystems like ZFS with \texttt{recordsize=8k}, where the filesystem never overwrites an 8~KB block in place.
\end{applicationbox}

\section{Commit Durability Tradeoffs, Group Commit, and \texttt{wal\_writer}}
\label{ch04:commit-durability}

Appending a 70-byte WAL record is sequential, avoiding scattered table seeks. Still, a sharp engineer should ask a latency question right here. Even sequential \texttt{fdatasync()} takes $80\;\mu\text{s}$ on local NVMe and $800\;\mu\text{s}$ on a cloud block volume. If one thread holds a lock for $800\;\mu\text{s}$ on every \texttt{COMMIT}, isn't a 64-core server stuck at $1 / 0.0008\text{ s} = 1{,}250$ commits per second?

If every session ran its own \texttt{fdatasync()} one by one, that ceiling of $1{,}250$ transactions per second (TPS) would be unbreakable. Breaking past it requires separating \emph{copying WAL bytes into shared RAM} from \emph{flushing shared RAM to flash}, then batching concurrent committers via \textbf{group commit}.

\subsection{\texttt{wal\_buffers}, Parallel Insertion Slots, and Group Commit}

In shared memory, PostgreSQL allocates a ring buffer of 8~KB WAL frames sized by \texttt{wal\_buffers} ($1/32$ of \texttt{shared\_buffers}, clamped between 64~KB and 16~MB). Two separate lock layers coordinate that ring:

\begin{enumerate}
  \item \textbf{Parallel RAM insertion (\texttt{NUM\_XLOGINSERT\_LOCKS = 8}):} When forty sessions run \texttt{INSERT} or \texttt{UPDATE} at once, each computes its \texttt{XLogRecord} checksum in private memory. Each session then grabs one of eight \texttt{WALInsertLocks}, reserves its exact byte slice $[L_{\text{start}}, L_{\text{end}})$ via an atomic fetch-add, and copies its bytes into \texttt{wal\_buffers} alongside seven other CPU cores.
  \item \textbf{Leader-follower disk flush (\texttt{WALWriteLock}):} When session $B_1$ runs \texttt{COMMIT}, it appends a tiny commit record ending at $L_1 = \texttt{0/1500}$ and calls \texttt{XLogFlush(0/1500)}. Only one process at a time holds \texttt{WALWriteLock} to call \texttt{write()} and \texttt{fdatasync()} on the WAL file. Watch what happens during the $800\;\mu\text{s}$ while $B_1$ waits inside the kernel for flash programming:
    \begin{itemize}
      \item Sessions $B_2, B_3, \dots, B_{40}$ do \emph{not} stall on copying. Using the eight insertion locks, all thirty-nine append their commit records into \texttt{wal\_buffers}, pushing the RAM tail from \texttt{0/1500} to $L_{40} = \texttt{0/4B20}$. They then queue behind \texttt{WALWriteLock}.
      \item Once $B_1$'s \texttt{fdatasync()} finishes, $B_1$ publishes \texttt{Flush = 0/1500} in shared memory and drops \texttt{WALWriteLock}.
      \item Session $B_2$ wakes up as the new \textbf{group leader}. Instead of flushing only to its own $L_2 = \texttt{0/1590}$, $B_2$ checks how far \texttt{wal\_buffers} has filled---\textbf{all the way to $L_{40} = \texttt{0/4B20}$}. Leader $B_2$ writes the whole slice \texttt{(0/1500 .. 0/4B20]} in one sequential \texttt{write()} and runs \textbf{one \texttt{fdatasync()}} for all thirty-nine transactions.
      \item When $B_2$ publishes \texttt{Flush = 0/4B20} and drops \texttt{WALWriteLock}, followers $B_3 \dots B_{40}$ see $\texttt{Flush} \ge L_i$ in shared memory and return \texttt{COMMIT} with \textbf{zero} system calls.
    \end{itemize}
\end{enumerate}

\begin{implementbox}
Here is the core leader-follower double-check pattern distilled from \texttt{XLogFlush()} in \texttt{src/backend/access/transam/xlog.c}:
\begin{lstlisting}[language=C]
void XLogFlush(XLogRecPtr record_end_lsn)
{
    /* Fast path: did an earlier group leader already sync past our LSN? */
    if (record_end_lsn <= LogwrtResult.Flush)
        return;

    /* Wait our turn (or wake up after the current leader finishes) */
    LWLockAcquire(WALWriteLock, LW_EXCLUSIVE);

    /* Refresh shared Flush pointer; if the previous leader swept our
     * commit record into its fdatasync batch, exit with ZERO syscalls! */
    RefreshLogwrtResult();
    if (record_end_lsn <= LogwrtResult.Flush)
    {
        LWLockRelease(WALWriteLock);
        return;
    }

    /* We are the new group leader: flush ALL ready WAL bytes in wal_buffers,
     * sweeping in every follower that appended while we waited! */
    XLogRecPtr insert_pos = WaitXLogInsertionsToFinish(GetXLogInsertRecPtr());
    XLogWrite(insert_pos);   /* sequential write() + single fdatasync()  */
    LWLockRelease(WALWriteLock);
}
\end{lstlisting}
Now forty clients on a $0.8\;\text{ms}$ cloud disk are no longer capped at $1{,}250$~TPS: batching thirty-nine commits per $0.8\;\text{ms}$ flush lifts durable throughput past $45{,}000$~TPS on the same drive. PostgreSQL also offers \texttt{commit\_delay} (a brief leader pause when at least \texttt{commit\_siblings} sessions are active), though real concurrency already builds full batches naturally while the previous \texttt{fdatasync()} runs.
\end{implementbox}

\subsection{The \texttt{synchronous\_commit} Spectrum and \texttt{wal\_writer}}

Suppose a table ingests millions of telemetry readings or click events per minute. Losing the last half-second of clicks during a rare power cut is fine, provided the database \textbf{never corrupts}.

Faced with that goal, developers sometimes reach for the wrong knob and destroy a cluster by setting \texttt{fsync = off}. Separate those two settings permanently:

\begin{trapbox}
\textbf{\texttt{synchronous\_commit = off} is safe engineering; \texttt{fsync = off} is Russian roulette.}
\begin{itemize}
  \item \textbf{\texttt{fsync = off}} strips \texttt{fdatasync()} out of PostgreSQL everywhere---commits, checkpoints, buffer evictions, and control-file updates. If power drops, table pages, B-tree pages, commit logs, and \texttt{pg\_control} hit disk out of order. That breaks the WAL Invariant and leaves the cluster unrecoverable. Use \texttt{fsync = off} \emph{only} on disposable test containers.
  \item \textbf{\texttt{synchronous\_commit = off}} (even per-transaction via \texttt{SET LOCAL synchronous\_commit = off;}) skips \emph{only} the foreground wait at \texttt{COMMIT}: the backend appends \texttt{XACT\_COMMIT} into \texttt{wal\_buffers} and replies right away without calling \texttt{XLogFlush()}. Even so, \textbf{\texttt{full\_page\_writes} and the WAL Invariant in \texttt{FlushBuffer()} stay $100\%$ active.} No dirty page can ever reach disk ahead of its synced WAL record.
\end{itemize}
\end{trapbox}

Who flushes \texttt{wal\_buffers} when sessions use \texttt{synchronous\_commit = off}? A background daemon named \textbf{\texttt{wal\_writer}} wakes every \texttt{wal\_writer\_delay} (default \texttt{200ms}, or once \texttt{wal\_writer\_flush\_after = 1MB} builds up) and flushes unwritten WAL. It writes full 8~KB WAL pages on normal ticks and flushes any partial tail page once a cycle passes, bounding unsynced commits on power loss to at most $3 \times \texttt{wal\_writer\_delay} \approx \mathbf{600\;\text{ms}}$. After a power outage, PostgreSQL recovers cleanly to a $100\%$ valid state from $\le 600\;\text{ms}$ earlier, with zero torn pages and zero broken indexes.

Better still, \texttt{synchronous\_commit} works per transaction. On the same connection pool, a payment transfer uses \texttt{synchronous\_commit = on}, while a click logger runs:
\begin{lstlisting}[language=SQL]
BEGIN;
SET LOCAL synchronous_commit = off;
INSERT INTO page_views (user_id, url, viewed_at) VALUES (4812, '/checkout', now());
COMMIT;  -- returns in ~15 microseconds without waiting on NVMe fdatasync!
\end{lstlisting}

\subsection{\texttt{UNLOGGED} Tables: Trading Crash Survival for Raw RAM-to-Disk Speed}

For scratch data---nightly ETL staging tables, rebuildable caches, or temporary session state---even compact WAL records are wasted work. Declaring a table \texttt{UNLOGGED}:
\begin{lstlisting}[language=SQL]
CREATE UNLOGGED TABLE etl_staging_events (
    batch_id    bigint NOT NULL,
    payload     jsonb  NOT NULL
);
\end{lstlisting}
tells PostgreSQL (\texttt{relpersistence = 'u'} in \texttt{pg\_class}) to \textbf{skip WAL completely} on writes and index updates. Sessions edit 8~KB pages in \texttt{shared\_buffers} without WAL locks, Full Page Images, or replication traffic, often doubling or tripling bulk load speed.

How does PostgreSQL stop half-flushed \texttt{UNLOGGED} pages from corrupting queries after a crash? During \texttt{CREATE UNLOGGED TABLE}, PostgreSQL writes one tiny WAL-logged template file next to the main file (say \texttt{base/16384/24580}): an empty initialization fork named \textbf{\texttt{24580\_init}} (plus an empty root \texttt{\_init} fork for each index).
\begin{itemize}
  \item On a \textbf{clean shutdown} (\texttt{pg\_ctl stop -m fast}), the shutdown checkpoint flushes every dirty \texttt{UNLOGGED} buffer cleanly, so all rows survive normal restarts.
  \item On \textbf{any crash recovery}, \texttt{ResetUnloggedRelations()} finds every relation in \texttt{PGDATA/base/} with an \texttt{\_init} fork, deletes the potentially torn main files, and copies \texttt{24580\_init} over \texttt{24580}. Every \texttt{UNLOGGED} table resets cleanly to zero rows before clients connect.
\end{itemize}

\section{Checkpoints, Background Writer, and Step-by-Step Crash Recovery}
\label{ch04:recovery}

One puzzle remains. If we append to \texttt{PGDATA/pg\_wal/} forever without flushing dirty pages to table files, \texttt{pg\_wal} fills the SSD, and a crash after six months of uptime has to replay six months of WAL from \texttt{0/0}.

A \textbf{checkpoint} establishes a safe floor on disk so PostgreSQL can recycle old 16~MB WAL files and keep crash recovery down to seconds. How an online checkpoint runs without freezing user traffic hinges on two separate pointers inside \texttt{pg\_control}.

\subsection{\texttt{global/pg\_control}, Fuzzy Checkpoints, and Why Recovery Rewinds to the Redo Point}

When a crashed server boots up, how does \texttt{StartupXLOG()} know where in \texttt{pg\_wal} to start reading? It opens a tiny metadata file at \texttt{PGDATA/global/pg\_control}. That file holds one checksum-protected struct (\texttt{ControlFileData}) small enough to fit inside a single 512-byte sector for atomic updates:

\begin{lstlisting}[language=C]
/* Simplified excerpt from src/include/catalog/pg_control.h */
typedef struct CheckPoint
{
    XLogRecPtr      redo;           /* Redo start LSN when ckpt BEGAN!   */
    TimeLineID      ThisTimeLineID; /* current WAL timeline              */
    FullTransactionId nextXid;      /* next free 64-bit XID              */
    /* ... oldestActiveXid, oldestMulti, timestamp ... */
} CheckPoint;

typedef struct ControlFileData
{
    uint64          system_identifier;
    DBState         state;          /* DB_SHUTDOWNED vs DB_IN_PRODUCTION */
    XLogRecPtr      checkPoint;     /* LSN of latest Checkpoint Record   */
    CheckPoint      checkPointCopy; /* embedded copy including .redo!    */
    uint32          data_checksum_version;
    pg_crc32c       crc;
} ControlFileData;
\end{lstlisting}

Look at those two LSN fields in \texttt{ControlFileData}: \texttt{checkPoint} (say \texttt{0/1230}) and \texttt{checkPointCopy.redo} (say \texttt{0/1000}). Why are they different?

Picture a server with 64~GB of \texttt{shared\_buffers} trying to take an instant ``stop-the-world'' checkpoint. It would have to freeze all writes, blast 20~GB of dirty pages to disk, \texttt{fsync} three hundred files, log one checkpoint record, and unfreeze clients. Every five minutes, user requests would stall for 25 seconds.

Instead, PostgreSQL runs \textbf{spread (fuzzy) online checkpoints} controlled by three settings:
\begin{itemize}
  \item \texttt{checkpoint\_timeout} (default \texttt{5min}, often tuned to \texttt{15min}--\texttt{30min}): max time between checkpoints.
  \item \texttt{max\_wal\_size} (default \texttt{1GB}, often \texttt{16GB}--\texttt{64GB}): soft WAL budget before starting an early checkpoint.
  \item \texttt{checkpoint\_completion\_target} (default \texttt{0.9}): fraction of the interval spent pacing disk writes ($0.9 \times 300\text{ s} = 270\text{ s}$).
\end{itemize}

Trace what happens from $t = 0\text{ s}$ to $t = 270\text{ s}$ while normal traffic keeps running:
\begin{enumerate}
  \item \textbf{At $t = 0\text{ s}$ (LSN \texttt{0/1000}):} \texttt{checkpointer} wakes up and records the current WAL offset as \textbf{\texttt{RedoRecPtr = 0/1000}} (triggering Full Page Images for pages touched from \texttt{0/1000} onward). It then flags every buffer \emph{already dirty at $t = 0\text{ s}$} with \texttt{BM\_CHECKPOINT\_NEEDED}.
  \item \textbf{Across $t \in (0\text{ s}, 270\text{ s})$:} \texttt{checkpointer} trickles those flagged buffers to disk with gentle pauses and finally calls \texttt{fsync()} on each touched file. Meanwhile, clients never stop writing. At $t = 40\text{ s}$ (LSN \texttt{0/1080}), client $T_1$ edits buffer~$B_7$ (which was clean at $t = 0\text{ s}$, or already flushed at $t = 10\text{ s}$). Buffer~$B_7$ now sits dirty in RAM with \texttt{pd\_lsn = 0/1080}, and \texttt{checkpointer} does \textbf{not} have to flush~$B_7$ during this cycle.
  \item \textbf{At $t = 270\text{ s}$ (LSN \texttt{0/1230}):} Once every pre-\texttt{0/1000} dirty buffer is synced to flash, \texttt{checkpointer} writes an \texttt{XLOG\_CHECKPOINT\_ONLINE} record at \texttt{0/1230} storing \texttt{redo = 0/1000}. It syncs WAL to \texttt{0/1230}, updates \texttt{global/pg\_control}, and recycles WAL segments strictly older than \texttt{0/1000}.
\end{enumerate}

\begin{recoverybox}
\textbf{Pause and check the two checkpoint LSNs.} The checkpoint record lands at \texttt{0/1230} when flushing \emph{finishes}, whereas \texttt{redo = 0/1000} marks when flushing \emph{started}. Only edits before \texttt{0/1000} are guaranteed to sit in table files on disk, so crash recovery always rewinds to \texttt{0/1000} and replays forward from there.
\end{recoverybox}

\begin{whybox}
Rewinding to \texttt{redo = 0/1000} protects every edit made while the checkpoint was running, such as $T_1$'s change to~$B_7$ at \texttt{0/1080}. Starting replay at \texttt{0/1230} would lose $T_1$'s committed row.

That overlap also explains PostgreSQL's WAL sizing formula (\texttt{CalculateCheckpointSegments}). While Checkpoint~2 runs for $c \cdot T$ seconds ($c = \texttt{checkpoint\_completion\_target} = 0.9$), PostgreSQL must still keep WAL back to Checkpoint~1's Redo point. Right before Checkpoint~2 finishes, live WAL spans $(1 + c)$ intervals:
\[
  \text{Peak live WAL} \;\approx\; (1 + \texttt{checkpoint\_completion\_target}) \times R_{\text{wal}} \times \texttt{checkpoint\_timeout}.
\]
At $R_{\text{wal}} = 20\;\text{MB/s}$ and \texttt{checkpoint\_timeout = 15min} ($18\;\text{GB}$ per interval), \texttt{max\_wal\_size} needs at least $1.9 \times 18\;\text{GB} \approx \mathbf{35\;\text{GB}}$ to avoid early forced checkpoints.
\end{whybox}

\subsection{Three Buffer Writers, Three Distinct Jobs}

Dirty 8~KB buffers leave \texttt{shared\_buffers} through three different processes, tracked in \texttt{pg\_stat\_checkpointer}, \texttt{pg\_stat\_bgwriter}, and PG~16+'s \texttt{pg\_stat\_io}:

\begin{itemize}
  \item \textbf{\texttt{checkpointer} (recovery floor \& WAL recycling):} Flushes every buffer dirtied before $\mathrm{RedoRecPtr}$ once per checkpoint and calls \texttt{fsync()}. On a well-tuned server, \texttt{checkpointer} performs $70\%$--$95\%$ of all data writes, collapsing 500 in-RAM updates to a hot block into a single disk write.
  \item \textbf{\texttt{bgwriter} (clean-buffer headroom):} Wakes every \texttt{bgwriter\_delay} (\texttt{200ms}) and sweeps just ahead of the clock-sweep hand, cleaning low-usage dirty buffers (up to \texttt{bgwriter\_lru\_maxpages}) so user queries find clean frames ready. It never writes checkpoints.
  \item \textbf{Client backend writes (the warning light):} When a user query needs a buffer frame and hits a dirty victim before \texttt{bgwriter} cleaned it, \emph{that user's \texttt{SELECT} must call \texttt{FlushBuffer()} inline.} Rising client-backend writes in \texttt{pg\_stat\_io} mean \texttt{shared\_buffers} or \texttt{bgwriter} is falling behind.
\end{itemize}

\subsection{Classic ARIES (3 Passes) vs.\ PostgreSQL's 1-Pass Redo-Only Recovery}

Most textbooks teach IBM's \textbf{ARIES} recovery algorithm (Mohan et al., 1992), designed for engines that overwrite rows in place. On startup, ARIES runs \textbf{three passes} over the log:
\begin{enumerate}
  \item \textbf{Analysis pass (forward):} Scans from the checkpoint to rebuild the Dirty Page Table and list uncommitted ``loser'' transactions.
  \item \textbf{Redo pass (forward, ``repeating history''):} Replays all logged physical edits---winners and losers alike---restoring pages to their exact pre-crash state.
  \item \textbf{Undo pass (backward):} Walks backward along each loser transaction's log chain, physically undoing uncommitted edits and writing Compensation Log Records. If a batch job updated $50\text{ million}$ rows and power died at $99\%$, eager ARIES Undo must roll back $50\text{ million}$ rows.
\end{enumerate}

Now open \texttt{src/backend/access/transam/xlogrecovery.c} in PostgreSQL and look for the Undo pass. \textbf{There isn't one.} PostgreSQL writes zero Undo records and never scans WAL backward.

\begin{connectionbox}
\textbf{How MVCC (Chapter~5) eliminates the Undo phase completely.}
Recall from Chapter~2 that a PostgreSQL \texttt{UPDATE} never overwrites a row in place: it marks \texttt{t\_xmax = 702} on the old version and inserts a new version marked \texttt{t\_xmin = 702}. During crash recovery, PostgreSQL runs \textbf{one forward Redo pass} from $\mathrm{RedoRecPtr}$ to the end of valid WAL, replaying both committed $T_1$ (\texttt{xid = 701}) \emph{and} crashed $T_2$ (\texttt{xid = 702}).

Why doesn't $T_2$'s uncommitted row corrupt queries when clients reconnect? Commit status lives in PostgreSQL's Commit Log (CLOG), stored under \texttt{PGDATA/pg\_xact/} with two bits per 32-bit transaction ID (XID): \texttt{00 = IN\_PROGRESS}, \texttt{01 = COMMITTED}, \texttt{10 = ABORTED}, and \texttt{11 = SUB\_COMMITTED}. Transaction~$T_1$ logged \texttt{XACT\_COMMIT}, so Redo sets \texttt{pg\_xact[701] = 01}. Crashed $T_2$ never logged \texttt{COMMIT}, so \texttt{pg\_xact[702]} stays \texttt{00} while recovery advances \texttt{nextXid} past \texttt{702}. Any past XID still marked \texttt{00} is \textbf{instantly treated as aborted by every snapshot}. Readers ignore $T_2$'s new version, keep seeing the old version, and let background \texttt{VACUUM} reclaim dead bytes later. Whether $T_2$ touched ten rows or a hundred million, startup Undo time is $\mathbf{0\;\text{ms}}$.
\end{connectionbox}

Inside \texttt{xlogutils.h}, every block reference inspected during that single forward Redo pass resolves to one of four explicit actions returned by \texttt{XLogReadBufferForRedoExtended()}:
\begin{lstlisting}[language=C]
typedef enum
{
    BLK_NEEDS_REDO, /* page.pd_lsn < record.end_lsn -> apply delta & set LSN */
    BLK_DONE,       /* page.pd_lsn >= record.end_lsn -> already applied, skip */
    BLK_RESTORED,   /* record carried an FPI -> 8 KB block restored from WAL  */
    BLK_NOTFOUND    /* relation/block truncated & dropped later -> skip       */
} XLogRedoAction;
\end{lstlisting}

Algorithm~\ref{ch04:alg-redo} puts the entire \texttt{StartupXLOG()} recovery state machine onto one page.

\begin{algorithm}[H]
\caption{\textsc{PostgresCrashRecovery}: Single-Pass Redo in \texttt{xlogrecovery.c}}
\label{ch04:alg-redo}
\KwIn{\texttt{global/pg\_control} and segment files in \texttt{PGDATA/pg\_wal/}.}
\KwOut{Consistent \texttt{shared\_buffers}, \texttt{pg\_xact}, and relation files ready for clients.}
Read \texttt{ControlFileData} from \texttt{global/pg\_control} and verify CRC32C\; \tcp*{Bootstrap control file.}
\If{$\mathrm{state} = \texttt{DB\_SHUTDOWNED}$}{\Return \tcp*{Clean shutdown; zero recovery needed.}}
Read Checkpoint Record at $\texttt{ControlFile.checkPoint}$ and set $\mathrm{RedoLSN} \gets \texttt{ckpt.redo}$\; \tcp*{Find Redo start.}
Initialize WAL reader at $\mathrm{RedoLSN}$\;
\While{\textsc{ReadNextXLogRecord}() returns header + payload with valid \texttt{xl\_prev} and CRC32C}{
  $L_{\text{end}} \gets$ ending byte offset of current \texttt{XLogRecord}\; \tcp*{Record end LSN.}
  $\mathrm{nextXid} \gets \max(\mathrm{nextXid},\; \texttt{record.xl\_xid} + 1)$\;
  \uIf{$\texttt{record.xl\_rmid} = \texttt{RM\_XACT\_ID}$}{
    Update \texttt{pg\_xact}[\texttt{record.xl\_xid}] to \texttt{01 (COMMITTED)} or \texttt{10 (ABORTED)}\; \tcp*{Update commit log.}
  }
  \Else{
    \ForEach{Block $B$ referenced in \texttt{record}}{
      \uIf{Block $B$ carries a Full Page Image (\texttt{BKPIMAGE\_APPLY})}{
        Zero frame $P$ in \texttt{shared\_buffers} and expand the FPI into $P$.\;
        Set $\texttt{P.pd\_lsn} \gets L_{\text{end}}$ and mark $P$ dirty\; \tcp*{\texttt{BLK\_RESTORED}: heals any tear.}
      }
      \Else{
        Read disk block $B$ into buffer frame $P$.\;
        \If{$\texttt{P.pd\_lsn} < L_{\text{end}}$}{
          Call \texttt{RmgrTable[record.xl\_rmid].rm\_redo(record, P)}\; \tcp*{\texttt{BLK\_NEEDS\_REDO}.}
          Set $\texttt{P.pd\_lsn} \gets L_{\text{end}}$ and mark $P$ dirty.\;
        }
        \tcp{Otherwise $\texttt{P.pd\_lsn} \ge L_{\text{end}} \implies \texttt{BLK\_DONE}$ (idempotent skip).}
      }
    }
  }
}
\tcp{First invalid CRC32C or header marks exact end-of-WAL boundary.}
\textsc{ResetUnloggedRelations}() \tcp*{Copy \texttt{\_init} forks over all \texttt{UNLOGGED} tables.}
Write end-of-recovery checkpoint (or promote); set $\mathrm{state} \gets \texttt{DB\_IN\_PRODUCTION}$\;
\end{algorithm}

\subsection{Worked LSN-by-LSN Crash Recovery Trace}

Let us trace Algorithm~\ref{ch04:alg-redo} on concrete hex LSNs so every step is crystal clear. Heap Block~7 of \texttt{accounts} starts on disk with $\texttt{pd\_lsn} = \texttt{0/0E20}$ and one row \texttt{(id=1, bal=500)}. Watch six events run right before power fails:

\begin{enumerate}
  \item \textbf{\texttt{0/1000} (Checkpoint starts):} \texttt{checkpointer} starts an online checkpoint and sets $\mathrm{RedoRecPtr} = \texttt{0/1000}$.
  \item \textbf{\texttt{0/1080} ($T_1$, \texttt{xid=701}, first touch):} $T_1$ inserts \texttt{(id=2, bal=300)} on Block~7. Because prior $\texttt{pd\_lsn} = \texttt{0/0E20} \le \texttt{0/1000}$, PostgreSQL logs \texttt{INSERT} with a \textbf{Full Page Image} ending at \texttt{0/1080}, stamping $\texttt{pd\_lsn} = \texttt{0/1080}$ in RAM.
  \item \textbf{\texttt{0/1140} ($T_1$, \texttt{xid=701}, delta update):} $T_1$ updates \texttt{id = 1} to \texttt{bal = 400} via a same-page \texttt{HOT\_UPDATE}. Because prior $\texttt{pd\_lsn} = \texttt{0/1080} > \texttt{0/1000}$, PostgreSQL logs only a 64-byte delta ending at \texttt{0/1140}.
  \item \textbf{\texttt{0/1190} ($T_2$, \texttt{xid=702}, uncommitted insert):} Concurrent session~$T_2$ inserts \texttt{(id=3, bal=999)} on Block~7 via a 58-byte delta ending at \texttt{0/1190}. Session~$T_2$ has \emph{not} committed yet.
  \item \textbf{\texttt{0/1210} ($T_1$ commits):} $T_1$ runs \texttt{COMMIT}, logs \texttt{COMMIT} for \texttt{xid=701}, and calls \texttt{XLogFlush(0/1210)}. Client~$T_1$ receives \texttt{COMMIT}.
  \item \textbf{\texttt{0/1230} (Checkpoint ends) \& \texttt{0/1260} (Torn write + power cut):} \texttt{checkpointer} logs \texttt{XLOG\_CHECKPOINT\_ONLINE} (\texttt{redo = 0/1000}) at \texttt{0/1230} and updates \texttt{pg\_control}. Moments later, \texttt{bgwriter} flushes Block~7 (\texttt{pd\_lsn = 0/1190})---allowed since WAL is synced past \texttt{0/1230}---and \textbf{power cuts mid-write}:
    \begin{itemize}
      \item On disk, \textbf{Block~7 is torn}: Sector~0 has \texttt{pd\_lsn = 0/1190} and three slot pointers, while Sector~1 still holds stale pre-\texttt{0/1000} bytes.
      \item In \texttt{pg\_wal}, $T_2$ was writing another record at \texttt{0/1260}; only 40 bytes reached flash, leaving a broken \texttt{xl\_crc}.
    \end{itemize}
\end{enumerate}

Look closely at row~2 (\texttt{0/1080}) of Table~\ref{ch04:tab-recovery-walk}. Had \texttt{0/1080} been a delta instead of an FPI, recovery would have read torn Block~7, seen Sector~0's \texttt{pd\_lsn = 0/1190}, skipped all three edits, and left Sector~1 full of garbage. Instead, \texttt{BLK\_RESTORED} replaced the torn disk block in RAM at \texttt{0/1080} and replayed \texttt{0/1140} and \texttt{0/1190} cleanly on top. Meanwhile, $T_2$'s uncommitted row \texttt{(id=3, bal=999)} stays harmlessly hidden behind \texttt{t\_xmin = 702}.

\begin{labbox}
In PostgreSQL~15 and later, the built-in \texttt{pg\_walinspect} extension lets you watch this exact FPI-then-delta transition live inside SQL without even leaving \texttt{psql}:

\begin{lstlisting}[language=SQL]
CREATE EXTENSION IF NOT EXISTS pg_walinspect;

CREATE TABLE wal_demo (id int PRIMARY KEY, bal int);
INSERT INTO wal_demo VALUES (1, 500);

-- Force a checkpoint so RedoRecPtr advances past wal_demo's current pd_lsn:
CHECKPOINT;

-- Capture LSN right after the checkpoint, then touch Block 0 TWICE:
SELECT pg_current_wal_lsn() AS start_lsn \gset
BEGIN;
INSERT INTO wal_demo VALUES (2, 300);            -- 1st touch -> logs an FPI!
UPDATE wal_demo SET bal = 400 WHERE id = 1;      -- 2nd touch -> tiny delta!
COMMIT;
SELECT pg_current_wal_lsn() AS end_lsn \gset

SELECT start_lsn, end_lsn, xid, resource_manager AS rmgr,
       record_type, record_length AS rec_len, fpi_length AS fpi_len
FROM pg_get_wal_records_info(:'start_lsn', :'end_lsn')
WHERE resource_manager IN ('Heap', 'Transaction');
\end{lstlisting}

Running this snippet produces output structured right along our theoretical trace:
\begin{lstlisting}[language=SQL]

-- -----------+-----------+-----+-------------+-------------+---------+---------
--  0/19420A8 | 0/1942150 | 745 | Heap        | INSERT      |     168 |     120
--  0/19421A0 | 0/19421E8 | 745 | Heap        | HOT_UPDATE  |      72 |       0
--  0/19421E8 | 0/1942210 | 745 | Transaction | COMMIT      |      40 |       0
\end{lstlisting}
Check the \texttt{fpi\_len} column. On the first edit after \texttt{CHECKPOINT}, \texttt{fpi\_len} is \texttt{120}~bytes: the 24-byte header, two 4-byte slot pointers, and two 44-byte rows, with the free-space hole stripped out. Total record size is $168$~bytes once you add the 24-byte \texttt{XLogRecord} header and block metadata. Twenty microseconds later, \texttt{HOT\_UPDATE} touches that same page and logs \texttt{fpi\_len = 0}---just a 72-byte delta, followed by a 40-byte \texttt{COMMIT}. Offline, you can inspect raw segment files with \texttt{pg\_waldump -p PGDATA/pg\_wal 000000010000000000000001}.
\end{labbox}

\begin{complexitybox}
\textbf{Cost Summary of PostgreSQL WAL \& Crash Recovery:}
\begin{itemize}
  \item \textbf{\texttt{COMMIT} I/O (\texttt{synchronous\_commit = on}):} $1$ sequential \texttt{write()} + $1$ \texttt{fdatasync()} shared across $K$ concurrent committers ($O(1/K)$ sync calls per transaction; zero random heap/index \texttt{fsync}s).
  \item \textbf{Per-row WAL size:} $\sim 55$--$90$ bytes per heap/B-tree delta; $+ (8{,}192 - \text{hole})$ bytes (or $\sim 0.3\times$ compressed with \texttt{lz4}) on \emph{only the first touch} per 8~KB block per checkpoint.
  \item \textbf{Crash recovery time:} $O(\text{WAL bytes since } \mathrm{RedoRecPtr})$ in a single forward scan, plus \textbf{$O(1) = 0$ Undo work} regardless of how many rows crashed transactions modified.
\end{itemize}
\end{complexitybox}

Everything in this chapter gives PostgreSQL a rock-solid physical floor: 8~KB pages never tear, committed rows never vanish, and crashed uncommitted writes sit behind \texttt{pg\_xact} status \texttt{00}. That sets up our next big question. When twenty queries read Block~7 at the same time, how does each query decide in nanoseconds which row versions belong to its snapshot? And who eventually reclaims dead rows like $T_2$'s aborted \texttt{(id=3, bal=999)} without blocking readers? That is the story of Multi-Version Concurrency Control, snapshots, and \texttt{VACUUM} in Chapter~5.

\section{Exercises}
\label{ch04:exercises}

\begin{exercise}[\texttt{pg\_lsn} hex arithmetic and 24-character segment filenames]
\label{ch04:ex-lsn-segments}
Consider two WAL positions $L_a = \texttt{2/FE800028}$ and $L_b = \texttt{3/24001A8}$ on timeline $T = 2$ with the default 16~MB segment size (\texttt{0x01000000} bytes):
\begin{enumerate}
  \item Write $L_a$ and $L_b$ as 64-bit hex integers and compute $\texttt{pg\_wal\_lsn\_diff}(L_b, L_a)$ in hex and decimal. How many 16~MB segment boundaries does $[L_a, L_b]$ cross?
  \item Using Definition~\ref{ch04:def-lsn}, give the 24-character filename in \texttt{PGDATA/pg\_wal/} and the decimal byte offset inside that file for $L_a$ and $L_b$.
  \item Repeat part~(2) for \texttt{initdb --wal-segsize=64} (64~MB segments $= \texttt{0x04000000}$ bytes, or $64 = \texttt{0x40}$ segments per 4~GB chunk).
\end{enumerate}
\end{exercise}

\begin{exercise}[Hole-stripped FPI byte budget and checkpoint WAL amplification]
\label{ch04:ex-fpi-amplification}
An 8,192-byte heap page holds $20$ live rows of $120$~bytes each and zero dead slots. Recall that \texttt{PageHeaderData} is $24$~bytes and each slot pointer is $4$~bytes.
\begin{enumerate}
  \item Compute \texttt{pd\_lower}, \texttt{pd\_upper}, the free-space hole length, and the uncompressed size of the hole-stripped FPI (plus $28$~bytes of record and image headers).
  \item Suppose an app runs $50$ single-row \texttt{HOT\_UPDATE} commits on this page. In-page pruning keeps live row bytes at $2{,}400$~bytes, and each non-FPI \texttt{HOT\_UPDATE} + \texttt{COMMIT} pair logs $72 + 40 = 112$~bytes. Compare total WAL bytes when (a) zero checkpoints start during the burst versus (b) a tiny \texttt{max\_wal\_size} starts a checkpoint every $10$ updates. How much does \texttt{wal\_compression = lz4} ($3\colon 1$ on FPIs) save in case~(b)?
\end{enumerate}
\end{exercise}

\begin{exercise}[Proving both failure cases of delta replay without \texttt{full\_page\_writes}]
\label{ch04:ex-prove-torn-failure}
Suppose an admin sets \texttt{full\_page\_writes = off} on \texttt{ext4} over a 4Kn NVMe SSD. Block~4 sits cleanly on disk at $\texttt{pd\_lsn} = \texttt{0/5000}$ with $\texttt{pd\_upper} = 8000$.
\begin{enumerate}
  \item Build a two-record WAL sequence: \texttt{0/5060} compacts rows via \texttt{PageRepairFragmentation}, and \texttt{0/50C0} inserts a 64-byte row. Prove step-by-step why replay corrupts Block~4 both when Sector~0 (\texttt{0..4095}) lands without Sector~1 (\texttt{4096..8191}) and when Sector~1 lands without Sector~0.
  \item With \texttt{initdb --data-checksums} enabled, does \texttt{pd\_checksum} let PostgreSQL \emph{repair} Block~4 without an FPI, or only stop with an error? Explain why.
\end{enumerate}
\end{exercise}

\begin{exercise}[Violating the WAL Invariant]
\label{ch04:ex-break-wal-rule}
Suppose you delete the \texttt{XLogFlush(lsn)} check inside \texttt{FlushBuffer()}. Uncommitted transaction~$T_9$ (\texttt{xid = 880}) splits B-tree leaf Block~10 into Block~10 and new Block~25 at LSN \texttt{0/7400} while \texttt{Flush} sits at \texttt{0/7100}. Next, \texttt{bgwriter} writes Block~10 (not Block~25) cleanly to flash, and power fails before \texttt{wal\_buffers} flushes past \texttt{0/7100}.
\begin{enumerate}
  \item Trace \texttt{StartupXLOG()} on reboot. What is the highest LSN replayed?
  \item Even though Block~10 did not tear and $T_9$ never committed, prove that index scans for rows committed \emph{hours earlier} can now miss rows or fail with missing-block errors. Why didn't MVCC save you?
\end{enumerate}
\end{exercise}

\begin{exercise}[Hand-tracing a multi-page crash recovery table]
\label{ch04:ex-trace-recovery}
After a power outage, \texttt{global/pg\_control} points to a checkpoint at \texttt{0/9200} with \texttt{redo = 0/9000} and \texttt{nextXid = 500}. On disk right after the crash:
\begin{itemize}
  \item Heap Block~3 is intact at $\texttt{pd\_lsn} = \texttt{0/8F00}$ with \texttt{(k='a', v=10)}.
  \item Heap Block~8 is \textbf{torn}: Sector~0 has $\texttt{pd\_lsn} = \texttt{0/9180}$, while Sector~1 holds stale bytes from \texttt{0/8D00}.
\end{itemize}
The WAL stream from \texttt{0/9000} holds eight records:
\begin{enumerate}
  \item \texttt{0/9060} (\texttt{xid=501}): \texttt{HEAP INSERT} + \textbf{FPI} on Block~8 (restores \texttt{(k='b', v=20)}).
  \item \texttt{0/90C0} (\texttt{xid=502}): \texttt{HEAP INSERT} + \textbf{FPI} on Block~3 (adds \texttt{(k='c', v=30)}).
  \item \texttt{0/9120} (\texttt{xid=501}): \texttt{HEAP HOT\_UPDATE} delta on Block~8 (\texttt{k='b'} updated to \texttt{v=25}).
  \item \texttt{0/9160} (\texttt{xid=502}): \texttt{XACT\_ABORT}.
  \item \texttt{0/9180} (\texttt{xid=503}): \texttt{HEAP INSERT} delta on Block~8 (adds \texttt{(k='d', v=40)}).
  \item \texttt{0/91C0} (\texttt{xid=501}): \texttt{XACT\_COMMIT}.
  \item \texttt{0/9200} (\texttt{xid=0}): \texttt{XLOG\_CHECKPOINT\_ONLINE} (\texttt{redo = 0/9000}).
  \item \texttt{0/9250} (\texttt{xid=503}): \texttt{XACT\_COMMIT} --- \textbf{truncated mid-record (\texttt{xl\_crc} mismatch)}.
\end{enumerate}
Build a trace table like Table~\ref{ch04:tab-recovery-walk} showing the \texttt{XLogRedoAction} for each record, the final \texttt{pd\_lsn} of Blocks~3 and~8, and the \texttt{pg\_xact} bits for XIDs \texttt{501}, \texttt{502}, and \texttt{503}. Which \texttt{(k, v)} rows does \texttt{SELECT * FROM t ORDER BY k} return after recovery? Under \texttt{synchronous\_commit = on}, could client \texttt{503} have received a \texttt{COMMIT} reply before power died?
\end{exercise}

\begin{exercise}[Group commit throughput and \texttt{synchronous\_commit} failure windows]
\label{ch04:ex-group-commit}
A primary runs on a cloud volume where \texttt{fdatasync()} takes $L_{\text{sync}} = 1.25\;\text{ms}$. Copying a transaction's WAL bytes into \texttt{wal\_buffers} takes $25\;\mu\text{s}$ of CPU across $8$ \texttt{WALInsertLocks}.
\begin{enumerate}
  \item With one sequential client ($C = 1$) and \texttt{synchronous\_commit = on}, what is the max \texttt{COMMIT/s}?
  \item With $C = 64$ concurrent clients running one-row transactions under \texttt{synchronous\_commit = on}, find (a) \texttt{fdatasync()} calls per second, (b) average commits per leader flush, and (c) the new throughput ceiling (comparing \texttt{fdatasync} against the $8$-lock insertion limit).
  \item Suppose a synchronous standby sits $2.0\;\text{ms}$ away (round-trip). For each \texttt{synchronous\_commit} mode in Table~\ref{ch04:tab-sync-commit}, give client commit latency and state whether acknowledged commits can be lost on (i) primary kernel panic, (ii) primary power loss, or (iii) permanent primary SSD loss.
\end{enumerate}
\end{exercise}

\begin{exercise}[Sizing \texttt{max\_wal\_size} and checkpointer I/O bandwidth]
\label{ch04:ex-checkpoint-sizing}
An OLTP cluster has \texttt{shared\_buffers = 32GB}, emits WAL at $R_{\text{wal}} = 45\;\text{MB/s}$, and dirties $14.4\;\text{GB}$ of buffers per checkpoint. Settings are \texttt{checkpoint\_timeout = 20min} and \texttt{checkpoint\_completion\_target = 0.9}.
\begin{enumerate}
  \item Find the WAL written per 20-minute interval. Using the $(1 + \texttt{checkpoint\_completion\_target})$ rule, compute the minimum \texttt{max\_wal\_size} (plus $20\%$ burst headroom) so checkpoints trigger by time rather than WAL volume.
  \item Compute the average write rate---in MB/s and in 8~KB I/O operations per second (IOPS)---that \texttt{checkpointer} sends to the OS across its spread window ($0.9 \times 1{,}200\;\text{s}$).
  \item Suppose power fails one second \emph{before} Checkpoint~$k+1$ writes its checkpoint record. How many gigabytes of WAL must \texttt{StartupXLOG()} scan on reboot, and how long does recovery take at $600\;\text{MB/s}$?
\end{enumerate}
\end{exercise}
