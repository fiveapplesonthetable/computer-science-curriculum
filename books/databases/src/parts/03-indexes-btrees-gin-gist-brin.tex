\chapter{Indexes: Lehman-Yao B-Link Trees, GIN, GiST, and BRIN}
\label{ch:indexes}

At the end of Chapter~2, we left our rows inside 8,192-byte slotted heap pages. Every row lives at a 6-byte physical address $\texttt{ctid} = (\text{block}, \text{slot})$: a 32-bit page number paired with a 16-bit slot number. Hand PostgreSQL $\texttt{ctid} = (8412, 9)$, and it pins page~8,412 in RAM, reads slot~9, and returns the row in microseconds.

The trouble is that SQL queries never hand you a \texttt{ctid}. An API request asks for every posting of \texttt{account\_id = 4291804} since October~1, or the user matching \texttt{email = 'ada@lovelace.org'}. Because heap pages place new rows wherever the Free Space Map finds room, rows have no physical order on disk. Without a separate lookup structure mapping column values to \texttt{ctid}s, PostgreSQL has only one option: read page~0, check every row, read page~1, and keep scanning to the end of the file.

\begin{focusbox}
This chapter builds PostgreSQL's indexes from the ground up and shows how to pick the right index for each query shape:
\begin{itemize}
  \item Why does a binary search tree stall on disk, and how does packing ~350 keys into one 8~KB B+tree page reach 100~million rows in three hops?
  \item How can hundreds of readers search a B-tree at full speed while writers are splitting pages right underneath them, without deadlocking?
  \item In a multi-column index, why does putting an equality column before a range column read one tight slice, while flipping the order scans thousands of cold pages?
  \item How can PostgreSQL answer a query from the index alone (\emph{Index-Only Scan}) when index entries carry zero transaction visibility stamps?
  \item When does a B-tree hit a wall, and when should you reach for a partial index, expression index, Hash, GIN, GiST, or BRIN instead?
\end{itemize}
\end{focusbox}

\chapterline

\section{Why Secondary Indexes Exist and B+Tree Branching Math}
\label{sec:ch03-fanout-math}

Put concrete numbers on that full-table scan first. Suppose \texttt{postings} holds $N = 100{,}000{,}000$ ($10^8$) rows. Each row stores an ID, account ID, amount, timestamp, currency, and status---72 payload bytes plus the 24-byte row header, or 96~bytes. Adding the 4-byte slot pointer brings each row to 100~bytes. An 8,192-byte page has 8,168 usable bytes after its 24-byte page header, so each page packs $\floor{8168 / 100} = 81$ rows.

Across $10^8$ rows, the table spans
\[
  \ceil*{\frac{100{,}000{,}000}{81}} = 1{,}234{,}568 \text{ pages} \times 8{,}192\text{ bytes} \approx 10.11\text{ GB}.
\]
Even on a fast NVMe drive streaming at $2.5\text{ GB/s}$, reading $10.11\text{ GB}$ for one lookup takes four seconds. At 500 lookups per second, the server would need 2,000 seconds of disk work every second.

\subsection{Why Binary Search Trees Lose Badly on Block Devices}

Your algorithms instinct says: build a balanced binary search tree over the keys. For $N = 10^8$, a red-black tree has height $\ceil{\log_2(10^8)} = 27$. Twenty-seven register comparisons take less than a microsecond. That is how Java's \texttt{TreeMap} works in RAM, where chasing an object reference costs nanoseconds.

On disk, comparisons are nearly free and \emph{page misses} dominate everything. Storage drives and \texttt{shared\_buffers} move data in 8,192-byte pages, not 32-byte nodes. As binary-tree nodes are allocated over months of random writes, parent and child nodes land on scattered pages. Even if the top 10 levels sit in RAM, walking the remaining 17 levels triggers 17 random 8~KB NVMe reads in sequence. At $70~\mu\text{s}$ per read, that stalls for $1.2\text{ ms}$---hauling 8,160 wasted bytes across the bus just to read one 8-byte key and two child pointers.

Rudolf Bayer and Edward McCreight solved this in 1970 by sizing each tree node to match a full disk page. In a \textbf{B+tree}, each 8~KB internal page packs \emph{hundreds} of separator keys and child page numbers, while all row pointers (\texttt{ctid}s) live at the bottom leaf level. Every step down the tree divides the remaining search space by roughly $350$ instead of $2$.

\begin{example}[Exact Fanout Arithmetic on an 8~KB \texttt{nbtree} Page]
\label{ex:ch03-fanout}
Let us count the bytes inside an 8,192-byte PostgreSQL B-tree (\texttt{nbtree}) internal page indexing an 8-byte \texttt{BIGINT} column such as \texttt{account\_id}:
\begin{itemize}
  \item \textbf{Usable space per page:} Subtracting the 24-byte page header at the top and a 16-byte sibling-link footer at the bottom ($\texttt{pd\_special} = 8176$) leaves $8{,}192 - 40 = 8{,}152$ bytes.
  \item \textbf{Bytes per index entry:} Each entry takes a 4-byte slot pointer plus a 16-byte index record: an 8-byte entry header (6~bytes for the target block/slot plus 2~bytes of length/null flags) followed by the 8-byte \texttt{BIGINT} key. Because $16$ is already a multiple of 8, no alignment padding is added. Each entry costs $4 + 16 = 20$~bytes.
  \item \textbf{Branching factor $B$:} Reserving one 20-byte slot for the page's upper-bound key leaves $\floor{8132 / 20} = 406$ child links on a packed page. After splits ($70\text{--}95\%$ fill) or with slightly wider keys, an everyday internal page averages roughly $B \approx 350$ children.
\end{itemize}
Watch how fast powers of $350$ grow as we step down from the root:
\begin{center}
\small
\begin{tabular}{@{}lrrl@{}}
\toprule
\textbf{Tree Level} & \textbf{Pages} & \textbf{Size ($8\text{ KB/pg}$)} & \textbf{Where It Lives in Production} \\
\midrule
Level~2 (Root page) & $1$ & $8\text{ KB}$ & Permanently hot in \texttt{shared\_buffers} \\
Level~1 (Internal) & $350$ & $2.73\text{ MB}$ & Permanently hot in \texttt{shared\_buffers} \\
Level~0 (Leaves, $350^2$) & $122{,}500$ & $957.03\text{ MB}$ & Hot subset in RAM; cold on NVMe \\
\bottomrule
\end{tabular}
\end{center}
By default, PostgreSQL leaves $10\%$ free room on new leaf pages (\texttt{fillfactor = 90}) to absorb future inserts. Each leaf page holds $\floor{0.90 \times 8132 / 20} = 365$ \texttt{(account\_id, ctid)} pairs. Multiply $122{,}500$ leaves by $365$ pairs: \textbf{three index levels cover $44.7$~million rows.} Add just one more internal level ($350^3$ leaves, with all non-leaf pages totaling $\approx 960\text{ MB}$ in RAM) and four levels cover \textbf{15.6~billion rows}.
\end{example}

Pause on the RAM column of Example~\ref{ex:ch03-fanout}. To find one row out of $44.7$~million:
\begin{enumerate}
  \item Pin the root page (in RAM, $0$ disk reads) and binary-search 350 keys ($9$ comparisons) to pick 1 of 350 level-1 pages.
  \item Pin that level-1 page (part of a $2.73\text{ MB}$ slice that stays in RAM, $0$ disk reads) and run 9 comparisons to pick 1 of $122{,}500$ leaf pages.
  \item Pin the leaf page (at most $1$ NVMe read if cold) and binary-search 365 entries to get $\texttt{ctid} = (8412, 9)$.
  \item Pin table page~8,412 (at most $1$ NVMe read if cold) and read slot~9.
\end{enumerate}
Instead of reading $1{,}234{,}568$ pages ($10.11\text{ GB}$), PostgreSQL pins \textbf{4 buffers} and does \textbf{0 to 2 NVMe reads} ($16\text{ KB}$ worst case)---a $630{,}000\times$ drop in I/O.

\subsection{Inside an 8~KB \texttt{nbtree} Page: \texttt{IndexTupleData} and \texttt{BTPageOpaqueData}}

PostgreSQL reuses Chapter~2's 8,192-byte slotted page layout for indexes too: the 24-byte page header sits at byte~0, and 4-byte slot pointers grow downward. Only two parts differ from a table page. First, each index entry starts with a tiny 8-byte header instead of a 23-byte row header. Second, the last 16~bytes of the page (\texttt{8176..8192}) hold left/right sibling page numbers and the page's tree level. In C (\texttt{src/include/access/itup.h} and \texttt{nbtree.h}), those two structs are \texttt{IndexTupleData} and \texttt{BTPageOpaqueData}:

\begin{lstlisting}[language=C]
/* 8-byte header prepended to every index entry (src/include/access/itup.h) */
typedef struct IndexTupleData {
    ItemPointerData t_tid;   /* 6 bytes: heap ctid on leaf, or child blkno on internal */
    unsigned short  t_info;  /* 2 bytes: bit 15 = has nulls, bit 14 = has varlena,
                                         bits 12..0 = tuple byte length (max 8191) */
} IndexTupleData;            /* Key column bytes follow immediately after t_info */

/* 16-byte trailer at offset 8176..8192 of every nbtree page (nbtree.h) */
typedef struct BTPageOpaqueData {
    BlockNumber btpo_prev;   /* 4 bytes: left sibling block (P_NONE = 0 if leftmost) */
    BlockNumber btpo_next;   /* 4 bytes: right sibling block (P_NONE = 0 if rightmost) */
    uint32      btpo_level;  /* 4 bytes: tree level (0 = leaf, >= 1 = internal;
                                         reused for xact epoch on deleted pages) */
    uint16      btpo_flags;  /* 2 bytes: BTP_LEAF, BTP_ROOT, BTP_META,
                                         BTP_DELETED, BTP_HALF_DEAD, BTP_INCOMPLETE_SPLIT */
    BTCycleId   btpo_cycleid;/* 2 bytes: vacuum cycle ID preventing split-scan races */
} BTPageOpaqueData;
\end{lstlisting}

Three details in those 24~bytes of C declarations matter:
\begin{itemize}
  \item \textbf{Dual use of \texttt{t\_tid}:} On a leaf page ($\texttt{btpo\_level} == 0$), \texttt{t\_tid} holds the 6-byte table \texttt{ctid} $(\text{block}, \text{slot})$. On an internal branch page ($\texttt{btpo\_level} \ge 1$), its 4-byte block field holds the \emph{child index page number}, while its 2-byte offset field packs status bits and column counts.
  \item \textbf{Dynamic root via Block~0's metapage:} Block~0 of every \texttt{nbtree} file is a small metadata page (\texttt{BTP\_META}) storing the current root block number (\texttt{btm\_root}) and tree height. When a single-leaf index splits, PostgreSQL allocates a new root block and updates \texttt{btm\_root}. Sessions cache that root block number locally so normal lookups skip Block~0 completely.
  \item \textbf{Doubly-linked sibling chains (\texttt{btpo\_prev} and \texttt{btpo\_next}):} Every level---especially leaf level~0---forms a doubly-linked horizontal ribbon of sorted pages. Once a range scan lands on its starting key, it \emph{never climbs back up to parent pages}. Forward scans (\texttt{ASC}) walk right via \texttt{btpo\_next}; backward scans (\texttt{DESC}) walk left via \texttt{btpo\_prev}.
\end{itemize}

\begin{intuitionbox}
\textbf{Why B+trees keep table pointers strictly at the leaves.} In Bayer's original 1970 B-tree, internal nodes carried row pointers too. A B+tree turns internal nodes into pure \emph{road signs} (separator keys + child block numbers), putting every key-to-\texttt{ctid} pair in the leaf chain. That pays off twice: internal nodes stay narrow so fanout $B$ stays huge, and a 5,000-row range scan walks straight across neighboring leaves instead of zigzagging up and down the tree.
\end{intuitionbox}

\section{From Textbook B+Trees to PostgreSQL's Lehman--Yao B-Link Tree}
\label{sec:ch03-lehman-yao}

A textbook B+tree flies on one thread. Now run 128 concurrent worker processes inserting orders and reading balances at 80,000 transactions per second. Under a textbook locking rule, all 128 cores quickly pile up waiting on a single 64-byte cache line: the page lock on the root node.

\subsection{Why Naive Top-Down Latch Crabbing Limits Multi-Core Scaling}

First see what breaks if two sessions touch a B+tree with no coordination at all:
\begin{enumerate}
  \item \textbf{Reader vs.\ concurrent leaf split:} Reader $Q$ checks parent $R$, sees that keys in $(40, 100]$ live on leaf $P$ (block~17), and pauses $2~\mu\text{s}$ before pinning block~17. In those $2~\mu\text{s}$, Writer $W$ fills block~17 and splits it into block~17 covering $(40, 60]$ and new block~41 covering $(60, 100]$, moving $\{71, 82, 85, 94\}$ to block~41. When Reader $Q$ wakes up and checks block~17 for $k = 85$, key $85$ is gone. A naive reader falsely reports that committed account $85$ does not exist.
  \item \textbf{Cascading splits upward:} When Writer $W$ inserts into a full leaf $P$, splitting $P$ adds a separator key to parent $R$. If $R$ is also full, $R$ splits too, cascading all the way up to the root.
\end{enumerate}

Textbooks prevent this with \textbf{latch crabbing} (hand-over-hand locking):
\begin{itemize}
  \item A \emph{reader} locks parent $R$, locks child $P$, and \emph{only then} unlocks $R$.
  \item A \emph{writer} holds exclusive locks down its ancestor chain until it reaches a node with spare room (so a lower split cannot cascade past it). Even optimistic variants force writers to re-walk from the root under exclusive locks whenever internal nodes fill up.
\end{itemize}

Holding two locks at every step hurts multi-core scaling. Even shared read locks execute atomic increments on the root buffer's header, bouncing that cache line across CPU sockets twice per lookup. Worse, holding a parent lock while waiting on an NVMe read stalls every writer under that parent.

In Java~6 terms, latch crabbing is nested \texttt{synchronized (parent) \{ synchronized (child) \{ ... \} \}}. Java~6's \texttt{ConcurrentSkipListMap} takes the smarter path: readers walk without locks, and writers publish new links atomically so an in-flight reader can always follow the chain rightward. Philip Lehman and S.~Bing Yao brought that exact idea to disk B-trees in 1981.

\subsection{The Lehman--Yao Insight: \texttt{P\_HIKEY} and Right-Links (\texttt{btpo\_next})}

Lehman and Yao's \textbf{B-link tree} (extended to page deletion by Lanin and Shasha in 1986) powers PostgreSQL's \texttt{nbtree} (\texttt{src/backend/access/nbtree/README}).

They asked one question: \emph{why did Reader $Q$ get lost when Leaf $P$ split?} Block~17 was missing two local clues:
\begin{enumerate}
  \item Looking only at block~17, $Q$ could not tell that key $85$ \emph{used} to belong here and had moved right.
  \item Even if $Q$ knew $85$ moved right, $Q$ had no direct pointer from block~17 to new block~41 while parent $R$ was still un-updated.
\end{enumerate}

The B-link tree fixes both by storing an explicit upper-bound key and a right-neighbor link on every page:

\begin{definition}[Lehman--Yao B-Link Page Invariants in PostgreSQL]
\label{def:ch03-blink-invariants}
Every live \texttt{nbtree} page $P$ (leaf or internal) maintains two local fields inside its 8~KB block:
\begin{enumerate}
  \item \textbf{Right-sibling link (\texttt{btpo\_next}):} Every non-rightmost page stores the block number of its right neighbor at the same level. When $P$ splits into $P$ and $P'$, $P.\texttt{btpo\_next}$ points to $P'$ \emph{before} $P$ is unlocked.
  \item \textbf{Explicit High Key (\texttt{P\_HIKEY}, slot~1):} On every non-rightmost page, slot~1 stores an upper-bound key $K_{\text{high}}$ rather than data. Every key on $P$ satisfies $k \le K_{\text{high}}$. Any lookup arriving at $P$ with $k > K_{\text{high}}$ knows $P$ split and steps right via \texttt{btpo\_next}. Real data entries start at slot~2 (or slot~1 on the rightmost page, whose upper bound is $+\infty$).
\end{enumerate}
\end{definition}

\begin{historybox}
\textbf{From Berkeley Postgres to Lehman--Yao.} Early university Postgres used simpler B-tree locking that bottlenecked under multi-user load. Paul Aoki and Mike Olson replaced it with the Lehman--Yao \texttt{nbtree} (``New B-Tree'') in the early 1990s. Tom Lane later added Lanin--Shasha page deletion, and Peter Geoghegan added \texttt{ctid} tie-breaking, suffix truncation, deduplication, and bottom-up deletion across PostgreSQL~12--14.
\end{historybox}

\subsection{Step-by-Step Trace: A Concurrent Reader Crossing an Unfinished Split}

Let us trace every lock and pointer step with small numbers so you see how a reader crosses an unfinished split safely.

Suppose parent $R$ (block~4) routes keys in $(40, 100]$ to leaf $P$ (block~17) and keys $> 100$ to block~29. Leaf $P$ has $\texttt{P\_HIKEY} = 100$ at slot~1, data keys $\{42, 49, 55, 60, 71, 82, 94\}$ in slots~2..8, and $\texttt{btpo\_next} = 29$.

Writer $W$ arrives to insert $k = 85$ ($\texttt{ctid} = (912, 6)$), and Leaf $P$ is full:

\begin{enumerate}
  \item \textbf{Phase~1 of Split (Leaf Only):} Writer $W$ locks $P$ (block~17) exclusively and allocates a fresh page $P'$ (block~41), locking block~41 exclusively too. Notice $W$ holds \textbf{zero locks on parent $R$}. Splitting at $60$, $W$ rewrites both leaves in RAM:
  \begin{itemize}
    \item Right sibling $P'$ (block~41) gets the old high key ($\texttt{P\_HIKEY} = 100$), upper keys $\{71, 82, 85, 94\}$, $\texttt{btpo\_prev} = 17$, and $\texttt{btpo\_next} = 29$.
    \item Original leaf $P$ (block~17) keeps $\{42, 49, 55, 60\}$, lowers its high key to $\texttt{P\_HIKEY} = 60$, sets $\texttt{btpo\_next} = 41$, and sets \texttt{BTP\_INCOMPLETE\_SPLIT} as a reminder that parent $R$ still needs updating.
  \end{itemize}
  $W$ logs the split to WAL and \textbf{unlocks both block~17 and block~41}.

  \item \textbf{The Half-Split Window (Reader $Q$ Descends):} At this exact microsecond, the OS pauses $W$ before it touches parent $R$. Reader $Q$ runs \texttt{SELECT * FROM accounts WHERE account\_id = 85}:
  \begin{itemize}
    \item $Q$ takes a shared lock on parent $R$ (block~4), sees $40 < 85 \le 100 \implies \text{block } 17$, and \textbf{unlocks block~4 completely} before locking block~17. Between those two steps, $Q$ holds \textbf{zero page locks anywhere in the tree}.
  \end{itemize}

  \item \textbf{Stepping Right (\texttt{\_bt\_moveright}):} Reader $Q$ checks block~17's slot~1 (\texttt{P\_HIKEY}) before searching data slots:
  \[
    k = 85 \;>\; P.\texttt{P\_HIKEY} = 60 \quad\Longrightarrow\quad \text{Block~17 split after we read its parent.}
  \]
  Without touching parent $R$, $Q$ follows $\texttt{btpo\_next} = 41$ rightward (locking block~41 shared, then unlocking block~17). On block~41, $85 \le 100$ holds, so binary search finds $(85, \texttt{ctid}=(912, 6))$ at slot~4.

  \item \textbf{Phase~2 of Split (Parent Update):} Writer $W$ wakes up, locks parent $R$ (and briefly block~17 to clear \texttt{BTP\_INCOMPLETE\_SPLIT}), inserts downlink $(60 \to \text{blk } 41)$ into $R$, and unlocks. Future readers seeking $85$ jump straight from block~4 to block~41.
\end{enumerate}

\begin{whybox}
\textbf{Why Lehman--Yao cannot deadlock (even if the writer crashes mid-split).} Notice the lock order across the entire tree:
\begin{itemize}
  \item Descending readers hold \emph{at most one page latch at a time}: they release the parent latch before locking the child. A thread holding zero locks while requesting one cannot join a wait cycle.
  \item Horizontal \texttt{\_bt\_moveright} steps lock pages strictly \emph{left-to-right} ($\text{Blk } 17 \to \text{Blk } 41$). Splitting writers also lock siblings left-to-right and climb strictly \emph{bottom-up}: they release leaf locks before locking the parent. Because held latches form a strict directed acyclic graph, page-latch deadlocks cannot occur.
  \item Even if power fails right before the parent receives Block~41's pointer, the index stays $100\%$ accurate. Lookups for $(60, 100]$ simply take one extra \texttt{\_bt\_moveright} hop from Block~17 to Block~41. Later, the next split on that parent sees \texttt{BTP\_INCOMPLETE\_SPLIT} and inserts the missing downlink.
\end{itemize}
\end{whybox}

\begin{recoverybox}
\textbf{Pause and check the two split tricks.} Every non-rightmost index page stores its own upper-bound key (\texttt{P\_HIKEY}) plus a right-sibling link (\texttt{btpo\_next}). If a concurrent split moved keys away while you were stepping down from the parent, \texttt{key > P\_HIKEY} tells you immediately, and \texttt{btpo\_next} walks you right to the moved keys.
\end{recoverybox}

\subsection{Modern \texttt{nbtree} Engineering: Tie-Breaking, Deduplication, and Bottom-Up Deletion}

Classical B-link trees struggled with three common OLTP patterns until PostgreSQL~12, 13, and~14 fixed each one:

\begin{enumerate}
  \item \textbf{Unique keys via heap \texttt{ctid} tie-breaking (PG~12):} What happens when 2,000,000 rows share \texttt{status = 'PENDING'}? Older versions stored duplicates in arbitrary physical order across thousands of leaf pages, turning inserts into slow scans. Since PostgreSQL~12, \texttt{nbtree} uses the 6-byte row \texttt{ctid} as an implicit final tie-breaker. Every entry $(k, \texttt{ctid})$ is now globally unique, so binary search lands straight on the right leaf page in $O(\log N)$ time.
  \item \textbf{Posting-list deduplication (PG~13):} Fast duplicates were still wide: storing \texttt{'USD'} 365 times on one page repeated the key and header 365 times. With \texttt{deduplicate\_items = on} (default since PG~13), a full leaf page runs a compression pass before splitting. Identical keys merge into one \textbf{posting list tuple} (\texttt{BT\_IS\_POSTING}): one copy of \texttt{'USD'} followed by a packed array of 6-byte \texttt{ctid}s. That cuts status and foreign-key indexes by $3\times$ to $4\times$.
  \item \textbf{Bottom-up index deletion (PG~14):} Remember from Chapter~2 that updating a row writes a new version at a new \texttt{ctid}. Whenever \emph{any} indexed column changes, PostgreSQL cannot use a same-page HOT chain; it must insert a new entry into \emph{every} index on the table. Before PG~14, updating \texttt{last\_seen\_at} 50~times pushed 50 dead duplicate entries into \texttt{idx\_accounts\_email}, splitting leaf pages before \texttt{autovacuum} arrived. PostgreSQL~14 added \textbf{bottom-up index deletion}: right before a duplicate-driven split, \texttt{nbtree} checks the heap pages for those duplicates, reclaims dead slots in place, and cancels the split.
\end{enumerate}

\begin{labbox}
Inspect a real \texttt{nbtree} metapage, \texttt{P\_HIKEY} slot, and PG~13+ deduplicated posting list tuple using PostgreSQL's built-in \texttt{pageinspect} extension:

\section{Composite Index Lexicographic Geometry and Column Order}
\label{sec:ch03-composite-geometry}

Single-column B-trees are straightforward because numbers and timestamps already live on a 1D line. Real production queries, however, almost always filter on two or three dimensions at once:
\begin{lstlisting}[language=SQL]
SELECT posting_id, amount_cents, created_at
FROM postings
WHERE account_id = 42
  AND created_at >= '2026-10-01 00:00:00+00'
ORDER BY created_at DESC
LIMIT 20;
\end{lstlisting}
A B-tree leaf chain is strictly one-dimensional: every entry sits before or after its neighbor along a single ribbon of pages linked by \texttt{btpo\_next}. How do we map a 2D plane of $(\texttt{account\_id}, \texttt{created\_at})$ pairs onto that 1D ribbon? And why does \texttt{(account\_id, created\_at DESC)} finish in $0.08\text{ ms}$ while \texttt{(created\_at DESC, account\_id)} on the same two columns takes $450\text{ ms}$?

\subsection{The Phonebook Ribbon: Equality Pins a Slice, Range Scatters Jumps}

Suppose we build:
\begin{lstlisting}[language=SQL]
CREATE INDEX idx_postings_acct_created
    ON postings (account_id ASC, created_at DESC);
\end{lstlisting}
PostgreSQL compares two composite keys $(a_1, t_1)$ and $(a_2, t_2)$ in \textbf{lexicographic (dictionary) order}, just like sorting a phonebook by $(\text{Last Name}, \text{First Name})$:
\[
  (a_1, t_1) \prec (a_2, t_2)
  \quad\Longleftrightarrow\quad
  (a_1 < a_2) \;\lor\; \bigl(a_1 = a_2 \;\land\; t_1 > t_2\bigr),
\]
where the second inequality flips to $t_1 > t_2$ because we specified \texttt{created\_at DESC}. In Java~6 this is exactly the \texttt{Comparator} you would hand to \texttt{Collections.sort} or to a \texttt{TreeMap}:
\begin{lstlisting}[language=Java]
public int compare(Posting x, Posting y) {
    if (x.accountId != y.accountId)
        return x.accountId < y.accountId ? -1 : 1;  // ascending
    return y.createdAt.compareTo(x.createdAt);      // descending
}
\end{lstlisting}
The B-tree keeps its leaf entries in this order, so everything you know about a sorted \texttt{TreeMap} (cheap range scans with \texttt{subMap}, no help for a lookup on the second field alone) carries over directly.

Picture the resulting leaf pages stretched left-to-right across the floor. First come \emph{all} postings for \texttt{account\_id = 1}, sorted newest-to-oldest from 2026 back to 2019. Immediately after account~1's oldest 2019 posting sits account~2's newest 2026 posting, and so on.

Now trace two queries across that exact same leaf ribbon (illustrated side by side in Figure~\ref{fig:ch03-composite-ribbon}):

\begin{enumerate}
  \item \textbf{Equality first, range second (\texttt{account\_id = 42 AND created\_at >= '2026-10-01'}):}
  Fixing $\texttt{account\_id} = 42$ narrows the outer dimension to one contiguous slice of the ribbon. Inside that slice, \texttt{created\_at} runs strictly newest to oldest. PostgreSQL seeks straight to $(42, +\infty)$ and reads consecutive entries while $\texttt{created\_at} \ge \text{'2026-10-01'}$. The instant it hits the first entry older than October~1, it \textbf{stops}. Every index entry it touched matched both conditions.
  \item \textbf{Range first, filter second (\texttt{account\_id BETWEEN 41 AND 43 AND created\_at >= '2026-10-25'}):}
  Because the leading column spans a range, October~2026 timestamps are no longer adjacent on the ribbon. Account~41's late-October entries appear first, followed by \emph{seven years of older postings for account~41} (\texttt{2026-10-24} down to \texttt{2019-01-02}), before account~42's late-October entries finally start. A range scan from $(41, +\infty)$ to $(43, \text{'2026-10-25'})$ must walk across thousands of cold historical leaf pages in between, checking $\texttt{created\_at} \ge \text{'2026-10-25'}$ on every skipped entry.
\end{enumerate}

\begin{trapbox}
\textbf{\texttt{IN (...)} lists vs.\ true range inequalities.} PostgreSQL's B-tree executor has a shortcut for small discrete lists like \texttt{WHERE account\_id IN (41, 42, 43) AND created\_at >= '2026-10-25'}. Instead of trudging through seven years of account~41's history, \texttt{\_bt\_advance\_array\_keys()} sees the end of $(41, \text{'2026-10-25'})$ and jumps straight to $(42, +\infty)$. Once your leading filter is a continuous inequality (\texttt{amount\_cents > 50000} or \texttt{created\_at >= ...}), however, there is no short list of keys to jump across. Follow this column-ordering rule for composite B-trees:
\[
  \textbf{1.\ Equality } (\texttt{=}) \;\longrightarrow\; \textbf{2.\ Range / } \texttt{ORDER BY} \;\longrightarrow\; \textbf{3.\ } \texttt{INCLUDE} \textbf{ payload.}
\]
Ignore the folk rule ``always put the highest-cardinality column first.'' If your query writes \texttt{WHERE tenant\_id = p\_tenant AND status = 'OPEN' AND created\_at >= p\_since}, both \texttt{tenant\_id} and \texttt{status} are equality filters. Both belong ahead of the range column \texttt{created\_at}, even if \texttt{status} has only four distinct values.
\end{trapbox}

\subsection{Sort Elimination and Backward Leaf Scans}

Column order also decides whether PostgreSQL can stream \texttt{ORDER BY ... LIMIT} $k$ in $O(k)$ page reads without allocating a \texttt{Sort} buffer. Look at our opening query:
\begin{lstlisting}[language=SQL]
EXPLAIN (ANALYZE, BUFFERS)
SELECT posting_id, amount_cents, created_at
FROM postings
WHERE account_id = 42
  AND created_at >= '2026-10-01 00:00:00+00'
ORDER BY created_at DESC
LIMIT 20;
-- Limit  (cost=0.56..28.41 rows=20 width=24) (actual time=0.031..0.068 rows=20 loops=1)
--   Buffers: shared hit=22
--   -> Index Scan using idx_postings_acct_created on postings
--        Index Cond: ((account_id = 42) AND (created_at >= '2026-10-01 00:00:00+00'::timestamptz))
\end{lstlisting}
Notice what is \emph{missing} from that plan: there is \textbf{no \texttt{Sort} node}. Even if account~42 has $5{,}000{,}000$ postings in October, PostgreSQL seeks to $(42, +\infty)$, emits the first 20 live rows from the ribbon, and stops after 22 buffer hits in $68~\mu\text{s}$.

What if an analyst asks for \texttt{ORDER BY account\_id DESC, created\_at ASC} against our \texttt{(account\_id ASC, created\_at DESC)} index? Because \emph{every} column's direction flipped at once, the requested order is the exact mirror image of our leaf ribbon. PostgreSQL runs an \texttt{Index Scan Backward}, walking \texttt{btpo\_prev} links right-to-left with zero sorting. By contrast, asking for \texttt{ORDER BY account\_id ASC, created\_at ASC} flips only the second column. Neither forward nor backward walks produce that order, so the planner must add a \texttt{Sort} (or PG~13+'s \texttt{Incremental Sort}, which sorts one \texttt{account\_id} group at a time).

\section{Covering Indexes (\texttt{INCLUDE}), the Visibility Map, and True Index-Only Scans}
\label{sec:ch03-visibility-map}

Look again at the \texttt{EXPLAIN (ANALYZE, BUFFERS)} plan at the end of Section~\ref{sec:ch03-composite-geometry}: returning 20 rows from a 3-level B-tree touched \textbf{22 buffers}. Where did those 22 hits come from? Three were index pages (root, level~1, leaf), and 19 were separate 8~KB table pages. Even when 20 index entries sit side by side on one leaf page, their row \texttt{ctid}s point to 19 historical blocks scattered across a 10~GB table. If those blocks are cold on NVMe, summing \texttt{SUM(amount\_cents)} across 10,000 postings triggers up to 10,000 random 8~KB disk reads ($\approx 700\text{ ms}$).

That invites a natural question: \emph{if we store \texttt{amount\_cents} and \texttt{currency} right inside the leaf entry next to \texttt{(account\_id, created\_at)}, can PostgreSQL answer the query from the index alone?}

\subsection{Why PostgreSQL Index Tuples Carry Zero MVCC Visibility Metadata}

Engines built around \textbf{clustered primary indexes} (like MySQL's InnoDB or SQL Server) make the primary-key B+tree \emph{be} the table. Leaf pages hold full rows plus transaction IDs, while secondary indexes point to the primary key.

PostgreSQL made the opposite bet: tables are unclustered slotted heaps addressed by 6-byte \texttt{ctid}s. Crucially, \textbf{an index entry (\texttt{IndexTupleData}) carries zero transaction visibility fields (\texttt{t\_xmin}, \texttt{t\_xmax}, \texttt{t\_cid})}. Check \texttt{struct IndexTupleData} in Section~\ref{sec:ch03-fanout-math}: 6~bytes of \texttt{t\_tid}, 2~bytes of \texttt{t\_info}, and raw column bytes. Nothing else.

\begin{intuitionbox}
\textbf{Why omit \texttt{xmin} and \texttt{xmax} from every index?} Count the write cost if indexes stored transaction headers. Suppose your \texttt{orders} table has 6 secondary indexes. When a session runs \texttt{DELETE FROM orders WHERE order\_id = 991}, heap-only MVCC stamps \texttt{t\_xmax} on \emph{one} 8~KB table page---zero index pages are dirtied at \texttt{DELETE} time. If every index entry carried its own \texttt{t\_xmax}, every \texttt{DELETE} and update would have to descend and dirty all 6 indexes synchronously, multiplying random write I/O and WAL volume by $6\times$.
\end{intuitionbox}

Omitting \texttt{xmin} and \texttt{xmax} from indexes keeps writes fast, but it creates a read puzzle. When an index scan sees \texttt{(account\_id=42, amount\_cents=12500, ctid=(8412, 9))}, how does it know whether row \texttt{(8412, 9)} committed five days ago? What if it was inserted two microseconds ago by an uncommitted transaction, or already deleted by another session?

Before PostgreSQL~9.2, the answer was blunt: \emph{it didn't}, so PostgreSQL had to visit the table page on every index match without exception.

\subsection{How the Visibility Map (\texttt{\_vm}) Rescues Index-Only Scans}

PostgreSQL~9.2 solved that puzzle without adding a single byte to \texttt{IndexTupleData}. Instead, it enlisted the \textbf{Visibility Map (\texttt{\_vm})} fork we met in Chapter~2.

Inside \texttt{PGDATA/base/<dbOid>/<relfilenode>\_vm}, PostgreSQL keeps just \textbf{2~bits per 8~KB table page}:
\begin{itemize}
  \item Bit~0 (\texttt{VISIBILITYMAP\_ALL\_VISIBLE}): when set to $1$, \texttt{VACUUM} has verified that \emph{every live row on that 8~KB block is committed and visible to all current and future snapshots}. Any subsequent insert, update, or delete on that block clears bit~0 back to $0$.
  \item Bit~1 (\texttt{VISIBILITYMAP\_ALL\_FROZEN}): tells aggressive \texttt{VACUUM} it can skip already-frozen pages during transaction-ID wraparound maintenance (Chapter~5).
\end{itemize}
Check the compression ratio of that bitmap. Two bits per 8,192~bytes means 1~byte of \texttt{\_vm} covers 4 table pages ($32\text{ KB}$), and one 8~KB \texttt{\_vm} page tracks $\approx 32{,}640$ table blocks ($255\text{ MB}$). For our entire $10.11\text{ GB}$ \texttt{postings} table ($1{,}234{,}568$ pages), the whole \texttt{\_vm} file takes just $\ceil{1{,}234{,}568 / 4} \approx \mathbf{308\text{ KB}}$---38 pages pinned permanently in \texttt{shared\_buffers}.

When every column a query needs sits inside the index leaf entry, PostgreSQL's \texttt{IndexOnlyScan} runs a two-path check for each match $\texttt{ctid} = (\text{blk}, \text{off})$ (Figure~\ref{fig:ch03-ios-visibility-map}):
\begin{enumerate}
  \item Check bit~0 for \texttt{blk} inside the cached \texttt{\_vm} page.
  \item \textbf{Fast path ($\texttt{ALL\_VISIBLE} == 1$):} Every row on block \texttt{blk} is guaranteed visible. Emit the columns straight from the leaf entry and move on. \textbf{Zero table page pins, zero NVMe reads.}
  \item \textbf{Fallback path ($\texttt{ALL\_VISIBLE} == 0$):} A recent write touched block \texttt{blk} and cleared its bit. Pin table block \texttt{blk}, check slot \texttt{off}'s visibility headers against the query snapshot, emit the row if visible, and bump the \texttt{Heap Fetches} counter in \texttt{EXPLAIN (ANALYZE, BUFFERS)}.
\end{enumerate}

\subsection{Why \texttt{INCLUDE} Beats Appending Payload Columns to the Key}

Since PostgreSQL~11, you create a covering index using the \texttt{INCLUDE} clause:
\begin{lstlisting}[language=SQL]
CREATE INDEX idx_postings_acct_created_cov
    ON postings (account_id ASC, created_at DESC)
    INCLUDE (amount_cents, currency);
\end{lstlisting}
Why write \texttt{INCLUDE (amount\_cents, currency)} instead of putting all four columns inside the key list \texttt{(account\_id, created\_at, amount\_cents, currency)}? Two concrete wins separate them:
\begin{enumerate}
  \item \textbf{Suffix truncation keeps internal pages narrow (\texttt{\_bt\_truncate}):} When a leaf splits, PostgreSQL promotes a separator key into the parent page. On an \texttt{INCLUDE} index, \texttt{\_bt\_truncate()} strips \emph{all} non-key \texttt{INCLUDE} columns (plus any trailing key columns not needed to separate the two halves) before writing the parent entry. Upper branch pages store only \texttt{(account\_id, created\_at)}, keeping $B \approx 350$ even if you \texttt{INCLUDE} a 64-byte description.
  \item \textbf{Clean uniqueness constraints:} Suppose \texttt{users.email} must be unique and login runs \texttt{SELECT user\_id, pw\_hash FROM users WHERE email = p\_email}. Writing \texttt{CREATE UNIQUE INDEX ON users (email, user\_id, pw\_hash)} breaks your constraint: two users could register the same \texttt{email} with different \texttt{user\_id}s. Writing \texttt{CREATE UNIQUE INDEX ON users (email) INCLUDE (user\_id, pw\_hash)} enforces uniqueness strictly on \texttt{email} while making login a single-leaf Index-Only Scan.
\end{enumerate}

\begin{trapbox}
\textbf{When ``Index Only Scan'' in \texttt{EXPLAIN} is a mirage.} Never stop reading \texttt{EXPLAIN} at the title \texttt{Index Only Scan}. Always run \texttt{EXPLAIN (ANALYZE, BUFFERS)} and check the line right below it: \texttt{Heap Fetches}. By default, \texttt{autovacuum\_vacuum\_scale\_factor = 0.20} waits until $20\%$ of a table changes before running \texttt{VACUUM}. On a 100-million-row table, millions of recently written blocks sit with $\texttt{ALL\_VISIBLE} = 0$. Your plan prints \texttt{Index Only Scan}, yet \texttt{Heap Fetches: 48219} reveals it read 48,219 table blocks anyway. Lowering per-table \texttt{autovacuum\_vacuum\_scale\_factor = 0.01} (or \texttt{autovacuum\_vacuum\_insert\_scale\_factor = 0.005} on append-heavy ledgers) keeps \texttt{\_vm} bits set and drives \texttt{Heap Fetches} back to~$0$.
\end{trapbox}

\section{Partial Indexes (\texttt{WHERE ...}) and Expression Indexes}
\label{sec:ch03-partial-expression}

Every index we have built so far paid storage, \texttt{shared\_buffers} RAM, and write-ahead log tax for $100\%$ of the rows in the table. Yet many of the hottest queries in production care about a tiny, predictable fraction of rows.

\subsection{Partial Indexes: Shrinking a 4~GB Queue Index to 2~MB}

Consider a transactional outbox or webhook job table \texttt{jobs} holding $100{,}000{,}000$ historical delivery rows. At any moment, $99{,}950{,}000$ rows ($99.95\%$) have \texttt{status = 'processed'}, while only $50{,}000$ rows ($0.05\%$) have \texttt{status = 'pending'}. Every millisecond, worker threads poll for the oldest ready jobs:
\begin{lstlisting}[language=SQL]
SELECT job_id, payload
FROM jobs
WHERE status = 'pending' AND run_after <= NOW()
ORDER BY run_after ASC
LIMIT 50
FOR UPDATE SKIP LOCKED;
\end{lstlisting}
Compare a full composite index against a \textbf{partial index} carrying a \texttt{WHERE} filter:
\begin{lstlisting}[language=SQL]
-- Naive full index: indexes all 100,000,000 rows (~3.8 GB on disk!)
CREATE INDEX idx_jobs_full ON jobs (status, run_after);

-- Partial index: indexes ONLY the 50,000 pending rows (~1.9 MB on disk!)
CREATE INDEX idx_jobs_pending ON jobs (run_after ASC)
    WHERE status = 'pending';
\end{lstlisting}
Count the wins of \texttt{idx\_jobs\_pending}:
\begin{itemize}
  \item \textbf{$2{,}000\times$ smaller RAM footprint:} $50{,}000$ rows at $\sim 28$~bytes each (plus churn slack) fit in $\approx 240$ pages ($\sim 1.9\text{ MB}$). That whole index stays warm in L3 cache and \texttt{shared\_buffers} instead of evicting $3.8\text{ GB}$ of table pages. Notice we omitted \texttt{status} from the key list \texttt{(run\_after ASC)}: every entry in the index already satisfies \texttt{status = 'pending'}.
  \item \textbf{Zero maintenance on excluded rows:} When an audit job updates a \texttt{'processed'} row, neither old nor new row matches \texttt{status = 'pending'}. PostgreSQL skips \texttt{idx\_jobs\_pending} completely and preserves same-page HOT updates.
  \item \textbf{Conditional uniqueness:} Partial unique indexes express rules that plain SQL \texttt{UNIQUE} cannot. The index below lets a customer save many cards (\texttt{is\_primary = FALSE}) while guaranteeing at most one primary card:
\begin{lstlisting}[language=SQL]
CREATE UNIQUE INDEX uq_one_primary_card
    ON payment_methods (customer_id)
 WHERE is_primary = TRUE;
-- A second primary card for customer 42 fails with:
-- ERROR:  duplicate key value violates unique constraint "uq_one_primary_card"
-- DETAIL:  Key (customer_id)=(42) already exists.
\end{lstlisting}
\end{itemize}

One rule governs planner matching: \textbf{the query's \texttt{WHERE} clause must logically imply the index's \texttt{WHERE} filter} at plan time. A query writing \texttt{WHERE status = 'pending'} matches immediately. A generic prepared plan for \texttt{WHERE status = p\_status} cannot use \texttt{idx\_jobs\_pending} because \texttt{p\_status} could be \texttt{'processed'} at runtime; PostgreSQL~12+'s custom-plan mode can use it once the literal \texttt{'pending'} is bound.

\subsection{Expression Indexes and Syntactic Predicate Alignment}

What if login runs case-insensitive lookups or filters a scalar field inside a \texttt{JSONB} webhook payload?
\begin{lstlisting}[language=SQL]
-- A plain index on (email) CANNOT satisfy LOWER(email) = ...!
CREATE UNIQUE INDEX idx_users_email_lower ON users (LOWER(email));

-- Indexing a scalar TEXT value extracted from a JSONB column
-- Note the mandatory double parentheses around non-function expressions!
CREATE INDEX idx_webhooks_merchant ON webhooks ((payload->>'merchant_id'));
\end{lstlisting}
In an \textbf{expression index}, PostgreSQL evaluates the function during \texttt{INSERT}/\texttt{UPDATE} and stores the \emph{result} inside the index entry. Thus \texttt{idx\_users\_email\_lower} stores \texttt{'ada@lovelace.org'} even when the table row holds \texttt{'Ada@Lovelace.org'}. Better yet, \texttt{ANALYZE} collects dedicated histograms on the expression itself in \texttt{pg\_stats}, giving the planner accurate row estimates for \texttt{(payload->>'merchant\_id')}.

Two strict rules bite teams who deploy expression indexes carelessly:
\begin{enumerate}
  \item \textbf{Expressions must be \texttt{IMMUTABLE}:} Given identical input bytes, the function must return the exact same output forever, independent of session settings or wall-clock time. Indexing \texttt{DATE\_TRUNC('day', created\_at)} on a \texttt{TIMESTAMPTZ} column fails with \texttt{ERROR: functions in index expression must be marked IMMUTABLE}, because ``midnight'' depends on the session's \texttt{TimeZone} setting. Pin the zone explicitly: \texttt{DATE\_TRUNC('day', created\_at AT TIME ZONE 'UTC')} is \texttt{IMMUTABLE}.
  \item \textbf{Query predicates must match syntactically:} The planner does not prove arbitrary string-function equivalences. If your index is on \texttt{LOWER(email)}, writing \texttt{WHERE email ILIKE 'ada@lovelace.org'} or \texttt{WHERE UPPER(email) = 'ADA@LOVELACE.ORG'} walks right past the index into a \texttt{Seq Scan}. Write \texttt{WHERE LOWER(email) = LOWER(p\_email)}.
\end{enumerate}

\section{Beyond B-Trees: Hash, GIN, GiST, and BRIN}
\label{sec:ch03-beyond-btrees}

A Lehman--Yao B-link tree assumes one foundational property about your search predicate: \emph{every row maps to a single scalar (or tuple) key drawn from a totally ordered 1D domain ($<, \le, =, \ge, >$)}.

The moment your data violates that assumption, B-trees hit a geometric wall:
\begin{itemize}
  \item What if keys are 250-byte URLs queried \emph{only} for exact equality \texttt{=}?
  \item What if a single row contains \emph{50 distinct searchable tokens}---an array \texttt{tags TEXT[]}, a nested \texttt{JSONB} document, or a 300-word full-text \texttt{tsvector}?
  \item What if keys live in 2D space (polygons, GPS coordinates) or represent intervals (\texttt{tstzrange}) tested for \emph{overlap} (\texttt{\&\&}), where no 1D total order preserves containment?
  \item What if an append-only ledger holds $10\text{ billion}$ rows ($1\text{ TB}$) and you cannot afford $215\text{ GB}$ of B-tree pages just to slice time windows?
\end{itemize}
Rather than hard-wiring B-trees into the executor, Stonebraker and Rowe designed Postgres around an extensible \textbf{Access Method API} (\texttt{pg\_am} and \texttt{IndexAmRoutine}). Let us open the hood on the four companions sitting beside \texttt{nbtree} in \texttt{src/backend/access/}.

\subsection{Hash Indexes (\texttt{USING hash}): 32-Bit Codes Only}

A PostgreSQL Hash index (\texttt{src/backend/access/hash/}) arranges 8~KB pages into dynamic linear-hashing buckets, chaining overflow pages only when collisions fill a bucket. Its key space-saving trick is what it omits: \textbf{a Hash index never stores the raw column bytes.} Each entry stores only a \textbf{4-byte (32-bit) hash code} plus the 6-byte row \texttt{ctid} (16~bytes aligned, sorted by hash code inside each bucket page for binary search).

Put numbers on that. Indexing a 240-byte \texttt{webhook\_url} across $50{,}000{,}000$ rows builds a $\sim 13.5\text{ GB}$ B-tree, whereas \texttt{CREATE INDEX ON deliveries USING hash (webhook\_url)} takes just $\sim 1.1\text{ GB}$. Because two distinct strings can share a 32-bit hash, a Hash scan \emph{always} visits the table page to recheck \texttt{webhook\_url = p\_url}. Consequently, Hash indexes cannot run Index-Only Scans, enforce \texttt{UNIQUE}, sort \texttt{ORDER BY}, or span multiple columns.

\begin{marginnotebox}
Before PostgreSQL~10, manuals warned against Hash indexes because bucket splits were not WAL-logged---a crash required a manual \texttt{REINDEX}. Since PostgreSQL~10, Hash indexes are $100\%$ WAL-logged, crash-safe, and replicated. Reach for them when you have wide \texttt{TEXT} or \texttt{BYTEA} keys queried strictly with \texttt{=}.
\end{marginnotebox}

\subsection{GIN (Generalized Inverted Index): Multi-Element Containment at Scale}

Suppose a \texttt{payments} table stores gateway metadata in a \texttt{JSONB} column \texttt{meta}, and risk engineers filter with \texttt{meta @>} on \texttt{"card\_brand": "visa"} and \texttt{"three\_ds": "failed"}. Or suppose support searches ticket text via \texttt{WHERE body\_tsv @@ plainto\_tsquery('english', 'chargeback reversal')}. A B-tree on the whole \texttt{JSONB} document cannot help: \texttt{'three\_ds'} sits buried mid-document, not at byte~0.

A \textbf{GIN index} (\texttt{src/backend/access/gin/}) works like the subject index at the back of a book. Instead of mapping one row to one key, GIN calls \texttt{extractValue} to split each row into \emph{dozens of atomic tokens}---words like \texttt{'chargeback'} or JSONB fields. It then maps each distinct token to the sorted list of row \texttt{ctid}s containing it (Figure~\ref{fig:ch03-gin-vs-brin}, top):
\begin{enumerate}
  \item \textbf{The Entry Tree:} A standard B-tree over \emph{distinct tokens}. Across 50~million documents, English stems or JSONB keys often number only $\sim 200{,}000$, keeping the Entry Tree compact.
  \item \textbf{Posting List vs.\ Posting Tree:} When a rare token like \texttt{'chargeback'} appears in 40 rows, GIN packs those 40 \texttt{ctid}s inline as a \textbf{varbyte delta-compressed list} (2--3~bytes per \texttt{ctid}). When a frequent token like \texttt{'visa'} outgrows the inline limit ($\sim\texttt{GinMaxItemSize}$), GIN spills its list into a dedicated \textbf{Posting Tree} keyed by \texttt{(block, offset)}. Keeping \texttt{ctid}s sorted lets multi-word queries (\texttt{'visa' AND 'failed'}) intersect bitmaps in one linear pass and read table blocks sequentially.
  \item \textbf{The \texttt{fastupdate} Pending List:} Notice GIN's write cost: inserting one 60-field JSONB row would otherwise dirty up to 60 separate Entry Tree leaves. To avoid $60\times$ foreground write amplification, PostgreSQL enables \texttt{fastupdate = on} by default. New token/\texttt{ctid} pairs append sequentially to an unsorted \textbf{pending list} (up to \texttt{gin\_pending\_list\_limit}, default $4\text{ MB}$). Readers check both the Entry Tree and the tiny pending list until \texttt{VACUUM} (or an insert crossing $4\text{ MB}$) bulk-merges the pending list in one sorted batch.
\end{enumerate}

\begin{applicationbox}
\textbf{\texttt{jsonb\_ops} vs.\ \texttt{jsonb\_path\_ops} and OLTP latency spikes.} PostgreSQL ships two GIN operator classes for \texttt{JSONB}:
\begin{lstlisting}[language=SQL]
-- Default jsonb_ops: indexes every key AND value separately (supports @>, ?, ?|, ?&)
CREATE INDEX idx_pay_meta_default ON payments USING gin (meta);

-- jsonb_path_ops: hashes each full root-to-leaf path (e.g. hash('card_brand','visa'))
-- Supports @> containment ONLY, but is 2x-3x smaller and much faster when values repeat!
CREATE INDEX idx_pay_meta_paths   ON payments USING gin (meta jsonb_path_ops);

-- Full-text search via generated stored tsvector column + GIN
ALTER TABLE support_tickets
  ADD COLUMN search_tsv TSVECTOR
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(subject,'') || ' ' || coalesce(body,''))) STORED;
CREATE INDEX idx_tickets_fts ON support_tickets USING gin (search_tsv);
\end{lstlisting}
Watch out for one classic p99 tail-latency spike. When an \texttt{INSERT} pushes the \texttt{fastupdate} list past $4\text{ MB}$, \emph{that user's foreground session} synchronously flushes all $4\text{ MB}$ into the Entry Tree, stalling one API call for 50--300~ms. On strict p99 tables, lower \texttt{gin\_pending\_list\_limit = '1MB'} with aggressive \texttt{autovacuum}, or set \texttt{WITH (fastupdate = off)} when rows emit only 2--4 tokens.
\end{applicationbox}

\subsection{GiST (Generalized Search Tree): Bounding Hierarchies and Exclusion Constraints}

In 1995, Joseph Hellerstein, Jeffrey Naughton, and Avi Pfeffer posed a bold design question. Could one balanced-tree engine power 2D R-trees for maps, interval trees for bookings, and nearest-neighbor $k$-NN search without rewriting buffer locking and crash recovery each time? Their answer, built in \texttt{src/backend/access/gist/}, is \textbf{GiST}.

Unlike a B-tree---which slices a 1D line into strictly non-overlapping intervals---an internal GiST entry stores a \textbf{bounding box} $P$ enclosing every item in its child subtree (such as a 2D rectangle around 300 delivery zones, or the min-start to max-end span of 300 \texttt{tstzrange} bookings). Crucially, \textbf{sibling bounding boxes in GiST may overlap.} A GiST search calls \texttt{consistent(entry, query)} on each entry of an internal page and visits \emph{every} child whose box overlaps the query. Inserts pick the child needing the smallest box expansion (\texttt{penalty}) and split full pages via \texttt{picksplit}.

Beyond PostGIS maps (\texttt{\&\&}, \texttt{ST\_Contains}, \texttt{<->}), GiST powers an integrity rule B-trees cannot express: \textbf{Exclusion Constraints}. Suppose no two bookings for the same \texttt{room\_id} may have overlapping \texttt{during} intervals. A B-tree \texttt{UNIQUE} index only forbids \emph{identical} intervals (\texttt{=}), and running \texttt{SELECT COUNT(*) ... WHERE during \&\& new\_slot} in app code races when two sessions insert concurrently under \texttt{READ COMMITTED}. With the built-in \texttt{btree\_gist} extension, PostgreSQL blocks overlaps directly inside the GiST index:
\begin{lstlisting}[language=SQL]
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_bookings (
    booking_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id    INT       NOT NULL,
    during     TSTZRANGE NOT NULL,
    -- Forbid any two rows where (room_id = room_id) AND (during && during)!
    CONSTRAINT no_double_booking
        EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
\end{lstlisting}
Like \texttt{UNIQUE} in \texttt{nbtree}, \texttt{EXCLUDE USING gist} checks physical index pages across both committed and uncommitted in-flight rows, blocking the second overlapping writer until the first commits or aborts. An overlapping insert fails cleanly:
\begin{lstlisting}[language=Plain]
ERROR:  conflicting key value violates exclusion constraint "no_double_booking"
DETAIL:  Key (room_id, during)=(7, ["2026-11-02 10:00:00+00","2026-11-02 11:00:00+00"))
         conflicts with existing key (room_id, during)=(7, ["2026-11-02 09:30:00+00",
         "2026-11-02 10:30:00+00")).
\end{lstlisting}

\subsection{BRIN (Block Range Index): Indexing a Terabyte in 30~Megabytes}

Finally, picture an append-only \texttt{ledger\_events} table holding $10{,}000{,}000{,}000$ ($10^{10}$) immutable rows at $\sim 100$~bytes each---$134{,}217{,}728$ pages, or \textbf{$1.0\text{ TB}$ of table data}. Analysts query 15-minute windows by \texttt{recorded\_at}. A B-tree on \texttt{recorded\_at} costs $\sim 20$~bytes $\times 10^{10}$ rows $\approx \mathbf{215\text{ GB}}$ on disk.

Pause and notice how those rows land on disk. Because events arrive in chronological order, blocks $0..127$ hold 00:00:00--00:00:04 on January~1, blocks $128..255$ hold 00:00:04--00:00:09, and so on. Why store ten billion individual row pointers when the table is \emph{already physically sorted by arrival time}?

Introduced in PostgreSQL~9.5 (\texttt{src/backend/access/brin/}), a \textbf{Block Range Index (BRIN)} drops per-row \texttt{ctid}s completely. It slices the table into consecutive chunks of \texttt{pages\_per\_range} blocks (default $128\text{ pages} = 1\text{ MB}$). For each 128-page chunk, BRIN stores \textbf{one tiny summary} holding only $(\texttt{min\_val}, \texttt{max\_val})$ across all rows in those 128 pages (Figure~\ref{fig:ch03-gin-vs-brin}, bottom):
\[
  \frac{134{,}217{,}728\text{ heap pages}}{128\text{ pages/range}} = 1{,}048{,}576\text{ ranges} \;\times\; \sim 28\text{ bytes/summary} \;\approx\; \mathbf{29.4\text{ MB total.}}
\]
That is \textbf{$215\text{ GB}$ for a B-tree versus $\sim 30\text{ MB}$ for BRIN}---more than $7{,}000\times$ smaller. When a query filters \texttt{recorded\_at} to a 15-minute window, PostgreSQL scans the $30\text{ MB}$ BRIN summary in milliseconds and skips $99.98\%$ of the 1~MB chunks whose $[\min, \max]$ misses the window. It then runs a \texttt{Bitmap Heap Scan} with \texttt{Recheck Cond} across only the $\approx 150$ matching 1~MB chunks.

\begin{attackbox}
\textbf{The BRIN trap: physical correlation decay.} BRIN stores no row pointers; its pruning power depends entirely on how tightly each 128-page chunk clusters values on disk. Check \texttt{SELECT correlation FROM pg\_stats WHERE tablename = 'ledger\_events' AND attname = 'recorded\_at';}:
\begin{itemize}
  \item When \texttt{correlation} sits near $+1.0$ or $-1.0$ (append-only monotonic timestamps or sequences, never updated or deleted), each 128-page chunk spans a narrow $[\min, \max]$ window and BRIN skips $> 99.9\%$ of the table.
  \item Now suppose you build BRIN on a random \texttt{UUIDv4} ($\texttt{correlation} \approx 0.00$). Or suppose a retention job deletes January rows, \texttt{VACUUM} marks free space in blocks $0..127$ inside \texttt{\_fsm}, and November inserts reuse those slots. \textbf{A single November row landing in block~12 stretches Range~0's summary from \texttt{[Jan 01, Jan 01]} to \texttt{[Jan 01, Nov 01]}.} Worse, BRIN never shrinks $[\min, \max]$ automatically when extreme rows are deleted; shrinking requires \texttt{brin\_desummarize\_range()} or \texttt{REINDEX}. Once scattered updates or \texttt{\_fsm} reuses mix old and new timestamps across chunks, every range overlaps every query, and your $30\text{ MB}$ BRIN index silently scans $100\%$ of the $1\text{ TB}$ table.
\end{itemize}
\end{attackbox}

\begin{exercise}[Exact B+Tree Fanout: \texttt{BIGINT} vs.\ \texttt{UUID} Keys]
\label{exer:ch03-fanout-uuid}
Use the 8,192-byte \texttt{nbtree} page layout from Section~\ref{sec:ch03-fanout-math}: 24-byte \texttt{PageHeaderData}, 16-byte \texttt{BTPageOpaqueData}, 4-byte \texttt{ItemIdData} per slot, 8-byte \texttt{IndexTupleData} header, and 8-byte \texttt{MAXALIGN} padding.
\begin{enumerate}
  \item Compute the exact per-entry byte cost (slot pointer plus aligned \texttt{IndexTupleData}) for a single 16-byte \texttt{UUID} column, and compare it against the 20-byte cost of an 8-byte \texttt{BIGINT}.
  \item Assume internal pages average $80\%$ occupancy after splits and leaf pages use \texttt{fillfactor = 90} (each reserving one slot for \texttt{P\_HIKEY}). Compute the internal branching factor $B$ and leaf capacity $L$ for both \texttt{BIGINT} and \texttt{UUID}.
  \item For $500{,}000{,}000$ ($5 \times 10^8$) rows, find the exact number of tree levels and the RAM needed to pin all non-leaf pages in \texttt{shared\_buffers} for both key types.
\end{enumerate}
\end{exercise}

\begin{exercise}[Tracing a Concurrent Lehman--Yao Split by Hand]
\label{exer:ch03-lehman-yao-trace}
Leaf Block~22 covers $(100, 200]$ ($\texttt{P\_HIKEY} = 200$, $\texttt{btpo\_prev} = 9$, $\texttt{btpo\_next} = 35$) and holds $\{108, 115, 124, 130, 152, 168, 191\}$. Parent Block~5 routes $(100, 200] \to \text{Block } 22$. Writer~$W$ inserts $175$, splits Block~22 at separator $130$ into Block~22 and new Block~59, unlocks both leaves, and pauses \emph{before} locking Parent Block~5.
\begin{enumerate}
  \item Write down \texttt{P\_HIKEY}, the data keys, \texttt{btpo\_prev}, \texttt{btpo\_next}, and \texttt{BTP\_INCOMPLETE\_SPLIT} on Block~22 and Block~59 during this pause.
  \item Trace the page pins, shared latches, and \texttt{P\_HIKEY} checks for Reader~$A$ ($k = 124$) and Reader~$B$ ($k = 175$). How many latches does Reader~$B$ hold at once during descent versus during \texttt{\_bt\_moveright}?
  \item Why must \texttt{\_bt\_moveright} lock pages left-to-right ($\text{Block } 22 \to \text{Block } 59$)? What deadlock risk appears during \emph{backward} scans (\texttt{ORDER BY k DESC} following \texttt{btpo\_prev} right-to-left) if a left neighbor splits concurrently, and how does releasing and re-checking avoid a latch cycle?
\end{enumerate}
\end{exercise}

\begin{exercise}[Deduplication Math and Bottom-Up Deletion]
\label{exer:ch03-dedup-math}
An \texttt{orders} table holds $20{,}000{,}000$ rows split evenly across 5 values of \texttt{status CHAR(4)} (\texttt{'OPEN'}, \texttt{'PAID'}, \texttt{'SHIP'}, \texttt{'DONE'}, \texttt{'VOID'}).
\begin{enumerate}
  \item With \texttt{deduplicate\_items = off}, compute the byte size of one leaf entry: an 8-byte \texttt{IndexTupleData} header plus a 1-byte \texttt{varlena} header and 4~ASCII bytes padded to 8~bytes, plus a 4-byte slot pointer. Estimate total leaf size in MB at \texttt{fillfactor = 90}.
  \item With \texttt{deduplicate\_items = on}, suppose each posting list packs $130$ 6-byte \texttt{ctid}s ($16\text{ B header+key} + 130 \times 6\text{ B} = 796\text{ B}$, padded to $800\text{ B}$ plus a 4-byte slot pointer). Recompute total leaf size in MB and the compression ratio.
  \item Suppose \texttt{orders} also indexes \texttt{updated\_at}, and a worker updates \texttt{updated\_at = NOW()} ten times on an \texttt{'OPEN'} row without changing \texttt{status}. Explain why HOT is blocked, why 10 \texttt{'OPEN'} entries land on the leaf page, and how PG~14's bottom-up deletion prevents a split.
\end{enumerate}
\end{exercise}

\begin{exercise}[Composite Ribbon Geometry and Sort Elimination]
\label{exer:ch03-composite-design}
A multi-tenant ledger \texttt{entries(entry\_id, tenant\_id, account\_id, status, posted\_at, amount\_cents)} runs three hot queries:
\begin{itemize}
  \item $Q_1$: \texttt{WHERE tenant\_id = p\_tenant AND account\_id = p\_acct AND posted\_at >= p\_start ORDER BY posted\_at DESC LIMIT 25}
  \item $Q_2$: \texttt{WHERE tenant\_id = p\_tenant AND status = 'SETTLED' AND posted\_at BETWEEN p\_start AND p\_end}
  \item $Q_3$: \texttt{WHERE tenant\_id = p\_tenant AND amount\_cents > 100000 AND posted\_at >= p\_start}
\end{itemize}
\begin{enumerate}
  \item Design the smallest set of composite B-trees so $Q_1$ runs with \textbf{zero \texttt{Sort} node} (touching $\sim 28$ entries) and $Q_2$ reads one contiguous slice. Give exact column orders and \texttt{ASC}/\texttt{DESC} directions.
  \item Using Figure~\ref{fig:ch03-composite-ribbon}, explain why no single 1D B-tree makes both \texttt{amount\_cents > 100000} and \texttt{posted\_at >= p\_start} contiguous in $Q_3$. If $0.1\%$ of a tenant's rows match \texttt{posted\_at >= p\_start} while $15\%$ match \texttt{amount\_cents > 100000}, which column belongs second after \texttt{tenant\_id}?
\end{enumerate}
\end{exercise}

\begin{exercise}[Visibility Map Churn and \texttt{Heap Fetches} Latency]
\label{exer:ch03-vm-math}
A $50{,}000{,}000$-row \texttt{transactions} table spans $600{,}000$ heap pages ($\approx 4.69\text{ GB}$) with covering index \texttt{(merchant\_id, created\_at) INCLUDE (net\_cents)}.
\begin{enumerate}
  \item Compute the exact byte size and 8~KB page count of its \texttt{\_vm} fork at 2~bits per table page.
  \item Right after \texttt{VACUUM}, $100\%$ of pages have \texttt{ALL\_VISIBLE = 1}. Over the next 20~minutes, $90{,}000$ random single-row updates hit the $600{,}000$ pages. Using $1 - (1 - 1/M)^K \approx 1 - e^{-K/M}$, find the fraction of pages whose \texttt{\_vm} bit is now $0$.
  \item A query runs \texttt{SELECT SUM(net\_cents) FROM transactions WHERE merchant\_id = 77}, matching $20{,}000$ index entries scattered across cold table pages ($80~\mu\text{s}$ per random NVMe read; index and \texttt{\_vm} warm in RAM). Compute expected \texttt{Heap Fetches} and wall-clock time right after \texttt{VACUUM} versus 20~minutes later.
\end{enumerate}
\end{exercise}

\begin{exercise}[Partial and Expression Index Debugging]
\label{exer:ch03-partial-debug}
A teammate proposes three indexes on a $150{,}000{,}000$-row \texttt{invoices} table ($99.7\%$ \texttt{'paid'}, $0.2\%$ \texttt{'open'}, $0.1\%$ \texttt{'overdue'}):
\begin{lstlisting}[language=SQL]
-- Index 1
CREATE INDEX idx_inv_day ON invoices (DATE_TRUNC('day', issued_at));
-- Index 2
CREATE INDEX idx_inv_code ON invoices (LOWER(reference_code));
-- Index 3
CREATE INDEX idx_inv_unpaid ON invoices (due_at) WHERE status IN ('open', 'overdue');
\end{lstlisting}
\begin{enumerate}
  \item \texttt{issued\_at} is \texttt{TIMESTAMPTZ}. Explain why Index~1 fails with an immutability error, and fix both \texttt{CREATE INDEX} and a UTC-day query for \texttt{2026-10-31}. Then show how a half-open range on bare \texttt{issued\_at} avoids an expression index altogether.
  \item App code runs \texttt{WHERE LOWER(TRIM(reference\_code)) = 'inv-901'}. Explain why PostgreSQL skips Index~2, and fix the contract cleanly.
  \item Estimate the size ratio of Index~3 versus a full index on \texttt{(status, due\_at)}. Can \texttt{WHERE status = 'overdue' AND due\_at < NOW()} use Index~3? Justify via predicate implication.
\end{enumerate}
\end{exercise}

\begin{exercise}[GIN Internals: \texttt{jsonb\_ops}, \texttt{jsonb\_path\_ops}, and Pending Flushes]
\label{exer:ch03-gin-trace}
Consider inserting this \texttt{JSONB} row into \texttt{charges(charge\_id, meta)}:
\begin{lstlisting}[language=SQL]
INSERT INTO charges (meta) VALUES
('{"gateway":"stripe","risk":{"score":92,"flags":["avs_mismatch","velocity"]}}');
\end{lstlisting}
\begin{enumerate}
  \item List all Entry Tree tokens extracted under default \texttt{jsonb\_ops} versus the root-to-leaf path hashes under \texttt{jsonb\_path\_ops}.
  \item Which queries can \texttt{jsonb\_path\_ops} accelerate, and which force a sequential scan: (a)~\texttt{meta @>} matching \texttt{velocity} inside \texttt{risk.flags}; (b)~\texttt{meta ? 'gateway'}; (c)~\texttt{meta->'risk'->>'score' = '92'}?
  \item Suppose each insert appends $\sim 256$~bytes to the GIN pending list (\texttt{gin\_pending\_list\_limit = 4MB}). After roughly how many inserts does a foreground session stall on a synchronous merge, and what two settings remove that p99 spike?
\end{enumerate}
\end{exercise}

\begin{exercise}[Quantifying BRIN Scan Amplification Under \texttt{\_fsm} Poisoning]
\label{exer:ch03-brin-poisoning}
An append-only \texttt{telemetry} table packs $102{,}400{,}000$ rows at $80$ rows per page across $1{,}280{,}000$ pages ($\approx 10\text{ GB}$). A BRIN index on \texttt{ts} with \texttt{pages\_per\_range = 128} creates $R = 10{,}000$ block ranges across 100 days (100 ranges per day).
\begin{enumerate}
  \item Initially rows are strictly chronological: querying the latest hour of Day~100 overlaps $\ceil{100 / 24} = 5$ ranges. How many MB of heap does PostgreSQL read?
  \item A job deletes $0.1\%$ of rows uniformly across Days~1..99 and runs \texttt{VACUUM}. On Day~100, \texttt{\_fsm} routes $K = 30{,}000$ new rows uniformly at random into the $9{,}900$ ranges of Days~1..99. What is the probability $1 - (1 - 1/9900)^{30000}$ that a historical range receives at least one Day-100 row?
  \item What happens to that historical range's $[\min, \max]$ summary when one Day-100 row lands inside it, and how many MB of heap must the ``latest hour of Day~100'' query now scan?
\end{enumerate}
\end{exercise}
