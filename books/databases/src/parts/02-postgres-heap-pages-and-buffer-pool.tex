\chapter{Inside an 8 KB Heap Page and the Buffer Pool}
\label{ch:heap-pages}

In Chapter~1, a table was a clean mathematical object: a relation (or a SQL bag of rows) governed by set algebra and three-valued logic. When you write \texttt{INSERT INTO accounts VALUES (1001, 'Ada', 50000, true)}, SQL lets you picture a neat rectangular spreadsheet gaining one horizontal line.

The Linux kernel knows nothing about relations, columns, or \texttt{BIGINT}s. An NVMe drive only reads and writes flat byte arrays at numeric block addresses. C pointers in RAM only know byte offsets and CPU alignment boundaries. Bridging that gap is the job of PostgreSQL's storage and buffer managers. Every mechanism later in this book rests on one physical container: an \textbf{8,192-byte (8~KB) slotted heap page}. Indexes point to slots inside those pages, crash recovery stamps log positions at byte~0, and \texttt{UPDATE} appends fresh row versions into their free space.

\begin{focusbox}
This chapter opens a table file on disk and follows an 8~KB page into RAM. Along the way, we answer five concrete engineering questions:
\begin{itemize}
  \item Which actual files on Linux hold a PostgreSQL table, and how can \texttt{TRUNCATE} wipe a giant table in milliseconds while still letting \texttt{ROLLBACK} restore every row?
  \item How does an 8~KB page pack variable-length rows and reclaim deleted gaps without breaking external index pointers?
  \item Why does the order of columns in \texttt{CREATE TABLE} silently add or save hundreds of megabytes of CPU alignment padding?
  \item Where does PostgreSQL put a 400~KB JSON document when no row is allowed to cross an 8~KB page boundary?
  \item How does PostgreSQL's RAM cache keep hot lookup pages in memory when an analyst runs a sequential scan over a 500~GB historical table?
\end{itemize}
\end{focusbox}

\section{Where a Table Actually Lives on Disk}
\label{sec:ch02-files-and-forks}
% ======================================================================

Let us create a small ledger table in \texttt{psql} and ask PostgreSQL a direct physical question: \emph{which file on the Linux filesystem holds these rows?}

\begin{lstlisting}[language=SQL]
CREATE TABLE accounts (
    account_id    BIGINT  PRIMARY KEY,
    owner_name    TEXT    NOT NULL,
    balance_cents BIGINT  NOT NULL,
    is_active     BOOLEAN NOT NULL
);

SELECT oid, relname, relfilenode
FROM pg_class
WHERE relname = 'accounts';
--   oid  | relname  | relfilenode
-- -------+----------+-------------
--  24576 | accounts |       24576

SELECT pg_relation_filepath('accounts');
--  pg_relation_filepath
-- ----------------------
--  base/16384/24576
\end{lstlisting}

Relative to your PostgreSQL data directory (\texttt{PGDATA}, such as \texttt{/var/lib/postgresql/17/main}), the table \texttt{accounts} is an ordinary regular file at \texttt{PGDATA/base/16384/24576}. Every piece of that path has a clear job:
\begin{itemize}
  \item \textbf{\texttt{base/}} holds all databases in the default tablespace (\texttt{pg\_default}). Cluster-wide catalogs such as \texttt{pg\_database} and \texttt{pg\_authid} live next door in \texttt{global/}.
  \item \textbf{\texttt{16384}} is the numeric object ID (\texttt{oid}) of the current database in \texttt{pg\_database}. Each database in the cluster gets its own subdirectory under \texttt{base/}.
  \item \textbf{\texttt{24576}} is the table's current physical file number (\texttt{pg\_class.relfilenode}), not its permanent table ID (\texttt{pg\_class.oid}). Right after \texttt{CREATE TABLE}, those two numbers happen to match. Watch what happens the moment we truncate the table.
\end{itemize}

\subsection{Why \texttt{oid} and \texttt{relfilenode} Split: Transactional File Swaps}

Suppose a transaction runs \texttt{TRUNCATE accounts;} and then, three statements later, hits an error and runs \texttt{ROLLBACK;}. Unlike many older database engines, PostgreSQL makes \texttt{TRUNCATE}, \texttt{CLUSTER}, and \texttt{VACUUM FULL} \textbf{fully transactional}.

Think about what would break if \texttt{TRUNCATE} simply asked the operating system to chop file \texttt{24576} down to zero bytes in place (via Linux \texttt{ftruncate(fd, 0)}). The instant the kernel zeroes the file length, the old 8~KB blocks are gone. If the transaction rolls back ten milliseconds later, nothing is left to restore.

\begin{intuitionbox}
PostgreSQL solves transactional table rewrites by separating \textbf{logical identity} (\texttt{pg\_class.oid}) from \textbf{physical storage file} (\texttt{pg\_class.relfilenode}):
\begin{itemize}
  \item Views, foreign keys, triggers, and grants all point to \texttt{oid = 24576}. That permanent ID never changes for the life of the table.
  \item When you run \texttt{TRUNCATE accounts} (or rewrite the table with \texttt{VACUUM FULL} or \texttt{CLUSTER}), PostgreSQL allocates a fresh file number---say \texttt{24589}---and creates a new empty file \texttt{base/16384/24589}. It then updates the catalog row for \texttt{oid = 24576} so its \texttt{relfilenode} column points to \texttt{24589}.
\end{itemize}
If your transaction runs \texttt{ROLLBACK}, that catalog row update disappears. PostgreSQL deletes the empty file \texttt{24589}, while original file \texttt{24576} still sits intact on disk. If your transaction runs \texttt{COMMIT}, the catalog swap becomes visible atomically, new queries open \texttt{24589}, and post-commit cleanup deletes old file \texttt{24576}.
\end{intuitionbox}

Let us verify this split directly in SQL:

\begin{lstlisting}[language=SQL]
BEGIN;
TRUNCATE accounts;

SELECT oid, relfilenode, pg_relation_filepath('accounts') AS path
FROM pg_class
WHERE relname = 'accounts';
--   oid  | relfilenode |       path
-- -------+-------------+------------------
--  24576 |       24589 | base/16384/24589

ROLLBACK;

SELECT oid, relfilenode, pg_relation_filepath('accounts') AS path
FROM pg_class
WHERE relname = 'accounts';
--   oid  | relfilenode |       path
-- -------+-------------+------------------
--  24576 |       24576 | base/16384/24576
\end{lstlisting}

To locate any table file on disk, PostgreSQL combines three integers: the tablespace ID, the database ID, and the current file number. In PostgreSQL~16+ C code (\texttt{src/include/storage/relfilelocator.h}), that triple is called \texttt{RelFileLocator}: \texttt{(spcOid, dbOid, relNumber)}. Whenever you inspect files on disk after maintenance, query \texttt{pg\_relation\_filepath(oid)} rather than assuming the filename still equals \texttt{pg\_class.oid}.

\subsection{1 GB Segment Splitting}

A busy production table easily grows past 100~GB, yet \texttt{ls -lh} inside \texttt{PGDATA/base/16384/} never shows a file larger than \textbf{1~GiB} ($1{,}073{,}741{,}824$ bytes).

PostgreSQL slices every table or index file into fixed segments of $131{,}072$ blocks of $8{,}192$ bytes ($\texttt{RELSEG\_SIZE} = 131{,}072$, totaling $1\text{ GiB}$). Originally added to avoid 2~GB file-size limits on 32-bit Unix systems, 1~GiB segments remain helpful on 64-bit Linux for parallel backups and file copies.

For a 2.6~GiB table with \texttt{relfilenode = 24589}, the directory contains three segment files:
\begin{itemize}
  \item \texttt{24589} \quad (blocks $0 \dots 131{,}071$, bytes $0 \dots 1\text{ GiB} - 1$)
  \item \texttt{24589.1} \quad (blocks $131{,}072 \dots 262{,}143$, the second GiB)
  \item \texttt{24589.2} \quad (blocks $262{,}144 \dots 340{,}786$, the remaining $0.6\text{ GiB}$)
\end{itemize}
Locating any 32-bit page number $B$ (\texttt{BlockNumber}) on disk takes one integer division and one remainder:
\[
  \text{segment\_index} = \floor*{\frac{B}{131{,}072}},
  \qquad
  \text{byte\_offset\_in\_segment} = (B \bmod 131{,}072) \times 8{,}192.
\]
For example, block $B = 300{,}000$ sits in segment $\floor{300{,}000 / 131{,}072} = 2$ (\texttt{24589.2}) at local block $37{,}856$, starting at byte $37{,}856 \times 8{,}192 = 310{,}116{,}352$. Because a block number is a 32-bit unsigned integer (with \texttt{0xFFFFFFFF} reserved as invalid), one standard PostgreSQL table holds up to $(2^{32} - 1) \times 8\text{ KiB} \approx \mathbf{32\text{ TiB}}$ before needing partitioning.

\subsection{Companion Forks: Free Space Map (\texttt{\_fsm}) and Visibility Map (\texttt{\_vm})}

Insert a few rows, run \texttt{VACUUM accounts;}, and check \texttt{PGDATA/base/16384/} again. Two helper files appear beside \texttt{24589}: \texttt{24589\_fsm} and \texttt{24589\_vm}. Each table can own up to four companion files on disk, which PostgreSQL calls \textbf{forks} (\texttt{ForkNumber} in \texttt{src/include/common/relpath.h}):

\begin{enumerate}
  \item \textbf{Main Fork (\texttt{MAIN\_FORKNUM = 0}, file \texttt{24589})}: Holds the actual 8~KB table pages (or index pages, for an index).

  \item \textbf{Free Space Map (FSM, \texttt{FSM\_FORKNUM = 1}, file \texttt{24589\_fsm})}: Suppose \texttt{accounts} spans one million pages ($\approx 8\text{ GB}$) with deleted gaps scattered throughout, and a session inserts a 110-byte row. Checking pages one by one for 110 free bytes would turn every \texttt{INSERT} into a slow linear scan.

  Instead, the Free Space Map summarizes each table page's free space in \textbf{one byte} (\texttt{0..255}), measured in 32-byte units ($\floor{\text{free\_bytes} / 32}$). A leaf byte of \texttt{4} promises at least $4 \times 32 = 128$ free bytes on that page. Inside each 8~KB \texttt{\_fsm} block, roughly 4,000 leaf bytes sit under a \textbf{binary max-heap tree} where every parent stores $\max(\text{left}, \text{right})$:
  \begin{itemize}
    \item If the root byte at the top of an \texttt{\_fsm} page reads \texttt{100} ($3{,}200$ bytes), at least one table page below has $3{,}200+$ free bytes.
    \item Finding room for our 110-byte row ($\lceil 110 / 32 \rceil = 4$ units) walks down from the root in $\Oh(\log N)$ steps, choosing any child $\ge 4$. Even on a multi-terabyte table, stacked \texttt{\_fsm} levels find a target page in at most \textbf{three 8~KB buffer lookups}.
    \item The Free Space Map is only a hint, not ground truth. If another session fills that page first, the inserter checks the real page header, lowers the \texttt{\_fsm} byte, and asks the tree for the next candidate.
  \end{itemize}

  \item \textbf{Visibility Map (VM, \texttt{VM\_FORKNUM = 2}, file \texttt{24589\_vm})}: Stores just \textbf{2 bits per table page}:
  \begin{itemize}
    \item Bit 0 (\texttt{VISIBILITYMAP\_ALL\_VISIBLE = 0x01}): Every row on that page is committed and visible to \emph{all} current and future transactions, with zero dead versions.
    \item Bit 1 (\texttt{VISIBILITYMAP\_ALL\_FROZEN = 0x02}): Every row on that page is also frozen against 32-bit transaction ID wraparound (Chapter~5).
  \end{itemize}
  Four table pages pack into each byte of the Visibility Map. Subtracting the 24-byte header leaves $8{,}168$ payload bytes, so \textbf{one 8~KB \texttt{\_vm} page tracks $32{,}672$ table pages}---about \textbf{255~MiB} of data. Those two bits drive two major speedups. First, \textbf{Index-Only Scans} (Chapter~3) check \texttt{\_vm} in RAM and skip reading the table page whenever \texttt{ALL\_VISIBLE} is \texttt{1}. Second, \textbf{\texttt{VACUUM}} (Chapter~5) skips pages already marked clean or frozen. Any write to page $B$ clears its bits.

  \item \textbf{Initialization Fork (\texttt{INIT\_FORKNUM = 3}, file \texttt{24589\_init})}: Created only for \texttt{UNLOGGED} tables and their indexes. It stores an empty template image. After an unclean crash, startup wipes the unlogged main file and copies \texttt{\_init} over it to reset the table cleanly (Chapter~4).
\end{enumerate}

\section{Anatomy of an 8,192-Byte Slotted Heap Page}
\label{sec:ch02-slotted-page}
% ======================================================================

Open \texttt{base/16384/24576} in a hex editor and slice it every $8{,}192$ bytes ($\texttt{BLCKSZ} = 8{,}192$). Each 8,192-byte chunk (offsets $0 \dots 8{,}191$) is a self-contained \textbf{slotted page}.

\begin{walkbox}
Try designing the page layout yourself first. You have an 8,192-byte array in RAM, and SQL rows are \textbf{variable-length} (\texttt{'Ada'} is 3 bytes, \texttt{'Grace Hopper'} is 12, and another row carries a 400-byte note). Worse, rows get deleted out of order, leaving holes in the middle of the page while external B-tree indexes hold pointers to live rows.

Suppose a B-tree index stored a row's raw byte offset, say \texttt{(block 0, byte 8072)}. The moment you slide rows together to close a deleted 64-byte gap, every moved row's byte offset changes. You would have to hunt down and rewrite entries across every index on the table. How can we pack variable-length rows into 8,192 bytes, merge free space into one gap, and move rows inside the page without breaking a single external index pointer?
\end{walkbox}

The slotted-page layout (pioneered in System~R and used across PostgreSQL) solves all three problems with two simple ideas:
\begin{enumerate}
  \item \textbf{Two-way growth toward a central free gap}: Fixed 4-byte \textbf{slot pointers} grow \emph{downward} from byte~24 toward higher addresses. Variable-length \textbf{rows} (called \emph{heap tuples}) grow \emph{upward} from byte~8,192 toward lower addresses. All unused bytes sit in one contiguous gap in the middle, bounded by a lower-bound byte offset (\texttt{pd\_lower}) and an upper-bound byte offset (\texttt{pd\_upper}). Neither side wastes space guessing a fixed boundary in advance.
  \item \textbf{One level of slot indirection}: External B-tree indexes never store a row's byte offset. Instead, they store a 6-byte tuple ID, \texttt{ctid = (block\_number, slot\_number)}, where \texttt{slot\_number} ($1, 2, 3, \dots$) selects a 4-byte slot at the top of the page. When PostgreSQL compacts a page, it slides row bytes upward in RAM and updates the byte offset \emph{inside that page's 4-byte slot}. Every \texttt{(block\_number, slot\_number)} in external indexes stays valid.
\end{enumerate}

\subsection{Byte-Offset Tour of \texttt{PageHeaderData} (Bytes \texttt{0..24})}

Before storing any slot pointers, every 8~KB page reserves its first 24 bytes for bookkeeping: the last log position that touched this page, a corruption checksum, free-space bounds, and cleanup hints. In PostgreSQL's C code (\texttt{src/include/storage/bufpage.h}), that 24-byte header is \texttt{PageHeaderData}:

\begin{lstlisting}[language=C]
/* Simplified from src/include/storage/bufpage.h */
typedef struct PageHeaderData
{
    /* [0..8)   LSN of last WAL record modifying this page */
    PageXLogRecPtr pd_lsn;

    /* [8..10)  16-bit page checksum (if data_checksums is enabled) */
    uint16         pd_checksum;

    /* [10..12) Flag bits: PD_HAS_FREE_LINES, PD_PAGE_FULL, PD_ALL_VISIBLE */
    uint16         pd_flags;

    /* [12..14) Byte offset to START of free space (end of line pointers) */
    LocationIndex  pd_lower;

    /* [14..16) Byte offset to END of free space (start of lowest tuple) */
    LocationIndex  pd_upper;

    /* [16..18) Byte offset to start of special access-method space */
    LocationIndex  pd_special;

    /* [18..20) Page size (upper 8 bits) + layout version (lower 8 bits) */
    uint16         pd_pagesize_version;

    /* [20..24) Oldest unpruned XMAX on page (hint for in-page pruning) */
    TransactionId  pd_prune_xid;

    /* [24..)   1-indexed array of 4-byte line pointers growing downward */
    ItemIdData     pd_linp[FLEXIBLE_ARRAY_MEMBER];
} PageHeaderData;
\end{lstlisting}

Let us walk through each field's job and verify that the byte offsets add up to \textbf{24 bytes}:
\begin{itemize}
  \item \textbf{Last log position (\texttt{[0..8)}, \texttt{pd\_lsn}, 8 bytes)}: Crash recovery needs to know how up-to-date this page is, so \texttt{pd\_lsn} records the 64-bit Write-Ahead Log position of the latest change to this block. (C splits it into two 32-bit halves so it stays 4-byte aligned on 32-bit hardware.) In Chapter~4 we will see the buffer manager check \texttt{pd\_lsn} before letting any dirty page reach disk.
  \item \textbf{Corruption detector (\texttt{[8..10)}, \texttt{pd\_checksum}, 2 bytes)}: Disks occasionally flip bits silently, so when checksums are enabled (\texttt{initdb --data-checksums}, the default in PostgreSQL~18), PostgreSQL hashes all 8,192 bytes plus the block number right before flushing to disk. If storage rot alters a byte later, the next read catches the mismatch and raises \texttt{ERROR: invalid page in block}.
  \item \textbf{Page-state hints (\texttt{[10..12)}, \texttt{pd\_flags}, 2 bytes)}: Quick status bits let readers and inserters avoid wasted scans:
  \begin{itemize}
    \item \texttt{PD\_HAS\_FREE\_LINES (0x0001)}: At least one slot is unused, so a future \texttt{INSERT} can recycle an old slot number instead of growing \texttt{pd\_lower}.
    \item \texttt{PD\_PAGE\_FULL (0x0002)}: A recent update ran out of room, warning future updates not to retry in-page placement until dead space is pruned.
    \item \texttt{PD\_ALL\_VISIBLE (0x0004)}: Page-local mirror of the Visibility Map's \texttt{ALL\_VISIBLE} bit.
  \end{itemize}
  \item \textbf{Central free-space bounds (\texttt{[12..14)} and \texttt{[14..16)}, \texttt{pd\_lower} and \texttt{pd\_upper}, 2 bytes each)}: Two 16-bit byte offsets frame the central free gap so inserts can check space in $\Oh(1)$ time. On a fresh empty table page, $\texttt{pd\_lower} = 24$ and $\texttt{pd\_upper} = 8{,}192$, leaving $8{,}192 - 24 = \mathbf{8{,}168\text{ free bytes}}$. Testing whether a row fits takes one subtraction: $\texttt{pd\_upper} - \texttt{pd\_lower}$.
  \item \textbf{Index trailer boundary (\texttt{[16..18)}, \texttt{pd\_special}, 2 bytes)}: Index pages reserve a small trailer at the very end of the 8~KB block for sibling pointers (16 bytes on a B-tree page, setting $\texttt{pd\_special} = 8{,}176$ in Chapter~3). Table pages need no trailer, so on every table page \textbf{$\texttt{pd\_special} = 8{,}192$}.
  \item \textbf{Size and format guard (\texttt{[18..20)}, \texttt{pd\_pagesize\_version}, 2 bytes)}: Prevents opening pages built with an incompatible block size or format, packing $\texttt{8192 | 4} = \texttt{0x2004} = 8{,}196$ (version~4 since PostgreSQL~8.3).
  \item \textbf{Cleanup trigger stamp (\texttt{[20..24)}, \texttt{pd\_prune\_xid}, 4 bytes)}: Stores the oldest deleting or updating transaction ID among dead rows on this page. If that transaction is older than every active snapshot, a reader knows right away that an in-page cleanup pass (Chapter~5) can reclaim space.
\end{itemize}

\subsection{The Line Pointer Array: \texttt{ItemIdData} (4 Bytes per Slot)}

Starting at byte~24 sits an array of 4-byte slot pointers. Each 32-bit slot packs three small integers: a 15-bit byte offset to the row, a 2-bit status flag, and a 15-bit row length. In C (\path{src/include/storage/itemid.h}), each 4-byte slot is an \texttt{ItemIdData} struct, and SQL numbers slots starting at~\textbf{1} (so slot~$k$ lives at byte $24 + 4(k - 1)$):

\begin{lstlisting}[language=C]
/* From src/include/storage/itemid.h */
typedef struct ItemIdData
{
    unsigned lp_off:15,   /* byte offset to tuple (0..32767) */
             lp_flags:2,  /* state of line pointer, see below */
             lp_len:15;   /* byte length of tuple (0..32767) */
} ItemIdData;

#define LP_UNUSED    0    /* unused slot (lp_len is always 0) */
#define LP_NORMAL    1    /* used slot pointing to a tuple (lp_len > 0) */
#define LP_REDIRECT  2    /* HOT redirect (lp_off = target slot, lp_len == 0) */
#define LP_DEAD      3    /* dead item, tuple storage already reclaimed */
\end{lstlisting}

Look how cleanly those 32 bits are budgeted:
\begin{itemize}
  \item \textbf{\texttt{lp\_off} (15 bits)}: Covers offsets $0 \dots 32{,}767$, addressing every byte of an 8~KB page (and supporting compile-time block sizes up to 32~KB).
  \item \textbf{\texttt{lp\_len} (15 bits)}: Exact unpadded byte length of the row.
  \item \textbf{\texttt{lp\_flags} (2 bits)}: Tracks the four-stage lifecycle of a slot. A live or newly deleted row starts as \texttt{LP\_NORMAL (1)}. A same-page chain root (Chapter~5) can become \texttt{LP\_REDIRECT (2)}, where \texttt{lp\_off} points to another \emph{slot number} on the page. Once a dead row's bytes are compacted away---before external indexes are cleaned---the slot turns into \texttt{LP\_DEAD (3)} ($\texttt{lp\_len} = 0$). Keeping that 4-byte gravestone lets index scans arriving at \texttt{(0, 2)} skip it safely. Later, \texttt{VACUUM} cleans the indexes and resets the slot to \texttt{LP\_UNUSED (0)} for reuse.
\end{itemize}

\subsection{Step-by-Step Trace: Inserting, Deleting, and Compacting Without Breaking Indexes}

Let us trace Page~0 of \texttt{accounts} from empty initialization through three inserts, one delete, and an in-page compaction (\texttt{PageRepairFragmentation}). In Section~\ref{sec:ch02-tuple-layout} we will verify that these three rows have raw lengths $49$, $57$, and $49$ bytes. Rounding each up to an 8-byte CPU alignment multiple (\texttt{MAXALIGN}) carves \textbf{56}, \textbf{64}, and \textbf{56} bytes from \texttt{pd\_upper}:

\begin{enumerate}
  \item \textbf{Fresh Empty Page~0}:
  \[
    \texttt{pd\_lower} = 24, \qquad \texttt{pd\_upper} = 8{,}192, \qquad \text{free gap} = 8{,}192 - 24 = 8{,}168\text{ B}.
  \]

  \item \textbf{Insert Row~1} (\texttt{1001, 'Ada', 50000, true}; raw $\texttt{lp\_len} = 49\text{ B}$, aligned $56\text{ B}$):
  \begin{itemize}
    \item Allocate Slot~1 at bytes \texttt{[24..28)}; advance $\texttt{pd\_lower}: 24 \to 28$.
    \item Pull $\texttt{pd\_upper}$ down by $56$ bytes: $8{,}192 - 56 = \mathbf{8{,}136}$. Copy the 49 tuple bytes into \texttt{[8136..8185)} (leaving \texttt{[8185..8192)} as 7 trailing alignment pad bytes).
    \item Write Slot~1 = \texttt{(lp\_off = 8136, lp\_flags = LP\_NORMAL, lp\_len = 49)}.
    \item The primary-key B-tree index \texttt{accounts\_pkey} records \texttt{1001} $\mapsto$ \texttt{ctid = (0, 1)}.
  \end{itemize}

  \item \textbf{Insert Row~2} (\texttt{1002, 'Grace Hopper', 125000, true}; raw $\texttt{lp\_len} = 57\text{ B}$, aligned $64\text{ B}$):
  \begin{itemize}
    \item Allocate Slot~2 at bytes \texttt{[28..32)}; advance $\texttt{pd\_lower}: 28 \to 32$.
    \item Pull $\texttt{pd\_upper}$ down by $64$ bytes: $8{,}136 - 64 = \mathbf{8{,}072}$. Copy the 57 tuple bytes into \texttt{[8072..8129)}.
    \item Write Slot~2 = \texttt{(lp\_off = 8072, lp\_flags = LP\_NORMAL, lp\_len = 57)}.
    \item \texttt{accounts\_pkey} records \texttt{1002} $\mapsto$ \texttt{ctid = (0, 2)}.
  \end{itemize}

  \item \textbf{Insert Row~3} (\texttt{1003, 'Edsger', 90000, false}; raw $\texttt{lp\_len} = 49\text{ B}$, aligned $56\text{ B}$):
  \begin{itemize}
    \item Allocate Slot~3 at bytes \texttt{[32..36)}; advance $\texttt{pd\_lower}: 32 \to 36$.
    \item Pull $\texttt{pd\_upper}$ down by $56$ bytes: $8{,}072 - 56 = \mathbf{8{,}016}$. Copy the 49 tuple bytes into \texttt{[8016..8065)}.
    \item Write Slot~3 = \texttt{(lp\_off = 8016, lp\_flags = LP\_NORMAL, lp\_len = 49)}.
    \item \texttt{accounts\_pkey} (and any secondary indexes on \texttt{owner\_name} or \texttt{balance\_cents}) records \texttt{1003} $\mapsto$ \textbf{\texttt{ctid = (0, 3)}}. Free gap is now $8{,}016 - 36 = 7{,}980\text{ B}$.
  \end{itemize}

  \item \textbf{Delete Row~2 (\texttt{1002}) and Compact Page~0 (\texttt{PageRepairFragmentation})}:
  \begin{itemize}
    \item Once the \texttt{DELETE} commits and no running transaction can see Row~2 anymore, bytes \texttt{[8072..8136)} form a \textbf{64-byte dead hole} trapped between Tuple~3 (\texttt{[8016..8072)}) and Tuple~1 (\texttt{[8136..8192)}).
    \item Inside RAM, PostgreSQL executes \texttt{memmove} to slide Tuple~3 upward by 64 bytes: from \texttt{[8016..8072)} into \textbf{\texttt{[8080..8136)}}.
    \item $\texttt{pd\_upper}$ jumps upward from $8{,}016$ to $\mathbf{8{,}080}$, merging all 64 reclaimed bytes straight back into the central free gap ($8{,}080 - 36 = 8{,}044\text{ B}$).
    \item Slot~2 (\texttt{[28..32)}) is marked \texttt{(lp\_off = 0, lp\_flags = LP\_DEAD, lp\_len = 0)}. Notice that \textbf{Slot~3 is never renumbered to Slot~2}.
    \item Slot~3 (\texttt{[32..36)}) simply rewrites its internal offset from \texttt{8016} to \textbf{\texttt{8080}}: \texttt{(lp\_off = 8080, lp\_flags = LP\_NORMAL, lp\_len = 49)}.
  \end{itemize}
\end{enumerate}

\begin{whybox}
Look at what happened to every external B-tree index pointing to \texttt{'Edsger'} at \texttt{ctid = (0, 3)}. Not a single index page had to be locked, dirtied, WAL-logged, or rewritten. When an index lookup lands on Page~0 and asks for Slot~3, it reads bytes \texttt{[32..36)}, follows the updated \texttt{lp\_off = 8080}, and lands on Edsger's relocated tuple in one memory dereference. Four bytes of per-row slot indirection decouple \emph{internal page defragmentation} from \emph{global index maintenance}.
\end{whybox}

Compare this with two mechanisms you already know. Java's compacting garbage collector also slides objects together, and then rewrites every reference to each moved object. It can afford that sweep because it pauses threads and walks RAM. PostgreSQL cannot rewrite external index files on disk every time it tidies one 8~KB page, so indexes store \texttt{(block, slot)} instead. Only the 4-byte slot inside the page holds the raw byte offset. In C terms, a raw pointer dangles when \texttt{realloc} moves a buffer, whereas an integer array index stays valid.

\section{Inside a Heap Tuple: Headers, Null Bitmaps, and Column Tetris}
\label{sec:ch02-tuple-layout}
% ======================================================================

Now let us zoom in on the 49 bytes starting at byte~8,136 of Page~0: Row~1 of \texttt{accounts}. Before storing column values, every PostgreSQL row version carries a compact bookkeeping header. It records which transaction created the row, which transaction deleted or superseded it, where any newer version sits, and which columns are \texttt{NULL}. In C (\path{src/include/access/htup_details.h}), that fixed \textbf{23-byte} prefix is \texttt{HeapTupleHeaderData}, optionally followed by a null bitmap and alignment padding up to byte \texttt{t\_hoff}:

\begin{lstlisting}[language=C]
/* Simplified from src/include/access/htup_details.h */
struct HeapTupleHeaderData
{
    union {
        HeapTupleFields t_heap;   /* [0..12) t_xmin (4B), t_xmax (4B), t_cid (4B) */
        DatumTupleFields t_datum; /* used for in-memory composite datums */
    } t_choice;

    ItemPointerData t_ctid;       /* [12..18) current or newer (block, slot) (6B) */

    uint16          t_infomask2;  /* [18..20) lower 11 bits = natts; upper = HOT flags */
    uint16          t_infomask;   /* [20..22) HASNULL, HASVARWIDTH, XMIN/XMAX hint bits */
    uint8           t_hoff;       /* [22..23) byte offset to user data (MAXALIGN'd!) */

    /* [23..) Optional null bitmap (1 bit per column when HEAP_HASNULL is set) */
    bits8           t_bits[FLEXIBLE_ARRAY_MEMBER];

    /* User column bytes start at exact offset t_hoff from start of header! */
};
\end{lstlisting}

\subsection{Why a 23-Byte Struct Produces a 24-Byte Header (and Free 8-Column Null Bitmaps)}

A Java~6 object on 64-bit HotSpot also starts with a header: an 8-byte mark word and a 4- or 8-byte class pointer. A PostgreSQL row header plays the same role on disk, except its fields track multi-version concurrency rather than garbage collection. Let us link each human job to its C field and count the bytes:
\begin{itemize}
  \item \textbf{Birth and expiration stamps (\texttt{[0..4)} \texttt{t\_xmin} and \texttt{[4..8)} \texttt{t\_xmax}, 4 bytes each)}: Concurrent snapshots need to know who created a row version and who retired it, so PostgreSQL stamps these two 32-bit transaction IDs on the front (Chapter~5).
  \item \textbf{Intra-transaction step counter (\texttt{[8..12)} \texttt{t\_cid}, 4 bytes)}: When one transaction runs several SQL statements in sequence, this command counter tracks which step wrote the version.
  \item \textbf{Version-chain link (\texttt{[12..18)} \texttt{t\_ctid}, 6 bytes)}: On the latest version of a row, \texttt{t\_ctid} points to itself, such as \texttt{(0, 1)}. When \texttt{UPDATE} creates a newer version, the old version's \texttt{t\_ctid} points forward to the new version's \texttt{(block, slot)}.
  \begin{implementbox}
  Why is \texttt{ItemPointerData} 6 bytes instead of 8 bytes when it holds a 32-bit block number plus a 16-bit slot number? In C, a struct with a \texttt{uint32} and a \texttt{uint16} gets 4-byte alignment and \texttt{sizeof} $= 8$, wasting 2 tail-padding bytes. PostgreSQL splits the block number into \emph{two 16-bit halves} (\texttt{bi\_hi} and \texttt{bi\_lo}). Alignment stays at 2 bytes and \texttt{sizeof(ItemPointerData)} stays \textbf{6 bytes}, shrinking every row header and every B-tree entry across the database.
  \end{implementbox}
  \item \textbf{Column count and chain flags (\texttt{[18..20)} \texttt{t\_infomask2}, 2 bytes)}: Stores the column count \texttt{natts} in its lower 11 bits and same-page update flags in its upper 5 bits.
  \item \textbf{Layout and commit-status flags (\texttt{[20..22)} \texttt{t\_infomask}, 2 bytes)}: Stores layout flags (null bitmap present, variable-width column present, or an external TOAST pointer for oversized out-of-line values, covered in Section~\ref{sec:ch02-toast}). It also caches commit/abort \textbf{hint bits} directly on the row so readers avoid repeated commit-log lookups.
  \item \textbf{Payload start offset (\texttt{[22..23)} \texttt{t\_hoff}, 1 byte)}: Records the exact byte offset where user column~1 begins after any optional null bitmap and alignment padding.
\end{itemize}

That brings us to offset~\textbf{23}. Why cannot user column~1 (\texttt{account\_id BIGINT}) start right at byte~23? On 64-bit CPUs, reading an 8-byte integer expects an 8-byte aligned address ($\texttt{MAXALIGN} = 8$). Because every row starts at an 8-byte aligned \texttt{pd\_upper}, user columns must also start at a multiple of 8 from the row header.

Watch the arithmetic across three cases:
\begin{enumerate}
  \item \textbf{Row has zero \texttt{NULL} values (\texttt{HEAP\_HASNULL = 0})}: PostgreSQL omits \texttt{t\_bits[]} completely. Rounding $23$ up to the next multiple of $8$ yields $\texttt{t\_hoff} = \mathbf{24}$ (byte~23 is a single zero-padding byte).
  \item \textbf{Row has at least one \texttt{NULL}, and $1 \le \text{natts} \le 8$ columns (\texttt{HEAP\_HASNULL = 1})}: The null bitmap needs $\ceil{\text{natts}/8} = 1$ byte, which drops neatly into \textbf{byte~23}---the exact byte previously wasted on padding. Now $23 + 1 = 24$, so \textbf{$\texttt{t\_hoff}$ is still $24$}. Even better, any \texttt{NULL} column writes \textbf{0 data bytes} into the row payload. (In PostgreSQL's bitmap, bit~\texttt{1} means \emph{present} and bit~\texttt{0} means \emph{NULL}.)
  \item \textbf{Row has at least one \texttt{NULL}, and $\text{natts} = 9$ columns}: Now the null bitmap needs $\ceil{9 / 8} = 2$ bytes (\texttt{[23..25)}), bringing the unaligned header to $25$ bytes. Rounding $25$ up to a multiple of $8$ jumps $\texttt{t\_hoff}$ from $24$ to \textbf{32 bytes} (7 padding bytes at \texttt{[25..32)}).
\end{enumerate}

\begin{trapbox}
Adding a 9th column (or a 73rd column, where $23 + 10 = 33 \to \texttt{t\_hoff} = 40$) to a wide nullable table adds an invisible \textbf{8-byte cliff} to every row with a \texttt{NULL}. On the bright side, \texttt{NULL} columns in PostgreSQL never reserve their column width on disk. A row with twenty \texttt{BIGINT} columns all set to \texttt{NULL} takes 23 header bytes + 3 bitmap bytes + 6 pad bytes = \textbf{32 bytes total}, not $160$ bytes.
\end{trapbox}

\subsection{CPU Alignment Padding and ``Column Tetris''}

Once PostgreSQL reaches \texttt{t\_hoff}, it writes each non-\texttt{NULL} column in exact \texttt{CREATE TABLE} order. Before writing column $i$, it advances the offset to the alignment boundary required by that column's type (\texttt{pg\_type.typalign}):

\begin{center}
\small
\begin{tabular}{@{}llp{6.6cm}l@{}}
\toprule
\textbf{\texttt{typalign}} & \textbf{Boundary} & \textbf{Common PostgreSQL Types} & \textbf{Width (\texttt{typlen})} \\
\midrule
\texttt{'d'} (double) & 8 bytes & \texttt{BIGINT} (\texttt{int8}), \texttt{DOUBLE PRECISION}, \texttt{TIMESTAMPTZ}, \texttt{TIMESTAMP} & 8 B (\texttt{INTERVAL}: 16 B) \\
\texttt{'i'} (int) & 4 bytes & \texttt{INTEGER} (\texttt{int4}), \texttt{REAL} (\texttt{float4}), \texttt{DATE}, 4B-header \texttt{varlena} & 4 B (or variable) \\
\texttt{'s'} (short) & 2 bytes & \texttt{SMALLINT} (\texttt{int2}) & 2 B \\
\texttt{'c'} (char) & 1 byte & \texttt{BOOLEAN}, \texttt{"char"}, \texttt{UUID} (16 B), short 1B-header \texttt{varlena} & 1 B, 16 B, or var. \\
\bottomrule
\end{tabular}
\end{center}

Look at \texttt{UUID} in the bottom row. Although a \texttt{UUID} is 16 bytes wide, its C type is an array of 16 single bytes (\texttt{unsigned char data[16]}), so \texttt{typalign = 'c'} (1-byte aligned, zero pre-padding). By contrast, \texttt{BIGINT} and \texttt{TIMESTAMPTZ} require 8-byte alignment (\texttt{'d'}). If the previous column ended at offset~25, PostgreSQL inserts \textbf{7 zero bytes} (\texttt{[25..32)}) so the \texttt{BIGINT} starts at offset~32.

Your C compiler applies the exact same rule to structs. On x86-64, \texttt{struct \{ char a; int64\_t b; \}} has \texttt{sizeof} 16, not 9, because \texttt{b} must start at offset~8. C pays that padding once in RAM; PostgreSQL pays it on disk, in the Write-Ahead Log, and in \texttt{shared\_buffers}. Java hides this because HotSpot automatically reorders class fields by size.

PostgreSQL \emph{never} reorders columns behind your back; physical order matches \texttt{CREATE TABLE} order. Let us compare two 50-million-row payment-event tables---one alternating narrow and 8-byte columns, and one ordered from widest alignment downward:

\begin{lstlisting}[language=SQL]
-- Layout A: Alternating 1B/2B and 8B columns ("Swiss-cheese tuple")
CREATE TABLE events_bad (
    is_settled   BOOLEAN     NOT NULL, -- 1B at [24..25) + 7B pad [25..32)
    account_id   BIGINT      NOT NULL, -- 8B at [32..40)
    region_code  SMALLINT    NOT NULL, -- 2B at [40..42) + 6B pad [42..48)
    created_at   TIMESTAMPTZ NOT NULL, -- 8B at [48..56)
    retry_flag   BOOLEAN     NOT NULL, -- 1B at [56..57) + 7B pad [57..64)
    amount_cents BIGINT      NOT NULL, -- 8B at [64..72)
    channel_id   INTEGER     NOT NULL, -- 4B at [72..76)
    fee_bps      SMALLINT    NOT NULL  -- 2B at [76..78) -> lp_len=78, MAXALIGN=80B!
);

-- Layout B: Identical 8 columns ordered 8B -> 4B -> 2B -> 1B ("Column Tetris")
CREATE TABLE events_good (
    account_id   BIGINT      NOT NULL, -- 8B at [24..32)
    created_at   TIMESTAMPTZ NOT NULL, -- 8B at [32..40)
    amount_cents BIGINT      NOT NULL, -- 8B at [40..48)
    channel_id   INTEGER     NOT NULL, -- 4B at [48..52)
    region_code  SMALLINT    NOT NULL, -- 2B at [52..54)
    fee_bps      SMALLINT    NOT NULL, -- 2B at [54..56)
    is_settled   BOOLEAN     NOT NULL, -- 1B at [56..57)
    retry_flag   BOOLEAN     NOT NULL  -- 1B at [57..58) -> lp_len=58, MAXALIGN=64B!
);
\end{lstlisting}

Check the math. Both tables store the exact same $8 + 8 + 8 + 4 + 2 + 2 + 1 + 1 = \mathbf{34\text{ bytes}}$ of user payload plus a 24-byte header ($58$ useful bytes total):
\begin{itemize}
  \item In \texttt{events\_bad}, three alignment gaps ($7 + 6 + 7 = 20\text{ B}$) inflate \texttt{lp\_len} to $78\text{ B}$, which \texttt{MAXALIGN} rounds to \textbf{80 bytes} on the page (+4~B slot = \textbf{84~B/row}). Each 8~KB page ($8{,}168$ usable bytes) holds $\floor{8{,}168 / 84} = \mathbf{97\text{ rows}}$. Across $50{,}000{,}000$ rows, \texttt{events\_bad} takes $515{,}464$ blocks $\approx \mathbf{4.22\text{ GB}}$.
  \item In \texttt{events\_good}, every column starts naturally on its boundary with \textbf{zero internal padding}: $\texttt{lp\_len} = 58\text{ B}$, \texttt{MAXALIGN} $= \mathbf{64\text{ bytes}}$ (+4~B slot = \textbf{68~B/row}). Each 8~KB page now holds $\floor{8{,}168 / 68} = \mathbf{120\text{ rows}}$. Across $50{,}000{,}000$ rows, \texttt{events\_good} takes $416{,}667$ blocks $\approx \mathbf{3.41\text{ GB}}$.
\end{itemize}
Reordering eight lines of Data Definition Language (DDL, i.e., \texttt{CREATE} or \texttt{ALTER TABLE}) saves \textbf{16 bytes per row} and \textbf{810 MB} of storage, WAL traffic, and RAM cache without changing a single query. If a table also has \texttt{TEXT} or \texttt{JSONB} columns, put all fixed-width \texttt{NOT NULL} columns \emph{first} ($8\text{B} \to 4\text{B} \to 2\text{B} \to 1\text{B}$) and variable-width or nullable columns \emph{last}. That lets PostgreSQL cache fixed byte offsets (\texttt{attcacheoff}) and jump straight to \texttt{amount\_cents} at offset~40 in $\Oh(1)$ instructions.

\section{TOAST: The Oversized-Attribute Storage Technique}
\label{sec:ch02-toast}
% ======================================================================

Stop and ask an uncomfortable question about fixed 8,192-byte pages. Every slot points to a single row inside a single 8~KB block. Subtracting the 24-byte page header plus one 4-byte slot leaves at most $8{,}160$ bytes on an empty page ($\texttt{MaxHeapTupleSize} = 8{,}160$). Yet PostgreSQL lets you insert a \textbf{400~KB} JSON document or a \textbf{50~MB} \texttt{TEXT} report into one column. Where do those bytes go when no row is allowed to span two 8~KB pages?

First, why \emph{does} PostgreSQL forbid rows from crossing page boundaries? Keeping every row inside one 8~KB frame keeps the storage engine simple and fast:
\begin{itemize}
  \item Reading a row by \texttt{ctid = (block, slot)} pins \textbf{one} buffer frame and takes \textbf{one} page lock---no multi-page lock deadlocks.
  \item Every 8~KB page carries a single log position (\texttt{pd\_lsn}) for crash recovery (Chapter~4).
  \item In-page compaction is a local \texttt{memmove} inside one 8,192-byte C array.
\end{itemize}
PostgreSQL goes one step further: it wants \emph{at least four rows} to fit on every 8~KB page whenever possible. That target sets the threshold at roughly \textbf{$2{,}000$ bytes} ($\texttt{TOAST\_TUPLE\_THRESHOLD} = 2{,}032\text{ B}$ on 64-bit builds). Whenever an inserted or updated row exceeds $2{,}032$ bytes, PostgreSQL runs \textbf{TOAST}---\emph{The Oversized-Attribute Storage Technique} (\texttt{src/backend/access/common/toast\_internals.c}).

\subsection{Inside \texttt{varlena} Headers: Saving 3 to 6 Bytes on Every Short String}

Before TOAST touches large strings, PostgreSQL first compacts \emph{short} variable-length values (\texttt{TEXT}, \texttt{VARCHAR}, \texttt{BYTEA}, \texttt{NUMERIC}, \texttt{JSONB}). Under the hood, all of them share a variable-length header layout called \textbf{\texttt{varlena}} (\texttt{src/include/varatt.h}).

A naive design prepends a 4-byte length integer to every string. On a 3-letter string like \texttt{'USD'} or \texttt{'Ada'}, a 4-byte header plus up to 3 alignment bytes would burn \textbf{7 overhead bytes} to store 3 characters. Instead, on little-endian CPUs (x86-64 and ARM64), PostgreSQL checks the \textbf{lowest two bits of the very first byte} to pick among four compact layouts:

\begin{center}
\small
\begin{tabular}{@{}lllp{5.8cm}@{}}
\toprule
\textbf{First-Byte Tag} & \textbf{Variant (\texttt{varatt.h})} & \textbf{Align} & \textbf{Payload \& Max Capacity} \\
\midrule
\texttt{xxxxxx00} (2b) & 4B uncompressed (\texttt{va\_4byte}) & 4 B (\texttt{'i'}) & Upper 30 bits = total len up to $2^{30}-1$ (\textbf{1~GB}) \\
\texttt{xxxxxx10} (2b) & 4B compressed (\texttt{va\_compressed}) & 4 B (\texttt{'i'}) & +4B \texttt{tcinfo} (raw size + \texttt{pglz}/\texttt{lz4} codec ID) \\
\texttt{xxxxxxx1} ($\neq \texttt{0x01}$) & \textbf{1B short} (\texttt{va\_1byte}) & \textbf{1 B (\texttt{'c'})} & Upper 7 bits = total len $1\dots 127$ (\textbf{0..126 data B}) \\
\texttt{00000001} (\texttt{0x01}) & \textbf{18B TOAST pointer} & \textbf{1 B (\texttt{'c'})} & Byte~1 = tag (\texttt{18}); bytes \texttt{2..18} = \texttt{varatt\_external} \\
\bottomrule
\end{tabular}
\end{center}

Look at the 1-byte short header (\texttt{xxxxxxx1}). Any \texttt{TEXT}, \texttt{VARCHAR}, or \texttt{NUMERIC} value up to \textbf{126 bytes} long takes just \textbf{1 header byte} and drops to \textbf{1-byte alignment} (zero pre-padding). That is why \texttt{VARCHAR(20)} is never smaller on disk than \texttt{TEXT} in PostgreSQL: both use the exact same 1-byte header.

Now check the fourth row. When byte~0 equals \texttt{0x01} and byte~1 equals \texttt{18} (\texttt{VARTAG\_ONDISK}), the giant value leaves the main table page completely. In its place sits an \textbf{18-byte pointer} (\texttt{struct varatt\_external}) recording the raw size, compressed size, companion table ID, and chunk ID:

\begin{lstlisting}[language=C]
/* From src/include/varatt.h -- 16-byte payload inside an 18-byte TOAST pointer */
typedef struct varatt_external
{
    int32    va_rawsize;     /* Original uncompressed size (incl. 4B header) */
    uint32   va_extinfo;     /* Lower 30 bits: stored size; upper 2: codec   */
    Oid      va_valueid;     /* Unique chunk_id inside the TOAST table       */
    Oid      va_toastrelid;  /* OID of pg_toast.pg_toast_<table_oid>         */
} varatt_external;
\end{lstlisting}

\subsection{The Four TOAST Strategies and \texttt{pg\_toast} Chunk Slicing}

Every column in \texttt{pg\_attribute} has a 1-character storage policy (\texttt{attstorage}) telling TOAST what it may do when a row passes $2{,}032$ bytes:

\begin{enumerate}
  \item \textbf{\texttt{PLAIN} (\texttt{'p'})}: Used by fixed-width types (\texttt{BIGINT}, \texttt{BOOLEAN}, \texttt{TIMESTAMPTZ}, \texttt{UUID}). Never compressed and never moved out-of-line.
  \item \textbf{\texttt{EXTENDED} (\texttt{'x'}, default for \texttt{TEXT}, \texttt{BYTEA}, \texttt{JSONB}, \texttt{NUMERIC})}: Allows \emph{both} inline compression (\texttt{pglz} by default, or faster \texttt{lz4} via \texttt{default\_toast\_compression = 'lz4'}) \emph{and} out-of-line chunk storage.
  \item \textbf{\texttt{EXTERNAL} (\texttt{'e'})}: Moves oversized values out-of-line while \textbf{disabling compression}. Two cases benefit from this. First, if a \texttt{BYTEA} column already holds pre-compressed PNGs, Zstandard archives, or ciphertext, compressing again wastes CPU for zero savings. Second, if queries read slices via \texttt{substring(payload, 50000, 80)}, uncompressed chunks let PostgreSQL jump straight to \textbf{one 2~KB chunk} instead of decompressing from byte~0.
  \item \textbf{\texttt{MAIN} (\texttt{'m'})}: Compresses inline and tries to keep the column \textbf{on the main page}. It moves the value out-of-line only when the row still exceeds $8{,}160$ bytes after \texttt{EXTENDED} and \texttt{EXTERNAL} columns have left.
\end{enumerate}

If no column is allowed to leave the page, an oversized row is rejected rather than split across two pages:
\begin{lstlisting}[language=SQL]
CREATE TABLE notes (body TEXT);
ALTER TABLE notes ALTER COLUMN body SET STORAGE PLAIN;
INSERT INTO notes SELECT repeat('x', 9000);
-- ERROR:  row is too big: size 9028, maximum size 8160
\end{lstlisting}
Here $9{,}028$ is the 24-byte row header + 4-byte length word + 9,000 payload bytes, exceeding the $8{,}160$-byte single-page limit.

Where do evicted values land? Whenever a table has a TOASTable column, PostgreSQL creates a hidden companion table \texttt{pg\_toast.pg\_toast\_}$\langle\text{oid}\rangle$ with a unique B-tree index on \texttt{(chunk\_id, chunk\_seq)}:

\begin{lstlisting}[language=SQL]
-- Conceptual schema of pg_toast.pg_toast_24576:
--   chunk_id   OID    (matches varatt_external.va_valueid)
--   chunk_seq  INT4   (0, 1, 2, ... in byte order)
--   chunk_data BYTEA  (up to TOAST_MAX_CHUNK_SIZE ~= 1,996 bytes each)
--   PRIMARY KEY (chunk_id, chunk_seq)
\end{lstlisting}

\begin{example}[Counting TOAST Chunks by Hand]
\label{ex:ch02-toast-chunks}
Suppose we add \texttt{audit\_json JSONB} (\texttt{EXTENDED}, \texttt{lz4}) to \texttt{accounts} (\texttt{oid = 24576}) and insert a row whose \texttt{audit\_json} serializes to $30{,}720\text{ bytes}$ ($30\text{ KiB}$).
\begin{enumerate}
  \item Because $30{,}720 + 49 > 2{,}032$, PostgreSQL first compresses \texttt{audit\_json} with \texttt{lz4}, shrinking it to \textbf{$9{,}000\text{ bytes}$}.
  \item $9{,}000 + 49 = 9{,}049\text{ B}$ still exceeds the $2{,}032$-byte target, so PostgreSQL moves the compressed bytes out-of-line.
  \item Each TOAST chunk holds at most $1{,}996\text{ bytes}$ ($\texttt{TOAST\_MAX\_CHUNK\_SIZE} = 1{,}996$, sized so four chunks pack cleanly onto one 8~KB TOAST page). Slicing $9{,}000\text{ bytes}$ yields:
  \[
    \ceil*{\frac{9{,}000}{1{,}996}} = \mathbf{5\text{ chunks}} \quad (\texttt{chunk\_seq} = 0, 1, 2, 3\text{ of }1{,}996\text{ B each, plus }\texttt{chunk\_seq} = 4\text{ of }1{,}016\text{ B}).
  \]
  \item Those 5 rows go into \texttt{pg\_toast.pg\_toast\_24576}. Meanwhile, the main \texttt{accounts} row replaces \texttt{audit\_json} with an \textbf{18-byte TOAST pointer}, keeping the main row at $49 + 18 = 67\text{ B}$ ($72\text{ B}$ aligned).
\end{enumerate}
\end{example}

\begin{applicationbox}
Understanding that 18-byte pointer explains two everyday production behaviors:
\begin{itemize}
  \item \textbf{Why \texttt{SELECT *} on wide tables is slow}: If an object-relational mapper (ORM) runs \texttt{SELECT * FROM accounts WHERE is\_active}, PostgreSQL must \emph{detoast} every matching row. It probes the TOAST index, reads 5 chunk rows, and decompresses 30~KB of JSON that your code immediately discards. Naming only the columns you need (\texttt{SELECT account\_id, balance\_cents}) scans $110+$ compact rows per 8~KB page and \textbf{never opens the TOAST table}.
  \item \textbf{Why \texttt{UPDATE} on narrow columns stays cheap}: When \texttt{UPDATE accounts SET balance\_cents = balance\_cents + 500} creates a new version of the main row (Chapter~5), \texttt{audit\_json} is unchanged. PostgreSQL \textbf{copies the 18-byte pointer verbatim} into the new row version without rewriting a single byte in \texttt{pg\_toast\_24576}. By contrast, appending one key to a 10~MB \texttt{JSONB} value rewrites all 10~MB of TOAST chunks.
\end{itemize}
\end{applicationbox}

\section{Double Buffering, \texttt{shared\_buffers}, Pins, and Clock-Sweep}
\label{sec:ch02-buffer-pool}
% ======================================================================

So far we have inspected 8~KB pages on disk. Now let us trace how a running PostgreSQL server moves those 8~KB blocks between NVMe storage and RAM.

PostgreSQL uses one OS process per client connection, and all backend processes attach to a shared RAM cache allocated at startup called \textbf{\texttt{shared\_buffers}} (\texttt{src/backend/storage/buffer/bufmgr.c}). Every read or write of a table, index, FSM, or VM page goes through \texttt{shared\_buffers} first.

\subsection{Why Not Just Rely on the Linux Page Cache? (Double Buffering)}

When a backend misses in \texttt{shared\_buffers}, it asks the OS kernel to read 8,192 bytes from the segment file (via the \texttt{pread()} system call). Inside \texttt{pread()}, Linux first reads the NVMe sectors into its own \textbf{OS page cache}, and then copies those 8,192 bytes into PostgreSQL's \texttt{shared\_buffers} frame. Briefly, the same 8~KB block sits in RAM \emph{twice}---once in the kernel cache and once in \texttt{shared\_buffers}. This \textbf{double buffering} is why database administrators (DBAs) usually set \texttt{shared\_buffers} to \textbf{25\%--40\% of machine RAM}, leaving the rest for the OS page cache plus query sort/hash memory.

Why not skip \texttt{shared\_buffers} and memory-map table files directly from the OS page cache with \texttt{mmap()}? Two hard requirements forbid it:
\begin{enumerate}
  \item \textbf{Strict Write-Ordering for Crash Safety (The WAL Rule)}: Chapter~4 proves the core rule of durability: \emph{a dirty 8~KB page must never reach disk before the log record describing its change (\texttt{pd\_lsn}) is synced to disk}. If PostgreSQL edited \texttt{mmap}ped kernel pages directly, Linux background threads could flush a half-committed page to NVMe before its log record hit disk. A power cut would then leave unrecoverable corruption. Holding dirty pages in user-space \texttt{shared\_buffers} ensures the kernel \emph{never sees} modified bytes until PostgreSQL checks $\texttt{FlushedWAL} \ge \texttt{pd\_lsn}$ and calls \texttt{pwrite()}.
  \item \textbf{Zero-Syscall Shared-Memory Reads}: Reading a hot B-tree root page in \texttt{shared\_buffers} stays entirely in user space: one hash lookup and one atomic CPU instruction, with zero kernel calls or 8~KB copies. (PostgreSQL~17 and~18 are also adding Direct I/O and \texttt{io\_uring} paths to cut OS-side double buffering.)
\end{enumerate}

\subsection{Inside \texttt{shared\_buffers}: Hash Partitions and \texttt{BufferDesc.state}}

Picture \texttt{shared\_buffers} with $N$ frames (say $\texttt{16GB} \implies N = 2{,}097{,}152$ frames of 8~KB) as three parallel arrays in shared memory (\path{src/include/storage/buf_internals.h}):
\begin{enumerate}
  \item \textbf{\texttt{BufferBlocks}}: A flat array of $N$ raw 8,192-byte page frames (\texttt{buf\_id = 0 .. N-1}).
  \item \textbf{Shared Buffer Lookup Hash Table}: Maps a page's 20-byte disk address (\texttt{BufferTag}: file locator, fork, and block number) to its frame index \texttt{buf\_id}. To keep 64 CPU cores from fighting over one lock, PostgreSQL splits this hash table across \textbf{128 independent lock partitions} (\texttt{NUM\_BUFFER\_PARTITIONS = 128}). Two backends looking up different blocks land in different partitions over 99\% of the time.
  \item \textbf{\texttt{BufferDescriptors}}: An array of $N$ \textbf{64-byte} frame headers (\texttt{BufferDesc}), sized to one CPU cache line so neighboring headers never bounce each other's cache lines.
\end{enumerate}

Inside each 64-byte frame header, PostgreSQL packs the frame's pin count, popularity score, and status flags into a \textbf{single 32-bit atomic integer} (\texttt{pg\_atomic\_uint32 state}):

\begin{lstlisting}[language=C]
/* Simplified from src/include/storage/buf_internals.h */
typedef struct BufferDesc
{
    BufferTag        tag;          /* (RelFileLocator, ForkNumber, BlockNumber) */
    int              buf_id;       /* Frame index 0 .. NBuffers-1               */

    /* Single 32-bit atomic word: [31..22 flags | 21..18 usage | 17..0 refcount] */
    pg_atomic_uint32 state;

    int              wait_backend_pgprocno; /* For cleanup-lock waiters         */
    int              freeNext;              /* Link in initial free list        */
    LWLock           content_lock;          /* Shared/Exclusive page byte lock  */
} BufferDesc;

/* Exact bit layout of BufferDesc.state:
 *   Bits  0..17 (18 bits): refcount (pin count, up to 262,143 concurrent pins!)
 *   Bits 18..21 ( 4 bits): usage_count (clock-sweep popularity, capped 0..5)
 *   Bits 22..31 (10 bits): BM_LOCKED, BM_DIRTY, BM_VALID, BM_TAG_VALID,
 *                          BM_IO_IN_PROGRESS, BM_PERMANENT, ...
 */
\end{lstlisting}

Why pack \texttt{refcount}, \texttt{usage\_count}, and \texttt{BM\_DIRTY} into one 32-bit word? Older PostgreSQL versions took a per-buffer spinlock on every pin and unpin, causing heavy CPU cache-line bouncing on hot index root pages. With one packed 32-bit \texttt{state} word, pinning a frame and bumping its popularity runs in \textbf{a single lock-free compare-and-swap (\texttt{CAS}) instruction}. Once \texttt{usage\_count} hits its cap of~\textbf{5}, \texttt{PinBuffer} simply adds $+1$ to \texttt{refcount}.

\subsection{Buffer Pins (\texttt{refcount}) vs.\ Content Locks (\texttt{LWLock})}

Two distinct tools protect a cached page: \textbf{pinning} the frame and \textbf{locking} its bytes.

\begin{center}
\small
\begin{tabular}{@{}llp{6.8cm}@{}}
\toprule
\textbf{Mechanism} & \textbf{Where Stored} & \textbf{What It Protects \& How Long It Is Held} \\
\midrule
\textbf{Pin} (\texttt{refcount > 0}) & \texttt{state[17:0]} & Prevents \emph{eviction} of the frame. Held across tuple evaluation; \textbf{never blocks} other readers or writers. \\
\textbf{Shared Lock} (\texttt{LW\_SHARED}) & \texttt{content\_lock} & Protects \texttt{pd\_linp[]} / tuple bytes from concurrent \texttt{memmove}; held for \textbf{microseconds} while locating tuples. \\
\textbf{Exclusive Lock} (\texttt{LW\_EXCLUSIVE}) & \texttt{content\_lock} & Acquired to insert/update tuples or modify header offsets; blocks other \texttt{LW\_SHARED}/\texttt{LW\_EXCLUSIVE} holders briefly. \\
\textbf{Cleanup Lock} & \texttt{LW\_EXCLUSIVE} + $\texttt{ref}=1$ & Required by \texttt{PageRepairFragmentation} / \texttt{VACUUM} before sliding tuple bytes so no C pointer goes stale. \\
\bottomrule
\end{tabular}
\end{center}

Trace one table-scan step to see why PostgreSQL needs both:
\begin{enumerate}
  \item Your backend hashes \texttt{(accounts, MAIN\_FORK, block 0)} to \texttt{buf\_id = 42}, bumps \texttt{refcount} ($0 \to 1$, \textbf{pinned}), and takes \texttt{content\_lock} in \texttt{LW\_SHARED} mode.
  \item Under \texttt{LW\_SHARED}, it checks which slots on Page~0 are visible, records them, and \textbf{immediately releases \texttt{content\_lock}}---while \emph{keeping its pin} ($\texttt{refcount} = 1$).
  \item Next, your backend runs \texttt{WHERE} filters and sends rows up the plan tree. Because \texttt{content\_lock} is free, another backend can grab \texttt{LW\_EXCLUSIVE} on Page~0, \texttt{INSERT} Row~4 into the free gap, and commit right away. Meanwhile, your pin ($\texttt{refcount} \ge 1$) forbids eviction and forbids \texttt{VACUUM} from sliding live row bytes underneath your C pointer.
  \item When your scan moves on to Page~1, it drops Page~0's \texttt{refcount} ($1 \to 0$, \textbf{unpinned}).
\end{enumerate}

\subsection{Clock-Sweep Eviction: Step-by-Step Trace on a 6-Frame Pool}

What happens when every frame in \texttt{shared\_buffers} is full and a backend misses on a block?

Textbooks teach doubly-linked \textbf{Least Recently Used (LRU)} queues: every read unlinks a node and moves it to the front of one global list. On a 64-core server doing two million cache hits per second, a global LRU queue stalls because every read mutates shared list pointers. In Java~6, \texttt{new LinkedHashMap<K,V>(16, 0.75f, true)} in access-order mode has the exact same trait: every \texttt{get()} relinks nodes, so wrapping it in \texttt{Collections.synchronizedMap} serializes every read behind one lock.

PostgreSQL avoids that bottleneck with \textbf{Clock-Sweep} (\texttt{StrategyGetBuffer} in \texttt{src/backend/storage/buffer/freelist.c}):
\begin{itemize}
  \item \textbf{On a buffer hit (the 99\% fast path)}: Touch \emph{nothing} global. Locally bump that frame's 4-bit \texttt{usage\_count} up to a cap of \textbf{5}. Capping at 5 (rather than 15) ensures that if the workload shifts, the clock hand never has to circle the pool 15 times to clear old pages.
  \item \textbf{On a buffer miss (eviction path)}: Advance the shared clock hand \texttt{nextVictimBuffer} modulo $N$, checking each frame:
  \begin{enumerate}
    \item \textbf{If $\texttt{refcount} > 0$ (pinned)}: Cannot evict. Leave \texttt{usage\_count} alone and step $\texttt{hand} \leftarrow (\texttt{hand} + 1) \bmod N$.
    \item \textbf{If $\texttt{refcount} = 0$ and $\texttt{usage\_count} > 0$}: Give the frame a second chance by decrementing $\texttt{usage\_count}$, and step $\texttt{hand}$ forward.
    \item \textbf{If $\texttt{refcount} = 0$ and $\texttt{usage\_count} = 0$}: \textbf{Victim found.} Pin the frame ($\texttt{refcount} = 1$) and advance \texttt{hand}. If \texttt{BM\_DIRTY} is set, check $\texttt{FlushedWAL} \ge \texttt{pd\_lsn}$ and write out the old page. (Usually the background writer \texttt{bgwriter} cleans low-usage buffers ahead of the clock hand so queries rarely wait on writes.) Finally, swap the hash-table tag and \texttt{pread()} the new 8~KB block with $\texttt{usage\_count} = 1$.
  \end{enumerate}
\end{itemize}

\begin{example}[Tracing the Clock Hand Across 6 Buffer Frames]
\label{ex:ch02-clock-trace}
Consider a 6-frame pool (\texttt{F0..F5}) with \texttt{nextVictimBuffer} starting at \textbf{Frame~0} and initial states \texttt{(refcount, usage)}:
\[
  \texttt{F0:(1, 3)}, \quad \texttt{F1:(0, 2)}, \quad \texttt{F2:(0, 1)}, \quad \texttt{F3:(2, 0)}, \quad \texttt{F4:(0, 1)}, \quad \texttt{F5:(0, 2)}.
\]
Watch how \texttt{StrategyGetBuffer} finds a victim when a backend misses on \texttt{accounts} block~9:
\begin{enumerate}
  \item \textbf{Tick 1 (Frame 0)}: $\texttt{refcount} = 1 > 0$ (pinned). Skip immediately; \texttt{F0} stays \texttt{(1, 3)}. Hand $\to$ \texttt{F1}.
  \item \textbf{Tick 2 (Frame 1)}: $\texttt{refcount} = 0, \texttt{usage} = 2 > 0$. Decrement $\texttt{usage}: 2 \to 1$. Hand $\to$ \texttt{F2}.
  \item \textbf{Tick 3 (Frame 2)}: $\texttt{refcount} = 0, \texttt{usage} = 1 > 0$. Decrement $\texttt{usage}: 1 \to \mathbf{0}$. Hand $\to$ \texttt{F3}.
  \item \textbf{Tick 4 (Frame 3)}: Even though $\texttt{usage} = 0$, $\texttt{refcount} = 2 > 0$ (two backends hold pins on \texttt{F3}). Pinned frames are immune to eviction; skip \texttt{F3}. Hand $\to$ \texttt{F4}.
  \item \textbf{Tick 5 (Frame 4)}: $\texttt{refcount} = 0, \texttt{usage} = 1 > 0$. Decrement $\texttt{usage}: 1 \to 0$. Hand $\to$ \texttt{F5}.
  \item \textbf{Tick 6 (Frame 5)}: $\texttt{refcount} = 0, \texttt{usage} = 2 > 0$. Decrement $\texttt{usage}: 2 \to 1$. Hand wraps $\to$ \texttt{F0}.
  \item \textbf{Tick 7 (Frame 0)}: Still pinned ($\texttt{refcount} = 1$). Skip. Hand $\to$ \texttt{F1}.
  \item \textbf{Tick 8 (Frame 1)}: $\texttt{refcount} = 0, \texttt{usage} = 1 > 0$. Decrement $\texttt{usage}: 1 \to 0$. Hand $\to$ \texttt{F2}.
  \item \textbf{Tick 9 (Frame 2)}: $\texttt{refcount} = 0$ \textbf{and} $\texttt{usage} = 0$. \textbf{Frame~2 is evicted.} It loads \texttt{accounts} block~9 with state \texttt{(refcount=1, usage=1)}, and \texttt{nextVictimBuffer} parks at \textbf{Frame~3} ready for the next miss.
\end{enumerate}
\end{example}

\subsection{Buffer Access Strategies: Why a 500 GB \texttt{Seq Scan} Doesn't Wipe Out RAM}

Clock-Sweep alone has one vulnerability. Suppose your server has $\texttt{shared\_buffers = 16 GB}$ ($2{,}097{,}152$ frames), holding your hot online transaction processing (OLTP) accounts and B-tree indexes at $\texttt{usage\_count} = 5$. At 2:00~PM, an analyst runs an unindexed report:
\begin{lstlisting}[language=SQL]
SELECT count(*), sum(amount_cents) FROM historical_ledger; -- 500 GB cold table!
\end{lstlisting}
Reading $500\text{ GB}$ streams $65{,}536{,}000$ cold blocks---more than \textbf{31 times larger} than the 16~GB pool. If every cold block used the global clock hand, the hand would spin dozens of times, knocking every hot OLTP page from $5$ down to $0$. One report would \textbf{wipe out your entire hot cache} for blocks read once and never needed again.

PostgreSQL stops this cache pollution with \textbf{Ring Buffers} (\emph{Buffer Access Strategies}, \texttt{GetAccessStrategy} in \texttt{freelist.c}):
\begin{itemize}
  \item \textbf{\texttt{BAS\_BULKREAD} (32-frame = 256~KB ring)}: Whenever a sequential scan reads a table larger than $\texttt{shared\_buffers} / 4$, the executor allocates a private ring of \textbf{32 frames} ($256\text{ KB}$). As the 500~GB scan streams blocks $0, 1, 2, \dots$, it recycles those same 32 frames over and over. If an OLTP query also touches one of those frames and bumps its $\texttt{usage\_count} > 1$ (or pins it), PostgreSQL keeps that popular frame in the main pool and pulls a fresh frame into the ring. Thus a 500~GB scan touches just 256~KB of \texttt{shared\_buffers}, leaving \textbf{99.998\%} of hot OLTP RAM untouched.
  \item \textbf{\texttt{BAS\_BULKWRITE} (2,048-frame = 16~MB ring)}: Used by \texttt{COPY FROM}, \texttt{CREATE TABLE AS}, and \texttt{SELECT INTO} so bulk loads cycle through 16~MB instead of flooding \texttt{shared\_buffers}.
  \item \textbf{\texttt{BAS\_VACUUM} (default 2~MB ring via \texttt{vacuum\_buffer\_usage\_limit})}: Keeps autovacuum inside a small ring so routine cleanup never evicts user query caches.
\end{itemize}

\begin{connectionbox}
\textbf{Synchronized sequential scans (\texttt{synchronize\_seqscans = on}).} Suppose Analyst~B starts a second \texttt{Seq Scan} on that 500~GB \texttt{historical\_ledger} halfway through Analyst~A's scan. PostgreSQL starts Analyst~B \emph{at the exact block Analyst~A is currently reading}, and wraps around to block~0 at the end. Both scans share the same 256~KB cache window and cut disk I/O in half. That is also why Chapter~1 warned that \texttt{SELECT} without \texttt{ORDER BY} never promises to return rows starting from block~0.
\end{connectionbox}

\begin{complexitybox}
\textbf{Physical Numbers Worth Memorizing}:
\begin{itemize}
  \item \textbf{Page size (\texttt{BLCKSZ})}: $8{,}192\text{ B}$ ($24\text{ B}$ \texttt{PageHeaderData} $\implies 8{,}168\text{ B}$ usable; $4\text{ B}$ per \texttt{ItemIdData} slot).
  \item \textbf{Segment size (\texttt{RELSEG\_SIZE})}: $131{,}072\text{ blocks} = 1\text{ GiB}$ per physical file; max standard table $\approx 32\text{ TiB}$.
  \item \textbf{Companion forks}: \texttt{\_fsm} = $1\text{ B}$/heap page in a binary max-heap tree; \texttt{\_vm} = $2\text{ bits}$/heap page ($32{,}672$ heap blocks $\approx 255\text{ MiB}$ per 8~KB VM block).
  \item \textbf{Tuple header}: $23\text{ B}$ struct $\to$ $\texttt{t\_hoff} = 24\text{ B}$ (with 0 nulls, or with nulls and $\le 8$ columns); $+4\text{ B}$ slot + 8-byte \texttt{MAXALIGN} means \textbf{even a single-boolean row costs $4 + 32 = 36\text{ bytes}$} on a page.
  \item \textbf{TOAST}: Triggers at $\approx 2{,}000\text{ B}$; short \texttt{varlena} uses $1\text{ B}$ header up to $126\text{ B}$; out-of-line pointer is $18\text{ B}$ pointing to $\approx 1{,}996\text{ B}$ chunks in \texttt{pg\_toast}.
  \item \textbf{\texttt{shared\_buffers}}: $128$ hash lock partitions; $\texttt{usage\_count} \in \{0 \dots 5\}$; \texttt{BAS\_BULKREAD} sequential-scan ring = $32\text{ frames} = 256\text{ KB}$.
\end{itemize}
\end{complexitybox}

A table \texttt{documents} with three \texttt{NOT NULL} columns (\texttt{doc\_id BIGINT}, \texttt{title TEXT}, \texttt{body TEXT}) stores a row with a 20-byte ASCII \texttt{title} and a $120{,}000$-byte \texttt{body}.
\begin{enumerate}[label=(\alph*)]
  \item Under default \texttt{EXTENDED} storage with \texttt{lz4}, \texttt{body} compresses by $3\times$ to $40{,}000$ bytes. How many rows are inserted into the \texttt{pg\_toast} table (assuming $\texttt{TOAST\_MAX\_CHUNK\_SIZE} = 1{,}996\text{ B}$), how many 8~KB TOAST heap pages do they occupy, and what is the exact \texttt{lp\_len} of the main heap row in \texttt{documents}?
  \item Suppose a hot API endpoint runs \texttt{SELECT substring(body, 110000, 64) FROM documents WHERE doc\_id = 42} ten thousand times per second. Compare how many TOAST chunks are fetched and decompressed per query under \texttt{EXTENDED} versus \texttt{EXTERNAL} storage. When does \texttt{EXTERNAL} win despite using $3\times$ more disk space?
\end{enumerate}
\end{exercise}

\begin{exercise}[Clock-Sweep Hand Simulation]
\label{ex:ch02-clock-sim}
A 5-frame toy buffer pool (\texttt{F0..F4}) starts with \texttt{nextVictimBuffer = F1} and states \texttt{(refcount, usage\_count)}:
\[
  \texttt{F0:(0, 3)}, \quad \texttt{F1:(1, 1)}, \quad \texttt{F2:(0, 2)}, \quad \texttt{F3:(0, 0)}, \quad \texttt{F4:(0, 4)}.
\]
\begin{enumerate}[label=(\alph*)]
  \item Backend~A misses on block~10 and calls \texttt{StrategyGetBuffer}. Trace every tick of the clock hand, give the victim frame, the new state of all 5 frames (assuming Backend~A keeps block~10 pinned for a moment), and the new position of \texttt{nextVictimBuffer}.
  \item Immediately afterward, Backend~A unpins its buffer ($\texttt{refcount}: 1 \to 0$) while Backend~B unpins \texttt{F1} ($\texttt{refcount}: 1 \to 0$), and Backend~C misses on block~11. Trace \texttt{StrategyGetBuffer} again from the current \texttt{nextVictimBuffer} until the second victim is chosen, listing the final \texttt{(refcount, usage\_count)} of every frame.
\end{enumerate}
\end{exercise}

\begin{exercise}[Sizing Ring Buffers vs.\ Cache Pollution]
\label{ex:ch02-ring-calc}
A server has $\texttt{shared\_buffers} = 32\text{ GiB}$. Two workloads run concurrently: $4{,}000$ OLTP point lookups per second hitting a $20\text{ GiB}$ hot index/heap working set, and a batch extract-transform-load (ETL) pipeline running \texttt{Seq Scan} over a $2\text{ GiB}$ staging table \texttt{raw\_imports} ten times per minute.
\begin{enumerate}[label=(\alph*)]
  \item Using PostgreSQL's $\texttt{shared\_buffers} / 4$ threshold for \texttt{BAS\_BULKREAD}, determine whether \texttt{Seq Scan} on \texttt{raw\_imports} uses the 256~KB ring buffer or allocates straight from the main pool, and explain why.
  \item Now suppose \texttt{raw\_imports} grows from $2\text{ GiB}$ to $12\text{ GiB}$. How does \texttt{Seq Scan}'s buffer allocation behavior suddenly change, and what happens to \texttt{EXPLAIN (ANALYZE, BUFFERS)} \texttt{shared hit} vs.\ \texttt{shared read} counts across consecutive scans of \texttt{raw\_imports}?
\end{enumerate}
\end{exercise}
