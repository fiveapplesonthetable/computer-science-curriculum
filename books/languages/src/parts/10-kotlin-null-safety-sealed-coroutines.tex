\chapter{Kotlin From Java 6: Null-Safety, Algebraic Hierarchies, and Coroutines on the JVM}
\label{ch:kotlin-null-sealed-coroutines}

In Chapter~9 we saw one path away from Java~6. TypeScript leaves the JVM altogether, treats types as mathematical sets of shapes, and erases every static annotation down to JavaScript on V8. That design fits browser interfaces and Node.js gateways well, yet it carries real trade-offs. Numbers default to 64-bit IEEE-754 floats unless you reach for \texttt{bigint}. Each V8 isolate runs on a single user-space thread, and no nominal class descriptors survive at runtime to guard external boundaries automatically.

Now ask a different engineering question---the exact question JetBrains faced in 2010 while maintaining millions of lines of Java~6 IDE and server code. \emph{What if we keep the JVM itself, and only fix the static language sitting on top of it?} Keeping the JVM preserves HotSpot's C2 JIT compiler, mature concurrent garbage collectors, profiling tools, and twenty years of tested Java libraries.

Look back at our list of Java~6 pain points from Chapter~1:
\begin{enumerate}
  \item \textbf{Billion-dollar nullability:} every reference type \texttt{Account} implicitly includes \texttt{null}, turning every dot (\texttt{acct.getOwner().trim()}) into a runtime \texttt{NullPointerException} gamble.
  \item \textbf{Ceremony and mutability by default:} an immutable three-field value record requires 65 lines of constructors, getters, \texttt{equals}, \texttt{hashCode}, and \texttt{toString}.
  \item \textbf{Wrapper boxing tax:} giving a primitive \texttt{long} account ID its own type \texttt{class AccountId} costs a 16-byte JVM object header plus pointer indirection on every instance.
  \item \textbf{Closed sum types require the Visitor pattern:} modeling a fixed set of payment outcomes demands four classes and a double-dispatch visitor interface.
  \item \textbf{One-thread-per-request concurrency:} every blocking JDBC or HTTP call ties up a 1~MB operating-system kernel thread, hitting an out-of-memory wall long before CPU or network bandwidth saturates.
\end{enumerate}

Kotlin solves all five problems while compiling down to standard JVM \texttt{.class} files. Those \texttt{.class} files call Java~6 JARs directly---and Java~6 code can call them right back---within the same process and heap. To master Kotlin as a Java~6 or Rust programmer, never treat its features as black-box syntax sugar. For every construct in this chapter, we will inspect \textbf{both} the Kotlin surface code \textbf{and} the JVM bytecode (decompiled back into Java~6) that \texttt{kotlinc} emits underneath. Watching the bytecode reveals the true cost of nullable primitives, \texttt{@JvmInline} value classes, \texttt{reified} generics, and \texttt{suspend} coroutines.

\section{Bridging Java 6 to Kotlin: Same Bytecode Machine, Sharper Lens}
\label{ch10:java6-to-kotlin-bridge}

Recall the compiler pipeline from Chapter~1: \texttt{javac} lowers Java source into \texttt{.class} bytecode, and HotSpot's JIT compiles hot bytecode paths into native machine instructions at runtime. When \texttt{kotlinc} compiles a Kotlin file, it targets that exact same JVM bytecode format (\texttt{aload}, \texttt{invokestatic}, \texttt{invokevirtual}, \texttt{checkcast}, \texttt{tableswitch}) plus a small runtime JAR (\texttt{kotlin-stdlib}, roughly 1.7~MB). It also attaches a \texttt{@kotlin.Metadata} annotation to each generated \texttt{.class} header. Other Kotlin compilations read \texttt{@kotlin.Metadata} to recover Kotlin-only type facts---nullability, \texttt{sealed} subclasses, and \texttt{inline} function bodies---that raw Java~6 bytecode descriptors cannot express on their own.

Let us warm up by translating four everyday Kotlin idioms straight down to the Java~6 bytecode \texttt{kotlinc} generates:

\begin{enumerate}
  \item \textbf{\texttt{val} vs.\ \texttt{var} and Properties (Not Raw Fields):}
  In Kotlin, \texttt{val} declares a read-only binding (like Java~6 \texttt{final}), while \texttt{var} declares a reassignable binding. On a class, \texttt{val balanceCents: Long} is \emph{not} a raw public Java field. Instead, \texttt{kotlinc} emits a \texttt{private final long balanceCents} backing field and a public \texttt{getBalanceCents()} method. Whether Java~6 calls \texttt{acct.getBalanceCents()} or Kotlin reads \texttt{acct.balanceCents}, both run the same \texttt{invokevirtual getBalanceCents()J} instruction. Later, you can replace a stored field with a computed getter like \texttt{val isOverdrawn: Boolean get() = balanceCents < 0L} without breaking binary compatibility.
  \item \textbf{Default Arguments via Synthetic Bitmask Bridges:}
  Java~6 requires writing three telescopic method overloads just to give two parameters default values. In Kotlin, you write one declaration:
\begin{lstlisting}[language=Kotlin]
fun openAccount(owner: String, currency: String = "USD", overdraftLimit: Long = 0L)
\end{lstlisting}
and \texttt{kotlinc} emits two methods in bytecode: the real 3-argument method, plus a synthetic bridge \texttt{openAccount\$default} that takes the same three arguments followed by an \texttt{int mask} and an unused \texttt{Object} marker. The bridge inspects bits of \texttt{mask} (\texttt{(mask \& 2) != 0}, \texttt{(mask \& 4) != 0}) to fill in whichever arguments the call site omitted. Adding a \texttt{@JvmOverloads} annotation tells \texttt{kotlinc} to emit the classic telescopic Java~6 overloads as well, so legacy Java callers get the defaults too.
  \item \textbf{Extension Functions Compile to Static Receiver-First Methods:}
  In Java~6 codebases, every project grows a drawer full of \texttt{StringUtils}, \texttt{CollectionUtils}, and \texttt{MoneyUtils} classes because you cannot add methods to \texttt{java.lang.String}. Kotlin lets you write a \emph{receiver type} right before the function name:
\end{enumerate}

\begin{lstlisting}[language=Kotlin]
// File: IbanStrings.kt
package ledger.util

fun String.maskedIban(): String {
    if (this.length <= 8) return "****"
    return this.take(4) + "..." + this.takeLast(4)
}

// Caller reads like a natural method call on String:
val safeLog = "DE89370400440532013000".maskedIban() // "DE89...3000"
\end{lstlisting}

How can Kotlin add \texttt{maskedIban()} to \texttt{java.lang.String} when \texttt{java.lang.String} is \texttt{final} inside \texttt{rt.jar}? It doesn't touch \texttt{java.lang.String} at all. Run \texttt{javap -c ledger.util.IbanStringsKt} and look at the decompiled Java~6 equivalent:

\begin{lstlisting}[language=Java]
// Exact JVM equivalent emitted by kotlinc for IbanStrings.kt:
public final class IbanStringsKt {
    public static final String maskedIban(String $this$maskedIban) {
        Intrinsics.checkNotNullParameter($this$maskedIban, "<this>");
        if ($this$maskedIban.length() <= 8) return "****";
        return StringsKt.take($this$maskedIban, 4) + "..."
             + StringsKt.takeLast($this$maskedIban, 4);
    }
}
\end{lstlisting}

\begin{trapbox}
\textbf{Extension Functions Dispatch Statically, Never Virtually.} Calling \texttt{a.describe()} on an extension function compiles to \texttt{invokestatic ExtensionsKt.\allowbreak{}describe(DeclaredType a)}, not \texttt{invokevirtual}. The JVM therefore picks the extension function using the \textbf{compile-time declared type} of the variable, \emph{not} the runtime class of the heap object. Suppose you define \texttt{fun Account.tag() = "base"} and \texttt{fun CorporateAccount.tag() = "corp"}. Writing \texttt{val x: Account = CorporateAccount(...); println(x.tag())} prints \texttt{"base"}. Use member methods inside an interface or sealed hierarchy whenever you need runtime polymorphism; reserve extension functions for stateless helpers attached from outside.
\end{trapbox}

\section{Nullability in the Type System: Splitting Every Reference Set in Two}
\label{ch10:nullability-type-system}

In Java~6, the reference type \texttt{String} actually represents the mathematical union $\mathrm{String} \cup \{\texttt{null}\}$, and the compiler refuses to let you name the subset $\mathrm{String}$ \emph{without} \texttt{null}. In Rust (Chapter~5), references are never null and optionality is an explicit sum type \texttt{Option<String>}. In TypeScript with \texttt{strictNullChecks} (Chapter~9), optionality is the explicit set union \texttt{string | null}.

Kotlin brings that exact set-theoretic split onto the JVM. Every type \texttt{T} in Kotlin has two distinct forms:
\begin{itemize}
  \item \textbf{\texttt{T} (non-null):} guaranteed at compile time never to hold \texttt{null}.
  \item \textbf{\texttt{T?} (nullable):} the mathematical union $[\![ \texttt{T} ]\!] \cup \{\texttt{null}\}$.
\end{itemize}
Because $[\![ \texttt{T} ]\!] \subsetneq [\![ \texttt{T?} ]\!]$, \textbf{every non-null type \texttt{T} is a subtype of its nullable counterpart \texttt{T?}} ($\texttt{String} <: \texttt{String?}$). Passing a \texttt{String} to a parameter expecting \texttt{String?} always succeeds; passing a \texttt{String?} to a parameter expecting \texttt{String} is a hard compile error.

At the bottom of Kotlin's lattice sits \texttt{Nothing} ($\emptyset$, the twin of TypeScript's \texttt{never} and Rust's \texttt{!}), which is a subtype of every type \texttt{T}. Its nullable sibling \texttt{Nothing?} ($\emptyset \cup \{\texttt{null}\} = \{\texttt{null}\}$) is the exact type of the literal \texttt{null}. At the top sits \texttt{Any} (the root of all non-null types, unifying classes and primitives like \texttt{Int}) directly below \texttt{Any?} (the universal top type).

\subsection{Zero-Wrapper Reference Nullability vs.\ Boxed Nullable Primitives}

Now ask the systems-programmer question: \textbf{what does \texttt{String?} vs.\ \texttt{String}---and \texttt{Long?} vs.\ \texttt{Long}---cost in JVM memory?}

In Java~8, the library team introduced \texttt{java.\allowbreak{}util.\allowbreak{}Optional<String>}. Unfortunately, \texttt{Optional} is an ordinary heap-allocated class. Wrapping a \texttt{String} reference inside \texttt{Optional.of(s)} allocates an \emph{extra} 16-byte JVM object header plus an 8-byte reference field (24 bytes with alignment) around the pointer.

Kotlin's \texttt{String?} pays \textbf{zero wrapper overhead}. At the hardware level, a 64-bit JVM reference pointer already reserves the all-zero bit pattern \texttt{0x0000000000000000} for \texttt{null}---the exact niche optimization we saw for Rust's \texttt{Option<\&T>} in Chapter~5. Therefore, in JVM bytecode:
\begin{itemize}
  \item Both \texttt{owner: String} and \texttt{memo: String?} compile to the \textbf{exact same bare JVM reference descriptor \texttt{Ljava/lang/String;}}. No \texttt{Optional} wrapper object is ever allocated.
  \item What if untyped Java~6 code passes \texttt{null} into a non-null Kotlin parameter across a JAR boundary? At the entry of public methods taking non-null references, \texttt{kotlinc} injects a cheap guard call (\texttt{Intrinsics.\allowbreak{}checkNotNullParameter}). That guard fails fast right at the boundary instead of letting \texttt{null} corrupt internal state ten calls deeper.
\end{itemize}

Now contrast reference types with 64-bit integers (\texttt{Long}). Every one of the $2^{64}$ bit patterns of a raw JVM primitive \texttt{long} (\texttt{J}) represents a valid signed integer from $-2^{63}$ to $2^{63}-1$; there is \emph{no spare bit pattern} left over to represent \texttt{null}. Here is what \texttt{kotlinc} must emit for \texttt{Long} vs.\ \texttt{Long?} (Figure~\ref{ch10:fig-kotlin-null-lattice}):
\begin{itemize}
  \item \textbf{\texttt{val cents: Long}} compiles to a raw 8-byte JVM primitive \texttt{long} (\texttt{J}) directly in a CPU register or stack slot---zero heap allocation, zero object header.
  \item \textbf{\texttt{val optionalFee: Long?}} \emph{must} compile to a boxed heap reference \texttt{Ljava/lang/Long;}. Whenever \texttt{optionalFee} is non-null (outside \texttt{Long.valueOf}'s tiny $-128..127$ cache), it points to a 24-byte heap object (16-byte JVM header + 8-byte \texttt{long}).
\end{itemize}

\begin{trapbox}
\textbf{Beware \texttt{Long?} and \texttt{Double?} Inside Million-Element Loops.} In Rust, \texttt{Option<i64>} occupies 16 bytes \emph{inline on the stack or inside a flat \texttt{Vec<Option<i64>>}} (an 8-byte tag+padding word next to the 8-byte \texttt{i64}, zero pointers, zero heap headers). On today's pre-Valhalla JVM, \texttt{Array<Long?>} or \texttt{List<Long>} allocates boxed \texttt{java.lang.Long} heap objects, scattering 24-byte nodes across memory. In hot financial aggregation loops on Kotlin/JVM, use Kotlin's specialized primitive array \texttt{LongArray} (which compiles to JVM \texttt{long[]}, a contiguous flat slab of 8-byte integers) and domain sentinels or parallel bitsets rather than \texttt{List<Long?>}.
\end{trapbox}

\subsection{Safe Calls, Elvis with \texttt{Nothing}, Smart Casts, and Platform Types}

Once \texttt{null} is isolated inside \texttt{T?}, Kotlin gives you concise, composable operators that compile directly into tight null-branching bytecode with zero allocations:

\begin{lstlisting}[language=Kotlin]
class Customer(val name: String, val taxCountry: String?)
class Account(val id: Long, val owner: Customer?)

fun resolveWithholdingCountry(account: Account?): String {
    // 1. Safe-call chain `?.` short-circuits to null on the first null link;
    // 2. Elvis `?:` supplies the right-hand fallback when the left side is null:
    return account?.owner?.taxCountry ?: "US"
}

fun requireOwnerName(account: Account?): String {
    // Because `throw ...` has type `Nothing` (empty set!), `Customer? ?: Nothing`
    // narrows `owner` directly to non-null `Customer` for the rest of the function!
    val owner: Customer = account?.owner
        ?: throw IllegalArgumentException("Account has no owner")
    return owner.name.trim() // `owner` is guaranteed non-null here!
}
\end{lstlisting}

Consider \texttt{val owner: Customer = account?.owner ?: throw ...} in \texttt{requireOwnerName}. Why does Kotlin allow a \texttt{throw} (or an early \texttt{return}) on the right-hand side of the Elvis operator \texttt{?:}? Apply the exact same set algebra we learned in Chapter~9. The left side of \texttt{?:} has type \texttt{Customer?}, which is $[\![ \texttt{Customer} ]\!] \cup \{\texttt{null}\}$. When \texttt{?:} handles the \texttt{null} case, the right side evaluates an expression of type \texttt{Nothing} ($\emptyset$). Thus the combined expression has type:
\[
  \bigl([\![ \texttt{Customer} ]\!] \setminus \{\texttt{null}\}\bigr) \;\cup\; [\![ \texttt{Nothing} ]\!]
  \;=\; [\![ \texttt{Customer} ]\!] \cup \emptyset
  \;=\; [\![ \texttt{Customer} ]\!].
\]
Compare this directly to Rust's \texttt{let Some(owner) = ... else \{ return ... \}} from Chapter~5: early-exit guards flatten nested \texttt{if (x != null)} pyramids into straight-line code.

Just like TypeScript's control-flow narrowing, \texttt{kotlinc} also performs \textbf{smart casts}. After \texttt{if (x != null)} or \texttt{if (x is CorporateAccount)}, \texttt{x} automatically narrows to non-null \texttt{T} or \texttt{CorporateAccount}. Notice one soundness rule where Kotlin is \emph{stricter} than TypeScript: \texttt{kotlinc} refuses to smart-cast a mutable \texttt{var} property (or a \texttt{val} with a custom getter) on an object. Another JVM thread could mutate that field between your \texttt{if (acct.owner != null)} check and your \texttt{acct.owner.name} read. Bind it to a local \texttt{val} first (\texttt{val owner = acct.owner; if (owner != null) ...}): JVM stack-frame locals are thread-private, so the smart cast is 100\% thread-safe.

\begin{trapbox}
\textbf{Guarding the Java 6 Boundary: Platform Types (\texttt{T!}).} What happens when Kotlin calls an unannotated legacy Java~6 method such as \texttt{java.sql.ResultSet.\allowbreak{}getString("memo")}? Forcing every Java return value to \texttt{String?} would demand thousands of redundant null checks, while assuming \texttt{String} would break the moment SQL returned \texttt{NULL}. Instead, \texttt{kotlinc} gives unannotated Java values a \textbf{platform type}, printed in diagnostics as \texttt{String!} (``\texttt{String} of unknown nullability''). Assigning a \texttt{String!} into \texttt{val s: String = rs.getString("memo")} emits a runtime \texttt{checkNotNullExpressionValue} check that throws \texttt{NullPointerException} immediately if SQL returned \texttt{NULL}. Rule of thumb: \emph{always write an explicit type} (\texttt{val memo: String? = rs.getString("memo")}) whenever a Java~6 value enters Kotlin.
\end{trapbox}

\section{Data, Value, and Sealed Types: Algebraic Modeling on the JVM}
\label{ch10:data-value-sealed}

With nullability tamed, let us bring the algebraic data types we loved in Rust and OCaml (Parts~II and~III) onto the JVM---and measure their exact object-header and bytecode costs.

\subsection{\texttt{data class}: Value Equality and Copy Without Boilerplate}

In Java~6, \texttt{Object.equals} defaults to pointer identity (\texttt{==}), so every domain value object (\texttt{Posting}, \texttt{Money}, \texttt{DateRange}) needs manual \texttt{equals}, \texttt{hashCode}, and \texttt{toString} implementations. Prefixing a Kotlin class with \texttt{data} instructs \texttt{kotlinc} to generate \texttt{equals}, \texttt{hashCode}, \texttt{toString}, \texttt{copy}, and \texttt{component1()}..\texttt{componentN()} destructuring methods directly from the primary constructor properties:

\begin{lstlisting}[language=Kotlin]
data class LedgerPosting(
    val accountId: AccountId,
    val amountCents: Long,
    val currency: String,
)

val p1 = LedgerPosting(AccountId(1001L), 25_00L, "USD")
val p2 = p1.copy(amountCents = 30_00L) // Immutable update; p1 is untouched!
val (acct, cents, curr) = p2           // Calls component1(), component2(), component3()
\end{lstlisting}

Notice Kotlin's equality operators (the reverse of Java~6): in Kotlin, \textbf{\texttt{a == b} compiles to null-safe structural \texttt{equals()}} (\texttt{Intrinsics.areEqual(a, b)}), while \textbf{\texttt{a === b} tests raw JVM heap pointer identity}. You will never again lose an afternoon in production because someone wrote \texttt{currency == "USD"} in Java~6 on a freshly allocated \texttt{String} and got \texttt{false}.

\begin{trapbox}
\textbf{Two Subtle \texttt{data class} Traps in Financial Code:}
\begin{enumerate}
  \item \textbf{Positional destructuring swaps same-typed fields silently.} Writing \texttt{val (from, to) = transfer} calls \texttt{component1()} and \texttt{component2()} purely by \emph{parameter position}, ignoring variable names. If a teammate reorders \texttt{data class Transfer(val toAccount: AccountId, val fromAccount: AccountId)}, every destructuring site silently debits the recipient and credits the sender. Prefer explicit property access (\texttt{transfer.fromAccount}) whenever a record has multiple fields of the same type.
  \item \textbf{Never put raw \texttt{ByteArray} or \texttt{LongArray} in a \texttt{data class} without overriding \texttt{equals}/\texttt{hashCode}.} On the JVM, array \texttt{.equals()} checks pointer identity rather than element contents (\texttt{Arrays.equals}). Two \texttt{data class HmacDigest(val bytes: ByteArray)} instances holding identical SHA-256 bytes will evaluate \texttt{d1 == d2} to \texttt{false}. Wrap byte buffers in an immutable \texttt{ByteString}, or override \texttt{equals}/\texttt{hashCode} with \texttt{contentEquals} and \texttt{contentHashCode}.
\end{enumerate}
\end{trapbox}

\subsection{\texttt{@JvmInline value class}: Zero-Header Domain Types on the JVM}

Recall from Chapter~1 why Java~6 engineers often avoided strongly typed wrappers like \texttt{AccountId} and \texttt{UsdCents} in high-throughput services. On a 64-bit JVM, wrapping an 8-byte \texttt{long} inside \texttt{final class AccountId} adds a 12-to-16-byte object header plus alignment padding (24 bytes on the heap). Worse, the referring object still pays another 8 bytes for the pointer, tripling memory use and causing L1 cache misses.

In Rust, \texttt{struct AccountId(i64)} has zero runtime header: at machine level it is just an \texttt{i64} in a CPU register. In TypeScript (Chapter~9), branded intersections \texttt{bigint \& \{ [Brand]: never \}} erased the wrapper at compile time. Kotlin achieves zero-allocation nominal wrappers on the JVM via \textbf{\texttt{@JvmInline value class}}:

\begin{lstlisting}[language=Kotlin]
@JvmInline
value class AccountId(val raw: Long) {
    init {
        require(raw > 0L) { "AccountId must be positive, got $raw" }
    }
}

@JvmInline
value class UsdCents(val raw: Long) {
    operator fun plus(other: UsdCents): UsdCents = UsdCents(this.raw + other.raw)
    operator fun minus(other: UsdCents): UsdCents = UsdCents(this.raw - other.raw)
}

fun bookDebit(account: AccountId, amount: UsdCents): UsdCents {
    return amount + UsdCents(150L) // + $1.50 wire fee
}
\end{lstlisting}

Now inspect the decompiled JVM bytecode emitted by \texttt{kotlinc} for \texttt{bookDebit}:

\begin{lstlisting}[language=Java]
// Exact JVM bytecode signature emitted by kotlinc (decompiled to Java):
// Notice the mangled suffix `-4k8pQ2A` and raw `long` (J) parameters & return!
public static final long bookDebit_4k8pQ2A/* $FF was: bookDebit-4k8pQ2A */(
    long account,
    long amount
) {
    return UsdCents.constructor_impl(amount + UsdCents.constructor_impl(150L));
}
\end{lstlisting}

Three details in that bytecode matter:
\begin{enumerate}
  \item \textbf{Zero heap allocation on the fast path:} Both \texttt{AccountId} and \texttt{UsdCents} were completely unboxed into raw 64-bit JVM \texttt{long} values passed in CPU registers. Even the call \texttt{UsdCents.\allowbreak{}constructor\_\allowbreak{}impl(150L)} is a static method returning primitive \texttt{long} (running the \texttt{init} validation check without allocating an object).
  \item \textbf{Why is the method name mangled to \texttt{bookDebit-4k8pQ2A}?} Suppose you overload \texttt{fun settle(x: UsdCents)} and \texttt{fun settle(x: EurCents)} in the same class. After unboxing, \emph{both} would share the JVM descriptor \texttt{settle(J)V}, which the classfile verifier rejects as a duplicate method. Hashing the value-class types into a suffix (\texttt{-4k8pQ2A} vs.\ \texttt{-9m2zR1B}) keeps their bytecode signatures distinct. In addition, a hyphen \texttt{-} is legal in JVM method names yet \emph{illegal} in Java source identifiers, stopping legacy Java~6 callers from passing swapped raw \texttt{long}s by mistake.
  \item \textbf{When does a \texttt{value class} still box onto the heap?} Just like Java~6 \texttt{int} $\to$ \texttt{Integer}, \texttt{kotlinc} generates a hidden wrapper class used \emph{only} when an object pointer is unavoidable. Boxing happens when \texttt{AccountId} is used as nullable \texttt{AccountId?}, upcast to \texttt{Any} or \texttt{Comparable<AccountId>}, or stored in a generic \texttt{List<AccountId>} (whose JVM backing array holds \texttt{Object[]} pointers).
\end{enumerate}

\subsection{\texttt{sealed interface} and Exhaustive \texttt{when}: Sum Types on the JVM}

Next, compare how Java~6, Rust, TypeScript, and Kotlin model a closed sum type of payment authorization outcomes. Marking a Kotlin \texttt{interface} or \texttt{class} as \textbf{\texttt{sealed}} requires all direct subtypes to live in the same package and compilation module. That rule lets \texttt{kotlinc} (and the JVM's \texttt{PermittedSubclasses} attribute on JDK~17+) know the complete, closed set of variants at compile time:

\begin{lstlisting}[language=Kotlin]
sealed interface AuthOutcome {
    data class Approved(
        val authCode: String,
        val authorizedAmount: UsdCents,
    ) : AuthOutcome

    data class Declined(
        val reason: String,
        val retryAfterSeconds: Int?,
    ) : AuthOutcome

    // `data object` = single JVM static singleton (zero allocation per return!)
    data object LedgerTemporarilyOffline : AuthOutcome
}

fun httpStatusFor(outcome: AuthOutcome): Int = when (outcome) {
    is AuthOutcome.Approved -> {
        // Smart-cast automatically to Approved: `outcome.authCode` is in scope!
        200
    }
    is AuthOutcome.Declined -> if (outcome.retryAfterSeconds != null) 429 else 422
    AuthOutcome.LedgerTemporarilyOffline -> 503
    // NO `else` branch needed -- and adding a 4th subtype breaks compilation here!
}
\end{lstlisting}

\texttt{when (outcome)} is a value-returning \emph{expression}, not a C/Java~6 \texttt{switch} statement that silently falls through when you forget \texttt{break}. Because \texttt{AuthOutcome} is \texttt{sealed}, \texttt{kotlinc} checks that the three arms (\texttt{Approved}, \texttt{Declined}, and the offline singleton) cover every subtype. Underneath, it emits a chain of JVM \texttt{instanceof} and \texttt{checkcast} instructions (or an \texttt{invokedynamic} type switch on newer targets).

\section{Functions, Receivers, Inline Reification, and Sequences}
\label{ch10:functions-inline-reified-sequences}

In Java~6, passing a two-line predicate into a method meant writing an eight-line anonymous inner class (\texttt{new Predicate<LedgerPosting>() \{ ... \}}). Each anonymous class generated a \texttt{MyService\$1.class} file on disk and allocated a heap object whenever it captured local variables. Kotlin treats functions as first-class types (\texttt{(LedgerPosting) -> Boolean}), yet function types alone would still pay closure-allocation and virtual-dispatch costs on the JVM. Let us see how \texttt{kotlinc} eliminates both taxes---and works around Java~6 generics erasure along the way.

\subsection{Lambdas with Receivers (\texttt{T.() -> R}): How Type-Safe Builders Work}

First, let us demystify one of Kotlin's signature features: \textbf{function types with a receiver}, written \texttt{Receiver.() -> ReturnType}. Beginners reading Gradle scripts, Ktor routes, or SQL builders often wonder how \texttt{journalEntry \{ debit(...); credit(...) \}} brings \texttt{debit} and \texttt{credit} into scope without an import.

There is zero compiler magic behind Kotlin DSLs. Recall from Section~\ref{ch10:java6-to-kotlin-bridge} that an extension function \texttt{fun String.maskedIban()} is just a static method whose first parameter is named \texttt{this}. A \textbf{lambda with receiver} \texttt{JournalBuilder.() -> Unit} applies the same trick to a function value. In JVM bytecode, it is an ordinary one-argument \texttt{Function1<JournalBuilder, Unit>} whose first argument becomes the implicit \texttt{this} inside \texttt{\{ ... \}}.

\begin{lstlisting}[language=Kotlin]
@DslMarker
annotation class LedgerDsl

@LedgerDsl
class JournalBuilder(private val description: String) {
    private val legs = mutableListOf<LedgerPosting>()

    fun debit(account: AccountId, cents: Long, currency: String = "USD") {
        require(cents > 0L)
        legs.add(LedgerPosting(account, -cents, currency))
    }

    fun credit(account: AccountId, cents: Long, currency: String = "USD") {
        require(cents > 0L)
        legs.add(LedgerPosting(account, +cents, currency))
    }

    fun build(): List<LedgerPosting> {
        val net = legs.sumOf { it.amountCents }
        check(net == 0L) { "Unbalanced journal '$description': net = $net cents" }
        return legs.toList()
    }
}

// Trailing lambda with receiver `JournalBuilder.() -> Unit`:
inline fun journalEntry(
    description: String,
    setup: JournalBuilder.() -> Unit,
): List<LedgerPosting> {
    val builder = JournalBuilder(description)
    builder.setup() // Equivalent to `setup.invoke(builder)`!
    return builder.build()
}

// Call site: reads like a custom language, fully type-checked by kotlinc!
val postings = journalEntry("Invoice #4092 settlement") {
    debit(AccountId(1010L), 250_00L)   // Implicitly `this.debit(...)` on JournalBuilder
    credit(AccountId(4000L), 250_00L)  // Implicitly `this.credit(...)` on JournalBuilder
}
\end{lstlisting}

Notice two details in those thirty lines:
\begin{enumerate}
  \item In Kotlin, whenever the \emph{last} parameter of a function is itself a function type, callers may move the lambda braces \emph{outside} the parentheses (\texttt{journalEntry("...") \{ ... \}}). Combine trailing lambdas with a receiver type \texttt{JournalBuilder.() -> Unit}, and you get type-safe builders in twenty lines of ordinary Kotlin.
  \item What does \texttt{@DslMarker} do? When builders nest (\texttt{ledger \{ journalEntry \{ ... \} \}}), both the outer \texttt{LedgerBuilder} and the inner \texttt{JournalBuilder} would otherwise stay in scope as implicit \texttt{this} receivers. Someone could then accidentally call an outer \texttt{journalEntry} method inside an inner block. Tagging builder classes with the same \texttt{@DslMarker} annotation hides outer implicit receivers unless you write \texttt{this@ledger} explicitly.
\end{enumerate}

\subsection{\texttt{inline} Functions and \texttt{reified T}: Defeating Closure Allocation and JVM Erasure}

Look back at the keyword \texttt{inline} on \texttt{inline fun journalEntry(...)} above. Why did we write \texttt{inline}, and what happens in JVM bytecode without it?

Suppose we write a helper \texttt{withDatabaseTx(conn) \{ ... \}} \emph{without} \texttt{inline} and call it inside a hot settlement loop. Inside the loop, our lambda captures two local variables: \texttt{accountId} and \texttt{amountCents}. Without \texttt{inline}, \texttt{kotlinc} compiles that lambda into a class implementing \texttt{Function0} (from \texttt{kotlin.\allowbreak{}jvm.\allowbreak{}functions}) with fields holding \texttt{accountId} and \texttt{amountCents}. Every single loop iteration then allocates a fresh closure object on the JVM heap and dispatches through \texttt{invokeinterface}.

Marking the higher-order function \textbf{\texttt{inline}} tells \texttt{kotlinc} to copy-paste \emph{both} the higher-order function \emph{and} the lambda body straight into each call site:

\begin{lstlisting}[language=Kotlin]
inline fun <T> timedOperation(metricName: String, block: () -> T): T {
    val startNs = System.nanoTime()
    try {
        return block()
    } finally {
        val elapsedNs = System.nanoTime() - startNs
        Metrics.recordLatency(metricName, elapsedNs)
    }
}
\end{lstlisting}

When a caller writes \texttt{val ok = timedOperation("post\_tx") \{ repo.save(tx) \}}, \texttt{kotlinc} splices the bytecode of \texttt{timedOperation} and \texttt{repo.save(tx)} straight into the caller's method body. There is \textbf{zero \texttt{Function0} class, zero heap closure allocation, and zero virtual call}. Because the lambda's bytecode now sits inside the caller's own stack frame, a bare \texttt{return} inside \texttt{timedOperation \{ if (invalid) return ... \}} performs a \textbf{non-local return} out of the enclosing function. That lets helpers like \texttt{synchronized}, \texttt{use}, and \texttt{forEach} behave just like built-in \texttt{for} and \texttt{if} statements. If an \texttt{inline} function hands a lambda to another thread pool where non-local \texttt{return} cannot jump across stack frames, mark that parameter \texttt{crossinline} (or \texttt{noinline} to keep it as a heap object).

Now watch the second payoff of \texttt{inline}---solving one of Java~6's most annoying generics limitations. In Java~6, because generic type arguments erase to \texttt{Object} in bytecode, you can \emph{never} write \texttt{if (x instanceof T)} or \texttt{T.class}:

\begin{lstlisting}[language=Java]
// Java 6: forced to pass an explicit `Class<T> clazz` token everywhere!
public static <T> T decodeJson(String raw, Class<T> clazz) {
    return OBJECT_MAPPER.readValue(raw, clazz);
}
// Call site repeats the type name:
TransferReq req = decodeJson(body, TransferReq.class);
\end{lstlisting}

Wait: why did Java~6 lose \texttt{T}? Because a normal generic method is compiled \emph{once} into a single bytecode body shared by all callers, so inside that single shared body \texttt{T} is unknown. What about a Kotlin \textbf{\texttt{inline}} function? Its bytecode is \emph{not} shared---it is pasted straight into each call site, and \textbf{at the call site the compiler knows the exact concrete type argument \texttt{TransferReq}}. Adding the modifier \textbf{\texttt{reified}} on an \texttt{inline} type parameter instructs \texttt{kotlinc} to embed the actual runtime \texttt{Class} token at every inlined call site:

\begin{lstlisting}[language=Kotlin]
inline fun <reified T : Any> decodeJson(raw: String): T {
    // Legal ONLY because `inline` + `reified` substitutes the concrete Class<T> at call sites!
    return OBJECT_MAPPER.readValue(raw, T::class.java)
}

inline fun <reified E : LedgerEvent> List<LedgerEvent>.filterVariant(): List<E> {
    val out = ArrayList<E>()
    for (item in this) {
        if (item is E) out.add(item) // Real JVM `instanceof` emitted for concrete E!
    }
    return out
}

// Call sites: zero Class<T> boilerplate, checked at runtime by the JVM!
val req: TransferReq = decodeJson(rawBody) // Inlines `ldc TransferReq.class`!
\end{lstlisting}

\begin{intuitionbox}
\textbf{Four Generics Strategies Compared.} The four generics designs in this book line up on one spectrum:
\begin{itemize}
  \item \textbf{TypeScript:} 100\% compile-time erasure; neither \texttt{List} nor \texttt{T} leaves a nominal runtime descriptor.
  \item \textbf{Java~6 (and non-inline Kotlin):} type-argument erasure; the container \texttt{ArrayList} exists at runtime, while \texttt{<T>} erases to \texttt{Object} plus \texttt{checkcast} at callers.
  \item \textbf{Kotlin \texttt{inline <reified T>}:} call-site bytecode inlining substitutes the concrete \texttt{T::class.java} and \texttt{instanceof} instructions at each caller without needing VM changes.
  \item \textbf{C++ Templates \& Rust Generics:} full compile-time monomorphization generates distinct native machine-code functions \emph{and} specialized flat memory layouts (\texttt{Vec<i64>} vs.\ \texttt{Vec<Posting>}). Note what Kotlin \texttt{reified} \emph{cannot} do: you still cannot declare a class \texttt{class Cache<reified T>} because class fields live on the heap across methods and cannot be ``inlined''.
\end{itemize}
\end{intuitionbox}

\subsection{Eager \texttt{Iterable} Extensions vs.\ Lazy \texttt{Sequence<T>}}

Here is a performance trap that catches almost every developer arriving in Kotlin from Java~8 \texttt{Stream}s or Rust \texttt{Iterator}s. Compare these two pipelines over a list of one million ledger postings:

\begin{lstlisting}[language=Kotlin]
// Pipeline A: EAGER `Iterable` extensions -- allocates TWO intermediate ArrayLists!
val firstThreeLargeIdsEager: List<AccountId> = postings
    .filter { it.amountCents >= 100_000_00L } // Allocates full List #1 of all matches!
    .map { it.accountId }                     // Allocates full List #2 of all AccountIds!
    .take(3)                                  // Copies first 3, throws the rest to GC!

// Pipeline B: LAZY `Sequence<T>` -- zero intermediate lists, stops on match #3!
val firstThreeLargeIdsLazy: List<AccountId> = postings
    .asSequence()
    .filter { it.amountCents >= 100_000_00L } // Builds lightweight Sequence stage
    .map { it.accountId }                     // Builds lightweight Sequence stage
    .take(3)                                  // Pulls elements ONE BY ONE until 3 match!
    .toList()                                 // Terminal op materializes 3-element List
\end{lstlisting}

Why did Kotlin make standard \texttt{List.filter} and \texttt{List.map} \emph{eager} instead of lazy? Look at how \texttt{Iterable.filter} is written in \texttt{kotlin-stdlib}: it is an \textbf{\texttt{inline}} function containing a plain \texttt{for} loop. On a small 10-element list, a single \texttt{.map \{ ... \}} allocates \emph{zero} closure or iterator objects and runs as fast as a hand-written Java~6 \texttt{for} loop. Chain \emph{multiple} stages (\texttt{filter} $\to$ \texttt{map} $\to$ \texttt{take}) over a million elements, however, and eager evaluation builds a brand-new intermediate \texttt{ArrayList} after every dot. Calling \texttt{.asSequence()} switches to vertical pull-based lazy evaluation---just like Rust's \texttt{iter().filter(...).map(...).take(3).collect()}---pulling one element through all stages before touching the next.

\section{Kotlin Coroutines Under the Hood: CPS State Machines and Structured Concurrency}
\label{ch10:coroutines-cps-structured}

We now reach the centerpiece of server-side and Android Kotlin engineering: \textbf{coroutines}.

Start with the hardware arithmetic that broke Java~6's one-thread-per-request server model. Suppose our payment gateway receives $100{,}000$ concurrent checkout requests during a flash sale. Each request spends $0.2$~ms of CPU time checking signatures and $150$~ms waiting on network I/O (PostgreSQL plus an external card network).

In Java~6 (classic Tomcat or blocking thread pools), every \texttt{java.lang.Thread} wraps a 1:1 operating-system kernel thread (\texttt{pthread} on Linux):
\begin{itemize}
  \item Each JVM thread reserves a contiguous \textbf{1~MB native call stack} by default (\texttt{-Xss1m}), plus kernel bookkeeping. Multiplied by $100{,}000$ concurrent requests, thread stacks alone demand \textbf{$100\text{ GB}$ of reserved address space}. Long before reaching that mark, the process hits the OS thread limit and crashes under $10\%$ CPU load with \texttt{OutOfMemoryError: unable to create new native thread}.
  \item Even at $10{,}000$ threads, parking and waking kernel threads costs roughly $1.5\text{--}3\,\mu\text{s}$ per context switch and thrashes CPU caches across disjoint 1~MB stacks.
\end{itemize}

To escape the 1~MB-per-connection wall in Java~6--8, engineers turned to asynchronous callbacks (Netty listeners or \texttt{CompletableFuture}). Callbacks solved the memory problem: $100{,}000$ small heap state objects fit in under $20$~MB. Readability, however, collapsed. Loops, \texttt{try/catch/finally} cleanup, and sequential logic fractured into nested callbacks whose stack traces began on an anonymous event-loop thread with all caller context lost.

Kotlin asks a clean compiler question. \textbf{What if you write ordinary sequential code with normal loops and \texttt{try/finally}, mark pausing functions with \texttt{suspend}, and let \texttt{kotlinc} compile each one into a tiny heap state machine?}

\subsection{Inside \texttt{kotlinc}: Continuation-Passing Style (CPS) and the \texttt{label} Switch}

Let us write a realistic twelve-line \texttt{suspend} function with two network suspension points, and then inspect the \emph{exact} Java~6 equivalent state machine that \texttt{kotlinc} generates.

\begin{lstlisting}[language=Kotlin]
suspend fun settleWire(txId: Long, feeCents: Long): Receipt {
    // State 0: runs up to Suspension Point #1
    val account: Account = fetchAccountAsync(txId)
    // State 1: resumes here once `account` arrives over the socket!
    val debitedCents: Long = account.balanceCents - feeCents
    val receipt: Receipt = postClearingHouseAsync(account.id, debitedCents)
    // State 2: resumes here once `receipt` arrives!
    auditLog(txId, receipt.confirmationCode)
    return receipt
}
\end{lstlisting}

The function \texttt{settleWire} makes two calls to other \texttt{suspend} functions: \texttt{fetchAccountAsync} and \texttt{postClearing\-HouseAsync}. Those two points divide the function body into \textbf{three sequential basic blocks (States 0, 1, and 2)}. Notice which local variables must stay alive \emph{across} suspension points:
\begin{itemize}
  \item \texttt{txId} and \texttt{feeCents} are alive across Suspension Point~\#1 (and \texttt{txId} is still needed after Suspension Point~\#2 for \texttt{auditLog}).
  \item \texttt{account} is computed at the end of State~0 and consumed in State~1; it is never used in State~2.
\end{itemize}
When \texttt{settleWire} releases its JVM worker thread to wait 80~ms on PostgreSQL, it \emph{cannot} leave \texttt{txId} and \texttt{feeCents} sitting on the thread stack. Another coroutine will reuse that exact OS thread stack two microseconds later.

So \texttt{kotlinc} performs two mechanical transformations:
\begin{enumerate}
  \item \textbf{Continuation-Passing Style (CPS) signature rewrite:} Every \texttt{suspend fun foo(args): R} gains a hidden trailing parameter \texttt{Continuation<? super R> \$completion}, and its JVM return type becomes \textbf{\texttt{Object}}. Why \texttt{Object}? A suspending call returns \emph{either} an immediate \texttt{Receipt} (when data is already cached) \emph{or} the sentinel \texttt{CoroutineSingletons.\allowbreak{}COROUTINE\_SUSPENDED}. Returning \texttt{COROUTINE\_SUSPENDED} tells the caller: ``I registered a socket callback; unwind the JVM stack now and free this worker thread.''
  \item \textbf{State-machine \texttt{ContinuationImpl} class:} \texttt{kotlinc} generates a compact class holding an \texttt{int label} field ($0, 1, 2$) plus fields (\texttt{J\$0}, \texttt{J\$1}, \texttt{L\$0}) for only those locals that cross a suspension point.
\end{enumerate}

Here is the decompiled Java~6 code corresponding directly to \texttt{kotlinc}'s bytecode for \texttt{settleWire}:

\begin{lstlisting}[language=Java]
// Simplified Java 6 decompilation of kotlinc's CPS state machine for `settleWire`:
public static final Object settleWire(
    long txId,
    long feeCents,
    Continuation<? super Receipt> $completion
) {
    // Re-entering from resumeWith? Reuse existing state machine; else allocate once!
    SettleWireCont sm;
    if ($completion instanceof SettleWireCont
            && (((SettleWireCont) $completion).label & Integer.MIN_VALUE) != 0) {
        sm = (SettleWireCont) $completion;
        sm.label -= Integer.MIN_VALUE;
    } else {
        sm = new SettleWireCont($completion);
    }

    Object $result = sm.result;
    Object SUSPENDED = CoroutineSingletons.COROUTINE_SUSPENDED;

    switch (sm.label) {
        case 0: {
            ResultKt.throwOnFailure($result); // Rethrow if resumed with an exception
            sm.J$0 = txId;                    // Spill `txId` to heap frame
            sm.J$1 = feeCents;                // Spill `feeCents` to heap frame
            sm.label = 1;                     // Next resume enters `case 1:`!
            $result = fetchAccountAsync(txId, sm);
            if ($result == SUSPENDED) {
                return SUSPENDED;             // Unwind JVM stack -> OS thread is FREE!
            }
            // Fast path: if already complete, fall straight through to case 1!
        }
        case 1: {
            feeCents = sm.J$1;                // Restore `feeCents`
            txId = sm.J$0;                    // Restore `txId`
            ResultKt.throwOnFailure($result);
            Account account = (Account) $result;
            long debitedCents = account.getBalanceCents() - feeCents;

            sm.J$0 = txId;                    // Keep `txId` for State 2
            sm.label = 2;                     // Next resume enters `case 2:`!
            $result = postClearingHouseAsync(account.getId(), debitedCents, sm);
            if ($result == SUSPENDED) {
                return SUSPENDED;             // Unwind JVM stack -> OS thread is FREE!
            }
        }
        case 2: {
            txId = sm.J$0;                    // Restore `txId`
            ResultKt.throwOnFailure($result);
            Receipt receipt = (Receipt) $result;
            auditLog(txId, receipt.getConfirmationCode());
            return receipt;                   // Normal completion!
        }
        default:
            throw new IllegalStateException("Invalid coroutine state");
    }
}
\end{lstlisting}

Reading that \texttt{switch (sm.label)} block from top to bottom answers two questions.
\begin{itemize}
  \item \textbf{How much memory does a suspended coroutine take?} \texttt{SettleWireCont} stores an object header, caller-continuation and context links, \texttt{int label}, \texttt{Object result}, and two \texttt{long} slots \texttt{J\$0} and \texttt{J\$1}. With compressed pointers, that totals \textbf{under 64 bytes on the JVM heap}, versus $1{,}048{,}576$~bytes for a parked OS thread. Spawning $100{,}000$ waiting coroutines uses a few dozen megabytes of young-generation heap instead of $100$~GB of kernel stacks.
  \item \textbf{What happens when the PostgreSQL socket finishes reading?} Netty or NIO wakes on a worker thread and calls \texttt{sm.resumeWith(Result.success(account))}. A non-recursive loop inside \texttt{BaseContinuationImpl.resumeWith} stores \texttt{sm.result = account}, flips the sign bit on \texttt{sm.label}, and calls \texttt{settleWire(0L, 0L, sm)}, jumping straight to \texttt{case 1:} via \texttt{tableswitch}. If the socket failed with \texttt{IOException}, \texttt{resumeWith(Result.failure(ex))} enters \texttt{case 1:} and \texttt{throwOnFailure} rethrows inside any surrounding \texttt{try/catch/finally}.
\end{itemize}

\begin{connectionbox}
\textbf{Kotlin CPS Coroutines vs.\ Rust \texttt{Future} State Machines (Preview of Chapter 12).} Both Kotlin and Rust use \emph{stackless} coroutines: the compiler turns \texttt{suspend} and \texttt{async} functions into state machines, unlike Go's 2~KB \emph{stackful} goroutines in Chapter~11. Yet they differ in one key memory detail:
\begin{itemize}
  \item \textbf{Kotlin (push-resumed CPS, per-frame heap object):} when \texttt{A()} calls suspending \texttt{B()}, which calls suspending \texttt{C()}, suspending allocates three small linked \texttt{ContinuationImpl} objects on the JVM heap ($A \leftarrow B \leftarrow C$). Because the JVM has a fast bump-pointer young-generation allocator, those tiny frames are cheap and allow direct recursive \texttt{suspend} calls.
  \item \textbf{Rust (pull-polled \texttt{Future::poll}, single flat inline struct):} when \texttt{async fn A()} awaits \texttt{B()}, which in turn awaits \texttt{C()}, Rust fuses all three state machines into \textbf{one contiguous inline \texttt{enum}} whose exact byte size is known at compile time. Spawning a top-level task on \texttt{tokio::spawn} allocates once, and nested \texttt{.await} calls allocate \emph{zero} extra heap blocks. Because that flat struct can hold pointers into its own fields across \texttt{.await} points, Rust requires \texttt{Pin<\&mut Self>} so it never moves in memory (Chapter~12).
\end{itemize}
\end{connectionbox}

\subsection{Dispatchers and Structured Concurrency: Taming Background Work}

Knowing how a single coroutine suspends is half the story; the other half is deciding \emph{which thread pool executes each resumption} and \emph{who owns the lifecycle of spawned coroutines}.

In \texttt{kotlinx.coroutines}, a \textbf{\texttt{CoroutineDispatcher}} governs thread scheduling:
\begin{itemize}
  \item \textbf{\texttt{Dispatchers.Default}:} a work-stealing pool sized to the number of CPU cores ($\max(2, N_{\text{cores}})$), designed strictly for CPU-bound calculation (hashing, JSON parsing, sorting).
  \item \textbf{\texttt{Dispatchers.IO}:} an elastic thread pool (up to $\max(64, N_{\text{cores}})$ threads) designed strictly to wrap \textbf{legacy blocking Java~6 calls} such as JDBC queries or blocking file I/O. It shares underlying worker threads with \texttt{Default} to avoid extra context switches, and you hop onto it via \texttt{withContext(\allowbreak{}Dispatchers.IO) \{ ... \}}.
  \item \textbf{\texttt{Dispatchers.Main}:} single UI event-loop thread (on Android/Desktop), keeping UI mutations race-free just like browser JavaScript.
\end{itemize}

Even more important than dispatchers is \textbf{Structured Concurrency}, popularized in Kotlin by Roman Elizarov. Think about why \texttt{new Thread(runnable).start()} in Java~6 leaks resources in large servers: once started, a detached thread has no lexical parent. If a client disconnects after 10~ms, or one of two parallel fraud checks fails after 5~ms, detached tasks keep burning database connections in the dark, and unhandled exceptions vanish.

Kotlin enforces a strict lexical invariant: \textbf{you cannot call \texttt{launch} or \texttt{async} out of thin air---every coroutine must be spawned inside a \texttt{CoroutineScope} whose \texttt{Job} forms a strict parent--child tree} (Figure~\ref{ch10:fig-structured-concurrency}):

\begin{lstlisting}[language=Kotlin]
data class EnrichedAccount(val account: Account, val riskScore: Int, val fxRate: BigDecimal)

// `coroutineScope` creates a lexical child scope; it NEVER returns until ALL children finish!
suspend fun loadEnrichedAccount(accountId: Long): EnrichedAccount = coroutineScope {
    // Spawn two concurrent child coroutines in parallel:
    val riskDeferred = async { fetchFraudRiskScoreAsync(accountId) }
    val fxDeferred   = async { fetchSpotFxRateAsync("USD", "EUR") }
    val account      = fetchAccountAsync(accountId)

    // If `fetchFraudRiskScoreAsync` throws an IOException after 5ms:
    // 1. `fxDeferred` is AUTOMATICALLY cancelled immediately!
    // 2. `coroutineScope` waits for `fxDeferred` cleanup (`finally` blocks), then rethrows!
    EnrichedAccount(
        account = account,
        riskScore = riskDeferred.await(),
        fxRate = fxDeferred.await(),
    )
}
\end{lstlisting}

Memorize the three guarantees of Kotlin's parent--child \texttt{Job} tree:
\begin{enumerate}
  \item \textbf{Lifetime containment (no leaked background work):} a \texttt{coroutineScope \{ ... \}} block cannot return to its caller until every child coroutine launched inside it has reached a terminal state (completed or finished cancelling).
  \item \textbf{Downward cancellation:} cancelling the parent scope (for instance, when an HTTP client disconnects or \texttt{withTimeout(250.milliseconds)} expires) recursively cancels every descendant coroutine in the subtree.
  \item \textbf{Upward failure propagation (\texttt{coroutineScope} vs.\ \texttt{supervisorScope}):} in a standard \texttt{coroutineScope}, if \emph{any} child throws an uncaught non-cancellation exception, the parent cancels all sibling children before rethrowing upward. That all-or-nothing rule fits computing one combined result like \texttt{EnrichedAccount}. When a batch processor launches \emph{independent} tasks where failure of task~\#1 must \emph{not} abort task~\#2, wrap them in \textbf{\texttt{supervisorScope \{ ... \}}} instead. A supervisor scope keeps downward cancellation intact while turning off upward sibling-killing.
\end{enumerate}

\begin{trapbox}
\textbf{Two Coroutine Cancellation Traps That Freeze Production Servers:}
\begin{enumerate}
  \item \textbf{Swallowing \texttt{CancellationException} inside \texttt{catch (e: Exception)}.} Kotlin cancels a suspended coroutine by resuming its continuation with \texttt{CancellationException}. In a retry loop like \texttt{while (true) \{ try \{ doRpc() \} catch (e: Exception) \{ log.warn(e) \} \}}, that broad \texttt{catch} swallows \texttt{CancellationException} and keeps looping forever. Always rethrow it first: \texttt{catch (e: CancellationException) \{ throw e \}}.
  \item \textbf{Cooperative CPU loops must check \texttt{ensureActive()}.} Coroutine cancellation never kills a thread mid-instruction; it checks for cancellation \emph{at suspension points} (\texttt{delay}, \texttt{withContext}, non-blocking socket I/O). A pure CPU loop has zero suspension points and ignores cancellation unless you call \texttt{ensureActive()} or \texttt{yield()} periodically.
\end{enumerate}
\end{trapbox}

\subsection{Cold \texttt{Flow<T>} vs.\ Hot \texttt{Channel<T>} and \texttt{StateFlow<T>}}

A \texttt{suspend fun} produces one asynchronous value, while a \texttt{Sequence<T>} pulls synchronous values on the caller's thread. What if an operation produces an \emph{asynchronous stream of values over time}, such as ten million PostgreSQL ledger rows or live FX ticks? Kotlin splits asynchronous streams into \textbf{cold} and \textbf{hot} primitives:

\begin{itemize}
  \item \textbf{Cold \texttt{Flow<T>} (lazy suspending recipe, with automatic backpressure):} Defining \texttt{val rows = flow \{ ... \}} starts \emph{zero} I/O and spawns no background coroutine. Nothing runs until a caller invokes the terminal \texttt{rows.collect \{ writeCsv(it) \}}. Inside \texttt{flow \{ ... \}}, \texttt{emit(value)} is itself a \textbf{\texttt{suspend} function} that calls the collector's lambda directly. When \texttt{writeCsv} spends 5~ms on slow disk I/O, \texttt{emit} suspends the database producer for 5~ms automatically, giving you zero-configuration \textbf{backpressure}.
  \item \textbf{Hot \texttt{Channel<T>} and \texttt{StateFlow<T>} (active concurrent communication):} Whereas each \texttt{.collect()} on a cold \texttt{Flow} starts a fresh run, a \textbf{\texttt{Channel<T>}} is a hot, thread-safe bounded queue between independent coroutines. Calling \texttt{send} suspends when the buffer is full, and calling \texttt{receive} suspends when it is empty---the Communicating Sequential Processes model we will study in Go in Chapter~11. Meanwhile, a \textbf{\texttt{StateFlow<T>}} holds a single latest state value (such as live circuit-breaker health) broadcast to all current subscribers.
\end{itemize}

\begin{connectionbox}
\textbf{Looking Ahead to Chapter 11 (Go and the Grand Synthesis).} Chapters~9 and~10 explored two distinct designs. TypeScript gave us structural set types with 100\% compile-time erasure on a single-threaded event loop. Kotlin kept the JVM heap and bytecode ecosystem while adding null-safety, \texttt{@JvmInline} value types, \texttt{sealed} hierarchies, and CPS coroutine state machines. Notice that both TypeScript (\texttt{async}/\texttt{await}) and Kotlin (\texttt{suspend}) split functions into two ``colors'': synchronous vs.\ suspending. In Chapter~11, we meet \textbf{Go}, which drops classes, exceptions, and function coloring in favor of flat value structs, 16-byte implicit interfaces, and 2~KB \emph{stackful} goroutines---before comparing all eight languages side by side.
\end{connectionbox}

\begin{exercise}[Hand-Compiling a \texttt{suspend} Loop into a CPS State Machine]

            return fetchAccountAsync(id)
