\chapter{TLS: Securing the Web}

Every chapter so far has built a single component. AES is a permutation on $128$-bit
blocks. GCM turns it into authenticated encryption. Diffie--Hellman lets two
strangers agree on a secret over a monitored channel, and elliptic curves make that
agreement small and fast. Digital signatures prove authorship, and certificates
(Chapter~24) bind a public key to a domain name you can read. TLS is the protocol
that assembles all of these pieces to secure the web.

When your browser shows a padlock and the address bar reads
\texttt{https://}, you are speaking \textbf{TLS}: Transport Layer Security. It is
the protocol underneath HTTPS, but also underneath secure email (Simple Mail Transfer Protocol (SMTP) over TLS),
encrypted Domain Name System (DNS) queries, most Virtual Private Networks (VPNs), the control channel of countless mobile apps, and the
back-end traffic of essentially every cloud service. Trillions of TLS handshakes
happen every day. In TLS, a single mismatched assumption between components has repeatedly become a real
attack with a logo and a CVE number.

We will focus on \textbf{TLS 1.3}, standardized in 2018 as RFC 8446. It is the
version you should deploy because its design fixes two decades of attacks on
earlier versions.

\section{What TLS provides, and against whom}

TLS assumes a \textbf{Dolev--Yao} attacker: an adversary who controls the
network and can read, drop, reorder, replay, and inject any packet.
She controls the routers, the coffee-shop access point, possibly the ISP. The
only thing she cannot do is break the cryptographic primitives or read memory
inside the endpoints. This models the public Internet.

Against that attacker, a completed TLS connection between a client (Alice's
browser) and a server (Bob's web server) promises three things.

\begin{itemize}
\item \textbf{Confidentiality.} Everything after the handshake --- URLs, cookies,
form data, page contents --- is encrypted. Eve sees ciphertext and traffic sizes,
not plaintext.
\item \textbf{Integrity.} Eve cannot alter a single byte of the conversation
without detection. Every record is authenticated; a flipped bit makes decryption
fail loudly.
\item \textbf{Authentication.} Alice's browser cryptographically verifies that it
is really talking to the server that owns \texttt{example.com}, not to Eve
impersonating it. This relies on certificates and the PKI from
the previous chapter. (By default only the server is authenticated; client
authentication is optional and used in enterprise and mutual-TLS settings.)
\end{itemize}

\begin{focusbox}
\textbf{What TLS does \emph{not} promise.} It does not hide \emph{that} you talked
to a server, nor how much, nor when. The server's identity leaks through the Server Name Indication (SNI)
field (where the client states the domain name it wants to reach) and through the IP address itself. TLS protects the
\emph{contents and integrity} of a channel to an \emph{authenticated} endpoint. It
says nothing about whether that endpoint is trustworthy --- a phishing site can
get a perfectly valid certificate for \texttt{paypa1.com}. Anonymity is the job of
Tor; endpoint trust is the job of the user and the browser's UI.
\end{focusbox}

TLS 1.3 also guarantees \textbf{forward secrecy} (Chapter~23): if an attacker
later steals the server's long-term private key, they cannot decrypt past
traffic recordings.

\begin{intuitionbox}
The handshake is the short, expensive phase in which client and server,
communicating over a network full of eavesdroppers and impostors, agree on keys
nobody else can compute and check the server's identity. The record protocol is
the long, cheap phase that follows, in which every message is encrypted and
authenticated under those keys. Eve can watch records go by and can destroy
them, but she cannot read them, forge them, or impersonate either endpoint.
\end{intuitionbox}

\section{The shape of a handshake}

A TLS connection has two phases. The \textbf{handshake} runs first: it
establishes shared keys and authenticates the server, using public-key
cryptography. Then the \textbf{record protocol} takes over: it carries the actual
application data under fast symmetric authenticated encryption. The handshake is
the expensive part (a few public-key operations and one network round trip); the
record protocol is cheap and runs for the life of the connection.

In TLS 1.3, the handshake takes a single round trip (1-RTT) before the client
can send encrypted application data, whereas TLS 1.2 needed two. The client
speculatively sends its key share for a common key-exchange group in its first
message. Figure~\ref{ch25:fig-handshake-comparison} compares the two.

In the text below, messages in the clear are sent before any key exists.
Messages in braces $\{\cdots\}$ are encrypted under \emph{handshake} keys --- a key
the two parties can compute the instant the ServerHello arrives, even though the
server has not yet proven who it is. Messages in brackets $[\cdots]$ ride under the
final \emph{application} keys. That TLS 1.3 encrypts most of the handshake itself
(the certificate, the extensions) is a privacy win over 1.2, where the server's
certificate flew in plaintext for any eavesdropper to log.

\section{Step 1: key exchange (the ClientHello)}

The client opens with a \texttt{ClientHello}. It carries:

\begin{itemize}
\item a random nonce $r_C$ ($32$ bytes), to make every handshake unique;
\item a list of \emph{cipher suites} it supports --- named bundles specifying the
authenticated cipher and hash function, such as \texttt{TLS\_AES\_128\_GCM\_SHA256};
\item a list of \emph{supported groups} for key exchange, such as X25519,
\texttt{secp256r1} (TLS's wire name for the NIST P-256 elliptic curve from Chapter~21),
or finite-field groups;
\item one or more \emph{key shares}: for each group it is betting on, an
ephemeral public value (a curve point for an elliptic-curve group, or $g^a \bmod p$
for a finite-field group);
\item the \emph{server name} it wants to reach (the SNI extension), so a server
hosting many sites knows which certificate to present.
\end{itemize}

The key share is the central field. The client picks a fresh random secret $a$,
computes its public share, and sends it immediately. Because $a$ is used once and
erased when the connection ends, this is \textbf{ephemeral} Diffie--Hellman ---
written \textbf{DHE} over finite fields or \textbf{ECDHE} over elliptic curves ---
which provides forward secrecy. TLS 1.3 allows \emph{only} ephemeral DHE or ECDHE
key exchange; the older static-RSA key transport, where the client encrypted a
secret under the server's long-term RSA public key, was removed because it lacked
forward secrecy.

\subsection{A worked exchange with tiny numbers}

To see the arithmetic using a small multiplicative group, take the prime $p = 23$
and generator $g = 5$ of $\Zns{23}$.

The client picks secret $a = 6$ and computes its key share $A = g^{a} \bmod p = 5^{6} \bmod 23$ by repeated squaring:
\begin{align*}
  5^2 &= 25 \equiv 2 \pmod{23}, \\
  5^4 &\equiv 2^2 = 4 \pmod{23}, \\
  A &= 5^6 = 5^4 \cdot 5^2 \\
    &\equiv 4 \cdot 2 = 8 \pmod{23}.
\end{align*}
The client sends $A = 8$.

The server picks secret $b = 15$ (binary $1111_2 = 8 + 4 + 2 + 1$) and computes its key share $B = g^{b} \bmod p = 5^{15} \bmod 23$:
\begin{align*}
  5^8 &\equiv 4^2 = 16 \pmod{23}, \\
  B &= 5^{15} = 5^8 \cdot 5^4 \cdot 5^2 \cdot 5^1 \\
    &\equiv 16 \cdot 4 \cdot 2 \cdot 5 \pmod{23}.
\end{align*}
Reducing step by step modulo $23$: $16 \cdot 4 = 64 = 2 \cdot 23 + 18 \equiv 18$, then
$18 \cdot 2 = 36 \equiv 13$, and $13 \cdot 5 = 65 = 2 \cdot 23 + 19 \equiv 19 \pmod{23}$.
The server sends $B = 19$.

Each side now raises the peer's public share to its own private exponent:
\[
\text{client computes } B^{a} \bmod 23 = 19^{6} \bmod 23, \qquad
\text{server computes } A^{b} \bmod 23 = 8^{15} \bmod 23.
\]
On the client side, writing $19 \equiv -4 \pmod{23}$ keeps the numbers small:
\begin{align*}
  19^2 &\equiv (-4)^2 = 16 \pmod{23}, \\
  19^4 &\equiv 16^2 = 256 \equiv 3 \pmod{23}, \\
  19^6 &= 19^4 \cdot 19^2 \\
       &\equiv 3 \cdot 16 = 48 \equiv 2 \pmod{23}.
\end{align*}
On the server side:
\begin{align*}
  8^2 &= 64 \equiv 18 \pmod{23}, \\
  8^4 &\equiv 18^2 = 324 \equiv 2 \pmod{23}, \\
  8^8 &\equiv 2^2 = 4 \pmod{23}, \\
  8^{15} &= 8^8 \cdot 8^4 \cdot 8^2 \cdot 8 \\
         &\equiv 4 \cdot 2 \cdot 18 \cdot 8 \equiv 2 \pmod{23},
\end{align*}
since $4 \cdot 2 = 8$, $8 \cdot 18 = 144 = 6 \cdot 23 + 6 \equiv 6$, and
$6 \cdot 8 = 48 \equiv 2 \pmod{23}$. Both arrive at the same shared secret:
\[
Z = g^{ab} \bmod p = 2.
\]
Eve, watching the wire, sees $p = 23$, $g = 5$, $A = 8$, and $B = 19$; recovering $a$
or $b$ requires solving the discrete logarithm. With $p = 23$ she can check all $22$
exponents by hand; on a $256$-bit elliptic curve she cannot, and the confidentiality
of the exchange rests on that gap.

\begin{connectionbox}
Computing $g^a \bmod p$ takes $O(\log a)$ modular multiplications via
square-and-multiply (Chapter~3), which is why $5^{15}$ needed only four squarings
and multiplications instead of fourteen. Security rests on the discrete-log
assumption (Chapter~18) or, for X25519 and P-256, the elliptic-curve discrete-log
problem (Chapter~21). Raw $Z = g^{ab}$ is \emph{not} used directly as an encryption
key: group elements have algebraic structure and are not uniformly distributed bit
strings. Instead, $Z$ is fed into a \textbf{key-derivation function (KDF)} in
Section~\ref{ch25:schedule}, following Chapter~23's rule to hash Diffie--Hellman
outputs before keying symmetric ciphers.
\end{connectionbox}

\section{Step 2: the ServerHello and the handshake key}

The server receives the ClientHello, picks one of the offered groups, generates
its own ephemeral secret $b$, and replies with a \texttt{ServerHello} containing
its random nonce $r_S$, the chosen cipher suite, and its key share $B$. Once
this message arrives, both parties hold the same shared secret $Z = g^{ab}$
and the same \textbf{transcript} --- the exact byte-for-byte sequence of handshake
messages exchanged so far (here, the two hellos).

From this point on, every message is encrypted. The server derives the handshake
traffic keys (Section~\ref{ch25:schedule}) and sends the rest of its flight under
them.

\begin{trapbox}
At this moment the client has a confidential, integrity-protected channel to
\emph{somebody}, yet it does not know \emph{who}. Unauthenticated Diffie--Hellman
proves nothing about identity: an active Eve could have completed her own exchange
with the client. Confidentiality without authentication only gives a private line
to the attacker. Authentication is the job of the next two messages
(\texttt{Certificate} and \texttt{CertificateVerify}); until those verify, the
client treats the peer as unverified.
\end{trapbox}

\section{Step 3: the key schedule}
\label{ch25:schedule}

We have a shared secret $Z$, and from it we need separate keys to encrypt the
server's handshake messages, the client's handshake messages, application data in
each direction, and the \texttt{Finished} MACs. TLS 1.3 derives all of them with
\textbf{HKDF}, the HMAC-based key-derivation function from Chapter~23 (built on
HMAC from Chapter~15).

HKDF has two stages. \emph{Extract} takes a non-secret $\text{salt}$ and raw input
keying material ($\mathrm{IKM}$) and compresses them into a fixed-length, uniform
pseudorandom key ($\mathrm{PRK}$):
\[
\mathrm{PRK} = \operatorname{HKDF\text{-}Extract}(\text{salt}, \mathrm{IKM})
= \operatorname{HMAC}(\text{salt}, \mathrm{IKM}).
\]
\emph{Expand} stretches a secret key into as many output keys as needed, binding
each to a purpose string ($\text{label}$), a transcript hash ($\text{context}$),
and a target byte length $L$:
\[
\operatorname{HKDF\text{-}Expand\text{-}Label}(\text{secret}, \text{label}, \text{context}, L).
\]
Distinct ASCII labels such as \texttt{"c hs traffic"} and \texttt{"s hs traffic"}
ensure that keys derived for different roles behave independently even though they
come from the same secret. Setting $\text{context}$ to the hash $\Hash(\cdots)$ of
all handshake messages exchanged so far (using the cipher suite's hash function,
such as SHA-256) binds every derived key to the exact conversation transcript.

TLS 1.3 chains three Extract-and-Expand stages into a \textbf{key schedule}
(Figure~\ref{ch25:fig-keyschedule}). The first stage absorbs an optional
\textbf{pre-shared key (PSK)} --- a secret saved from a previous session with the
same server, replaced by a block of zero bytes on a fresh visit. The second stage
mixes in the fresh Diffie--Hellman secret $Z$, and the third produces the
application keys.

In Figure~\ref{ch25:fig-keyschedule}: the
\textbf{Early Secret} is extracted from the PSK (or a hash-length string of zero
bytes if there is none). The \textbf{Handshake Secret} extracts the Diffie--Hellman
shared secret $Z$, and from it both handshake traffic secrets are expanded so the
server can encrypt immediately after \texttt{ServerHello}. Once the handshake
finishes, the \textbf{Master Secret} (extracted with a zero-byte input because all
fresh entropy has already entered) produces the application traffic secrets and a
resumption secret for the next visit.

Each stage hands off to the next via the helper function
\[
\operatorname{Derive\text{-}Secret}(S, \text{label}, \text{msgs})
= \operatorname{HKDF\text{-}Expand\text{-}Label}\bigl(S, \text{label}, \Hash(\text{msgs}), L\bigr),
\]
where $S$ is the current stage's secret and $L$ is the hash output length ($32$
bytes for SHA-256). Evaluated with label \texttt{"derived"} and an empty message
string \texttt{""}, it turns the Early Secret into $\mathrm{Salt}_1$ for the
Handshake Secret, and turns the Handshake Secret into $\mathrm{Salt}_2$ for the
Master Secret.

\begin{whybox}
Why use a three-stage chain instead of a single Expand from $Z$? Three properties
motivate the design. \textbf{(1) Domain separation:} distinct labels keep handshake
keys cryptographically independent of application keys, so exposing one phase's key
does not expose another's. \textbf{(2) Transcript binding:} expanding each traffic
secret with the hash of the handshake messages so far ensures that tampering with
any message makes the two sides derive different keys, causing the \texttt{Finished}
check to fail. \textbf{(3) Clean PSK + DH mixing:} chaining two Extract calls folds
in both a resumed PSK and a fresh Diffie--Hellman secret $g^{ab}$, giving resumed
sessions forward secrecy too. TLS~1.2 derived session keys in one custom
pseudorandom-function (PRF) call without full transcript binding, enabling attacks
such as Triple Handshake (2014), where an active attacker stitched three sessions
together so two connections shared keys while disagreeing on who authenticated whom.
\end{whybox}

\begin{implementbox}
A toy of the TLS 1.3 key schedule using Python's \texttt{hmac} and
\texttt{hashlib}. It mirrors the three-stage structure with simplified label
formatting and fixed lengths. \textbf{Learning only: never use this to secure
anything.}

\begin{lstlisting}[language=Python]
import hmac, hashlib

def hkdf_extract(salt, ikm):
    return hmac.new(salt, ikm, hashlib.sha256).digest()

def hkdf_expand_label(secret, label, context, length=32):
    # Real TLS encodes (length, "tls13 "+label, context) into the info field.
    info = b"tls13 " + label + b"|" + context
    out, t, i = b"", b"", 1
    while len(out) < length:
        t = hmac.new(secret, t + info + bytes([i]), hashlib.sha256).digest()
        out += t
        i += 1
    return out[:length]

def derive_secret(secret, label, transcript_hash):
    return hkdf_expand_label(secret, label, transcript_hash)

zeros     = b"\x00" * 32
empty_th  = hashlib.sha256(b"").digest()                  # Hash("") for "derived"
dh_shared = b"...the g^{ab} bytes go here..."             # from the (EC)DHE step
th = hashlib.sha256(b"ClientHello||ServerHello").digest() # toy transcript hash

early_secret     = hkdf_extract(zeros, zeros)             # no PSK -> zeros
handshake_secret = hkdf_extract(
    derive_secret(early_secret, b"derived", empty_th), dh_shared)
c_hs_traffic     = derive_secret(handshake_secret, b"c hs traffic", th)
s_hs_traffic     = derive_secret(handshake_secret, b"s hs traffic", th)
master_secret    = hkdf_extract(
    derive_secret(handshake_secret, b"derived", empty_th), zeros)
# Application keys come from master_secret once the transcript is final.
print("client handshake key:", c_hs_traffic.hex())
\end{lstlisting}
\end{implementbox}

\section{Step 4: authentication (Certificate and CertificateVerify)}

Now the server proves it is who the client wanted. It sends, all under the
handshake key:

\begin{itemize}
\item \texttt{EncryptedExtensions} --- assorted negotiated parameters that do not
need to be public.
\item \texttt{Certificate} --- the server's X.509 certificate chain: its own
certificate (binding its public key to its domain name) followed by any
intermediate CA certificates up toward a root the client trusts. This is the PKI
machinery from Chapter~24.
\item \texttt{CertificateVerify} --- the authenticating step. The server takes the entire
handshake transcript hashed so far, signs it with the \emph{private key
corresponding to the public key in its certificate}, and sends the signature.
\end{itemize}

The CertificateVerify message binds the server's identity to this connection. The
certificate alone proves nothing: anyone can copy Bob's certificate, since it is
public. What an attacker cannot do is produce a valid signature over
\emph{this particular transcript} --- which includes the client's fresh random and
the ephemeral key shares --- without Bob's private key. The signature is fresh,
bound to this handshake, and unforgeable.

\begin{whybox}
\textbf{Why signing the transcript authenticates the key exchange.} The transcript
the server signs contains the ServerHello, hence the server's key share $B$, hence
(together with the client's $A$) the shared secret $Z$. So the signature
simultaneously proves that the server holds the certified private key \emph{and}
owns the key share from which the session keys will be derived.
This is the textbook \emph{signed Diffie--Hellman} pattern from
Chapter~23: ephemeral DH gives forward secrecy, a signature over the DH
values gives authentication, and binding them in one transcript stops a
man-in-the-middle from splicing her own key share in. If active Eve had injected
her share, the transcript Bob signs would not match the one Alice computed, and
verification --- or the Finished check --- fails.
\end{whybox}

The client verifies the certificate chain (validity dates, name match against the
SNI it requested, a path to a trusted root, revocation status), then verifies the
CertificateVerify signature against the public key in that certificate. Only if
both pass does the client believe it is talking to the real server.

\section{Step 5: Finished (the MAC that seals the handshake)}

The server sends one more handshake message: \texttt{Finished}. It is a MAC
(specifically $\operatorname{HMAC}$ under a finished key expanded from the handshake
traffic secret) computed over the hash of the \emph{entire transcript up to this
point}. The client, holding the same secret and transcript, recomputes the MAC and
checks it. Then the client sends its own \texttt{Finished} over the transcript
including the server's \texttt{Finished}, and the server verifies that in turn.

Figure~\ref{ch25:fig-downgrade-finished} traces what happens if an active attacker
edits an earlier handshake message in transit.

\begin{whybox}
\textbf{Why Finished defeats tampering and downgrades.} Every handshake message
(cipher suite list, supported groups, key shares, certificate) feeds into the
transcript hash. The \texttt{Finished} MAC covers that hash under a key derived
from $g^{ab}$, which Eve does not know. If Eve alters \emph{any} earlier message ---
swaps a strong cipher suite for a weak one, strips an elliptic-curve group, or flips
a bit in an extension --- the two sides' transcripts diverge, their MACs disagree,
and the handshake aborts. That mechanism gives TLS 1.3 \textbf{downgrade
protection}: although initial negotiation happens in cleartext, its outcome is
verified under the shared key before application data flows. TLS~1.2 did not
authenticate the full negotiation cleanly, and attacks such as FREAK and Logjam
(2015) forced connections down to 1990s U.S.-export-capped $512$-bit keys by
editing unprotected handshake messages.
\end{whybox}

\begin{focusbox}
\textbf{Summary of handshake guarantees.} Each flight pins down one of Section~1's
promises:
\begin{itemize}
\item \texttt{ClientHello} / \texttt{ServerHello} key shares $\Rightarrow$ a fresh
\emph{shared secret} (confidentiality and forward secrecy).
\item \texttt{Certificate} + \texttt{CertificateVerify} $\Rightarrow$ the server
holds the certified private key for the requested domain (authentication).
\item \texttt{Finished} (both directions) $\Rightarrow$ both peers saw the exact
same negotiation bytes (handshake integrity and downgrade protection).
\end{itemize}
\end{focusbox}

\section{The record protocol and AEAD}

With the handshake done, the connection switches to the \textbf{record protocol}.
Application data is split into records of up to $2^{14} = 16{,}384$ bytes of
plaintext each, and each record is sealed with an \textbf{AEAD} cipher
(authenticated encryption with associated data, Chapter~16). TLS 1.3 permits only
AEAD suites: AES-GCM, AES-CCM (Counter with CBC-MAC), or ChaCha20-Poly1305. Older
cipher-block-chaining (CBC, Chapter~13) and separate-MAC constructions are gone;
one primitive provides both confidentiality and integrity.

An AEAD seal takes four inputs --- the traffic key $k$, a per-record $\text{nonce}$,
associated data ($\mathrm{AD}$) that is authenticated without being encrypted, and
the $\text{plaintext}$ --- and outputs ciphertext plus an authentication tag:
\[
\operatorname{Seal}_k(\text{nonce}, \mathrm{AD}, \text{plaintext})
\longrightarrow (\text{ciphertext}, \text{tag}).
\]
Decryption recomputes the tag and rejects the record before releasing any plaintext
if verification fails, tearing down the connection on even a single flipped bit.

\subsection{Nonces and the sequence number}

AES-GCM and ChaCha20-Poly1305 fail catastrophically if a $(k, \text{nonce})$ pair
ever repeats: reusing an AES-GCM nonce leaks the XOR of two plaintexts and exposes
the authentication subkey, allowing tag forgeries (Chapter~16). TLS 1.3 prevents
nonce reuse without transmitting nonces on the wire. Each side keeps an implicit
$64$-bit \textbf{sequence number} $\mathrm{seq}_{64}$ starting at $0$ and
incrementing by $1$ per record, left-padded with $32$ zero bits ($0^{32}$) to match
the $96$-bit ($12$-byte) initialization vector (\texttt{static\_iv}) derived from
that direction's traffic secret:
\[
\text{nonce} = \mathtt{static\_iv} \xor \bigl(0^{32} \concat \mathrm{seq}_{64}\bigr).
\]

\begin{focusbox}
\textbf{Why this construction never repeats a nonce.} Within one key's lifetime,
distinct sequence numbers XORed with the same fixed $\mathtt{static\_iv}$ produce
distinct $96$-bit nonces, and client-to-server and server-to-client directions have
independent keys and IVs. Because both peers count records in lockstep over
reliable transport, the counter costs zero wire bytes. For instance, if the last
two bytes of $\mathtt{static\_iv}$ are $\mathtt{A5C3}$, records $0, 1, 2$ use nonces
ending in $\mathtt{A5C3}, \mathtt{A5C2}, \mathtt{A5C1}$. Long before the $64$-bit
counter can wrap, AES-GCM's safety bound (about $2^{24.5} \approx 2.4 \times 10^7$
full-size records per key) triggers a \texttt{KeyUpdate} message, which applies a
one-way HKDF step (\emph{ratcheting}) to derive a fresh traffic secret and erase the
old one.
\end{focusbox}

\subsection{What the record header authenticates}

In TLS 1.3, every encrypted record carries a $5$-byte cleartext outer header: a
frozen content-type byte (\texttt{0x17}, the code for \texttt{application\_data},
used even on encrypted handshake records), a legacy version field (\texttt{0x0303},
TLS~1.2's version bytes, retained so older network equipment does not drop packets),
and the $2$-byte ciphertext length. The true record type --- such as \texttt{0x16}
for handshake messages, \texttt{0x17} for application data, or \texttt{0x15} for
error and close notifications (\emph{alerts}) --- is appended to the plaintext
\emph{before} encryption, hiding record types from eavesdroppers. Passing the
$5$-byte outer header as the AEAD associated data ($\mathrm{AD}$) authenticates the
cleartext length and header fields without encrypting them
(Figure~\ref{ch25:fig-aead-record}).

lookups), saving battery while avoiding cache-timing leaks.

\section{Forward secrecy in TLS 1.3}

A protocol has \textbf{forward secrecy} if compromising long-term secrets in the
future does not compromise past session keys. In TLS 1.3 the server's long-term
secret is its certificate private key $sk_S$, while session keys come from the
\emph{ephemeral} Diffie--Hellman secret $Z = g^{ab}$, whose private exponents $a$
and $b$ are generated per connection and erased as soon as the handshake derives
traffic keys (Figure~\ref{ch25:fig-forward-secrecy}).

\begin{intuitionbox}
Suppose Eve records gigabytes of your encrypted TLS 1.3 traffic today and archives
it. Five years from now she steals Bob's server, including its certificate private
key $sk_S$. Can she decrypt the old recordings? \textbf{No.} That key only
\emph{signed} handshake transcripts; it never encrypted a session secret. The
encryption keys came from $g^{ab}$, and $a$ and $b$ were erased when those
connections closed. With only $g^a$ and $g^b$ on the recording, recovering $Z$
still requires solving a discrete logarithm. The stolen signing key lets Eve
impersonate Bob \emph{from now on} until the certificate expires or is revoked,
not read old sessions.
\end{intuitionbox}

\begin{historybox}
TLS grew out of Netscape's Secure Sockets Layer (SSL~2.0 in 1995 and SSL~3.0 in
1996, designed by Paul Kocher, Taher ElGamal, and colleagues) and was standardized
by the IETF as TLS~1.0 in 1999. Through TLS~1.2, a widely deployed option was
\emph{RSA key transport}: the client encrypted the session's premaster secret under
the server's long-term RSA public key, leaving every recorded session decryptable by
anyone who obtained that RSA private key at any point in the future. The 2013
Snowden disclosures showed the operational danger: bulk traffic recording combined
with later key compromise (by theft, subpoena, or coercion) exposed years of past
traffic at once. Under editor Eric Rescorla, TLS~1.3 (RFC~8446, 2018) deleted static
RSA key transport altogether, despite pushback from enterprises whose network
appliances (\emph{middleboxes}, such as corporate firewalls and traffic inspectors
placed between clients and servers) relied on copies of the server's RSA key to
decrypt internal traffic passively. In TLS~1.3, forward secrecy is mandatory rather
than an option an administrator can forget to turn on.
\end{historybox}

\section{Resumption and 0-RTT (and its one sharp edge)}

Re-running a full certificate signature and chain check for every connection to a
site you recently visited wastes both CPU and latency. TLS 1.3 lets the server send
a \textbf{session ticket} after a handshake: a pre-shared key (PSK) derived from the
\texttt{resumption\_master\_secret} that the client can present on a return visit to
skip certificate authentication. A resumed 1-RTT handshake still mixes fresh
Diffie--Hellman shares into the Handshake Secret, preserving forward secrecy.

TLS 1.3 also offers \textbf{0-RTT} (zero round-trip time) early data: using a
resumption PSK, the client can send encrypted application data in its first
\textbf{flight} (the initial batch of packets sent before waiting for a server
reply), eliminating handshake latency on repeat visits. That speedup comes at a
concrete security cost.

\begin{trapbox}
\textbf{0-RTT data has no replay protection.} Early data is encrypted under a key
derived from the PSK and the client's \texttt{ClientHello} alone, before the server
has contributed a fresh nonce or ephemeral share. Eve cannot read the ciphertext,
yet she \emph{can} copy the 0-RTT packets and send them to the server again. An
operation is \textbf{idempotent} if repeating it has the same effect as running it
once (such as an HTTP \texttt{GET} that fetches a static page), whereas a
\textbf{non-idempotent} request changes state on each execution (such as an HTTP
\texttt{POST} that transfers $\$100$ or posts a comment). Replaying a non-idempotent
0-RTT request executes the action a second time. Applications must therefore send
only idempotent read requests in 0-RTT, and many servers reject 0-RTT for everything
except safe \texttt{GET} requests.
\end{trapbox}

\section{Famous TLS attacks}

Two decades of attacks on SSL~3.0 and TLS~1.0--1.2 directly shaped TLS~1.3. Each
attack below exploited a real deployment, and each maps to a specific change in
TLS~1.3 that removed the underlying flaw.

\begin{attackbox}
\textbf{BEAST (2011) --- a predictable IV in CBC mode.} TLS~1.0 used CBC mode with a
shortcut: the IV for each record was the \emph{last ciphertext block of the previous
record}, visible on the wire before the next plaintext was chosen. Recall from
Chapter~13 that CBC encrypts block $i$ as $C_i = \Enc_k(P_i \xor C_{i-1})$. Suppose
Eve recorded an earlier target block $C^* = \Enc_k(S \xor C^*_{\mathrm{prev}})$
whose $16$-byte plaintext $S$ contains $15$ known bytes (such as an HTTP header
prefix) and one unknown cookie byte. Using malicious JavaScript in Alice's browser
to send chosen plaintext after a known previous ciphertext block $C_{i-1}$, Eve
tests a byte guess $G$ by submitting $P_i = G \xor C^*_{\mathrm{prev}} \xor C_{i-1}$:
\begin{align*}
  C_i &= \Enc_k(P_i \xor C_{i-1}) \\
      &= \Enc_k\bigl((G \xor C^*_{\mathrm{prev}} \xor C_{i-1}) \xor C_{i-1}\bigr) \\
      &= \Enc_k(G \xor C^*_{\mathrm{prev}}).
\end{align*}
Because $C_{i-1} \xor C_{i-1} = 0$ cancels out and $\Enc_k$ is a permutation,
$C_i = C^*$ holds if and only if $G = S$. Testing at most $256$ guesses recovers
one secret byte, and sliding the boundary recovers the whole cookie. \emph{Fix:}
TLS~1.1 switched to a fresh unpredictable IV per record; TLS~1.3 dropped CBC mode
altogether in favor of nonce-based AEAD.
\end{attackbox}

\begin{attackbox}
\textbf{POODLE (2014) --- padding you cannot trust.} CBC mode pads messages out to a
multiple of the block size, and a \emph{padding oracle} (Chapter~13) is any error or
timing signal that reveals whether a tampered ciphertext decrypted to valid padding.
In SSL~3.0, CBC padding bytes were \emph{unauthenticated} and unconstrained except
for the final length byte, and SSL~3.0 used \textbf{MAC-then-encrypt} (Chapter~16):
the receiver decrypted, stripped padding, and checked the MAC last. An active
man-in-the-middle replaced the final ciphertext block with an earlier target block;
with probability $1/256$ the decrypted final byte happened to indicate valid padding
and valid MAC alignment, leaking one byte of plaintext per accepted probe. Because
many browsers automatically retried failed TLS connections on SSL~3.0, attackers
triggered POODLE via a forced version downgrade. \emph{Fix:} disable SSL~3.0,
authenticate version negotiation, and mandate AEAD, which checks integrity before
inspecting any decrypted bytes. (Serge Vaudenay's 2002 CBC attack, the 2013 Lucky
Thirteen timing attack, and POODLE all exploited the same authenticate-too-late
ordering.)
\end{attackbox}

\begin{attackbox}
\textbf{Heartbleed (2014) --- a memory-safety bug, not a protocol flaw.} Heartbleed
was a \textbf{buffer over-read} --- a bug in which a program reads past the end of
the memory buffer allocated for an input --- in OpenSSL's C implementation of the
TLS heartbeat extension (a keep-alive ping message). A heartbeat request says ``echo
back these $N$ bytes of payload,'' and OpenSSL trusted the sender's claimed length
$N$ without checking it against the actual packet length
(Figure~\ref{ch25:fig-heartbleed}). Sending a $1$-byte payload with a claimed length
of $64\,\text{KB}$ ($65{,}535$ bytes) made the server copy $65{,}534$ bytes of
\emph{adjacent heap memory} into its encrypted reply --- leaking other users' HTTP
requests, session cookies, and the server's own certificate private key. No
cryptographic primitive failed: one missing bounds check exposed private keys across
a large fraction of the web, forcing mass certificate revocation and re-issuance.
\emph{Lesson:} a protocol is only as secure as its implementation. Chapters~37--39
return to memory safety, bounds checks, and shrinking the \emph{attack surface} (the
total exposed code and optional extensions an attacker can probe). Servers that used
ephemeral key exchange at least kept archived sessions safe when their private keys
leaked.
\end{attackbox}

\begin{attackbox}
\textbf{The downgrade family --- FREAK and Logjam (2015).} For 1990s export
regulations, TLS retained support for deliberately weak ``export-grade'' RSA
($512$-bit) and DH ($512$-bit) parameters. FREAK and Logjam were active attacks
that tampered with the unauthenticated negotiation in TLS 1.2 to coax a client
and server into using these weak parameters. The attacker then factored the
$512$-bit RSA modulus or solved the $512$-bit discrete log offline --- feasible with
modest compute, especially since many servers shared the \emph{same} DH group, letting
one big precomputation crack many sites (Logjam). \emph{Fix:} TLS 1.3 removes
export ciphers and all the legacy weak groups, fixes a short list of strong groups,
and --- the structural cure --- authenticates the entire negotiation via the Finished
MAC, so an attacker who edits the cipher/group choice is caught.
\end{attackbox}

\begin{focusbox}
\textbf{The pattern across all of them.} Predictable IVs (BEAST), authenticate-too-late
padding (POODLE, Lucky Thirteen), unauthenticated negotiation (FREAK, Logjam), and
implementation memory bugs (Heartbleed). TLS 1.3's answers: random per-record
nonces from a counter, AEAD only (encrypt-and-authenticate together), a fully
transcript-bound Finished MAC, and a smaller, simpler surface with fewer options to
get wrong. Much of the 1.3 specification is a direct response to one of these.
\end{focusbox}

\section{How the pieces fit together}

\begin{connectionbox}
TLS uses nearly every primitive in this book. Ephemeral ECDHE key exchange runs
Diffie--Hellman over the elliptic curves of Chapter~21, supplying the shared secret
and forward secrecy. The key schedule is HKDF (Chapter~23), built from HMAC
(Chapter~15). The server's \texttt{CertificateVerify} is a digital signature
(ECDSA, RSA-PSS, or Ed25519) from Chapter~22, verified against a certificate chain
validated by the PKI of Chapter~24. The \texttt{Finished} messages are HMACs over
the transcript hash. The record layer uses AEAD (AES-GCM, AES-CCM, or
ChaCha20-Poly1305) from Chapter~16, built on AES from Chapter~12 and ChaCha20 from
Chapter~10. The nonces and ephemeral private exponents come from a
cryptographically secure pseudorandom number generator (CSPRNG, Chapter~17). Every
piece carries load: a flaw in any one of them (a predictable random-number
generator, a broken hash, a signature forgery) breaks the connection.
\end{connectionbox}

\begin{marginnotebox}
To inspect a live handshake, run \texttt{openssl s\_client -connect example.com:443
-tls1\_3} and read the printed messages, or capture TCP port $443$ (the standard
port for HTTPS) in Wireshark (a network packet analyzer) and expand the TLS layer.
You will see \texttt{ClientHello} with its key share and SNI in cleartext,
\texttt{ServerHello}, a burst of encrypted handshake records, and then encrypted
application data.
\end{marginnotebox}

TLS secures a byte stream carried by the Transmission Control Protocol (TCP, the
transport layer that delivers reliable, ordered bytes over IP packets) once packets
are already moving between endpoints. What protects the local wireless hop before a
packet even reaches the router, where anyone within radio range can capture or
inject traffic out of thin air? Chapter~26 takes up Wi-Fi security.

\section{Exercises}

\begin{exercise}
\textbf{Trace a tiny handshake's key exchange.} Using $p = 23$, $g = 5$, let the
client pick $a = 4$ and the server pick $b = 9$. Compute the public shares $A$ and
$B$ and the shared secret $Z = g^{ab} \bmod 23$ two ways (as $B^a \bmod 23$ and as
$A^b \bmod 23$), checking they agree. Then explain precisely what Eve sees on the
wire and what hard problem she would have to solve to recover $Z$.
\end{exercise}

\begin{exercise}
\textbf{Why hash the DH output.} The shared secret $Z = g^{ab}$ is an element of
$\Zns{p}$, not a uniform bit string. Give one concrete reason raw $Z$ is unsuitable
as an AES key, and explain what the HKDF-Extract step fixes. (Hint: think about the
distribution of $Z$ and about which subgroup of $\Zns{p}$ it can land in.)
\end{exercise}

\begin{exercise}
\textbf{The role of CertificateVerify.} Suppose a server sent its Certificate but
\emph{not} the CertificateVerify message. Describe a concrete man-in-the-middle
attack an active Eve could mount, and pinpoint which security property
(confidentiality, integrity, or authentication) collapses. Then explain why the
certificate by itself is not enough.
\end{exercise}

\begin{exercise}
\textbf{Finished as downgrade defense.} An attacker edits the ClientHello to remove
all strong cipher suites, leaving only a weak one, hoping the server will pick it.
Trace through the handshake and identify the exact step at which this tampering is
detected. Why does it matter that the Finished MAC is computed over the
\emph{entire} transcript rather than just the final messages?
\end{exercise}

\begin{exercise}
\textbf{Forward secrecy by contrast.} In old RSA-key-transport TLS, the client
encrypts the session secret under the server's long-term RSA public key. Show that
an adversary who records the traffic and \emph{later} obtains the server's RSA
private key can decrypt the session. Then explain, step by step, why the same
adversary fails against ephemeral ECDHE even after stealing the server's signing
key.
\end{exercise}

\begin{exercise}
\textbf{Nonce arithmetic.} A TLS 1.3 connection uses a 12-byte
\texttt{static\_iv} = \texttt{0x01020304\allowbreak 05060708\allowbreak 090A0B0C}. Give the AEAD nonces
for record sequence numbers $0$, $1$, and $258$ (the nonce is
$\mathtt{static\_iv} \xor \mathrm{seq}$, with the sequence number right-aligned in
the 12 bytes). Argue that within a single connection no (key, nonce) pair can ever
repeat, and explain why that is essential for AES-GCM specifically.
\end{exercise}

\begin{exercise}
\textbf{Break BEAST on paper.} In CBC mode $C_i = \Enc_k(P_i \xor C_{i-1})$.
Assume Eve knows $C_{i-1}$ (the previous record's last block, used as the next IV
in TLS 1.0) and can choose the next plaintext block $P_i$. She wants to test
whether an unknown secret block $S$ equals a guess $G$. Show how she picks $P_i$ so
that a ciphertext-block collision reveals the answer, and state precisely what
about TLS 1.0's IV choice made this possible. What does TLS 1.3 do that removes the
attack entirely?
\end{exercise}

\begin{exercise}
\textbf{0-RTT replay.} A client uses 0-RTT to send the HTTP request
\texttt{POST /transfer?}\allowbreak\texttt{amount=100\&to=eve} as early data. Describe how an active
attacker exploits the lack of replay protection, what damage results, and the
general rule a server should follow about which requests may be accepted as 0-RTT
data. Contrast this with why the main 1-RTT data is not replayable.
\end{exercise}

\begin{exercise}
\textbf{Heartbleed was not crypto.} Explain why Heartbleed could leak a server's
private key even though every cryptographic algorithm in TLS was implemented
correctly. Identify the class of bug, the role of the unchecked length field, and
the general principle it teaches about the relationship between protocol security
and implementation security.
\end{exercise}

\begin{exercise}
\textbf{Trace the whole machine.} For a single TLS 1.3 connection, list every
cryptographic primitive used and the exact purpose each serves: the key exchange,
the key-derivation function (KDF), the signature, the certificate validation, the
record cipher, and the randomness source. For each, name one earlier chapter it
came from and state what breaks in the handshake if that one primitive is broken.
\end{exercise}
