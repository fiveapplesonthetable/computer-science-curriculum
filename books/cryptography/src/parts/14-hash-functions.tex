\chapter{Hash Functions}

In Chapter 13 we saw how block cipher modes encrypt messages of arbitrary length, hiding their content from an eavesdropper without guaranteeing that no one has flipped bits along the way. A cryptographic hash function takes a message of any length and compresses it down to a short, fixed-length string of bits -- its \emph{digest}. SHA-256 (from the Secure Hash Algorithm family) turns the complete works of Shakespeare, or a single byte, or this entire book, into 256 bits. Mapping long inputs to short outputs is easy on its own: plenty of cheap functions do that. What makes a hash function \emph{cryptographic} is a set of guarantees about how hard it is to find inputs that misbehave -- two distinct inputs that \emph{collide} at the same digest, or an input that hits a target digest chosen in advance.

Those guarantees let a 32-byte digest stand in for a multi-gigabyte file when checking integrity, let a website verify your password without storing the password itself, and let a public ledger summarize millions of transactions in one 32-byte number. Nearly every later chapter builds on a cryptographic hash: message authentication codes (MACs, Chapter~15), digital signatures (Chapter~22), key derivation, commitments (Chapter~32), and blockchain data structures (Chapter~36). How do we state those security guarantees precisely, and how do we build a function on arbitrary-length inputs that keeps them?

\section{What a hash function is, and what it must promise}
\label{ch14:properties}

Formally, a hash function $\Hash$ maps bit strings of any finite length to bit strings of a fixed length $n$:
\[
  \Hash : \set{0,1}^{*} \to \set{0,1}^{n},
\]
where $\set{0,1}^{*}$ is the set of all finite bit strings and $\set{0,1}^{n}$ is the set of $n$-bit strings ($n = 256$ for SHA-256, $n = 512$ for SHA-512). The input is called the \emph{message} or \emph{preimage}; the output is the \emph{digest}, \emph{hash}, or \emph{fingerprint}.

A \emph{collision} is a pair of distinct messages $x \ne x'$ that produce the same digest, $\Hash(x) = \Hash(x')$. Because the input set $\set{0,1}^{*}$ is infinite and the output set $\set{0,1}^{n}$ has only $2^{n}$ elements, collisions \emph{must} exist: by the \emph{pigeonhole principle} (if you place more items into boxes than there are boxes, at least one box holds two or more items), infinitely many pairs of distinct messages share a digest. Cryptography never claims collisions do not exist. It claims no realistic computation can \emph{find} one.

There are three security properties, in increasing order of strength.

\begin{definition}[Preimage resistance]
\label{ch14:def-preimage}
$\Hash$ is \emph{preimage resistant} (``one-way'') if, given a target digest $y = \Hash(x)$ for an input $x$ chosen uniformly at random from a large input set (such as $\set{0,1}^{2n}$), no efficient adversary can find \emph{any} message $x'$ with $\Hash(x') = y$, except with negligible probability. For an ideal $n$-bit hash the best attack is brute force, costing about $2^{n}$ hash evaluations (calls to $\Hash$).
\end{definition}

\begin{definition}[Second-preimage resistance]
\label{ch14:def-second}
$\Hash$ is \emph{second-preimage resistant} if, given a message $x$ chosen uniformly at random (say from $\set{0,1}^{2n}$), no efficient adversary can find a \emph{different} message $x' \ne x$ with $\Hash(x') = \Hash(x)$, except with negligible probability. The ideal cost is again about $2^{n}$ evaluations.
\end{definition}

\begin{definition}[Collision resistance]
\label{ch14:def-collision}
$\Hash$ is \emph{collision resistant} if no efficient adversary can find \emph{any} pair $x \ne x'$ with $\Hash(x) = \Hash(x')$, except with negligible probability. Here the adversary chooses both messages freely. Section~\ref{ch14:birthday} proves that the generic attack cost drops to about $2^{n/2}$ evaluations.
\end{definition}

\begin{intuitionbox}
A clean way to keep the three straight is to ask \emph{who chooses what}.
\begin{itemize}
  \item \textbf{Preimage}: the challenger hands you an \emph{output} $y$; you must produce \emph{some} input mapping to it. (``Here is a hash. What message made it?'')
  \item \textbf{Second-preimage}: the challenger hands you an \emph{input} $x$; you must produce a \emph{different} input with the same hash. (``Here is a contract. Forge a different one that hashes the same.'')
  \item \textbf{Collision}: the challenger hands you \emph{nothing}; you produce \emph{any} two distinct inputs that hash alike. (``Find any two inputs that clash.'')
\end{itemize}
More freedom for the attacker means an easier attack, which is why collision resistance is the strongest property and the first to fall.
\end{intuitionbox}

These properties are related: collision resistance implies second-preimage resistance.

\begin{proposition}[Collision resistance implies second-preimage resistance]
\label{ch14:cr-implies-spr}
If $\Hash$ is collision resistant then it is second-preimage resistant.
\end{proposition}

\begin{whybox}
The argument is a security reduction: we show that breaking the weaker property breaks the stronger one, so the stronger one is at least as hard.

Suppose an adversary $\mathcal{A}$ finds second preimages. Build a collision finder $\mathcal{B}$: sample a uniform message $x \getsr \set{0,1}^{2n}$ yourself, hand it to $\mathcal{A}$, and receive $x' \ne x$ with $\Hash(x') = \Hash(x)$. Then $(x, x')$ is a collision. If second preimages are easy to find, collisions are too; by the contrapositive, if collisions are hard, so are second preimages. Because $\mathcal{B}$ runs $\mathcal{A}$ once with the same success probability and almost no extra work, the reduction is \emph{tight} (there is no gap in running time or advantage between the two attacks).
\end{whybox}

The relationship between collision resistance and \emph{preimage} resistance is subtler. For a random function whose output is much shorter than its input, both properties hold together, though one can construct artificial functions that are collision resistant yet reveal parts of their input, or that are one-way yet have easy collisions. In practice we demand all three properties from any cryptographic hash.

\begin{trapbox}
A non-cryptographic hash -- such as CRC-32 (a 32-bit cyclic redundancy check built to detect accidental transmission bit-flips) or fast hash-table functions like Java's \texttt{hashCode()}, Fowler--Noll--Vo (FNV), and MurmurHash -- has \emph{none} of these properties and is easy to collide on purpose. Those functions spread typical inputs evenly for lookup speed, not to resist an adversary. Using \texttt{hashCode()} or CRC-32 anywhere a security check depends on the output creates a severe vulnerability. ``Hash function'' means two different things in systems programming and in cryptography.
\end{trapbox}

\subsection{The random-oracle ideal}

When cryptographers reason about a hash informally, they often model it as a \emph{random oracle}: an idealized black box that, on each new input, flips $n$ fair coins to choose an output, records the pair in an internal table, and returns that same output whenever the input is queried again. A random oracle is automatically one-way and collision resistant, and its outputs are independent and uniform, because there is no internal structure to exploit -- the only way to learn $\Hash(x)$ is to query the box on $x$.

Real hash functions are deterministic public algorithms rather than secret lookup tables, so the random-oracle model is a \emph{heuristic} (an idealized design aid rather than a literal truth about code). Security proofs in the random-oracle model are weaker than proofs in the \emph{standard model}, where the adversary sees the actual code of $\Hash$ and proofs rely only on stated computational hardness assumptions. Even so, random-oracle proofs guide practical padding and signature schemes in Chapters~19 and~22, provided we watch for places where concrete hash constructions depart from the ideal -- such as the length-extension flaw in Section~\ref{ch14:length-ext}.

\section{The birthday bound: why $n$-bit hashes give $n/2$-bit collision security}
\label{ch14:birthday}

Brute-forcing a preimage of an $n$-bit hash takes about $2^{n}$ tries: you are searching for one specific output among $2^{n}$. Collisions are far cheaper, for the same mathematical reason that 23 people in a room have better than an even chance of sharing a birthday (Chapter~7).

\begin{intuitionbox}
You are not looking for a message that hashes to one \emph{fixed} target. You are looking for \emph{any} two of your messages that hash to the \emph{same} value -- and the more messages you hash, the faster the number of \emph{pairs} grows. Among $q$ messages there are $\binom{q}{2} = \frac{q(q-1)}{2} \approx \frac{q^{2}}{2}$ unordered pairs, each colliding with probability $2^{-n}$. The expected number of colliding pairs crosses $1$ when $q^{2}/2 \approx 2^{n}$, so when $q \approx 2^{(n+1)/2} \approx \sqrt{2}\cdot 2^{n/2}$. Collisions appear after roughly the \emph{square root} of the total number of digests.
\end{intuitionbox}

\begin{theorem}[Birthday bound]
\label{ch14:thm-birthday}
Draw $q$ outputs independently and uniformly from a set of size $N = 2^{n}$, and write $p(q)$ for the probability that at least two draws coincide. Then
\[
  p(q) \;=\; 1 - \prod_{j=1}^{q-1}\Bigl(1 - \frac{j}{N}\Bigr)
        \;\ge\; 1 - e^{-q(q-1)/(2N)},
\]
where $e \approx 2.718$ is the base of the natural logarithm. For $q \ll N$, this lower bound is also a close approximation, and $p(q) \ge \tfrac12$ once $q \ge \ceil[\big]{\tfrac{1}{2} + \sqrt{2N\ln 2}} \approx 1.177\sqrt{N} = 1.177 \cdot 2^{n/2}$.
\end{theorem}

\begin{whybox}
Number the draws $1, 2, \dots, q$. Given that the first $j$ draws are all distinct, draw $j+1$ avoids those $j$ occupied values with probability $1 - j/N$. Multiplying these conditional probabilities for $j = 1, \dots, q-1$, the probability that \emph{all} $q$ draws are distinct is
\[
  1 - p(q) = \prod_{j=1}^{q-1}\Bigl(1 - \frac{j}{N}\Bigr).
\]
Apply the inequality $1 - x \le e^{-x}$, valid for every real number $x$:
\begin{align*}
  \prod_{j=1}^{q-1}\Bigl(1 - \frac{j}{N}\Bigr)
    &\le \prod_{j=1}^{q-1} e^{-j/N} &&\text{(since $1 - x \le e^{-x}$ for each factor)} \\
    &= \exp\!\Bigl(-\frac{1}{N}\sum_{j=1}^{q-1} j\Bigr) &&\text{(product of exponentials is exponential of sum)} \\
    &= \exp\!\Bigl(-\frac{q(q-1)}{2N}\Bigr) &&\text{(using $1 + 2 + \dots + (q-1) = \tfrac{q(q-1)}{2}$).}
\end{align*}
Subtracting from $1$ reverses the inequality:
\[
  p(q) \;\ge\; 1 - \exp\!\Bigl(-\frac{q(q-1)}{2N}\Bigr).
\]
Setting $\frac{q(q-1)}{2N} = \ln 2$ makes the right-hand side equal $\tfrac{1}{2}$, giving $q(q-1) = 2N\ln 2$ and therefore $q \approx \sqrt{2\ln 2}\,\sqrt{N} \approx 1.177\sqrt{N}$.
\end{whybox}

\begin{connectionbox}
Replacing the 365 days of the year in Chapter~7's birthday calculation with $N = 2^{n}$ digests gives the same constant: $1.177\sqrt{365} \approx 22.5$ (so 23 people) becomes $1.177 \cdot 2^{n/2}$. A naive birthday attack stores all $q \approx 2^{n/2}$ hashes in a table, which would run out of memory long before running out of time. As noted in Chapter~7, Pollard's rho cycle-finding method removes that memory bottleneck: by iterating $x_{i+1} = \Hash(x_i)$ until the sequence loops back on itself, an attacker finds the two distinct inputs entering the loop in roughly $2^{n/2}$ hash evaluations using only a handful of stored values. The algorithms companion develops both cycle-finding and the $N^{1/3}$ bound for three-way collisions.
\end{connectionbox}

\begin{example}[A toy 16-bit hash]
\label{ch14:ex-16bit}
Take $n = 16$, so $N = 2^{16} = 65{,}536$. Finding a preimage of a fixed digest costs about $65{,}536$ evaluations on average. Finding a collision costs about $1.177\sqrt{65{,}536} = 1.177 \cdot 256 \approx 301$ evaluations: hashing 300 distinct short strings already gives nearly a $50\%$ chance of a repeat. Substituting $q = 300$ into Theorem~\ref{ch14:thm-birthday}:
\[
  \frac{q(q-1)}{2N} = \frac{300 \cdot 299}{2 \cdot 65{,}536} \approx 0.684,
  \qquad
  p(300) \approx 1 - e^{-0.684} \approx 0.495.
\]
Figure~\ref{ch14:fig-birthday-curve} plots $p(q)$ across $q$: the collision probability passes $0.50$ at $q = 301$ and exceeds $0.99$ by $q = 778$, when fewer than $1.2\%$ of the $65{,}536$ possible digests have been sampled.
\end{example}

\begin{focusbox}
\textbf{Design consequence.} To resist collision attacks at the ``$b$-bit security level'' (meaning $2^{b}$ operations) you need an output of $n = 2b$ bits. A 128-bit security target therefore demands a 256-bit hash. That is why 128-bit MD5 ($2^{64}$ generic collision work) and 160-bit SHA-1 ($2^{80}$ generic work, lowered further by cryptanalysis) are no longer collision-safe: $2^{64}$ evaluations take a weekend on rented hardware, and public SHA-1 collisions have been computed since 2017 (Section~\ref{ch14:realworld}). Preimage attacks on these same functions remain near $2^{n}$ and stay out of reach; collisions always fall first.
\end{focusbox}

\begin{walkbox}
A protocol truncates SHA-256 to its first 80 bits to save space in a fingerprint. What is the collision security level, and is that safe? \\[0.3em]
\textbf{Answer.} Collision work is about $2^{80/2} = 2^{40}$, roughly a trillion evaluations -- a few minutes on a graphics processing unit (GPU, a parallel processor built with thousands of arithmetic cores). If the fingerprint is only ever compared to a digest computed by an honest party (a second-preimage setting), generic work is near $2^{80}$, which is marginal against well-funded attackers. If an attacker can choose \emph{both} inputs being compared (a collision setting, such as preparing a benign document and a malicious substitute with the same 80-bit fingerprint), $2^{40}$ is broken. Always check which security property your protocol relies on.
\end{walkbox}

\section{Building a hash from a small component: Merkle--Damg\aa{}rd}
\label{ch14:md}

Suppose we know how to compress a \emph{fixed-size} chunk of bits using a mixing function. How do we hash a message of \emph{arbitrary} length? The classic answer, used by Message Digest~5 (MD5), SHA-1, and the SHA-2 family, is the \emph{Merkle--Damg\aa{}rd} construction. It steps a fixed-input \emph{compression function} across the message one block at a time, carrying forward a running $n$-bit state called the \emph{chaining value}.

In 1989, Ralph Merkle and Ivan Damg\aa{}rd independently proved the reduction theorem behind this design: if the fixed-size compression function is collision resistant, then the full iterated hash is collision resistant as well. That theorem reduced hashing arbitrary-length messages to designing one fixed-input compression function. Almost every standard hash from 1990 to 2010 -- MD4, MD5, SHA-0, SHA-1, SHA-256, and SHA-512 -- adopted this architecture. Its main structural flaw, the length-extension vulnerability, is examined in Section~\ref{ch14:length-ext}.

The compression function is
\[
  f : \set{0,1}^{n} \times \set{0,1}^{b} \to \set{0,1}^{n},
\]
taking an $n$-bit chaining value and a $b$-bit message block to a new $n$-bit chaining value. To hash a message $M$ (Figure~\ref{ch14:fig-md-chain}):

\begin{enumerate}
  \item \textbf{Pad} $M$ to a multiple of the block size $b$ by appending a \texttt{1} bit, enough \texttt{0} bits, and an encoding of the original bit-length of $M$ at the end of the final block (``Merkle--Damg\aa{}rd strengthening''). Split the padded message into $b$-bit blocks $M_1, M_2, \dots, M_k$.
  \item \textbf{Initialize} the chaining value to a public starting constant $H_0 = \mathit{IV}$ (the \emph{initialization vector}) specified by the standard.
  \item \textbf{Compress} each block in order: $H_i = f(H_{i-1}, M_i)$ for $i = 1, \dots, k$.
  \item \textbf{Output} $H_k$ (possibly after an output truncation or transform).
\end{enumerate}

\begin{theorem}[Merkle--Damg\aa{}rd collision resistance]
\label{ch14:md-thm}
If the compression function $f$ is collision resistant, then the Merkle--Damg\aa{}rd hash $\Hash$ built from it (with length-strengthening padding) is collision resistant.
\end{theorem}

\begin{whybox}
Suppose someone hands us two distinct messages $M \ne M'$ with $\Hash(M) = \Hash(M')$, padded into $k$ blocks $M_1, \dots, M_k$ and $k'$ blocks $M'_1, \dots, M'_{k'}$. We extract a collision in $f$, contradicting its collision resistance.

Walk the two chains \emph{backward} from their equal final outputs $H_k = H'_{k'}$. The last compression step gives
\[
  f(H_{k-1}, M_k) = H_k = H'_{k'} = f(H'_{k'-1}, M'_{k'}).
\]
If the two input pairs to $f$ differ -- meaning $(H_{k-1}, M_k) \ne (H'_{k'-1}, M'_{k'})$ -- we have found a collision in $f$ and we stop. Otherwise both parts match: $H_{k-1} = H'_{k'-1}$ and $M_k = M'_{k'}$, so we step back one block and repeat the comparison.

Two cases cover every pair $M \ne M'$:
\begin{itemize}
  \item \textbf{Different bit-lengths.} Length-strengthening padding writes the original bit-length into the end of the final block, forcing $M_k \ne M'_{k'}$. Then $(H_{k-1}, M_k) \ne (H'_{k'-1}, M'_{k'})$, yielding a collision in $f$ at the final step.
  \item \textbf{Equal bit-lengths.} Then $k = k'$ and both chains start from $H_0 = H'_0 = \mathit{IV}$. Because $M \ne M'$, the padded block sequences must differ somewhere. At the last index $i$ where $(H_{i-1}, M_i) \ne (H'_{i-1}, M'_i)$, the outputs $H_i = H'_i$ are already equal, giving a collision in $f$.
\end{itemize}
Either way an $\Hash$-collision produces an $f$-collision, proving the theorem by contrapositive.
\end{whybox}

def compress(h, block):          # h: int in 0..255, block: int in 0..255
    # A deliberately weak toy mixer. NOT cryptographic.
    x = (h ^ block) & 0xFF
    x = ((x << 3) | (x >> 5)) & 0xFF      # rotate left 3
    x = (x * 167 + 13) & 0xFF             # mix
    return x ^ ((h + block) & 0xFF)

def md_hash(message: bytes) -> int:
    h = 0x6A                              # the IV
    msg = message + bytes([len(message) & 0xFF])   # length strengthening
    for byte in msg:                     # each byte is one "block"
        h = compress(h, byte)
    return h

print(hex(md_hash(b"hello")))            # e.g. 0x..
print(hex(md_hash(b"world")))
# Find a collision by brute force -- with only 256 outputs it is instant:
seen = {}
i = 0
while True:
    d = md_hash(str(i).encode())
    if d in seen:
        print("collision:", seen[d], "and", i, "both ->", hex(d))
        break
    seen[d] = i
    i += 1
\end{lstlisting}
Run it and a collision appears after roughly two dozen tries -- matching the birthday bound for $n = 8$ ($1.177\cdot 2^{4} \approx 19$ for even odds, with an average near $20$). By the pigeonhole principle it can never take more than $257$ inputs. Scaling the state to 256 bits and replacing \texttt{compress} with a strong 64-round mixer is what puts collisions out of reach.
\end{implementbox}

\section{Length extension: the Merkle--Damg\aa{}rd weakness}
\label{ch14:length-ext}

Merkle--Damg\aa{}rd has a structural leak that has caused real security breaches. The published digest $H_k$ \emph{is} the live internal chaining value, with nothing hiding it. Anyone who knows $\Hash(M)$ and the \emph{byte-length} of $M$ can load $H_k$ back into the hash state, resume the block iteration, and compute $\Hash(M \concat \text{pad} \concat S)$ for any chosen suffix $S$ -- \emph{without knowing $M$ itself}.

\begin{attackbox}
\textbf{The length-extension attack against a secret-prefix MAC.}

A tempting but broken way to authenticate a message $M$ with a shared secret key $k$ is the ``prefix MAC'':
\[
  t = \Hash(k \concat M).
\]
The designer assumes only someone holding $k$ can compute a valid tag $t$. With an unkeyed Merkle--Damg\aa{}rd hash this fails (Figure~\ref{ch14:fig-lenext}).

Suppose an attacker intercepts a legitimate pair $(M, t)$ where $t = \Hash(k \concat M)$, and knows (or guesses) the byte-length of $k$. Because $t$ equals the chaining value after compressing $k \concat M \concat \text{pad}_1$, where $\text{pad}_1$ is the deterministic padding for that total length, the attacker:
\begin{enumerate}
  \item initializes a hash state directly to $t$ instead of $\mathit{IV}$;
  \item feeds in any chosen suffix $S$ (padded with $\text{pad}_2$ for the new total length);
  \item reads off $t' = \Hash(k \concat M \concat \text{pad}_1 \concat S)$.
\end{enumerate}
The output $t'$ is a \emph{valid tag} under $k$ for the extended message $M' = M \concat \text{pad}_1 \concat S$, computed without ever learning $k$. In early web APIs that authenticated query strings this way, appending \verb|&admin=true| after $\text{pad}_1$ produced a request that passed server verification.
\end{attackbox}

\begin{walkbox}
Why can the attacker resume without $k$ or $M$ (Figure~\ref{ch14:fig-lenext})? Because the next compression call $f(H_k, \cdot)$ depends on past blocks \emph{only} through the chaining value $H_k$, and that value is the tag $t$ sent in the clear. Merkle--Damg\aa{}rd never hides its final state. The attacker only needs to reconstruct $\text{pad}_1$, which depends solely on the byte-length of $k \concat M$ -- and guessing a short key length takes a handful of tries.
\end{walkbox}

Three standard designs block length extension:

\begin{itemize}
  \item \textbf{HMAC} (Hash-based Message Authentication Code, Chapter~15) nests two hash evaluations, $\Hash\bigl(k_{\text{out}} \concat \Hash(k_{\text{in}} \concat M)\bigr)$, where $k_{\text{in}}$ and $k_{\text{out}}$ are two keys derived from $k$ by XORing with fixed constants. Because the outer hash hides the inner digest under $k_{\text{out}}$, extending the inner chain is impossible and extending the outer chain does not match any valid message input.
  \item \textbf{Truncated output.} SHA-512/256 runs SHA-512 internally (a 512-bit chaining state) and outputs only 256 bits, keeping half the chaining value hidden so an attacker cannot reconstruct the full state to resume from. SHA-224 and SHA-384 work the same way.
  \item \textbf{Sponge hashes.} Sponge-based designs such as SHA-3 (Section~\ref{ch14:sponge}) never expose their full internal state in the digest, blocking length extension by construction.
\end{itemize}

\begin{implementbox}
Length extension is mechanical enough to fit in a few lines of pseudocode. \textbf{Learning only -- the lesson is ``never deploy a raw prefix MAC,'' not ``go forge tags.''}
\begin{lstlisting}[language=Python]
# Pseudocode against a Merkle-Damgard hash H with block-aligned padding.
# Attacker knows: message M, tag t = H(secret || M), and len(secret).
def forge(t, M, secret_len, suffix):
    glue = md_padding(secret_len + len(M))   # the pad H would have appended
    forged_message = M + glue + suffix       # what the new tag authenticates
    # Resume the hash from the leaked internal state == t:
    h = HashState.from_digest(t)             # set chaining value = t
    h.set_length(secret_len + len(M) + len(glue))
    h.update(suffix)
    forged_tag = h.digest()                  # == H(secret || M || glue || suffix)
    return forged_message, forged_tag
\end{lstlisting}
Public tools (\texttt{hashpump}, the \texttt{hlextend} library) automate this exact calculation. Never expose an unkeyed $\Hash(k \concat M)$ as an authentication tag on a Merkle--Damg\aa{}rd hash; use HMAC or KMAC.
\end{implementbox}

\section{The sponge construction and SHA-3}
\label{ch14:sponge}

In 2007 NIST opened a public competition for a new hash standard, hedging against the chance that the cryptanalytic techniques behind the MD5 and SHA-1 breaks might eventually threaten SHA-2. The winner, selected in 2012 and standardized as SHA-3 in 2015, was \emph{Keccak}, built on an entirely different architecture: the \emph{sponge}.

A sponge maintains a wide internal state of $b = r + c$ bits, initialized to all zeros ($0^r$ and $0^c$) and split into two lanes: a \emph{rate} part of $r$ bits (which interacts with message blocks and output blocks) and a \emph{capacity} part of $c$ bits (a hidden buffer that never touches inputs or outputs directly). A single public, unkeyed permutation $\pi : \set{0,1}^{b} \to \set{0,1}^{b}$ -- a fixed invertible rearrangement of all $2^{b}$ states, equal in Keccak to the 1600-bit permutation Keccak-$f$ -- mixes the two lanes together. Hashing runs in two phases:

\begin{description}
  \item[Absorbing.] Pad the message and split it into $r$-bit blocks. For each block, XOR it into the $r$-bit rate portion of the state, then apply $\pi$ to the entire $b$-bit state. The $c$-bit capacity never meets the message directly; it changes only when $\pi$ mixes the full state.
  \item[Squeezing.] Read off the $r$-bit rate portion of the state as output; if more output bits are requested, apply $\pi$ again and read another $r$ bits, repeating until enough bits have been produced, then truncate to $n$ bits.
\end{description}

Figure~\ref{ch14:fig-sponge} traces both phases across the split state: message blocks enter and output blocks exit through the top $r$-bit rate lane, while the bottom $c$-bit capacity lane stays sealed inside the permutation chain.

\begin{whybox}
\textbf{Why capacity governs security, and why length extension fails.}

The security of a sponge against generic attacks depends on both the output length $n$ and the capacity $c$: when $\pi$ behaves like a random permutation, collision resistance is roughly $\min(2^{c/2}, 2^{n/2})$ (because two inputs whose hidden $c$-bit capacity values ever match at the end of absorption produce identical outputs, an internal birthday event of cost $2^{c/2}$) and preimage resistance is roughly $\min(2^{c/2}, 2^{n})$. SHA3-256 sets $c = 512$ and $n = 256$, achieving $2^{128}$ collision resistance and $2^{256}$ preimage resistance.

Length extension fails because the digest reveals at most the squeezed $r$-bit rate lane while the $c$-bit capacity remains hidden. Resuming absorption on new blocks requires the \emph{entire} $b$-bit state, and guessing the missing $c = 512$ capacity bits is infeasible. Protocols can therefore build a MAC directly from a sponge without double-hashing, standardized by NIST as \emph{Keccak Message Authentication Code} (KMAC).
\end{whybox}

\begin{focusbox}
\textbf{The SHA-3 family.} All six standards share the $b = 1600$-bit Keccak-$f$ permutation ($r + c = 1600$) and differ only in their rate/capacity split and output length:

SHAKE128 and SHAKE256 are \emph{extendable-output functions} (XOFs): their squeeze phase can run for as many blocks as the caller requests, turning a short seed or message into an output stream of arbitrary length $n$. Post-quantum standards (Chapter~35) such as ML-KEM (Kyber, key encapsulation) and ML-DSA (Dilithium, digital signatures) use SHAKE to expand short seeds deterministically into large polynomial matrices.
\end{focusbox}

\begin{connectionbox}
The Keccak-$f$ permutation arranges its 1600-bit state as a $5 \times 5 \times 64$ array of bits and applies five sub-steps per round ($\theta, \rho, \pi, \chi, \iota$) across 24 rounds over the two-element field $\F_2 = \set{0,1}$. Four of the steps are linear over $\F_2$ and scatter bit differences across slices and lanes, while $\chi$ supplies degree-2 nonlinearity via bitwise AND -- the same division of labor between linear diffusion and algebraic nonlinearity that Chapter~6 analyzed for AES.
\end{connectionbox}

\section{SHA-2 in practice}
\label{ch14:sha2}

Even with SHA-3 standardized, the dominant hash family in deployed cryptography remains \emph{SHA-2}, led by SHA-256 and SHA-512. SHA-2 is a Merkle--Damg\aa{}rd hash whose compression function follows the \emph{Davies--Meyer} blueprint (Figure~\ref{ch14:fig-davies-meyer}): build a reversible block-cipher-like core $E_{M_i}$ keyed by the message block $M_i$, apply it to the incoming chaining state $H_{i-1}$, and combine the result with $H_{i-1}$ via a \emph{feed-forward} step:
\[
  H_i = E_{M_i}(H_{i-1}) \boxplus H_{i-1},
\]
where $\boxplus$ denotes word-by-word addition modulo $2^{32}$ (in binary Davies--Meyer texts this feed-forward is often written with $\xor$). Without the feed-forward term $+ H_{i-1}$, $E_{M_i}$ would be invertible for any chosen block $M_i$: an attacker given a target $H_i$ could pick $M_i$ freely and run $E_{M_i}^{-1}(H_i)$ backward to recover a matching $H_{i-1}$. Adding $H_{i-1}$ into the output couples the input and output of $E_{M_i}$, blocking backward inversion.

\begin{focusbox}
\textbf{SHA-256 parameters and round structure.}
\begin{itemize}
  \item \textbf{Widths:} 256-bit digest, 512-bit message block, and a working state of eight 32-bit words $a, b, \dots, h$ (256 bits total).
  \item \textbf{Padding:} append a \texttt{1} bit, then enough \texttt{0} bits so the bit-length is $64$ short of a multiple of $512$, followed by the original message length as a 64-bit integer.
  \item \textbf{Message schedule and constants:} expand each 512-bit block into sixty-four 32-bit \emph{message-schedule} words $W_0, \dots, W_{63}$ and mix one $W_t$ and one round constant $K_t$ per round for 64 rounds. The constants $K_t$ are the first 32 fractional bits of the cube roots of the first 64 primes -- a public ``nothing-up-my-sleeve'' recipe showing the designers had no room to tune hidden backdoors.
  \item \textbf{Operations:} addition modulo $2^{32}$, bitwise XOR, bitwise AND, and fixed bit rotations -- an add--rotate--XOR (ARX) style augmented with bitwise choice/majority gates that runs fast in both software and hardware.
\end{itemize}
SHA-512 widens the same design to 64-bit words, 80 rounds, and a 1024-bit block. On 64-bit processors SHA-512 often hashes \emph{more bytes per second} than SHA-256 because each round processes twice as many bits per native register operation.
\end{focusbox}

\begin{applicationbox}
\textbf{Where SHA-2 runs.}
\begin{itemize}
  \item \textbf{TLS} (Chapter~25): website certificate signatures, the handshake \emph{transcript hash} (a running digest of every handshake message exchanged so far), and the \emph{HMAC-based Key Derivation Function} (HKDF) all use SHA-256 or SHA-384. The cipher-suite name \texttt{TLS\_AES\_128\_GCM\_SHA256} names the hash at the end.
  \item \textbf{Bitcoin} (Chapter~36): block headers and \emph{proof-of-work} mining (searching for a block header whose digest begins with a required number of zero bits) compute double SHA-256, $\text{SHA-256}(\text{SHA-256}(x))$, whose outer call also blocks length extension.
  \item \textbf{Software distribution:} Git is migrating repository object hashes from SHA-1 to SHA-256, and package managers (\texttt{apt}, \texttt{npm}, \texttt{pip}) verify downloaded archives against published SHA-256 digests.
  \item \textbf{Digital signatures} (Chapter~22): RSA, ECDSA, and the \emph{Edwards-curve Digital Signature Algorithm} (EdDSA, using SHA-512) all sign $\Hash(M)$ rather than $M$ directly. Hashing compresses an arbitrary-length document to a fixed-size input, so signature security requires collision resistance of $\Hash$.
\end{itemize}
Server, laptop, and phone CPUs (x86 and ARM) include dedicated SHA-2 instructions (\texttt{SHA256RNDS2}, ARMv8 \texttt{SHA256H}) that sustain several gigabytes per second on a single core.
\end{applicationbox}

\begin{trapbox}
\textbf{Do not confuse fast with safe for passwords.} SHA-256's throughput helps when verifying large files and hurts when storing user passwords: an attacker can evaluate tens of billions of SHA-256 guesses per second on a single GPU. Password storage requires a deliberately \emph{slow}, memory-intensive function -- bcrypt, scrypt, or Argon2 -- as Section~\ref{ch14:passwords} develops. Storing bare $\text{SHA-256}(\text{password})$ is a frequent and severe deployment error.
\end{trapbox}

\section{Application 1: fingerprints and integrity}
\label{ch14:fingerprints}

The simplest use of a hash is as a \emph{fingerprint}: a short value that stands in for a large file so you can detect any modification. Publish $\Hash(\text{file})$ over a trusted channel; anyone who downloads the file over an untrusted network recomputes the hash and compares. By the avalanche property, flipping even a single bit in the file flips roughly half the digest bits, so corruption or tampering is caught immediately.

Fingerprints secure software updates, \emph{content-addressed storage} -- systems like Git, the InterPlanetary File System (IPFS), and container image registries where every object is named by its digest, making the name itself a checkable identity -- and \emph{deduplication} (storing one copy when identical files produce the same digest). When an honest author publishes the original file first, the security property doing the work is \emph{second-preimage} resistance: given that fixed file, an attacker must not be able to craft a \emph{different} file with the same fingerprint.

\begin{attackbox}
\textbf{When fingerprints rely on the wrong property: the SHA-1 collision and ``evil twins.''}

If an attacker controls \emph{both} the original and the replacement file -- say, a signer who later wants to repudiate (deny having signed) an agreement, or an attacker who submits a benign file for approval and later swaps in a malicious twin sharing its hash -- then \emph{collision} resistance is what matters, and a 128- or 160-bit hash is too short. In 2017 the SHAttered attack produced two distinct PDF files with identical SHA-1 digests in roughly $2^{63}$ compressions. By 2020 \emph{chosen-prefix} SHA-1 collisions (where the two files start with arbitrary attacker-chosen prefixes) became practical, forging Pretty Good Privacy (PGP) identity certificates. Whenever an adversary can influence the original document, a fingerprint is only as strong as the hash's collision resistance -- making MD5 and SHA-1 unusable.
\end{attackbox}

\subsection{Merkle trees: fingerprinting a collection}

Suppose you want to fingerprint a collection of $N$ data blocks $d_1, \dots, d_N$ so that a verifier holding one short digest can check \emph{any single block} without downloading the other $N - 1$ blocks. A \emph{Merkle tree} arranges the hashes in a \emph{binary tree} -- a hierarchy of nodes in which each parent combines two children, down to bottom \emph{leaf} nodes that hash the individual data blocks (Figure~\ref{ch14:fig-merkle-tree}). Each internal node hashes the concatenation of its two children's digests, and the single top digest -- the \emph{Merkle root} -- commits to the entire ordered collection.

To prove that block $d_3$ sits at leaf~3 under a known $\text{root}$ (Figure~\ref{ch14:fig-merkle-tree}), the prover sends $d_3$ together with its \emph{authentication path}: the sibling hashes $h_4$ and $h_{12}$ needed at each level along the path to the root. The verifier computes
\[
  h_3 = \Hash(d_3), \qquad
  h_{34} = \Hash(h_3 \concat h_4), \qquad
  r' = \Hash(h_{12} \concat h_{34}),
\]
and accepts if $r' = \text{root}$. In a tree of $N$ leaves, an authentication path contains only $\ceil{\log_2 N}$ sibling hashes -- $20$ hashes to verify one block out of a million. By collision resistance of $\Hash$ (applied up the tree as in Theorem~\ref{ch14:md-thm}), no efficient attacker can substitute a different block $d'_3 \ne d_3$ that recomputes to the same $\text{root}$.

\begin{applicationbox}
Merkle trees anchor integrity across distributed systems. Bitcoin and Ethereum place a Merkle root of each block's transactions into the block header so \emph{light clients} (wallets storing only block headers rather than full blocks) can verify a single payment with a $\log_2 N$-hash proof. \emph{Certificate Transparency} logs record every issued TLS website certificate in an append-only Merkle tree so domain owners can spot mis-issued certificates. Git directory trees, BitTorrent~v2, the ZFS and Btrfs file systems, and file-sync protocols all use the same tree structure. Chapter~36 develops the blockchain version in full.
\end{applicationbox}

\section{Application 2: commitments}
\label{ch14:commitments}

A \emph{commitment scheme} is the digital version of sealing a written choice inside an envelope and placing it on the table. You lock in a value $m$ now and open it later, with two guarantees: \emph{binding} (once the envelope is on the table, you cannot change $m$) and \emph{hiding} (until you open it, nobody watching learns anything about $m$).

A cryptographic hash builds a commitment in two lines (Figure~\ref{ch14:fig-commitment}). To commit to a message $m$, sample a uniform 256-bit random \emph{nonce} $r \getsr \set{0,1}^{256}$ and publish the commitment digest
\[
  c = \Hash(m \concat r).
\]
To open the commitment later, reveal the pair $(m, r)$; the verifier recomputes $\Hash(m \concat r)$ and checks that it equals $c$.

\begin{whybox}
\textbf{Why it binds and why it hides.}
\begin{itemize}
  \item \textbf{Binding} rests on collision resistance. Opening the same $c$ to a different message $m' \ne m$ requires producing $(m', r')$ with $\Hash(m' \concat r') = \Hash(m \concat r)$. Because $m' \ne m$ (assuming unambiguous encoding of the pair), $(m \concat r)$ and $(m' \concat r')$ are distinct inputs with the same digest -- a collision in $\Hash$.
  \item \textbf{Hiding} rests on preimage resistance together with the high-entropy nonce $r$. Without $r$, committing to a low-entropy choice (``yes'' or ``no'', or a bid between $\$1$ and $\$1000$) would let anyone hash every candidate $m$ and match $c$. Appending $256$ uniform bits $r$ spreads each candidate $m$ across $2^{256}$ equally likely inputs; in the random-oracle model, $c$ is uniform and independent of $m$ until $r$ is revealed.
\end{itemize}
Omitting the random nonce $r$ breaks hiding whenever $m$ comes from a searchable set -- the exact same flaw as hashing passwords without a salt (Section~\ref{ch14:passwords}).
\end{whybox}

\begin{applicationbox}
Hash commitments run inside coin-flipping protocols over a network (Alice commits to a random bit $b_A$, Bob announces $b_B$, Alice opens $b_A$, and the outcome is $b_A \xor b_B$), sealed-bid auctions, the ``commit--reveal'' pattern in blockchain \emph{smart contracts} (programs executed publicly on a blockchain, where raw bids would otherwise be copied before settlement), and the \emph{Fiat--Shamir transform} that converts interactive zero-knowledge proofs (proofs convincing a verifier a claim is true without revealing why) into standalone digital signatures by replacing the verifier's random challenge with a hash of the prover's commitment (Chapters~22 and~31). When a protocol does not need algebraic structure -- such as the \emph{additively homomorphic} commitments of Chapter~32, where multiplying two commitments yields a commitment to the sum of the hidden values -- $\Hash(m \concat r)$ is the standard choice.
\end{applicationbox}

\section[Password Hashing, Memory-Hard Key Derivation, and Phishing-Resistant Authentication]{Password Hashing, Memory-Hard Key Derivation, \protect\linebreak and Phishing-Resistant Authentication}
\label{ch14:passwords}

Up to this point in the chapter, speed has been an unmixed advantage. Merkle--Damg\aa{}rd and sponge designs stream multiple gigabytes per second through wide CPU \emph{vector registers} (registers that operate on several 32- or 64-bit words in one instruction). On x86 and ARM processors, SHA-256 compresses a 64-byte block in under 200 nanoseconds, while BLAKE3 reaches three gigabytes per second per core. For verifying operating-system images, signing code, and computing Merkle roots, high throughput is what we want.

For storing human passwords, that same throughput works for the attacker.

Compare the legitimate login server with an offline cracker. A user logging in types a password, submits the form, and waits; whether the server spends two microseconds or two hundred milliseconds checking the password, the login feels instant, and the server runs that check once per session. An adversary who steals a database table of password hashes, by contrast, runs trillions of guesses offline without contacting the server. At 200 nanoseconds per hash, a desktop holding eight modern GPUs evaluates more than $10^{11}$ candidate passwords every second.

Human passwords cannot survive that guessing rate because people pick predictable strings. A cryptographic key drawn uniformly from $\set{0,1}^{256}$ has 256 bits of Shannon entropy (Chapter~7); testing $10^{11}$ keys per second across $2^{256}$ possibilities would take $3 \times 10^{58}$ years. Human-chosen passwords cluster between 25 and 40 bits of entropy. Even an eight-character password chosen uniformly from all 95 printable ASCII characters has only $95^8 \approx 6.6 \times 10^{15} \approx 2^{52.6}$ possibilities, and real users favor dictionary words, names, dates, and predictable substitutions (\texttt{P@ssw0rd123}). Against a dictionary of $10^9 \approx 2^{30}$ common passwords, an 8-GPU rig running at $10^{11}$ hashes per second finishes the entire list in $0.01\,\text{seconds}$ (ten milliseconds).

Protecting human passwords therefore requires a hash that is deliberately slow and whose cost comes from hardware resources -- above all, memory -- that an attacker cannot parallelize cheaply.

\subsection{Why raw hashes and unsalted hashes fail}

A naive login database stores the bare digest of each user's password $P$:
\[
  h = \Hash(P).
\]
When the user submits $P'$ at login, the server checks whether $\Hash(P') = h$. Once the database leaks, this design fails in two ways:

\begin{enumerate}
  \item \textbf{Precomputation and rainbow tables.} Because $\Hash(P)$ depends only on $P$, an attacker can hash a large dictionary $\mathcal{D}$ of candidate passwords \emph{before} breaching any server. In 2003, Philippe Oechslin introduced \emph{rainbow tables}, a \emph{space-time tradeoff} (spending a one-time precomputation and modest disk space to make later lookups fast) built from alternating hash-and-reduce chains:
  \[
    P_0 \xrightarrow{\Hash} H_0 \xrightarrow{R_1} P_1 \xrightarrow{\Hash} H_1 \xrightarrow{R_2} \cdots \xrightarrow{R_L} P_L.
  \]
  Here $\Sigma$ is the character alphabet (such as printable ASCII) and each $R_i : \set{0,1}^n \to \Sigma^k$ is a public step-indexed \emph{reduction function} (unrelated to a security reduction) that maps an $n$-bit digest deterministically back to a $k$-character candidate string. Storing only the chain endpoints $(P_0, P_L)$ packs billions of precomputed hashes into gigabytes of storage; inverting a stolen digest takes milliseconds, and one table cracks every unsalted database on the internet.
  \item \textbf{Visible password reuse.} If Alice and Bob pick the same password $P$, their rows store identical digests $\Hash(P)$, revealing shared passwords across the table at a glance even before cracking $P$.
\end{enumerate}

To defeat precomputation, the server samples a fresh 128-bit random \emph{salt} $s \getsr \set{0,1}^{128}$ for each user at registration and stores it openly beside the salted digest:
\[
  (s, h), \qquad h = \Hash(s \concat P).
\]
The salt is not secret; its job is to make every user's hash function distinct. Because $s$ comes from $2^{128}$ possible values, a global precomputed table over dictionary $\mathcal{D}$ (of size $\abs{\mathcal{D}}$, the number of candidate words) would require $\abs{\mathcal{D}} \cdot 2^{128}$ hash evaluations. Moreover, independent salts $s_{\text{Alice}} \ne s_{\text{Bob}}$ make $\Hash(s_{\text{Alice}} \concat P) \ne \Hash(s_{\text{Bob}} \concat P)$, hiding whether two accounts share a password.

\begin{trapbox}
\textbf{The salt arithmetic trap.} Salting eliminates global precomputation across users, yet adds zero cost to a targeted attack on one stolen row. Given Alice's record $(s_{\text{Alice}}, h_{\text{Alice}})$, the attacker reads $s_{\text{Alice}}$ in plaintext and tests each dictionary word $w$ by computing $\Hash(s_{\text{Alice}} \concat w)$. Against bare SHA-256 at $10^{11}$ guesses per second, a $10^9$-word dictionary still falls in ten milliseconds, and a 35-bit password ($\approx 3.4 \times 10^{10}$ guesses) falls in a third of a second.
\end{trapbox}

\subsection{Iterative CPU-hard stretching and its silicon limits}

To slow down attacks on an individual salted record, \emph{key stretching} forces each guess through many sequential rounds. In 2000, RSA Laboratories standardized \textbf{PBKDF2} (Password-Based Key Derivation Function~2, RFC~2898), which iterates a keyed pseudorandom function -- usually HMAC-SHA-256, taking password $P$ as key -- for an iteration count $c$:
\begin{align*}
  U_1 &= \operatorname{HMAC}\bigl(P,\, s \concat \operatorname{INT}(1)\bigr), \\
  U_2 &= \operatorname{HMAC}(P,\, U_1), \quad \dots, \quad U_c = \operatorname{HMAC}(P,\, U_{c-1}), \\
  T   &= U_1 \xor U_2 \xor \cdots \xor U_c,
\end{align*}
where $\operatorname{INT}(1)$ is the four-byte big-endian encoding of the integer~$1$ (for output blocks beyond one hash width, PBKDF2 repeats with $\operatorname{INT}(2)$, and so on). Setting $c = 600{,}000$ makes computing $T$ take roughly $100\,\text{ms}$ on a server CPU, multiplying the HMAC calls for $10^9$ dictionary guesses to $6 \times 10^{14}$.

Yet purely sequential CPU stretching still loses badly against GPUs and \emph{Application-Specific Integrated Circuits} (ASICs, chips custom-manufactured to run one fixed algorithm). The gap comes from how silicon die area is spent.

Over $90\%$ of a general-purpose x86 or ARM processor die goes to machinery for complex, unpredictable programs: branch predictors (circuitry that guesses which path an \texttt{if} statement will take), instruction decoders, out-of-order schedulers, and megabytes of fast on-chip \emph{static RAM} (SRAM) caches (L1, L2, and L3). The 32-bit arithmetic logic units (ALUs) that execute additions, rotations, and XORs occupy a tiny sliver of silicon.

SHA-256 needs none of that general-purpose machinery. Its working state is eight 32-bit words -- 32 bytes of 1-bit hardware storage cells (\emph{flip-flops}) -- and its round logic uses stateless \emph{combinational gates} (AND, XOR, fixed bit-wires for rotations, and 32-bit adders). An ASIC designer strips away caches and decoders and packs tens of thousands of \emph{pipelined} SHA-256 cores (wired like an assembly line so every clock cycle finishes a new round) onto one $250\,\text{W}$ chip. Because PBKDF2 uses only 32 bytes of state per guess, every core runs inside its own registers without ever touching external memory. Both the defender's CPU and the attacker's ASIC must run $c$ rounds per guess, so raising $c$ slows the login server and the ASIC in the same ratio while leaving the ASIC's huge parallelism advantage intact.

\subsection{Memory-hard key derivation: scrypt and Argon2}

To erase that custom-hardware advantage, password hashing must bottleneck on the one resource an ASIC cannot pack densely for free: \textbf{memory} (RAM) and memory bandwidth.

On-chip SRAM uses six transistors per bit, so putting $64\,\text{MiB}$ of SRAM ($1\,\text{MiB} = 2^{20} = 1{,}048{,}576$ bytes; $1\,\text{KiB} = 1024$ bytes) onto an ASIC consumes roughly $50\text{--}60\,\text{mm}^{2}$ of silicon per core -- leaving room for only a handful of cores per chip instead of tens of thousands. Off-chip \emph{dynamic RAM} (DRAM, main memory storing each bit in a tiny capacitor on separate memory dies) is denser, yet cores must reach it across physical copper pins or \emph{through-silicon vias} (TSVs, microscopic vertical wires through stacked dies) whose aggregate bandwidth rarely exceeds $1\text{--}2\,\text{TB/s}$ (terabytes per second) per package.

In 2009, Colin Percival introduced \emph{memory-hard functions} with \textbf{scrypt}, measuring hardware attack cost by \textbf{Area-Time ($AT$) complexity}: the silicon area $A$ multiplied by execution time $T$. Requiring $64\,\text{MiB}$ of active memory per password guess prevents an attacker from placing $10^4$ cores on a die, and forces any attacker who drops a fraction of memory blocks to pay a steep \emph{time-memory tradeoff} (TMTO) penalty in repeated recomputation. In 2015, the Password Hashing Competition selected \textbf{Argon2} (Alex Biryukov, Daniel Dinu, and Dmitry Khovratovich; standardized as RFC~9106). Argon2 organizes memory and computation as follows:

\begin{itemize}
  \item \textbf{Memory matrix.} Working RAM of $m\,\text{KiB}$ is arranged as a $p \times q$ grid of $1\,\text{KiB}$ blocks ($p$ parallel \emph{lanes} by $q = m/p$ columns, where each $1\,\text{KiB}$ block holds $128$ 64-bit words). Allocating $m = 64\,\text{MiB} = 65{,}536\,\text{KiB}$ across $p = 4$ lanes forms a $4 \times 16{,}384$ block matrix, swept $t$ times (\emph{passes}).
  \item \textbf{Four synchronization slices.} Each pass divides the $q$ columns into four vertical \emph{slices} (Slices~0--3). Within a slice, all $p$ lanes update in parallel without interfering; at slice boundaries, lanes synchronize so blocks can reference other lanes safely.
  \item \textbf{Block compression $G$.} Each step combines the preceding block with an earlier reference block through a mixing function $G$ built from BLAKE2b's 64-bit ARX rounds, designed for \emph{single-instruction, multiple-data} (SIMD) vector units (such as x86 AVX2 and ARM Neon) so honest CPUs fill memory at full RAM bandwidth.
\end{itemize}

How the reference block's coordinates $(i', j')$ are chosen creates a tradeoff between TMTO resistance and cache-timing safety, giving three Argon2 modes:

\begin{description}
  \item[Argon2d (data-dependent addressing).] To fill block $B_{i,j}$, Argon2d derives the lookup coordinates $(i', j')$ from a 64-bit word inside the preceding block $B_{i,j-1}$ and computes $B_{i,j} = G(B_{i,j-1}, B_{i',j'})$. Because $(i', j')$ is unpredictable until $B_{i,j-1}$ is computed, discarding blocks forces steep recomputation penalties. However, because memory addresses depend on password-derived data, a co-located attacker sharing the same physical CPU (for instance across virtual machines under a \emph{cloud hypervisor}, the software sharing one server among tenants) can time CPU cache misses to leak information about the password (Chapter~37).
  \item[Argon2i (data-independent addressing).] Coordinates $(i', j')$ are generated from public inputs -- pass number, lane $i$, slice number, and a counter -- without reading password-dependent blocks. Memory access addresses reveal nothing to cache-timing observers, at the cost of a predictable dependency graph that attackers can analyze with \emph{graph-pebbling} schedules (algorithms on directed data-dependency graphs that choose which intermediate nodes to keep in memory and which to recompute) to shave a modest factor off the Area-Time product.
  \item[Argon2id (the recommended hybrid).] During Pass~0, Slices~0 and~1 use data-independent addressing (Argon2i) so early password-dependent state never drives memory addresses; Slices~2 and~3 of Pass~0 and all later passes $1, \dots, t-1$ switch to data-dependent addressing (Argon2d), combining cache-timing protection with strong Area-Time hardness.
\end{description}

\begin{implementbox}
Computing Argon2id with standard parameters. In production systems, invoke a vetted C binding such as \texttt{argon2-cffi} or \texttt{libsodium}.
\begin{lstlisting}[language=Python]
import os, hmac
from argon2.low_level import hash_secret_raw, Type

def register_user(password: str) -> tuple[bytes, bytes]:
    # 16-byte random salt per user defeats rainbow tables:
    salt = os.urandom(16)
    # 64 MiB memory, 3 passes, 4 parallel lanes:
    digest = hash_secret_raw(
        secret=password.encode("utf-8"),
        salt=salt,
        time_cost=3,
        memory_cost=64 * 1024,   # 64 MiB in KiB
        parallelism=4,
        hash_len=32,
        type=Type.ID             # Argon2id hybrid
    )
    return salt, digest          # salt is stored openly next to the digest

def verify_user(password: str, salt: bytes, stored_digest: bytes) -> bool:
    candidate = hash_secret_raw(
        secret=password.encode("utf-8"),
        salt=salt,
        time_cost=3,
        memory_cost=64 * 1024,
        parallelism=4,
        hash_len=32,
        type=Type.ID
    )
    # Mandatory constant-time comparison to prevent timing side channels:
    return hmac.compare_digest(candidate, stored_digest)
\end{lstlisting}
\end{implementbox}

\begin{focusbox}
\textbf{Salt vs.\ pepper.} A \emph{salt} is unique per user, chosen at random, and stored in plaintext next to the password digest to defeat precomputation and hide password reuse. A \emph{pepper} is a single secret key shared across all accounts, stored outside the database inside a \emph{hardware security module} (HSM, a dedicated tamper-resistant key-storage appliance) or secret-management service, and mixed into the hash (for example via HMAC) before or after Argon2id. If an attacker dumps the database without compromising the application server or HSM, the missing pepper blocks offline dictionary guessing altogether. A pepper adds \emph{defense-in-depth} (an independent backup defense if the database leaks alone), and never replaces per-user salts.
\end{focusbox}

\subsection{Origin-bound phishing-resistant authentication: WebAuthn and passkeys}

Argon2id raises the cost of offline password cracking after a database breach, yet even a gigabyte of RAM per hash leaves a second weakness untouched: \textbf{a password is a shared secret typed into a webpage the user might misidentify}.

Suppose an attacker registers a look-alike domain (such as \texttt{g00gle.com}), sends a lure email, and serves a replica of a login page. When the victim submits their password, the attacker's \emph{reverse proxy} (a relay server sitting between the victim's browser and the genuine website, forwarding traffic both ways) captures the plaintext password and forwards it immediately to the real server. Add-on \emph{multi-factor authentication} (MFA) codes that the user types or copies -- text-message (SMS) codes and six-digit \emph{time-based one-time passcodes} (TOTP, RFC~6238) -- fail against the same relay: automated proxy toolkits forward the six-digit one-time passcode (OTP) in real time and receive the real server's authenticated \emph{session cookies} (browser tokens that keep an account logged in). Expecting people to spot subtle character swaps in URL bars under time pressure does not work reliably.

The \textbf{Web Authentication} standard (\textbf{WebAuthn}), developed by the World Wide Web Consortium (W3C) and the Fast Identity Online (FIDO) Alliance and deployed to users as \emph{passkeys}, eliminates shared secrets altogether. Instead of sending a secret string over the network, WebAuthn proves identity with an \textbf{origin-bound digital signature} computed inside local security hardware -- a phone or laptop's dedicated security chip (such as an Apple Secure Enclave or a PC's Trusted Platform Module, TPM) or a plug-in USB security key (FIDO2 token).

The protocol runs in two phases:

\begin{enumerate}
  \item \textbf{Registration.} When a user registers at a website -- called the \emph{relying party} (for example, \url{https://accounts.google.com}) -- the browser asks the authenticator to create a fresh credential bound to the canonical Relying Party Identifier:
  \[
    \text{RP ID} = \texttt{"accounts.google.com"}.
  \]
  The authenticator generates a public/private signature key pair $(pk, sk)$ using a standard elliptic-curve scheme such as Ed25519 or ECDSA over NIST P-256 (Chapter~22). The private key $sk$ stays sealed inside the security chip, while the public key $pk$ and a credential identifier go to the server. Because the server stores only $pk$ -- no password and no secret -- a database dump exposes only public keys.
  \item \textbf{Authentication (challenge--response).} At login, the server sends a fresh 256-bit random challenge nonce $c \getsr \set{0,1}^{256}$. Reading the verified domain from its own address bar, the browser assembles a UTF-8 JSON record (a structured key--value text string), denoted \texttt{clientDataJSON}:
  \begin{align*}
    \text{\texttt{clientDataJSON}} = \{ & \texttt{"type"}: \texttt{"webauthn.get"}, \\
    & \texttt{"challenge"}: c, \\
    & \texttt{"origin"}: \texttt{"https://accounts.google.com"} \},
  \end{align*}
  and hashes it with SHA-256:
  \[
    h_{\text{client}} = \text{SHA-256}(\text{\texttt{clientDataJSON}}).
  \]
  The browser hands $h_{\text{client}}$ and the RP ID to the authenticator. After checking local user presence via fingerprint, face unlock, or a device PIN, the authenticator builds a header \texttt{authenticatorData} -- containing $\text{SHA-256}(\text{RP ID})$, user-presence flags, and a counter -- and computes a digital signature
  \[
    \sigma = \Sign_{sk}(\text{authenticatorData} \concat h_{\text{client}}),
  \]
  where $\Sign_{sk}(x)$ produces a signature on message $x$ using private key $sk$, paired with a public verification algorithm $\Vrfy_{pk}(x, \sigma)$ that checks $\sigma$ against $x$ under $pk$ (Chapter~22). The browser returns $(\text{authenticatorData}, \text{\texttt{clientDataJSON}}, \sigma)$ to the server, which checks that \texttt{origin} equals \url{https://accounts.google.com}, that the challenge equals $c$, that \texttt{authenticatorData} begins with $\text{SHA-256}(\texttt{"accounts.google.com"})$, and that
  \[
    \Vrfy_{pk}\bigl(\text{authenticatorData} \concat \text{SHA-256}(\text{\texttt{clientDataJSON}}),\, \sigma\bigr) = 1.
  \]
\end{enumerate}

Suppose an attacker lures a user to \url{https://evil-login.com}, fetches a fresh challenge $c$ from \texttt{accounts.google.com}, and relays $c$ to the victim's browser. When the malicious page calls WebAuthn, the page cannot lie about its own origin: the browser reads the verified TLS address bar directly, setting
\[
  \text{\texttt{origin}} = \texttt{"https://evil-login.com"}, \qquad
  \text{RP ID} = \texttt{"evil-login.com"}.
\]
Two independent defenses stop the relay:

\begin{enumerate}
  \item \textbf{Credential scoping.} For RP ID \texttt{"evil-login.com"}, the authenticator looks up matching keys. Because the user's Google key pair was bound at registration to \texttt{"accounts.google.com"}, no key matches and the authenticator refuses to sign.
  \item \textbf{Hashed origin binding.} Even if a faulty token signed anyway, $\sigma$ covers $\text{authData}_{\text{evil}} \concat h_{\text{client}}$, where $h_{\text{client}}$ hashes the evil-origin \texttt{clientDataJSON} record. Forwarding that record unchanged fails the server's \texttt{origin} check; rewriting the origin string to \texttt{"https://accounts.google.com"} changes the server's digest to
  \[
    h_{\text{expected}} = \text{SHA-256}(\text{\texttt{clientDataJSON}}_{\text{rewritten}}) \;\ne\; h_{\text{client}}
  \]
  (by second-preimage resistance of SHA-256), so $\Vrfy_{pk}(\text{authenticatorData} \concat h_{\text{expected}}, \sigma)$ rejects.
\end{enumerate}

Phishing resistance therefore rests on hashing the browser-verified origin into the signed statement, rather than hoping the user notices a forged domain name.

\section{The real-world status of named hashes}
\label{ch14:realworld}

\begin{center}

\begin{historybox}
Ron Rivest designed MD4 (1990) and MD5 (1991) for fast 32-bit software hashing, while the NSA and NIST published SHA-0 (1993) and SHA-1 (1995). Weaknesses in MD4 appeared almost at once. At Crypto~2004, Xiaoyun Wang and co-authors introduced differential attacks that found MD5 collisions in minutes, and in 2005 showed theoretical collision attacks on SHA-1 well below $2^{80}$. Certificate authorities kept signing with MD5 until Alexander Sotirov and collaborators used a chosen-prefix MD5 collision in 2008 to forge a rogue certificate-authority (CA) certificate trusted by browsers. A full SHA-1 collision was computed in 2017 (SHAttered, Marc Stevens et al., roughly $2^{63}$ compressions), followed by practical chosen-prefix collisions in 2020.

Every one of those broken standards combined Merkle--Damg\aa{}rd iteration with a 128- or 160-bit digest and an under-margined compression function. That record prompted NIST's public SHA-3 competition (2007--2012), won by Keccak (Guido Bertoni, Joan Daemen, Micha\"el Peeters, and Gilles Van Assche), providing a sponge standard independent of SHA-2's design. SHA-2 (2001) remains unbroken at full rounds, and the historical pattern -- collisions falling long before preimages, with security governed by digest width and compression-function margin -- matches what the birthday bound and the Merkle--Damg\aa{}rd reduction predict.
\end{historybox}

\begin{aestheticbox}
Hash functions are the most versatile primitive in cryptography. One well-studied function that is one-way, collision resistant, and free of structural leaks lets a system verify files, commit to hidden choices, build a MAC, compress inputs for digital signatures, derive keys, name objects by their content, and link blocks in a public ledger. Because so many protocols rest on the same hash, any break ripples across deployed systems -- which is why digest length, domain-extension structure, and years of open cryptanalysis matter so much.
\end{aestheticbox}

\begin{connectionbox}
An unkeyed hash proves that a file matches a trusted digest, yet anyone who intercepts both a message $M$ and its digest $\Hash(M)$ on an untrusted channel can replace them with $M'$ and $\Hash(M')$. Chapter~15 mixes a shared secret key into hashing to build Message Authentication Codes (MACs) and HMAC, turning unkeyed digests into unforgeable tags.
\end{connectionbox}

\section{Exercises}
\label{ch14:exercises}

\begin{exercise}[Counting pairs]
A hash has $n = 32$ output bits. Roughly how many random inputs must you hash before you expect a collision? How many before you expect to hit one \emph{specific} target digest by chance? Explain the $2^{16}$ versus $2^{32}$ gap in one sentence using the birthday bound.
\end{exercise}

\begin{exercise}[Birthday probability]
Using $p(q) \approx 1 - e^{-q(q-1)/(2N)}$ with $N = 2^{40}$, find the smallest $q$ (to the nearest power of two) for which the collision probability exceeds $1/2$. Compare to the rule of thumb $q \approx 1.177\sqrt{N}$.
\end{exercise}

\begin{exercise}[Which property?]
For each application, state which of the three resistance properties it most directly relies on, and give a one-line attack if that property fails. Consider: (a) a software-download checksum published by the vendor; (b) a sealed-bid auction using $\Hash(\text{bid}\concat r)$; (c) deduplicating a backup store by content hash; and (d) a signature over $\Hash(\text{contract})$ where the signer wrote the contract.
\end{exercise}

\begin{exercise}[Reduction]
Prove that if $\Hash$ is collision resistant then the function $\Hash'(x) = \Hash(\Hash(x))$ is also collision resistant. Where does your reduction use collision resistance of $\Hash$?
\end{exercise}

\begin{exercise}[Length extension by hand]
A naive server authenticates messages with $t = \Hash(k \concat M)$ for a Merkle--Damg\aa{}rd hash and an 8-byte secret $k$. Given a captured pair $(M = \texttt{"amount=10"}, t)$, describe precisely the bytes of the forged message you can authenticate without knowing $k$, and the one piece of information about $k$ you must know or guess. Then explain in one sentence why HMAC blocks your attack.
\end{exercise}

\begin{exercise}[Toy collision]
Run the toy Merkle--Damg\aa{}rd hash from Section~\ref{ch14:md} (8-bit state). Empirically, after how many distinct inputs does the first collision appear on average over 20 runs? Compare to the $50\%$-probability threshold $1.177 \cdot 2^{4} \approx 19$, and explain why the mean waiting time ($\approx \sqrt{\pi N / 2} \approx 20.1$) is slightly higher than the median.
\end{exercise}

\begin{exercise}[Sponge security]
SHA3-256 has capacity $c = 512$ and output $n = 256$. State its collision and preimage security levels and explain, in terms of the rate/capacity split, why an attacker cannot mount a length-extension attack against $\text{SHA3-256}(k \concat M)$.
\end{exercise}

\begin{exercise}[Salt arithmetic]
A breached database stores $(\text{salt}, \text{SHA-256}(\text{salt}\concat\text{password}))$ for $10\,\text{million}$ users with unique 16-byte salts. An attacker has a wordlist of $10^{9}$ candidate passwords and a rig computing $10^{10}$ SHA-256 evaluations per second. (a) How long does it take to test the wordlist against \emph{one} target account? (b) Why does the per-user salt force the total work across all $10\,\text{million}$ accounts to be $10\,\text{million}$ times part~(a), rather than one shared pass? (c) How does switching to Argon2id calibrated at $0.5\,\text{seconds}$ per guess on that rig change part~(a)?
\end{exercise}

\begin{exercise}[Pepper]
Explain why a secret pepper stored outside the database renders a database-only breach uncrackable, yet does \emph{not} replace per-user salts. Give a concrete scenario where using only a pepper (no salt) leaks password reuse across users.
\end{exercise}

\begin{exercise}[Merkle proof]
A Merkle tree has 8 leaves $d_1, \dots, d_8$. Write out the authentication path (the list of sibling hashes, from bottom to top) needed to prove $d_5$ is in the tree, and the sequence of hash computations the verifier performs to reach the root. How does the proof size grow with the number of leaves $N$?
\end{exercise}

\begin{exercise}[Break a homemade commitment]
A protocol commits to a single decision bit $b \in \set{0,1}$ by publishing $c = \Hash(b)$ with no nonce. Show that this commitment is not hiding by giving the attacker's procedure. Then show that adding a 256-bit random nonce $r$ and publishing $\Hash(b \concat r)$ restores hiding, naming the security property of $\Hash$ you rely on.
\end{exercise}
