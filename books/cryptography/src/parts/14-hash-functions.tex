\chapter{Hash Functions}

In Chapter 13 we saw how block cipher modes encrypt messages of arbitrary length, hiding their content from an eavesdropper without guaranteeing that no one has flipped bits along the way. A cryptographic hash function takes a message of any length and crushes it down to a short, fixed-length string of bits -- its \emph{digest}. SHA-256 turns the complete works of Shakespeare, or a single byte, or this entire book, into exactly 256 bits. That much is easy: any number of cheap functions can map long inputs to short outputs. What makes a hash function \emph{cryptographic} is a set of promises about how hard it is to find inputs that behave in inconvenient ways -- inputs that collide, or inputs that hit a target you picked in advance.

Those promises are what let a 32-byte digest stand in for a multi-gigabyte file with no loss of trust. They are what let a website store something derived from your password without storing the password. They are what let a blockchain commit to a billion transactions with one number. Hash functions are the most-used primitive in all of cryptography, and nearly every later chapter depends on them: MACs (Chapter 15), signatures (Chapter 22), key derivation, commitments (Chapter 32), and the Merkle trees that hold blockchains together (Chapter 36) all sit on top of a good hash.

This chapter builds the idea from the security properties up. We will pin down what ``hard to break'' means, derive the birthday bound that governs collision-finding, dissect the two construction styles (Merkle--Damgard and the sponge), break a Merkle--Damgard hash with a length-extension attack, and end with fingerprints, commitments, and memory-hard password hashing.

\section{What a hash function is, and what it must promise}
\label{ch14:properties}

Formally, a hash function is a function
\[
  \Hash : \set{0,1}^{*} \to \set{0,1}^{n},
\]
where $\set{0,1}^{*}$ is the set of all finite bit strings and $n$ is the fixed output length (256 for SHA-256, 512 for SHA-512). The input is sometimes called the \emph{message} or \emph{preimage}; the output is the \emph{digest}, \emph{hash}, or \emph{fingerprint}.

Because the domain is infinite and the range is finite, collisions \emph{must} exist: there are infinitely many messages and only $2^{n}$ possible digests, so by the pigeonhole principle countless pairs of distinct messages share a digest. Cryptography never claims collisions do not exist. It claims you cannot \emph{find} one with any feasible amount of work.

There are three security properties, in increasing order of how much they buy you.

\begin{definition}[Preimage resistance]
\label{ch14:def-preimage}
$\Hash$ is \emph{preimage resistant} (``one-way'') if, given a target digest $y = \Hash(x)$ for a randomly chosen $x$, no efficient adversary can find \emph{any} message $x'$ with $\Hash(x') = y$, except with negligible probability. For an ideal $n$-bit hash the best attack is brute force, costing about $2^{n}$ evaluations.
\end{definition}

\begin{definition}[Second-preimage resistance]
\label{ch14:def-second}
$\Hash$ is \emph{second-preimage resistant} if, given a specific message $x$, no efficient adversary can find a \emph{different} message $x' \ne x$ with $\Hash(x') = \Hash(x)$, except with negligible probability. The ideal cost is again about $2^{n}$.
\end{definition}

\begin{definition}[Collision resistance]
\label{ch14:def-collision}
$\Hash$ is \emph{collision resistant} if no efficient adversary can find \emph{any} pair $x \ne x'$ with $\Hash(x) = \Hash(x')$, except with negligible probability. Here the adversary picks both messages and has total freedom. As we will prove in Section~\ref{ch14:birthday}, the ideal cost is only about $2^{n/2}$.
\end{definition}

\begin{intuitionbox}
A clean way to keep the three straight is to ask \emph{who chooses what}.
\begin{itemize}
  \item \textbf{Preimage}: the world hands you an \emph{output} $y$; you must produce \emph{some} input mapping to it. (``Here is a hash. What message made it?'')
  \item \textbf{Second-preimage}: the world hands you an \emph{input} $x$; you must produce a \emph{different} input with the same hash. (``Here is a contract. Forge a different one that hashes the same.'')
  \item \textbf{Collision}: the world hands you \emph{nothing}; you produce \emph{any} two inputs that hash alike. (``Just find any clash at all.'')
\end{itemize}
More freedom for the attacker means an easier attack, which is why collision resistance is the strongest property and the first to fall.
\end{intuitionbox}

These properties are not independent. Collision resistance is the strongest of the three in the following precise sense.

\begin{proposition}[Collision resistance implies second-preimage resistance]
\label{ch14:cr-implies-spr}
If $\Hash$ is collision resistant then it is second-preimage resistant.
\end{proposition}

\begin{whybox}
The argument is a \emph{reduction}: we show that breaking the weaker property would break the stronger one, so the stronger one is at least as hard.

Suppose an adversary $\mathcal{A}$ finds second preimages. Build a collision finder $\mathcal{B}$: sample a random message $x$ yourself, hand it to $\mathcal{A}$, and receive $x' \ne x$ with $\Hash(x') = \Hash(x)$. Then $(x, x')$ is a collision. So if second preimages are easy to find, collisions are too -- contrapositively, if collisions are hard, so are second preimages. The reduction loses nothing here; it is tight.
\end{whybox}

The relationship between collision resistance and \emph{preimage} resistance is subtler. For a random function with output much shorter than its input they tend to come together, but one can hand-craft contrived functions that are collision resistant yet not one-way, or vice versa. In practice we demand all three from any hash we are willing to call cryptographic, and we design and test for all three.

\begin{trapbox}
A non-cryptographic hash -- CRC32, the hash behind a Java \texttt{HashMap}, FNV, MurmurHash -- has \emph{none} of these properties and is trivial to collide on purpose. These functions exist to spread inputs evenly for speed, not to resist an adversary. Using \texttt{hashCode()} or a CRC anywhere a security decision depends on the output is a classic, fatal mistake. ``Hash function'' means two completely different things to a systems engineer and to a cryptographer.
\end{trapbox}

\subsection{The random-oracle ideal}

When cryptographers reason about a hash informally, they often pretend it is a \emph{random oracle}: an idealized black box that, for each new input, flips $n$ fair coins to produce the output, and thereafter returns that same output whenever the input repeats. A random oracle has every property we could want -- it is one-way, collision resistant, and its outputs look independent and uniform -- because there is simply no structure to exploit; the only way to learn $\Hash(x)$ is to ask.

Real hash functions are deterministic public algorithms, not idealized black boxes, so the random-oracle \emph{model} is a heuristic, and proofs ``in the random-oracle model'' are weaker than proofs in the standard model. But the heuristic is enormously useful for intuition and for the security arguments behind RSA-OAEP, Fiat--Shamir signatures, and much else. We will lean on it whenever it sharpens the picture, and flag the places where the gap between the ideal and reality has actually bitten people.

\section{The birthday bound: why $n$-bit hashes give $n/2$-bit collision security}
\label{ch14:birthday}

Brute-forcing a preimage of an $n$-bit hash takes about $2^{n}$ tries: you are searching for one specific output among $2^{n}$. Collisions are far cheaper, and the reason is the same mathematics behind the famous party trick that 23 people suffice for an even chance of two sharing a birthday.

\begin{intuitionbox}
You are not looking for a message that hashes to one \emph{fixed} target. You are looking for \emph{any} two of your messages that hash to the \emph{same} value -- and the more messages you have, the more \emph{pairs} you have. With $q$ messages there are $\binom{q}{2} \approx q^{2}/2$ pairs, each of which collides with probability about $2^{-n}$. The expected number of colliding pairs crosses $1$ when $q^{2}/2 \approx 2^{n}$, i.e. when $q \approx 2^{(n+1)/2} \approx 2^{n/2}$. Collisions appear after only the \emph{square root} of the naive number of tries.
\end{intuitionbox}

Let us do the probability carefully.

\begin{theorem}[Birthday bound]
\label{ch14:thm-birthday}
Draw $q$ outputs independently and uniformly from a set of size $N = 2^{n}$. The probability that at least two coincide satisfies
\[
  p(q) \;=\; 1 - \prod_{j=1}^{q-1}\Bigl(1 - \frac{j}{N}\Bigr)
        \;\approx\; 1 - e^{-q(q-1)/(2N)}.
\]
Consequently $p(q) \ge \tfrac12$ once $q \approx 1.177\sqrt{N} = 1.177 \cdot 2^{n/2}$.
\end{theorem}

\begin{whybox}
Number the draws $1, 2, \dots, q$. Given that the first $j$ draws are all distinct, draw $j+1$ avoids those $j$ earlier values with probability $1 - j/N$. Multiplying these conditional probabilities for $j = 1, \dots, q-1$, the chance that \emph{all} $q$ draws are distinct is
\[
  \prod_{j=1}^{q-1}\Bigl(1 - \frac{j}{N}\Bigr).
\]
Now use $1 - x \le e^{-x}$, valid for all real $x$:
\[
  \prod_{j=1}^{q-1}\Bigl(1 - \frac{j}{N}\Bigr)
   \le \prod_{j=1}^{q-1} e^{-j/N}
   = \exp\!\Bigl(-\frac{1}{N}\sum_{j=1}^{q-1} j\Bigr)
   = \exp\!\Bigl(-\frac{q(q-1)}{2N}\Bigr).
\]
The collision probability is one minus that. Setting the exponent equal to $\ln 2$ gives $q(q-1) \approx 2N\ln 2$, hence $q \approx \sqrt{2\ln 2}\,\sqrt{N} \approx 1.177\sqrt{N}$.
\end{whybox}

\begin{connectionbox}
This is exactly the birthday-collision calculation from the companion probability book, with the 365 days of the year replaced by the $N = 2^{n}$ possible digests. There we found $\approx 1.177\sqrt{365} \approx 22.5$, so 23 people. Here the same constant rides on top of a $2^{n/2}$ that swamps everything. The cube-root variant -- three-way collisions appearing at $N^{1/3}$ -- and the memoryless cycle-finding methods (Pollard's rho, Floyd's tortoise-and-hare, van Oorschot--Wiener parallel collision search) that find collisions in $\approx 2^{n/2}$ time but tiny memory are all developed in the algorithms companion.
\end{connectionbox}

\begin{example}[A toy 16-bit hash]
\label{ch14:ex-16bit}
Take $n = 16$, so $N = 65536$. A preimage costs about $2^{16} = 65{,}536$ evaluations. A collision costs about $1.177\sqrt{65536} = 1.177 \cdot 256 \approx 301$ evaluations -- you would expect a collision after hashing roughly 300 random short strings and watching for a repeat. With $q = 300$ the exponent is $-300\cdot 299/(2\cdot 65536) \approx -0.684$, giving $p \approx 1 - e^{-0.684} \approx 0.495$, almost exactly even odds. The square-root gap between $65{,}536$ and $301$ is why output length matters so much.
\end{example}

\begin{focusbox}
\textbf{Design consequence.} To resist collision attacks at the ``$b$-bit security level'' (meaning $2^{b}$ work) you need an output of $n = 2b$ bits. That is why a 128-bit security target demands a 256-bit hash. It is why 128-bit-output hashes like MD5 ($2^{64}$ collision work) and 160-bit SHA-1 ($2^{80}$ nominal) are no longer collision-safe: $2^{64}$ is now a weekend on rented hardware, and SHA-1 collisions have actually been computed (see Section~\ref{ch14:realworld}). Preimage attacks on these same functions remain near $2^{n}$ and are still out of reach; it is always \emph{collisions} that fall first.
\end{focusbox}

\begin{walkbox}
A protocol truncates SHA-256 to its first 80 bits to save space in a fingerprint. What is the collision security level, and is that wise in 2026? \\[0.3em]
\textbf{Answer.} Collision work is $2^{80/2} = 2^{40}$, about a trillion evaluations -- a few minutes on a GPU. If the fingerprint is only ever compared to a value a legitimate party computed (a second-preimage setting), security is closer to $2^{80}$, which is borderline. If an attacker can choose \emph{both} sides of the comparison (a collision setting -- e.g. getting two documents to share a fingerprint), $2^{40}$ is catastrophic. Always ask which property your application actually relies on.
\end{walkbox}

\section{Building a hash from a small component: Merkle--Damgard}
\label{ch14:md}

We can compress a \emph{fixed} pair of blocks with a carefully designed mixing function. How do we hash a message of \emph{arbitrary} length? The classic answer, used by MD5, SHA-1, and the SHA-2 family, is the \emph{Merkle--Damgard} construction. It iterates a fixed-input \emph{compression function} across the message, carrying a running state called the \emph{chaining value}.

In 1989, Ralph Merkle and Ivan Damgard independently proved the reduction theorem that makes this design work: if the underlying compression function is collision resistant, then the full iterated hash is collision resistant as well. That result reduced the problem of hashing arbitrary-length messages to the simpler task of building a single fixed-input compression function. Nearly every widely deployed hash from 1990 to 2010 -- MD4, MD5, SHA-0, SHA-1, SHA-256, and SHA-512 -- adopted this Merkle--Damgard architecture. The structure's one notorious architectural wart, the length-extension vulnerability, is examined in Section~\ref{ch14:length-ext}.

The compression function is
\[
  f : \set{0,1}^{n} \times \set{0,1}^{b} \to \set{0,1}^{n},
\]
taking an $n$-bit chaining value and a $b$-bit message block to a new $n$-bit chaining value. To hash a message $M$:

\begin{enumerate}
  \item \textbf{Pad} $M$ so its length is a multiple of the block size $b$. The padding includes the message's original bit-length (``Merkle--Damgard strengthening''), which is what makes the security proof go through. Split the padded message into blocks $M_1, M_2, \dots, M_k$.
  \item \textbf{Initialize} the chaining value to a fixed constant $H_0 = \mathit{IV}$ baked into the standard.
  \item \textbf{Absorb} each block: $H_i = f(H_{i-1}, M_i)$ for $i = 1, \dots, k$.
  \item \textbf{Output} $H_k$ (possibly after a final transform).
\end{enumerate}

\begin{theorem}[Merkle--Damgard collision resistance]
\label{ch14:md-thm}
If the compression function $f$ is collision resistant, then the Merkle--Damgard hash $\Hash$ built from it (with length-strengthening padding) is collision resistant.
\end{theorem}

\begin{whybox}
Suppose someone hands us two distinct messages $M \ne M'$ with $\Hash(M) = \Hash(M')$. We will extract a collision in $f$, contradicting its collision resistance.

Walk the two chains \emph{backwards} from the equal final outputs. The last compression step gives
\[
  f(H_{k-1}, M_k) = H_k = H'_{k'} = f(H'_{k'-1}, M'_{k'}).
\]
If the two inputs to $f$ differ -- that is, $(H_{k-1}, M_k) \ne (H'_{k'-1}, M'_{k'})$ -- we have found a collision in $f$ and we stop. Otherwise the inputs are equal, so $H_{k-1} = H'_{k'-1}$ and the last blocks match; step back one position and repeat the argument.

If the messages have different lengths, the length-strengthening padding forces the final blocks to differ (they encode different lengths), so the walk produces a collision at the last step. If the lengths are equal but the messages differ, they must differ in some block; the first block (scanning from the end) where they differ yields distinct inputs to $f$ with equal outputs. Either way we manufacture an $f$-collision. So $\Hash$-collisions imply $f$-collisions, and the theorem follows by contrapositive.
\end{whybox}

\begin{implementbox}
A toy Merkle--Damgard hash with an 8-bit chaining value, just to watch the machinery move. \textbf{This is for learning only -- its 8-bit state means a collision after $\approx 16$ inputs, and the ``compression function'' has no cryptographic strength. Never use anything like this for real.}
\begin{lstlisting}[language=Python]
def compress(h, block):          # h: int in 0..255, block: int in 0..255
    # A deliberately weak toy mixer. NOT cryptographic.
    x = (h ^ block) & 0xFF
    x = ((x << 3) | (x >> 5)) & 0xFF      # rotate left 3
    x = (x * 167 + 13) & 0xFF             # mix
    return x ^ ((h + block) & 0xFF)

def md_hash(message: bytes) -> int:
    h = 0x6A                              # the IV
    msg = message + bytes([len(message) & 0xFF])   # length strengthening
    for byte in msg:                     # each byte is one "block"
        h = compress(h, byte)
    return h

print(hex(md_hash(b"hello")))            # e.g. 0x..
print(hex(md_hash(b"world")))
# Find a collision by brute force -- with only 256 outputs it is instant:
seen = {}
i = 0
while True:
    d = md_hash(str(i).encode())
    if d in seen:
        print("collision:", seen[d], "and", i, "both ->", hex(d))
        break
    seen[d] = i
    i += 1
\end{lstlisting}
Run it and you will see a collision pop out after a few hundred tries at most -- exactly the birthday bound for $n = 8$ ($\approx 1.177\cdot 2^{4} \approx 19$, with variance pushing the typical first hit somewhat higher). Scaling the state to 256 bits is what turns this toy into something nobody can collide.
\end{implementbox}

\section{Length extension: the Merkle--Damgard wart}
\label{ch14:length-ext}

Merkle--Damgard has a structural leak that is easy to miss and has caused real breaches. The final output $H_k$ \emph{is} the internal chaining value -- there is nothing hiding it. So if you know $\Hash(M)$ and the \emph{length} of $M$, you can resume the iteration from $H_k$ and compute $\Hash(M \concat \text{pad} \concat S)$ for a suffix $S$ of your choosing, \emph{without knowing $M$ itself}.

\begin{attackbox}
\textbf{The length-extension attack, and how it breaks a homemade MAC.}

A tempting but broken way to authenticate a message with a secret key $k$ is the ``prefix MAC'':
\[
  t = \Hash(k \concat M).
\]
The idea is that only someone who knows $k$ can produce a valid tag $t$ for $M$. With a Merkle--Damgard hash this is false.

Suppose an attacker sees a legitimate pair $(M, t)$ where $t = \Hash(k \concat M)$, and knows (or guesses) the length of $k$. The tag $t$ is exactly the chaining value after absorbing $k \concat M \concat \text{pad}_1$, where $\text{pad}_1$ is the padding the hash appended. The attacker now:
\begin{enumerate}
  \item sets the internal state of a fresh hash object to $t$;
  \item feeds in any chosen suffix $S$;
  \item reads off $t' = \Hash(k \concat M \concat \text{pad}_1 \concat S)$.
\end{enumerate}
The result is a \emph{valid tag} for the new message $M' = M \concat \text{pad}_1 \concat S$ -- a message the attacker partly chose -- even though they never learned $k$. The notorious instance: a web request signed by appending \verb|&admin=true| after the legitimate padding still verifies.
\end{attackbox}

\begin{walkbox}
Why can the attacker resume without $k$ or $M$ (Figure~\ref{ch14:fig-lenext})? Because the only thing the next compression step needs is the \emph{current chaining value}, and that value is the tag $t$ sitting in plain view. Merkle--Damgard never ``closes off'' the state. The attacker does need to reconstruct $\text{pad}_1$, which encodes the length of $k \concat M$ -- hence they must know or brute-force the key length. Keys are short, so that is cheap.
\end{walkbox}

There are several clean fixes, and you should recognize all of them:

\begin{itemize}
  \item \textbf{HMAC} (Chapter 15) nests two hash calls, $\Hash(k_{\text{out}} \concat \Hash(k_{\text{in}} \concat M))$. The outer hash hides the inner chaining value, so resuming buys the attacker nothing. This is the right way to key a Merkle--Damgard hash, and the reason you should never roll your own prefix MAC.
  \item \textbf{Truncation / output transform.} SHA-512/256 runs SHA-512 internally (512-bit state) but outputs only 256 bits, so the full chaining value is never revealed. SHA-224 and SHA-384 are similar.
  \item \textbf{A different construction.} Sponge-based hashes (SHA-3, next section) are immune to length extension by design, because their output is a \emph{squeeze} of a larger hidden state.
\end{itemize}

\begin{implementbox}
Length extension is so mechanical that standard libraries reproduce it in a few lines. We show it here so you can see how little the attacker needs. \textbf{Learning only -- the lesson is ``do not build prefix MACs,'' not ``go forge tags.''}
\begin{lstlisting}[language=Python]
# Pseudocode against a Merkle-Damgard hash H with block-aligned padding.
# Attacker knows: message M, tag t = H(secret || M), and len(secret).
def forge(t, M, secret_len, suffix):
    glue = md_padding(secret_len + len(M))   # the pad H would have appended
    forged_message = M + glue + suffix       # what the new tag authenticates
    # Resume the hash from the leaked internal state == t:
    h = HashState.from_digest(t)             # set chaining value = t
    h.set_length(secret_len + len(M) + len(glue))
    h.update(suffix)
    forged_tag = h.digest()                  # == H(secret || M || glue || suffix)
    return forged_message, forged_tag
\end{lstlisting}
Real tools (\texttt{hashpump}, the \texttt{hlextend} library) automate exactly this. The defense is never to expose a raw $\Hash(k \concat M)$ as an authenticator.
\end{implementbox}

\section{The sponge construction and SHA-3}
\label{ch14:sponge}

In 2007 NIST opened a public competition for a new hash standard, partly hedging against the possibility that the MD-family weaknesses behind the MD5 and SHA-1 breaks might eventually reach SHA-2. The winner, announced in 2012 and standardized as SHA-3 in 2015, was \emph{Keccak}, built on a completely different idea: the \emph{sponge}.

A sponge maintains a wide internal state of $b = r + c$ bits, conceptually split into a \emph{rate} part of $r$ bits (the part that touches the message) and a \emph{capacity} part of $c$ bits (the secret reservoir that never directly meets the input or output). A fixed permutation $\pi$ -- for Keccak this is the 1600-bit permutation Keccak-$f$ -- stirs the whole state. Hashing proceeds in two phases.

\begin{description}
  \item[Absorbing.] Pad the message and cut it into $r$-bit blocks. For each block, XOR it into the rate part of the state, then apply $\pi$ to the full $b$-bit state. The capacity part is never touched by the message directly; it only changes through $\pi$.
  \item[Squeezing.] To produce output, read off the first $r$ bits of the state; if more output is needed, apply $\pi$ and read another $r$ bits, repeating until enough bits are out. Truncate to the desired digest length.
\end{description}

Figure~\ref{ch14:fig-sponge} traces both phases across the split state: message blocks enter and output blocks exit through the top $r$-bit rate lane, while the bottom $c$-bit capacity lane remains sealed inside the permutation chain.

\begin{whybox}
\textbf{Why the capacity buys security, and why length extension dies.}

The collision and (second-)preimage resistance of a sponge are governed by the \emph{capacity} $c$, not the output length alone: a well-built sponge offers roughly $\min(2^{c/2}, 2^{n/2})$ collision resistance and $\min(2^{c/2}, 2^{n})$ preimage resistance, where $n$ is the digest length. SHA3-256 uses $c = 512$, comfortably above its $2^{128}$ collision target.

Length extension cannot work because the digest is only the \emph{rate} portion that gets squeezed out -- the $c$-bit capacity is never revealed. An attacker who wants to resume the computation would need the full $b$-bit internal state, but the output exposes at most $r$ of those bits per squeeze and \emph{none} of the capacity. There is no leaked chaining value to continue from. This immunity is a clean, structural win over Merkle--Damgard, and it is why protocols can safely use raw $\text{SHA3}(k \concat M)$ as a MAC (KMAC formalizes exactly this).
\end{whybox}

SHAKE128 and SHAKE256 are \emph{extendable-output functions} (XOFs): the squeeze phase can run as long as you like, so a single call produces a stream of any length. XOFs are heavily used in post-quantum schemes (Chapter 35) for deterministic randomness expansion -- Kyber and Dilithium both lean on SHAKE.

\begin{connectionbox}
The Keccak-$f$ permutation organizes the 1600-bit state as a $5 \times 5 \times 64$ array of bits and applies five sub-steps per round ($\theta, \rho, \pi, \chi, \iota$) for 24 rounds, all over $\F_2$. The diffusion analysis -- how a one-bit change spreads to touch the whole state -- is linear-algebra-over-$\F_2$ in spirit, the same finite-field machinery from Chapter 6 that underlies AES's MixColumns.
\end{connectionbox}

\section{SHA-2 in practice}
\label{ch14:sha2}

Despite SHA-3's elegance, the dominant standard in deployed cryptography in 2026 is still \emph{SHA-2}, specifically SHA-256 and SHA-512. SHA-2 is a Merkle--Damgard hash whose compression function is itself built from a block-cipher-like round function (a Davies--Meyer construction: $H_i = E_{M_i}(H_{i-1}) \xor H_{i-1}$, where the feed-forward XOR is what makes a permutation one-way).

\begin{focusbox}
\textbf{SHA-256 at a glance.}
\begin{itemize}
  \item Output: 256 bits. Block: 512 bits. State: eight 32-bit words $a, b, \dots, h$ (256 bits total).
  \item Padding: append a \texttt{1} bit, then \texttt{0}s, then the 64-bit message length, to reach a multiple of 512 bits.
  \item 64 rounds per block, each mixing in one 32-bit ``message schedule'' word $W_t$ and one round constant $K_t$ (the $K_t$ are fractional parts of cube roots of the first 64 primes -- a ``nothing-up-my-sleeve'' choice so no one suspects a planted backdoor).
  \item Operations per round: modular addition mod $2^{32}$, bitwise XOR/AND, and fixed rotations -- the ``ARX-like'' style, fast in both hardware and software.
\end{itemize}
SHA-512 is the same design widened to 64-bit words, an 80-round schedule, a 1024-bit block, and a higher security margin across the board. On 64-bit CPUs SHA-512 is often \emph{faster per byte} than SHA-256 because it digests twice the data per block.
\end{focusbox}

\begin{applicationbox}
\textbf{Where SHA-2 actually runs.}
\begin{itemize}
  \item \textbf{TLS} (Chapter 25): certificate signatures, the transcript hash in the handshake, and HKDF key derivation all use SHA-256 or SHA-384. The cipher-suite name \texttt{TLS\_AES\_128\_GCM\_SHA256} names the hash explicitly.
  \item \textbf{Bitcoin} (Chapter 36): block hashing and proof-of-work are double SHA-256, $\text{SHA256}(\text{SHA256}(x))$ -- the double application was Satoshi's reflex defense against length extension.
  \item \textbf{Git} stores every object under its SHA-1 name and is migrating to SHA-256; \textbf{package managers} (apt, npm, pip) ship SHA-256 digests so you can verify a download was not tampered with.
  \item \textbf{Signatures} (Chapter 22): RSA, ECDSA, and EdDSA all sign $\Hash(M)$, never $M$ directly. The hash is what lets a fixed-size signature cover an arbitrarily long message, and signature unforgeability depends on the collision resistance of the hash.
\end{itemize}
Modern x86 and ARM cores include SHA extensions (\texttt{SHA256RNDS2}, ARMv8 \texttt{SHA256H}) that hash at several gigabytes per second per core.
\end{applicationbox}

\begin{trapbox}
\textbf{Do not confuse fast with safe for passwords.} SHA-256's speed is a virtue for fingerprints and signatures and a \emph{liability} for password storage: an attacker can try billions of password guesses per second per GPU against a bare SHA-256. Password hashing needs a deliberately \emph{slow}, memory-hard function -- bcrypt, scrypt, Argon2 -- as Section~\ref{ch14:passwords} explains. ``Hash the password with SHA-256'' is one of the most common and most dangerous half-measures in the wild.
\end{trapbox}

\section{Application 1: fingerprints and integrity}
\label{ch14:fingerprints}

The simplest use of a hash is as a \emph{fingerprint}: a short value that stands in for a large object so you can detect any change. Publish $\Hash(\text{file})$ over a trusted channel; anyone who downloads the file over an untrusted channel recomputes the hash and compares. A single flipped bit anywhere in the file changes about half the digest bits (the \emph{avalanche} property), so tampering is caught with overwhelming probability.

This is the backbone of software-update integrity, content-addressed storage (Git, IPFS, Docker image layers -- each object is named by its hash, so the name \emph{is} a verifiable identity), and deduplication. The property that does the work is \emph{second-preimage} resistance: given the published file, an attacker must not be able to craft a \emph{different} file with the same fingerprint.

\begin{attackbox}
\textbf{When fingerprints rely on the wrong property: the SHA-1 collision and ``evil twins.''}

If an attacker controls \emph{both} the original and the tampered file -- say, a software author who later wants to repudiate, or an attacker who submits a benign file for review then swaps in a malicious twin with the same hash -- then \emph{collision} resistance is what matters, and a 128- or 160-bit hash is too weak. In 2017 the SHAttered attack produced two distinct PDF files with identical SHA-1 digests at a cost of $\approx 2^{63}$ compressions. In 2019--2020 \emph{chosen-prefix} SHA-1 collisions (where the two files can begin with arbitrary attacker-chosen prefixes) became practical, breaking SHA-1's use in PGP web-of-trust certificates. The lesson: a fingerprint is only as trustworthy as the hash's collision resistance whenever the adversary can influence the original, and SHA-1 and MD5 are finished for that role.
\end{attackbox}

\subsection{Merkle trees: fingerprinting a collection}

To fingerprint not one file but a whole set -- and to let someone verify a single element without downloading the rest -- hash the elements pairwise up a binary tree. Each leaf is the hash of a data block; each internal node is the hash of its two children's hashes; the single \emph{root} hash commits to the entire collection.

\begin{center}
\begin{tikzpicture}[
   nd/.style={draw, rounded corners, minimum width=1.1cm, minimum height=0.55cm, font=\scriptsize, fill=blue!6},
   lf/.style={draw, minimum width=0.95cm, minimum height=0.5cm, font=\scriptsize, fill=green!8},
   >={Stealth}, level distance=1.0cm,
   level 1/.style={sibling distance=4.6cm},
   level 2/.style={sibling distance=2.3cm}]
  \node[nd] (root) {root $= \Hash(h_{12}\|h_{34})$}
    child {node[nd] (h12) {$h_{12}=\Hash(h_1\|h_2)$}
      child {node[lf] (h1) {$h_1=\Hash(d_1)$}}
      child {node[lf] (h2) {$h_2=\Hash(d_2)$}}
    }
    child {node[nd] (h34) {$h_{34}=\Hash(h_3\|h_4)$}
      child {node[lf] (h3) {$h_3=\Hash(d_3)$}}
      child {node[lf] (h4) {$h_4=\Hash(d_4)$}}
    };
\end{tikzpicture}
\end{center}

To prove block $d_3$ is in the tree under a known root, you reveal $d_3$ and the \emph{authentication path}: the sibling hashes $h_4$ and $h_{12}$. The verifier recomputes $h_3 = \Hash(d_3)$, then $h_{34} = \Hash(h_3 \concat h_4)$, then $\Hash(h_{12} \concat h_{34})$ and checks it equals the root. A proof for one element among $N$ has only $\log_2 N$ hashes. Collision resistance of $\Hash$ means a cheater cannot present a different $d_3'$ that recomputes to the same root.

\begin{applicationbox}
Merkle trees are everywhere: Bitcoin and Ethereum commit each block's transactions to a Merkle root in the block header (so a light client verifies one payment with a $\log N$ proof); Certificate Transparency logs are Merkle trees of every issued TLS certificate; Git's tree objects, BitTorrent v2, ZFS and Btrfs block checksums, and the \texttt{rsync}/Dropbox style sync protocols all use the same structure. Chapter 36 develops the blockchain version in full.
\end{applicationbox}

\section{Application 2: commitments}
\label{ch14:commitments}

A \emph{commitment scheme} is a cryptographic envelope. You want to lock in a value now and reveal it later, in a way that (a) you cannot change after committing, and (b) reveals nothing in the meantime. Think of sealing a prediction in an envelope and handing it over: \emph{binding} (you cannot swap the contents) and \emph{hiding} (no one can peek).

A hash gives a simple commitment. To commit to a message $m$, choose a random \emph{nonce} $r$ (say 256 bits) and publish
\[
  c = \Hash(m \concat r).
\]
To open, reveal $m$ and $r$; the verifier recomputes $\Hash(m \concat r)$ and checks it equals $c$.

\begin{whybox}
\textbf{Why it binds and why it hides.}
\begin{itemize}
  \item \textbf{Binding} rests on collision resistance. To open the same $c$ to a different message $m' \ne m$, you would need $(m', r')$ with $\Hash(m' \concat r') = \Hash(m \concat r)$ -- a collision. Find one and you have broken the hash.
  \item \textbf{Hiding} rests on one-wayness, with help from the random $r$. Without $r$, committing to a low-entropy value (``yes''/``no'', or a chess move from a small set) would let anyone just hash all possibilities and match $c$. The nonce $r$ injects enough entropy that the digest reveals nothing guessable about $m$ -- in the random-oracle model, $c$ is uniform and independent of $m$ until $r$ is revealed.
\end{itemize}
The random nonce is not optional. A commitment to a value from a small or guessable set, computed as $\Hash(m)$ with no nonce, is immediately broken by brute force over the possibilities -- the same mistake as unsalted password hashing.
\end{whybox}

\begin{applicationbox}
Hash commitments power coin-flipping and fair lotteries (each party commits to a random value, then both open and XOR), sealed-bid auctions, the ``commit--reveal'' pattern in smart contracts, and the Fiat--Shamir transform that turns interactive zero-knowledge proofs into non-interactive signatures (Chapters 22 and 31). When you cannot afford the algebraic, additively-homomorphic Pedersen commitments of Chapter 32, a salted hash commitment is the cheap default.
\end{applicationbox}

\section[Password Hashing, Memory-Hard Key Derivation, and Phishing-Resistant Authentication]{Password Hashing, Memory-Hard Key Derivation, \protect\linebreak and Phishing-Resistant Authentication}
\label{ch14:passwords}

Up to this point in the chapter, speed has been an unmixed advantage. We praised Merkle--Damg\aa{}rd and sponge designs that stream multiple gigabytes per second through vector registers. On modern x86 and ARM silicon, SHA-256 compresses a 64-byte block in under 200 nanoseconds, while BLAKE3 saturates memory buses at three gigabytes per second per core. For verifying operating system images, signing code, and aggregating transactions into Merkle roots, this high throughput is essential.

For storing human passwords, however, the same speed is a serious weakness.

Consider the physical asymmetry between the legitimate user and the attacker. A human user logging into an account types their password, submits the form, and waits. If the server takes two microseconds or two hundred milliseconds to verify the credential, the human perceives no difference: two hundred milliseconds feels instantaneous. And the server performs that calculation once per login session.

Now place a compromised database dump of password hashes into the hands of an adversary. The attacker does not execute one hash; they execute trillions of guesses against every compromised row. If the verification algorithm requires only 200 nanoseconds, a commodity desktop equipped with eight modern GPUs evaluates more than $10^{11}$ candidate passwords every second.

The problem is that people choose predictable passwords. A cryptographic key chosen uniformly from $\set{0,1}^{256}$ contains 256 bits of Shannon entropy; testing $10^{11}$ keys per second across $2^{256}$ possibilities would require $3 \times 10^{58}$ years. But passwords are created by humans, not physical entropy sources. Empirical studies of billions of leaked credentials reveal that human passwords have low entropy, clustering between 25 and 40 bits. Even an eight-character password drawn from the full set of 95 printable ASCII symbols yields only $95^8 \approx 6.6 \times 10^{15} \approx 2^{52.6}$ combinations. Real users rarely sample uniformly: they select dictionary words, familiar names, calendar dates, and predictable substitutions (\texttt{P@ssw0rd123}). Against a realistic dictionary of $10^9 \approx 2^{30}$ common passwords, a cluster running at $10^{11}$ hashes per second exhausts the entire search space in ten milliseconds.

Faster hashing helps an offline password cracker far more than it helps a login server. To protect human credentials, we do not want a hash that is fast. We need a function that is deliberately slow and whose cost is tied to hardware resources that cannot be parallelized away.

\subsection{Why raw hashes and unsalted hashes fail}

The naive approach to password authentication stores the direct digest of the password:
\[
  h = \Hash(P).
\]
When the user logs in with candidate password $P'$, the server checks whether $\Hash(P') == h$. If an attacker steals the database, this scheme collapses under two independent failure modes:

\begin{enumerate}
  \item \textbf{Precomputation and Rainbow Tables.} Because the hash function is deterministic and input-independent, an attacker does not need to perform brute force after stealing the database. The attacker selects a dictionary $\mathcal{D}$ of candidate passwords and computes $\Hash(w)$ for every $w \in \mathcal{D}$ in advance. In 2003, Philippe Oechslin introduced \emph{rainbow tables}, a space-time tradeoff that stores reduction chains of the form:
  \[
    P_0 \xrightarrow{\Hash} H_0 \xrightarrow{R_1} P_1 \xrightarrow{\Hash} H_1 \xrightarrow{R_2} \cdots \xrightarrow{R_L} P_L,
  \]
  where each $R_i : \set{0,1}^n \to \Sigma^k$ is a reduction function mapping a hash digest back to a candidate password string. By storing only the endpoints $(P_0, P_L)$, the attacker compresses millions of precomputed hashes into a few gigabytes of disk storage. Looking up a stolen digest takes milliseconds. Worse, a single precomputed table cracks matching passwords across every leaked database worldwide.
  \item \textbf{Leakage of Password Reuse.} If Alice and Bob choose the same password $P$, their database entries contain identical hashes $\Hash(P)$. An attacker holding a database dump spots shared credentials at a glance, enabling cross-account tracking without cracking the underlying string.
\end{enumerate}

To defeat precomputed tables, the server generates a fresh, cryptographically secure 128-bit random value $s \getsr \set{0,1}^{128}$ (the \emph{salt}) for each user upon registration. The server stores the salt in plaintext alongside the salted hash:
\[
  (s, h), \quad \text{where } h = \Hash(s \concat P).
\]
The salt is public and requires no secrecy. Its purpose is to make each user's hash input unique. Because $s$ is drawn from a space of $2^{128}$ possibilities, an attacker cannot use a global precomputed table: that table would have to be computed for $\Hash(s \concat P)$ across all $2^{128}$ salts, requiring $|\mathcal{D}| \cdot 2^{128}$ evaluations. In addition, if Alice and Bob choose the identical password, their independent salts $s_{\text{Alice}} \ne s_{\text{Bob}}$ ensure that $\Hash(s_{\text{Alice}} \concat P) \ne \Hash(s_{\text{Bob}} \concat P)$, concealing reuse.

\begin{trapbox}
\textbf{The salt arithmetic trap.} Salting completely destroys global precomputation across multiple users, but it provides zero protection against targeted attacks on a single stolen row. Consider an attacker focusing on Alice's compromised record $(s_{\text{Alice}}, h_{\text{Alice}})$. The salt $s_{\text{Alice}}$ is known. To test a candidate password $w$, the attacker computes $\Hash(s_{\text{Alice}} \concat w)$ and compares it to $h_{\text{Alice}}$. If $\Hash$ is SHA-256, an attacker running hardware capable of $10^{11}$ evaluations per second tests candidate passwords against Alice's record at that exact speed. Salting forces the attacker to do dedicated work per user, but if each test costs only a few nanoseconds, a 35-bit password falls in under a second.
\end{trapbox}

\subsection{Iterative CPU-hard stretching and its silicon limits}

To protect a single salted record against brute-force search, the verification function must consume measurable time. This is the concept of \emph{key stretching}: artificially inflating the number of sequential operations required to evaluate the hash.

In 2000, RSA Laboratories standardized \textbf{PBKDF2} (Password-Based Key Derivation Function 2, RFC 2898). PBKDF2 iterates a pseudorandom function (typically HMAC-SHA-256) across a user-specified iteration count $c$:
\[
  U_1 = \operatorname{HMAC}(P, s \concat \operatorname{INT}(1)), \quad U_2 = \operatorname{HMAC}(P, U_1), \quad \dots, \quad U_c = \operatorname{HMAC}(P, U_{c-1}),
\]
and computes the stretched output as the XOR sum:
\[
  T = U_1 \xor U_2 \xor \cdots \xor U_c.
\]
If a server selects $c = 600{,}000$, computing $T$ takes approximately 100 milliseconds on a server CPU. An attacker attempting $10^9$ dictionary guesses must now evaluate $6 \times 10^{14}$ HMAC operations, multiplying their cracking duration by a factor of 600,000.

Yet PBKDF2 fails against modern adversaries armed with custom ASICs and GPUs. The reason is the economics of chip area.

A general-purpose CPU is engineered to execute complex, branch-heavy instructions on unpredictable data. More than 90\% of the physical silicon area on an x86 or ARM CPU die is dedicated to out-of-order execution pipelines, branch predictors, instruction decoders, register renaming tables, and multi-megabyte SRAM caches (L1, L2, and L3). The actual 32-bit arithmetic logic unit (ALU) that performs the additions and bitwise shifts of SHA-256 occupies a minuscule fraction of the chip.

In contrast, computing SHA-256 requires almost no silicon state. The entire working memory of SHA-256 consists of eight 32-bit words -- just 32 bytes (256 bits) of register flip-flops. The round logic consists of simple combinational gates (AND, XOR, bit rotations, and modular 32-bit adders). An adversary building an Application-Specific Integrated Circuit (ASIC) discards all branch predictors, instruction caches, and memory buses. The ASIC designer packs tens of thousands of fully unrolled, pipelined SHA-256 cores onto a single $250\,\text{W}$ silicon die.

Because PBKDF2 is purely sequential and requires only 32 bytes of working memory, each tiny ASIC core runs completely in registers without touching external RAM. While a high-end 16-core CPU executes 32 concurrent threads, a single custom ASIC executes $10^{4}$ independent candidate streams in parallel at gigahertz clock frequencies. Both defender and attacker must compute $c$ iterations per guess, but an iteration on custom silicon costs fractions of a nanojoule. CPU-bound iteration scales linearly for defender and attacker alike, allowing custom hardware to overcome the iteration count.

\subsection{Memory-hard key derivation: scrypt and Argon2}

To negate the advantage of custom silicon, cryptographers identified the one physical component that an attacker cannot miniaturize cheaply: \textbf{memory} (RAM) and memory bandwidth.

An SRAM memory bit requires a six-transistor cell (6T SRAM). Placing 64 megabytes of SRAM directly onto an ASIC die consumes roughly $60\,\text{mm}^{2}$ of expensive silicon, crowding out compute logic. Dynamic RAM (DRAM) is denser, but DRAM must reside on separate memory dies connected through physical copper pins or through-silicon vias (TSVs). Those physical interfaces are strictly constrained by pin count, thermal dissipation, and bus bandwidth limits (high-bandwidth memory rarely exceeds 1 to 2 TB/s per package).

In 2009, Colin Percival introduced the concept of \emph{memory-hard functions} in the design of \textbf{scrypt}. Percival formalized the defensive metric through \textbf{Area-Time (AT) complexity}. The true cost of designing and running custom hardware is proportional to the product of the silicon die area $A$ and the execution time $T$ ($AT$ or $AT^2$). If an algorithm requires 64 MiB of working memory per instance, an ASIC designer can no longer place $10^4$ parallel cores on a chip: the physical memory required would demand an impossibly large die. If the cores share an external DRAM bus, thousands of cores contend for memory channels and stall on memory latency.

Memory-hard functions also enforce a severe \emph{time-memory tradeoff} (TMTO): if an attacker attempts to save silicon area by storing only a fraction $1/M$ of the intermediate states, they must repeatedly recompute the discarded blocks, causing total execution time $T$ to explode.

In 2015, the Password Hashing Competition (PHC) selected \textbf{Argon2}, designed by Alex Biryukov, Daniel Dinu, and Dmitry Khovratovich, as the new standard (RFC 9106). Argon2 turns memory hardness into a concrete design:

\begin{itemize}
  \item \textbf{Memory Matrix Layout.} Argon2 configures memory as a 2D matrix of $p$ parallel lanes (threads) and $q = m/p$ columns, where each matrix cell is a 1\,KiB block (1024 bytes, structured as an $8 \times 16$ array of 64-bit words). A standard configuration allocating $m = 64\,\text{MiB}$ across $p = 4$ lanes establishes a matrix of $4 \times 16{,}384$ blocks.
  \item \textbf{Four Slices.} Computation across all lanes proceeds through four vertical synchronization slices (Slice 0 through Slice 3). Within a slice, the $p$ lanes compute blocks in parallel; at slice boundaries, lanes synchronize.
  \item \textbf{Block Mixing Function $G$.} The core permutation $G$ operates on two 1\,KiB blocks using the round function of BLAKE2b. It evaluates eight 64-bit SIMD rounds, vectorizing efficiently on CPU vector units (AVX2, AVX-512, ARM Neon) while using only 64-bit additions, rotations, and XORs.
\end{itemize}

Argon2 resolves a subtle tension between memory hardness and side-channel security through three distinct variants:

\begin{description}
  \item[Argon2d (Data-Dependent Addressing).] To compute block $B_{i,j}$, the algorithm takes the 64-bit integer stored in the first word of the previous block $B_{i,j-1}$ and uses it to compute a pseudorandom reference index $(i', j')$. Block $B_{i,j}$ is then computed as $G(B_{i,j-1}, B_{i',j'})$. Because the memory address depends directly on the data, an attacker who drops blocks cannot predict which block will be referenced next, forcing full memory retention. However, because memory lookup addresses depend on password data, an attacker sharing physical CPU hardware or a cloud hypervisor can monitor CPU cache misses (cache-timing attacks like Flush+Reload) to deduce memory addresses and recover password bits.
  \item[Argon2i (Data-Independent Addressing).] The reference address $(i', j')$ is generated by applying $G$ to a deterministic sequence counter, the lane index, and the slice index, without reading any password-dependent block contents. Because memory access patterns are independent of secret data, Argon2i is immune to cache-timing side channels. However, because the access sequence is predictable in advance, an attacker can use graph-pebble algorithms to construct time-memory tradeoffs with lower recomputation penalties.
  \item[Argon2id (The Hybrid Default).] Argon2id combines both approaches. During the first pass, Slices 0 and 1 compute reference addresses using data-independent addressing (Argon2i mode), overwriting memory and shielding the early password-dependent state against cache-timing leaks. Slices 2 and 3 of the first pass, and all subsequent passes $2, \dots, t$, switch to data-dependent addressing (Argon2d mode), locking in maximal Area-Time hardness against ASICs and GPUs.
\end{description}

\begin{lstlisting}[language=Python]
import os, hmac
from argon2.low_level import hash_secret_raw, Type

def register_user(password: str) -> tuple[bytes, bytes]:
    # 16-byte random salt per user defeats rainbow tables:
    salt = os.urandom(16)
    # 64 MiB memory, 3 passes, 4 parallel lanes:
    digest = hash_secret_raw(
        secret=password.encode("utf-8"),
        salt=salt,
        time_cost=3,
        memory_cost=64 * 1024,   # 64 MiB in KiB
        parallelism=4,
        hash_len=32,
        type=Type.ID             # Argon2id hybrid
    )
    return salt, digest          # salt is stored openly next to the digest

def verify_user(password: str, salt: bytes, stored_digest: bytes) -> bool:
    candidate = hash_secret_raw(
        secret=password.encode("utf-8"),
        salt=salt,
        time_cost=3,
        memory_cost=64 * 1024,
        parallelism=4,
        hash_len=32,
        type=Type.ID
    )
    # Mandatory constant-time comparison to prevent timing side channels:
    return hmac.compare_digest(candidate, stored_digest)
\end{lstlisting}
\end{implementbox}

\begin{focusbox}
\textbf{Salt vs.\ pepper.} A \emph{salt} is unique per user, random, and stored publicly in the database table next to the hash digest. Its sole job is to destroy precomputation and rainbow tables. A \emph{pepper} is a single secret key shared across all users, held in an isolated hardware security module (HSM) or secret-management service, and injected into the hash computation. If an adversary dumps the SQL database but lacks access to the application server or HSM, the pepper prevents offline dictionary attacks entirely. A pepper provides defense-in-depth, but it does not replace per-user salts: omitting salts would still expose password reuse across accounts.
\end{focusbox}

\subsection{Origin-bound phishing-resistant authentication: WebAuthn and passkeys}

Argon2id forces attackers to expend vast memory and silicon die area per guess, raising the computational barrier to offline password cracking. Yet even if a server provisions a gigabyte of RAM per hash, password authentication has a basic weakness: \textbf{a password is a shared secret entered into an untrusted client interface}.

If an attacker registers a lookalike domain name (such as \texttt{g00gle.com}), sends a convincing email lure, and presents a replica of a legitimate login portal, the human user willingly types their plaintext password into the form.

The attacker's reverse proxy intercepts the plaintext string. The proxy immediately forwards that password to the genuine service and authenticates as the user. Traditional multi-factor authentication (MFA) mechanisms -- including SMS one-time passcodes and six-digit time-based codes (TOTP, RFC 6238) -- fail to defeat this attack. Automated reverse-proxy frameworks (such as Evilginx) intercept and relay the user's six-digit OTP in real time, obtain the authenticated session cookies from the legitimate server, and compromise the account. Human vigilance cannot solve this problem: users cannot reliably detect microscopic typographic substitutions in URL address bars under stress.

The \textbf{Web Authentication} standard (\textbf{WebAuthn}), formulated by the W3C and the FIDO Alliance (and popularized under the commercial moniker \emph{Passkeys}), resolves the vulnerability by discarding shared secrets entirely.

Instead of authenticating through a shared secret string transmitted across the network, WebAuthn authenticates via an \textbf{origin-bound asymmetric digital signature} executed by local security hardware -- such as a Secure Enclave in an iPhone or Mac, a Trusted Platform Module (TPM) on a PC, or an external hardware security key (FIDO2 token).

The protocol divides authentication into two phases:

\begin{enumerate}
  \item \textbf{Registration.} When a user registers with a relying party (such as \url{https://accounts.google.com}), the browser requests credential creation from the hardware authenticator via the WebAuthn API. The browser explicitly declares the canonical Relying Party Identifier:
  \[
    \text{RP ID} = \texttt{"accounts.google.com"}.
  \]
  The authenticator creates an asymmetric keypair $(pk, sk)$ (e.g., Ed25519 or ECDSA over NIST P-256). The private key $sk$ is sealed within tamper-resistant silicon and cannot be extracted under any software instruction. The public key $pk$ is returned to the server alongside a credential identifier. The server stores only $pk$. The server stores no password, no hash digest, and no secret. If the server database is breached, the attacker acquires only public keys.
  \item \textbf{Authentication (Challenge-Response).} During login, the server generates a fresh 256-bit cryptographically random challenge nonce $c \getsr \set{0,1}^{256}$ and transmits it to the client. The browser constructs a structured UTF-8 JSON object called \texttt{clientDataJSON}:
  \begin{align*}
    \text{\texttt{clientDataJSON}} = \{ & \texttt{"type"}: \texttt{"webauthn.get"}, \\
    & \texttt{"challenge"}: c, \\
    & \texttt{"origin"}: \texttt{"https://accounts.google.com"} \}.
  \end{align*}
  The browser computes the SHA-256 digest of this structure:
  \[
    h_{\text{client}} = \text{SHA-256}(\text{\texttt{clientDataJSON}}).
  \]
  The browser passes $h_{\text{client}}$ and the requested RP ID to the hardware authenticator. After verifying local user presence through biometric confirmation (TouchID/FaceID) or a PIN, the authenticator signs the concatenation:
  \[
    \sigma = \Sign_{sk}(\text{authenticatorData} \concat h_{\text{client}}).
  \]
  The browser transmits $\sigma$ and \texttt{clientDataJSON} back to the server. The server computes $\text{SHA-256}(\text{\texttt{clientDataJSON}})$, verifies that the origin field in \texttt{clientDataJSON} strictly matches the expected origin \url{https://accounts.google.com}, verifies that the challenge matches $c$, and checks that $\Vrfy_{pk}(\sigma, \dots)$ accepts.
\end{enumerate}

Suppose an attacker tricks a user into visiting \url{https://evil-login.com}. The phishing server connects to \texttt{accounts.google.com}, obtains a valid challenge $c$, and relays $c$ to the victim's browser. The victim agrees to authenticate.

When the malicious webpage invokes the WebAuthn API, the browser itself determines the origin. The webpage cannot spoof this value: the browser user agent reads the active, verified address bar origin:
\[
  \text{\texttt{origin}} = \texttt{"https://evil-login.com"}.
\]
The browser passes RP ID \texttt{"evil-login.com"} to the authenticator and constructs \texttt{clientDataJSON} containing that domain string.

Two separate mechanisms stop the attack:

\begin{enumerate}
  \item \textbf{Credential Isolation.} The hardware authenticator looks up keys scoped to the RP ID \texttt{"evil-login.com"}. Because the authenticator isolated the user's Google keypair strictly to \texttt{"accounts.google.com"}, no matching private key exists for the phishing domain, and the authenticator refuses to sign.
  \item \textbf{Cryptographic Origin Binding.} Even if the authenticator held a key registered under \texttt{evil-login.com}, the signature $\sigma$ commits to the digest of the client data:
  \[
    h_{\text{client}} = \text{SHA-256}(\dots \texttt{"https://evil-login.com"} \dots).
  \]
  When the phishing relay transmits $\sigma$ to \texttt{accounts.google.com}, the genuine server evaluates:
  \[
    h_{\text{expected}} = \text{SHA-256}(\dots \texttt{"https://accounts.google.com"} \dots).
  \]
  Because the hash function is second-preimage resistant, $h_{\text{client}} \ne h_{\text{expected}}$, and signature verification $\Vrfy_{pk}(\sigma, \dots)$ fails.
\end{enumerate}

Phishing resistance therefore comes from binding the origin into the signed data, not from the user's ability to spot a fake domain.

\begin{historybox}
The history of broken hashes is a cautionary one. Ron Rivest designed MD4 (1990) and MD5 (1991) as fast software hashes, while the NSA and NIST published SHA-0 (1993) and SHA-1 (1995). Weaknesses in MD4 were found almost immediately. At Crypto 2004, Xiaoyun Wang and co-authors presented differential attacks that found MD5 collisions in minutes and showed SHA-1 breakable in theory in 2005. Despite Wang's attack, certificate authorities kept issuing MD5 certificates until Sotirov et al.\ forged a rogue root CA certificate in 2008. A full SHA-1 collision was computed in 2017 (SHAttered, Stevens et al., roughly $2^{63}$ operations), followed by chosen-prefix collisions in 2020.

Every one of those broken hashes was Merkle--Damgard with a short output and an under-analyzed compression function. That drove NIST's public SHA-3 competition (2007--2012), won by Keccak (Guido Bertoni, Joan Daemen, Micha\"el Peeters, and Gilles Van Assche), which introduced the sponge construction as a backup independent of Merkle--Damgard. SHA-2 (2001) has stood for over two decades, and the pattern across all of them -- collisions first, preimages much later or never, output length and compression-function strength deciding the timeline -- is what the birthday bound and the MD security proof predict.
\end{historybox}

\begin{aestheticbox}
Hash functions are the most general-purpose tool in cryptography. A single primitive that is one-way, collision resistant, and behaves like a random oracle lets you fingerprint data, commit to secrets, key a MAC, build a signature, store a password, name an object by its content, and anchor a blockchain -- often all in the same system. That is why an attack on a widely used hash is front-page news in the field, and why so much care goes into output length, construction style, and the slow, public scrutiny that earns a hash the right to be trusted.
\end{aestheticbox}

\begin{connectionbox}
An unkeyed hash proves that a file matches its digest, but anyone who intercepts a message $M$ can replace it with $M'$ and recompute $\Hash(M')$. In Chapter~15 we mix a shared secret key into the hash to build Message Authentication Codes (MACs) and HMAC, turning unkeyed digests into tamper-evident seals.
\end{connectionbox}

\section{Exercises}
\label{ch14:exercises}

\begin{exercise}[Counting pairs]
A hash has $n = 32$ output bits. Roughly how many random inputs must you hash before you expect a collision? How many before you expect to hit one \emph{specific} target digest by chance? Explain the $2^{16}$ versus $2^{32}$ gap in one sentence using the birthday bound.
\end{exercise}

\begin{exercise}[Birthday probability]
Using $p(q) \approx 1 - e^{-q(q-1)/(2N)}$ with $N = 2^{40}$, find the smallest $q$ (to the nearest power of two) for which the collision probability exceeds $1/2$. Compare to the rule of thumb $q \approx 1.177\sqrt{N}$.
\end{exercise}

\begin{exercise}[Which property?]
For each application, state which of the three resistance properties it most directly relies on, and give a one-line attack if that property fails: (a) a software-download checksum published by the vendor; (b) a sealed-bid auction using $\Hash(\text{bid}\concat r)$; (c) deduplicating a backup store by content hash; (d) a signature over $\Hash(\text{contract})$ where the signer wrote the contract.
\end{exercise}

\begin{exercise}[Reduction]
Prove that if $\Hash$ is collision resistant then the function $\Hash'(x) = \Hash(\Hash(x))$ is also collision resistant. Where exactly does your reduction use collision resistance of $\Hash$?
\end{exercise}

\begin{exercise}[Length extension by hand]
A naive server authenticates messages with $t = \Hash(k \concat M)$ for a Merkle--Damgard hash and an 8-byte secret $k$. Given a captured pair $(M = \texttt{"amount=10"}, t)$, describe precisely the bytes of the forged message you can authenticate without knowing $k$, and the one piece of information about $k$ you must know or guess. Then explain in one sentence why HMAC blocks your attack.
\end{exercise}

\begin{exercise}[Toy collision]
Run the toy Merkle--Damgard hash from Section~\ref{ch14:md} (8-bit state). Empirically, after how many random inputs does the first collision typically appear? Average over 20 runs and compare to the birthday prediction $1.177 \cdot 2^{4}$. Why is the empirical mean a bit higher than that point estimate?
\end{exercise}

\begin{exercise}[Sponge security]
SHA3-256 has capacity $c = 512$ and output $n = 256$. State its collision and preimage security levels and explain, in terms of the rate/capacity split, why an attacker cannot mount a length-extension attack against $\text{SHA3-256}(k \concat M)$.
\end{exercise}

\begin{exercise}[Salt arithmetic]
A breached database stores $(\text{salt}, \text{SHA256}(\text{salt}\concat\text{password}))$ for 10 million users with unique 16-byte salts. An attacker has a wordlist of $10^{9}$ candidate passwords and a rig doing $10^{10}$ SHA-256/s. (a) How long to crack \emph{one} target account? (b) Why does the per-user salt mean the total work to crack all 10 million accounts is essentially 10 million times that, rather than amortized? (c) How would switching to Argon2 with a 0.5-second cost per guess change part (a)?
\end{exercise}

\begin{exercise}[Pepper]
Explain why a secret pepper stored outside the database renders a database-only breach uncrackable, but does \emph{not} replace per-user salts. Construct a scenario where using only a pepper (no salt) leaks password reuse across users.
\end{exercise}

\begin{exercise}[Merkle proof]
A Merkle tree has 8 leaves $d_1, \dots, d_8$. Write out the exact authentication path (the list of sibling hashes, in order) needed to prove $d_5$ is in the tree, and the sequence of hash computations the verifier performs to reach the root. How does the proof size grow with the number of leaves?
\end{exercise}

\begin{exercise}[Break a homemade commitment]
A protocol commits to a single decision bit $b \in \set{0,1}$ by publishing $c = \Hash(b)$ with no nonce. Show that this commitment is not hiding by giving the attacker's exact procedure. Then show that adding a 256-bit random nonce $r$ and publishing $\Hash(b \concat r)$ restores hiding, citing the property of $\Hash$ you rely on.
\end{exercise}
