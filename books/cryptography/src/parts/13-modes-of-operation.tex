\chapter{Modes of Operation}

In Chapter~12, AES gave us a fast, secure permutation for a single $128$-bit block ($16$ bytes, the length of ``\texttt{attack at dawn!!}''). Real messages are rarely $16$ bytes long -- an email is kilobytes, a disk image is gigabytes -- so the first practical question after building a block cipher is how to encrypt a multi-block message when the cipher processes only one block at a time.

The obvious approach -- chop the message into blocks and encrypt each one on its own -- leaks repeated patterns directly into the ciphertext. Fixing that leak requires a \emph{mode of operation}: a rule for combining multiple calls to the block cipher with feedback, counters, and fresh randomness so that the ciphertext reveals nothing beyond the message's length.

\chapterline

\section{The block cipher as a tool, and what it is not}

Let $E\colon \set{0,1}^k \times \set{0,1}^n \to \set{0,1}^n$ be a block cipher with $k$-bit keys and $n$-bit blocks, where $\set{0,1}^n$ denotes the set of all $n$-bit strings. For a fixed key $K \in \set{0,1}^k$, the encryption map $E_K(\cdot) = E(K,\cdot)$ is a permutation (bijection) of $\set{0,1}^n$, so its inverse decryption map $D_K = E_K^{-1}$ exists and recovers the input block: $D_K(E_K(x)) = x$. For AES, $n = 128$ (with $k \in \set{128, 192, 256}$); for the older Data Encryption Standard (DES), $n = 64$.

The security goal established in Chapter~11 for the block cipher itself is that $E_K$ is a \emph{pseudorandom permutation} (PRP): to anyone who does not know $K$, the function $E_K$ is computationally indistinguishable from a permutation drawn uniformly at random from all $(2^n)!$ permutations of $n$-bit strings. That is a statement about \emph{one} block. It says nothing about what happens when you call $E_K$ many times on related inputs. A mode of operation builds a multi-block encryption algorithm $\Enc_K$ and decryption algorithm $\Dec_K$ out of $E_K$ and $D_K$, lifting the per-block guarantee to whole messages.

\begin{focusbox}
A block cipher is a building block, not an encryption scheme. ``Encrypt this file with AES'' is an underspecified instruction -- it is like saying ``build this house with bricks'' without saying how the bricks are stacked. The mode of operation specifies how the cipher is applied across blocks, and a bad mode makes the scheme insecure no matter how strong the cipher is.
\end{focusbox}

\subsection{The security target: IND-CPA}

What does ``secure'' mean for a scheme $(\Enc_K, \Dec_K)$ that encrypts multi-block messages? We carry over the standard notion from Chapter~1: \emph{indistinguishability under a chosen-plaintext attack} (IND-CPA). In the security game between a challenger and an adversary $\mathcal{A}$:

\begin{enumerate}
\item The challenger picks a random key $K \getsr \set{0,1}^k$ and a secret bit $b \getsr \set{0,1}$ (where $\getsr$ means drawn uniformly at random).
\item $\mathcal{A}$ may submit any plaintexts it likes and receive their encryptions under $\Enc_K$ (this ``chosen-plaintext'' power models attackers who can induce a server or client to encrypt data they choose).
\item $\mathcal{A}$ submits two equal-length challenge messages $m_0$ and $m_1$, and the challenger returns the ciphertext $c^\star = \Enc_K(m_b)$.
\item $\mathcal{A}$ may ask for further encryptions, then outputs a guess $b' \in \set{0,1}$ and wins if $b' = b$.
\end{enumerate}

The scheme is IND-CPA secure if every efficient (polynomial-time) adversary $\mathcal{A}$ wins with probability at most $\tfrac{1}{2} + \negl(k)$, where $\negl(k)$ is a negligible function of the key length (vanishing faster than any inverse polynomial). In plain terms: even an attacker who can get arbitrary plaintexts encrypted, and who picks the two candidate messages itself, cannot tell which of the two was encrypted any better than flipping a coin.

\begin{whybox}
IND-CPA has a direct consequence: \textbf{encryption must be randomized (or stateful)}. Suppose $\Enc_K$ were a deterministic function. Then $\mathcal{A}$ queries $\Enc_K(m_0)$ during step~2, and submits $(m_0, m_1)$ in step~3. If the challenge ciphertext $c^\star$ equals the ciphertext from step~2, then $b = 0$; otherwise $b = 1$. The adversary wins with probability~$1$. A deterministic encryption scheme \emph{cannot} be IND-CPA secure. This observation alone rules out naive block-by-block encryption and explains why every secure mode injects either fresh per-message randomness or a non-repeating counter.
\end{whybox}

\section{ECB: the mode you must never use}

Electronic Codebook (ECB) mode is the naive rule. Split the plaintext into $\ell$ blocks $m_1, m_2, \dots, m_\ell$ of $n$ bits each, and encrypt each block independently under the same key $K$:
\[
c_i = E_K(m_i), \qquad i = 1, \dots, \ell.
\]
Decryption applies the inverse cipher block by block: $m_i = D_K(c_i)$. The name comes from the fact that $E_K$ acts like a fixed lookup table -- a ``codebook'' -- mapping each possible plaintext block to one fixed ciphertext block.

The structural flaw is visible in Figure~\ref{ch13:ecb-diagram}: there is no chaining between columns. Each block is encrypted in isolation. Because $E_K$ is deterministic, \textbf{equal plaintext blocks always produce equal ciphertext blocks}. Repeated blocks in the plaintext appear unchanged as repeated blocks in the ciphertext.

\begin{intuitionbox}
Think of ECB as a monoalphabetic substitution cipher whose alphabet is the set of all $n$-bit blocks instead of the $26$ letters. In Chapter~2, frequency analysis broke letter-by-letter substitution ciphers. Here the ``alphabet'' has $2^{128}$ symbols, far too large for single-symbol frequency tables, yet \emph{any repetition in the plaintext aligned to block boundaries becomes an exact repetition in the ciphertext}. For structured data -- uncompressed images, fixed-width database records, repeated protocol headers -- those repeats happen constantly.
\end{intuitionbox}

\subsection{A tiny ECB trace}

To trace this by hand, take a toy block cipher with block size $n = 4$ bits. Each block is one hexadecimal digit -- a $4$-bit \emph{nibble} from $\mathtt{0} = 0000_2$ through $\mathtt{F} = 1111_2$ -- and $E_K$ is the fixed bijection below:

\begin{center}
\begin{tabular}{@{}c|cccccccccccccccc@{}}
\toprule
$x$ & $\mathtt{0}$ & $\mathtt{1}$ & $\mathtt{2}$ & $\mathtt{3}$ & $\mathtt{4}$ & $\mathtt{5}$ & $\mathtt{6}$ & $\mathtt{7}$ & $\mathtt{8}$ & $\mathtt{9}$ & $\mathtt{A}$ & $\mathtt{B}$ & $\mathtt{C}$ & $\mathtt{D}$ & $\mathtt{E}$ & $\mathtt{F}$\\
\midrule
$E_K(x)$ & $\mathtt{6}$ & $\mathtt{4}$ & $\mathtt{C}$ & $\mathtt{5}$ & $\mathtt{0}$ & $\mathtt{7}$ & $\mathtt{2}$ & $\mathtt{E}$ & $\mathtt{1}$ & $\mathtt{F}$ & $\mathtt{3}$ & $\mathtt{D}$ & $\mathtt{8}$ & $\mathtt{A}$ & $\mathtt{9}$ & $\mathtt{B}$\\
\bottomrule
\end{tabular}
\end{center}

Encrypt the six-nibble plaintext $m = (\mathtt{A}, \mathtt{1}, \mathtt{A}, \mathtt{1}, \mathtt{C}, \mathtt{A})$ in ECB mode:
\[
c = \big(E_K(\mathtt{A}),\, E_K(\mathtt{1}),\, E_K(\mathtt{A}),\, E_K(\mathtt{1}),\, E_K(\mathtt{C}),\, E_K(\mathtt{A})\big) = (\mathtt{3},\mathtt{4},\mathtt{3},\mathtt{4},\mathtt{8},\mathtt{3}).
\]
In the ciphertext $(\mathtt{3},\mathtt{4},\mathtt{3},\mathtt{4},\mathtt{8},\mathtt{3})$, the repeated pair $(\mathtt{A},\mathtt{1})$ shows up as the repeated pair $(\mathtt{3},\mathtt{4})$, and every $\mathtt{A}$ maps to $\mathtt{3}$. An eavesdropper who never learns $K$ still sees every position where the plaintext repeated itself. With a $4$-bit block, repeats are inevitable after at most $17$ blocks; with a $128$-bit block, they are equally inevitable whenever the plaintext contains $16$-byte-aligned repeats.

\subsection{The penguin}

\begin{attackbox}
The classic visual demonstration is the ``ECB penguin'' (Figure~\ref{ch13:fig-ecb-penguin}). Take an uncompressed bitmap image of Tux, the Linux mascot, encrypt the raw pixel bytes with AES in ECB mode, and render the ciphertext bytes as pixels. Large regions of the picture have a solid color -- such as the background or the white belly -- where many consecutive $16$-byte blocks are identical. ECB maps every copy of a repeated plaintext block to the same ciphertext block, so each uniform region stays a uniform (remapped) color. The penguin's silhouette, eyes, beak, belly, and feet remain recognizable even though every $16$-byte block went through full AES.

The failure extends well beyond images. Encrypt a table of fixed-width records in ECB and you reveal which rows share field values. Encrypt a network protocol with repeated headers and you reveal message types and boundaries. ECB hides the value of an isolated block, not the \emph{equality pattern} across blocks.
\end{attackbox}

Why does the penguin break ECB in the IND-CPA game? Because ECB is \emph{deterministic} and \emph{stateless across blocks}, an adversary wins in a single challenge query: submit $m_0 = (P, P)$ and $m_1 = (P, Q)$ for any two distinct $n$-bit blocks $P \ne Q$. Under $m_0$, the two ciphertext blocks $(c_1, c_2)$ satisfy $c_1 = c_2$; under $m_1$, they satisfy $c_1 \ne c_2$ because $E_K$ is a bijection. Checking whether $c_1 = c_2$ identifies $b$ with probability~$1$, with no key recovery required.

\begin{trapbox}
``My data is high-entropy -- already compressed or random-looking, with high unpredictability per byte -- so ECB is fine.'' This common rationalization fails on three counts. First, callers rarely control plaintext structure as tightly as they assume: protocol framing, padding, and fixed file headers introduce block-aligned repeats. Second, an encryption layer outlives its first caller, and the next engineer will feed it structured data. Third, because ECB fails IND-CPA, no security proof for any surrounding protocol can rest on it. Never choose ECB over CTR or CBC; treat its appearance in a code review as a bug.
\end{trapbox}

\section{CBC: chaining blocks with feedback}

To hide block patterns and achieve IND-CPA security, each block's encryption must depend on earlier blocks and start from fresh per-message randomness. Cipher Block Chaining (CBC) accomplishes both. Choose a fresh random $n$-bit \emph{initialization vector} ($\mathit{IV}$), and compute:
\[
c_0 = \mathit{IV}, \qquad c_i = E_K(m_i \xor c_{i-1}), \quad i = 1, \dots, \ell,
\]
where $\xor$ denotes bitwise exclusive-OR (XOR). Each plaintext block $m_i$ is XORed with the previous ciphertext block $c_{i-1}$ before entering $E_K$, as shown in Figure~\ref{ch13:cbc-diagram}. The $\mathit{IV}$ serves as a ``zeroth ciphertext block'' $c_0$. The transmitted ciphertext is $(\mathit{IV}, c_1, \dots, c_\ell)$: the $\mathit{IV}$ is sent in the clear alongside the ciphertext, because it needs to be unpredictable rather than secret.

\begin{intuitionbox}
Chaining makes ciphertext block $c_i$ depend on $m_i$ \emph{and every block before it}. Two identical plaintext blocks at different positions are XORed with different preceding ciphertexts before entering $E_K$, so they produce unrelated outputs; the encrypted penguin image looks like uniform noise. And because each message chooses a fresh random $\mathit{IV}$, encrypting the same file twice produces two completely different ciphertexts -- satisfying the randomization requirement of IND-CPA.
\end{intuitionbox}

\subsection{A tiny CBC trace}

Using the $4$-bit toy permutation $E_K$ from the ECB section, encrypt the nibble stream $m = (\mathtt{A}, \mathtt{1}, \mathtt{A})$ with random initialization vector $\mathit{IV} = \mathtt{D} = 1101_2$:
\begin{align*}
c_1 &= E_K(m_1 \xor \mathit{IV}) = E_K(\mathtt{A} \xor \mathtt{D}) = E_K(1010_2 \xor 1101_2) = E_K(\mathtt{7}) = \mathtt{E},\\
c_2 &= E_K(m_2 \xor c_1) = E_K(\mathtt{1} \xor \mathtt{E}) = E_K(0001_2 \xor 1110_2) = E_K(\mathtt{F}) = \mathtt{B},\\
c_3 &= E_K(m_3 \xor c_2) = E_K(\mathtt{A} \xor \mathtt{B}) = E_K(1010_2 \xor 1011_2) = E_K(\mathtt{1}) = \mathtt{4}.
\end{align*}
The transmitted ciphertext is $(\mathit{IV}, c_1, c_2, c_3) = (\mathtt{D}, \mathtt{E}, \mathtt{B}, \mathtt{4})$. The two identical plaintext blocks $m_1 = m_3 = \mathtt{A}$ now map to distinct ciphertext blocks $\mathtt{E}$ and $\mathtt{4}$.

To check decryption on the third block, invert the table lookup ($E_K(\mathtt{1}) = \mathtt{4}$ implies $D_K(\mathtt{4}) = \mathtt{1}$) and XOR with $c_2$:
\[
m_3 = D_K(c_3) \xor c_2 = D_K(\mathtt{4}) \xor \mathtt{B} = 0001_2 \xor 1011_2 = 1010_2 = \mathtt{A}.
\]

\subsection{Why the IV must be unpredictable}

For CBC mode, uniqueness of the $\mathit{IV}$ is not enough: the $\mathit{IV}$ must be \emph{unpredictable to the adversary at the moment the plaintext is chosen}. When an attacker can predict the next $\mathit{IV}$, chosen-plaintext queries break confidentiality directly (Figure~\ref{ch13:fig-beast-iv}).

\begin{attackbox}
\textbf{Predictable-IV attack on CBC (the BEAST mechanism).} Suppose an implementation sets the $\mathit{IV}$ of each new message to a value the attacker already knows -- for example, the last ciphertext block of the preceding message, as Secure Sockets Layer (SSL) and Transport Layer Security (TLS)~1.0 did. Suppose the attacker observed an earlier first-block encryption
\[
c^\star = E_K(s \xor \mathit{IV}^\star)
\]
for an unknown secret block $s$ under a known earlier $\mathit{IV}^\star$, and wants to test whether $s$ equals a candidate guess $g$. Knowing that the next encryption will use $\mathit{IV}'$, the attacker submits the chosen first block
\[
m_1 = g \xor \mathit{IV}^\star \xor \mathit{IV}'.
\]
CBC XORs $m_1$ with $\mathit{IV}'$ before calling $E_K$, so $\mathit{IV}' \xor \mathit{IV}' = 0$ cancels out:
\begin{align*}
c_1 &= E_K(m_1 \xor \mathit{IV}') \\
    &= E_K\big((g \xor \mathit{IV}^\star \xor \mathit{IV}') \xor \mathit{IV}'\big) \\
    &= E_K(g \xor \mathit{IV}^\star).
\end{align*}
Because $E_K$ is a bijection, $c_1 = c^\star$ holds if and only if $g = s$. One chosen-plaintext query tests any guessed block with certainty. Combined with byte-boundary alignment so only one unknown byte enters the block at a time, this mechanism powered the 2011 BEAST (\emph{Browser Exploit Against SSL/TLS}) attack on TLS~1.0 to steal browser session cookies (short-lived login tokens). TLS~1.1 and later versions switched to fresh random per-record IVs to close the flaw.
\end{attackbox}

\begin{whybox}
The IND-CPA security proof for CBC requires the $\mathit{IV}$ to be drawn uniformly at random \emph{after} the adversary commits to its plaintext, independent of all prior ciphertexts. \end{whybox}

\subsection{CBC malleability and the bit-flipping attack}

Confidentiality does not imply integrity. CBC prevents a passive eavesdropper from reading the plaintext, yet provides zero protection against active tampering. This property -- that an attacker can alter a ciphertext to cause a controlled, predictable change in the decrypted plaintext without knowing the key -- is called \emph{malleability}.

Recall the CBC decryption equation for block $i$:
\[
m_i = D_K(c_i) \xor c_{i-1}.
\]
Suppose an active attacker intercepts the ciphertext and replaces block $c_1$ with $c_1' = c_1 \xor \Delta$, where $\Delta \in \set{0,1}^n$ is a chosen $n$-bit pattern (a \emph{bitmask}) with $1$s in the exact bit positions the attacker wants to flip. As Figure~\ref{ch13:fig-cbc-bitflip} shows, two things happen when the recipient decrypts:
\begin{enumerate}
  \item \textbf{Block $1$ is scrambled:} The recipient computes $m_1' = D_K(c_1 \xor \Delta) \xor \mathit{IV}$. Because $D_K$ behaves like a random permutation, flipping even one bit of its input flips roughly half of its output bits unpredictably, turning $m_1'$ into garbled noise.
  \item \textbf{Block $2$ is modified at the exact bit positions of $\Delta$:} The recipient computes
  \begin{align*}
  m_2' &= D_K(c_2) \xor c_1' \\
       &= D_K(c_2) \xor (c_1 \xor \Delta) && \text{(substituting $c_1' = c_1 \xor \Delta$)} \\
       &= \big(D_K(c_2) \xor c_1\big) \xor \Delta && \text{(associativity of $\xor$)} \\
       &= m_2 \xor \Delta.
  \end{align*}
\end{enumerate}
Because $c_1'$ enters the decryption of block~$2$ only in the final XOR after $D_K(c_2)$, the inverse cipher $D_K$ never touches $\Delta$. The bitmask $\Delta$ passes straight into $m_2$.

\subsection{Sequential encryption and PKCS\#7 padding}

CBC carries two operational costs. First, encryption is strictly \emph{sequential}: computing $c_i = E_K(m_i \xor c_{i-1})$ requires $c_{i-1}$ to finish first, so encryption of a single message cannot be parallelized across CPU cores (decryption, as Figure~\ref{ch13:fig-cbc-dec} showed, \emph{is} parallelizable). Second, $E_K$ accepts only complete $n$-bit blocks, whereas real messages have arbitrary byte lengths, so the sender must \emph{pad} the plaintext to a multiple of the block size before encrypting.

The standard byte-level rule is \emph{PKCS\#7 padding} (from Public-Key Cryptography Standards~\#7), illustrated in Figure~\ref{ch13:fig-pkcs7}. If $p$ bytes are needed to reach the next block boundary (with $1 \le p \le B$, where $B = n/8$ is the block size in bytes), append $p$ bytes each equal to the integer $p$. For AES ($B = 16$), if $5$ bytes are missing, append five bytes of $\mathtt{0x05}$. If the message already ends on a $16$-byte boundary, append a \emph{full extra block} of $16$ bytes, each equal to $\mathtt{0x10}$ (hexadecimal for $16$). To unpad after decryption, read the final byte $p$, check that $1 \le p \le B$ and that all final $p$ bytes equal $p$, and strip them off.

\section{The padding-oracle attack (a preview)}

CBC by itself provides \emph{confidentiality} (hiding plaintext from passive eavesdroppers) without \emph{integrity} (detecting unauthorized edits): an attacker can modify any ciphertext block and CBC will decrypt it to some $16$-byte block without complaint. If the receiving system leaks a single bit of information -- whether the decrypted result ended with valid PKCS\#7 padding -- an attacker can decrypt any captured ciphertext block without knowing the key. Chapter~16 develops authenticated encryption to prevent this; seeing the attack first shows why encryption and authentication cannot be separated safely.

\begin{attackbox}
\textbf{The padding oracle.} A \emph{padding oracle} is any service that accepts a ciphertext and reveals whether decryption produced valid PKCS\#7 padding -- via a distinct error message, an HTTP status code, or a measurable response-time difference. Suppose the attacker wants to decrypt a captured $16$-byte ciphertext block $c_i$ (whose bytes are indexed $0$ through $15$). Under CBC decryption, $m_i = D_K(c_i) \xor c_{i-1}$. Write $I_i = D_K(c_i)$ for the secret intermediate $16$-byte state, so $m_i = I_i \xor c_{i-1}$.

The attacker constructs a two-block ciphertext $(c', c_i)$, where $c'$ is an arbitrary $16$-byte block under the attacker's control, and sends it to the service. The service decrypts the final block as $m' = D_K(c_i) \xor c' = I_i \xor c'$. Varying the last byte $c'[15]$ across all $256$ byte values ($\mathtt{0x00}$ through $\mathtt{0xFF}$), the attacker watches for the response ``padding valid.'' Valid padding occurs when $m'[15] = \mathtt{0x01}$ (the rare accidental match with $\mathtt{0x02\;0x02}$ or longer pads can be ruled out by flipping $c'[14]$ and re-testing). Because $m'[15] = I_i[15] \xor c'[15] = \mathtt{0x01}$, that single hit reveals both the secret intermediate byte and the true plaintext byte:
\[
I_i[15] = c'[15] \xor \mathtt{0x01}, \qquad m_i[15] = I_i[15] \xor c_{i-1}[15].
\]

Next, the attacker sets $c'[15] = I_i[15] \xor \mathtt{0x02}$ to force $m'[15] = \mathtt{0x02}$, and sweeps $c'[14]$ across all $256$ values until the oracle accepts the two-byte pad $\mathtt{0x02\;0x02}$. Repeating from byte $15$ down to byte $0$ recovers the entire $16$-byte block in at most $16 \times 256 = 4{,}096$ queries without ever touching the key $K$ (Figure~\ref{ch13:fig-padding-oracle}). Serge Vaudenay published this attack in 2002; variants of it (including Lucky Thirteen in 2013 and POODLE in 2014) repeatedly broke deployed SSL/TLS servers.
\end{attackbox}

\begin{intuitionbox}
See how byte $15$ unlocks byte $14$. Once $c'[15] = \mathtt{0x7B}$ triggers ``padding valid'' in Figure~\ref{ch13:fig-padding-oracle}, the attacker knows $I_i[15] = \mathtt{0x7B} \xor \mathtt{0x01} = \mathtt{0x7A}$. To attack the second-to-last byte $I_i[14]$, the attacker fixes the last byte of $c'$ to
\[
c'[15] = I_i[15] \xor \mathtt{0x02} = \mathtt{0x7A} \xor \mathtt{0x02} = \mathtt{0x78},
\]
guaranteeing that the decrypted last byte is now $m'[15] = \mathtt{0x7A} \xor \mathtt{0x78} = \mathtt{0x02}$. Now sweeping $c'[14]$ from $\mathtt{0x00}$ to $\mathtt{0xFF}$ triggers ``padding valid'' precisely when $m'[14] = \mathtt{0x02}$ (completing $\mathtt{0x02\;0x02}$), which immediately gives $I_i[14] = c'[14] \xor \mathtt{0x02}$ and $m_i[14] = I_i[14] \xor c_{i-1}[14]$. Each recovered byte lets the attacker dial in the tail for the next byte to the left.
\end{intuitionbox}

\begin{whybox}
\textbf{Encryption without integrity turns error handling into a decryption oracle.} The structural fix is to \emph{authenticate} the ciphertext: attach a \emph{message authentication code} (MAC -- a keyed cryptographic tag covered in Chapter~15) computed over $(\mathit{IV}, c_1, \dots, c_\ell)$, and verify that tag in \emph{constant time} (executing the same operations regardless of where a mismatch occurs, so response timing leaks nothing) \emph{before} calling $D_K$ or inspecting padding. Forged ciphertexts are rejected at the door and never reach the unpadding code. Chapter~16 formalizes this ``encrypt-then-MAC'' rule and modern \emph{authenticated encryption with associated data} (AEAD) schemes that build confidentiality and integrity into a single primitive.
\end{whybox}

\section{CTR: turn the block cipher into a stream cipher}

Counter (CTR) mode takes a simpler route. Instead of passing plaintext blocks through $E_K$, it uses $E_K$ to generate a pseudorandom \emph{keystream} and XORs that keystream with the plaintext -- turning the block cipher into a stream cipher.

Choose a \emph{nonce} $N$ (a public value used at most once per key) and form a sequence of $n$-bit counter blocks $T_1, T_2, \dots, T_\ell$, where $T_i = N \concat i$ concatenates ($\|$) the fixed nonce bits in the upper part of the block with the binary block counter $i$ in the lower part (for $128$-bit AES, a standard split is a $96$-bit nonce followed by a $32$-bit counter). Evaluating $E_K(T_i)$ produces keystream block $i$, and encryption and decryption are:
\[
c_i = m_i \xor E_K(T_i), \qquad m_i = c_i \xor E_K(T_i).
\]
Figure~\ref{ch13:ctr-diagram} shows the data flow. Encryption and decryption are the \emph{same} operation -- both XOR their input with $E_K(T_i)$ -- because XOR is its own inverse. CTR never calls $D_K$; both directions evaluate $E_K$ in the forward direction only.

\begin{intuitionbox}
In CTR mode, the block cipher acts as a keyed random-access pad generator: feed it distinct counter blocks $N \concat 1, N \concat 2, \dots$ and it emits pad blocks that look uniformly random to anyone without $K$ (by Chapter~11's PRP/PRF switching lemma, evaluating a secure PRP on distinct inputs is indistinguishable from evaluating a pseudorandom function, or PRF, up to the birthday bound). Encryption is then $c = m \xor \text{pad}$, carrying over both the simplicity of the one-time pad and its central rule: never reuse a pad.
\end{intuitionbox}

\subsection{A tiny CTR trace}

Using the same $4$-bit toy permutation $E_K$, let the three counter blocks be the nibbles $\mathtt{9}, \mathtt{A}, \mathtt{B}$. Applying $E_K$ gives the keystream:
\[
E_K(\mathtt{9}) = \mathtt{F}, \qquad E_K(\mathtt{A}) = \mathtt{3}, \qquad E_K(\mathtt{B}) = \mathtt{D}.
\]
Encrypting $m = (\mathtt{A}, \mathtt{1}, \mathtt{A})$ XORs each plaintext nibble with its keystream nibble:
\begin{align*}
c_1 &= m_1 \xor \mathtt{F} = \mathtt{A}\xor\mathtt{F} = 1010_2 \xor 1111_2 = 0101_2 = \mathtt{5},\\
c_2 &= m_2 \xor \mathtt{3} = \mathtt{1}\xor\mathtt{3} = 0001_2 \xor 0011_2 = 0010_2 = \mathtt{2},\\
c_3 &= m_3 \xor \mathtt{D} = \mathtt{A}\xor\mathtt{D} = 1010_2 \xor 1101_2 = 0111_2 = \mathtt{7}.
\end{align*}
The resulting ciphertext blocks are $(\mathtt{5},\mathtt{2},\mathtt{7})$. To decrypt, regenerate the identical keystream $(\mathtt{F},\mathtt{3},\mathtt{D})$ from $(\mathtt{9},\mathtt{A},\mathtt{B})$ and XOR again: $\mathtt{5}\xor\mathtt{F} = 0101_2 \xor 1111_2 = 1010_2 = \mathtt{A}$, $\mathtt{2}\xor\mathtt{3} = \mathtt{1}$, and $\mathtt{7}\xor\mathtt{D} = \mathtt{A}$.

\subsection{CTR's strengths and its nonce-uniqueness rule}

\begin{focusbox}
What CTR buys you:
\begin{itemize}
\item \textbf{Parallelism.} Every $E_K(T_i)$ is independent, so you can compute the whole keystream across all cores at once, in either direction. CBC cannot do this on encrypt.
\item \textbf{Random access / seekability.} To decrypt block $4242$ you compute $E_K(N \concat 4242)$ directly -- no need to process blocks $1$ through $4241$. Full-disk and database encryption rely on counter-derived modes for this reason.
\item \textbf{No padding.} Truncating the final keystream block to the remaining plaintext bytes handles messages of any byte length without PKCS\#7 padding, eliminating padding-oracle attacks.
\item \textbf{Decrypt uses only $E_K$.} Hardware and embedded implementations never need the inverse circuit $D_K$.
\end{itemize}
\end{focusbox}

\begin{trapbox}
The one non-negotiable rule: \textbf{never reuse a $(K, T_i)$ key-and-counter pair.} If two plaintext blocks $m$ and $m'$ are ever XORed with the \emph{same} keystream block $E_K(T)$, then
\begin{align*}
c \xor c' &= \big(m \xor E_K(T)\big) \xor \big(m' \xor E_K(T)\big) \\
          &= m \xor m' \xor \big(E_K(T) \xor E_K(T)\big) = m \xor m'.
\end{align*}
The keystream cancels completely, handing the attacker the bitwise XOR of the two plaintexts -- the two-time-pad failure from Chapters~9 and~10. This happens whenever a nonce $N$ repeats under the same key $K$, or when per-message counter ranges overlap. With a $96$-bit random nonce, collisions stay unlikely well below the birthday bound ($\ll 2^{48}$ messages); with a stateful counter nonce, the sender must guarantee non-repetition across restarts. Nonce reuse in CTR does not degrade security gradually: it exposes $m \xor m'$ at every reused block position.
\end{trapbox}

\subsection{A tiny two-time-pad example}

Using the toy permutation and keystream $(\mathtt{F},\mathtt{3},\mathtt{D})$ from counter blocks $(\mathtt{9},\mathtt{A},\mathtt{B})$, suppose a buggy sender encrypts \emph{two} messages under the \emph{same} nonce (Figure~\ref{ch13:fig-ctr-reuse}). Message one is $m = (\mathtt{A},\mathtt{1},\mathtt{A})$, giving $c = (\mathtt{5},\mathtt{2},\mathtt{7})$. Message two is $m' = (\mathtt{C},\mathtt{1},\mathtt{4})$:
\begin{align*}
c'_1 &= \mathtt{C}\xor\mathtt{F} = 1100_2 \xor 1111_2 = 0011_2 = \mathtt{3},\\
c'_2 &= \mathtt{1}\xor\mathtt{3} = 0001_2 \xor 0011_2 = 0010_2 = \mathtt{2},\\
c'_3 &= \mathtt{4}\xor\mathtt{D} = 0100_2 \xor 1101_2 = 1001_2 = \mathtt{9}.
\end{align*}
An eavesdropper who intercepts $c = (\mathtt{5},\mathtt{2},\mathtt{7})$ and $c' = (\mathtt{3},\mathtt{2},\mathtt{9})$ without knowing $K$ or the keystream XORs the ciphertexts nibble by nibble:
\[
c \xor c' = (\mathtt{5}\xor\mathtt{3},\; \mathtt{2}\xor\mathtt{2},\; \mathtt{7}\xor\mathtt{9}) = (\mathtt{6},\,\mathtt{0},\,\mathtt{E}).
\]
Comparing directly with the plaintexts confirms $m \xor m' = (\mathtt{A}\xor\mathtt{C},\,\mathtt{1}\xor\mathtt{1},\,\mathtt{A}\xor\mathtt{4}) = (\mathtt{6},\,\mathtt{0},\,\mathtt{E})$. Position~$2$ being $\mathtt{0}$ tells the attacker immediately that $m_2 = m'_2$. On natural-language text or structured records, $m \xor m'$ lets an attacker \emph{crib-drag} -- slide guessed common words such as \texttt{" the "} along $m \xor m'$ to read out fragments of the other message, as in Chapter~9 -- recovering both plaintexts in full.

\begin{connectionbox}
``How big must a random nonce be before collisions get likely?'' is a birthday-bound question (Chapter~7). \end{connectionbox}

\section{CFB and OFB: the older stream-cipher modes}

Before CTR became standard, two earlier modes turned a block cipher into a stream-like cipher using \emph{feedback} rather than a counter. They still appear in legacy protocols -- such as Pretty Good Privacy (PGP), which uses a Cipher Feedback variant, and older hardware link encryptors -- and comparing them clarifies what feedback does.

\textbf{Output Feedback (OFB).} Generate the keystream by repeatedly applying $E_K$, starting from $\mathit{IV}$ and feeding the cipher's \emph{output} $z_{i-1}$ back as its next input:
\[
z_0 = \mathit{IV}, \qquad z_i = E_K(z_{i-1}), \qquad c_i = m_i \xor z_i.
\]
The keystream $z_1, z_2, \dots$ depends only on $K$ and $\mathit{IV}$, never on the plaintext (Figure~\ref{ch13:ofb-diagram}), so it forms a pseudorandom pad XORed with the message, and decryption is identical to encryption ($m_i = c_i \xor z_i$). OFB is CTR with a chained feedback state in place of an incrementing counter. Its drawbacks are that keystream generation is strictly sequential ($z_i$ waits on $z_{i-1}$) and that hitting a short cycle in $E_K$ would repeat the pad; CTR's explicit counter avoids both problems.

\textbf{Cipher Feedback (CFB).} Here the \emph{ciphertext} block $c_{i-1}$ feeds back into the cipher (Figure~\ref{ch13:cfb-diagram}):
\[
c_0 = \mathit{IV}, \qquad c_i = m_i \xor E_K(c_{i-1}).
\]
Decryption computes $m_i = c_i \xor E_K(c_{i-1})$, which again uses only the forward cipher $E_K$ (never $D_K$) and can run in parallel once all $c_i$ have arrived. CFB turns CBC inside out: CBC XORs $m_i$ with $c_{i-1}$ \emph{before} calling $E_K$, whereas CFB calls $E_K$ on $c_{i-1}$ \emph{before} XORing with $m_i$.

\begin{remark}
The modes also differ in \emph{error propagation} -- how a single corrupted ciphertext bit affects decrypted plaintext blocks (Figure~\ref{ch13:fig-error-prop}). In CTR and OFB, flipping one bit of $c_2$ flips only the matching bit of $m_2$ because $c_2$ never enters $E_K$ or $D_K$. In CBC ($m_i = D_K(c_i) \xor c_{i-1}$), flipping one bit of $c_2$ scrambles the entire block $m_2$ (via $D_K(c_2)$) \emph{and} flips the single aligned bit of $m_3$ (via $\xor c_2$). CFB ($m_i = c_i \xor E_K(c_{i-1})$) is the mirror image: flipping one bit of $c_2$ flips the single aligned bit of $m_2$ \emph{and} scrambles the entire next block $m_3$ (via $E_K(c_2)$). None of these modes \emph{detects} tampering -- that requires a MAC -- and attackers actively exploit these exact propagation patterns in bit-flipping and padding-oracle attacks.
\end{remark}

\noindent $^\dagger$ Secure only with a correctly generated IV/nonce \emph{and} only for confidentiality -- none of these modes provides integrity on its own.

\begin{intuitionbox}
The table summarizes the trade-offs. ECB is the outlier: deterministic, hence broken. The middle three (CBC, CFB, OFB) are the classic feedback modes, each making the cipher randomized through feedback, each with awkward edges (sequential encryption, padding, IV fragility). CTR is the modern choice: parallel both ways, seekable, no padding, decrypt without $D_K$ -- a clean pseudorandom pad. That is why today's authenticated ciphers are built on it.
\end{intuitionbox}

\section{Toy code: ECB versus CBC versus CTR}

\begin{implementbox}
The snippet below implements all three modes on top of AES's single-block primitive (via Python's \texttt{pycryptodome} library) so you can watch ECB leak repeated blocks while CBC and CTR hide them. It is deliberately minimal -- no MAC and no side-channel protections.

\textbf{Learning only. Do not use this in production.} It has no integrity check (leaving it open to bit-flipping and padding-oracle attacks), omits padding, and implements no rekeying or stateful nonce tracking. In production code, call a vetted library's AEAD interface -- such as AES-GCM (AES in Galois/Counter Mode) or ChaCha20-Poly1305 (the ChaCha20 stream cipher paired with the Poly1305 MAC) -- and never assemble a bare mode by hand.

\begin{lstlisting}[language=Python]
from Crypto.Cipher import AES   # raw 16-byte block primitive
import os

BS = 16  # AES block size in bytes

def blocks(data):
    return [data[i:i+BS] for i in range(0, len(data), BS)]

def xor(a, b):
    return bytes(x ^ y for x, y in zip(a, b))

def ecb_encrypt(key, msg):           # NEVER use ECB for real data
    e = AES.new(key, AES.MODE_ECB)
    return b"".join(e.encrypt(b) for b in blocks(msg))   # msg must be block-aligned

def cbc_encrypt(key, msg):           # msg must be block-aligned (pad in real code)
    e = AES.new(key, AES.MODE_ECB)   # we drive the single-block primitive ourselves
    iv = os.urandom(BS)              # unpredictable IV from the OS CSPRNG
    prev, out = iv, []
    for m in blocks(msg):
        c = e.encrypt(xor(m, prev))  # c_i = E_K(m_i XOR c_{i-1})
        out.append(c)
        prev = c
    return iv + b"".join(out)

def ctr_keystream(key, nonce, nblocks):
    e = AES.new(key, AES.MODE_ECB)
    ks = []
    for i in range(nblocks):
        ctr = nonce + i.to_bytes(BS - len(nonce), "big")  # nonce || counter
        ks.append(e.encrypt(ctr))     # keystream block = E_K(nonce || i)
    return b"".join(ks)

def ctr_encrypt(key, nonce, msg):     # nonce MUST be unique per key -- never reuse
    ks = ctr_keystream(key, nonce, (len(msg) + BS - 1) // BS)
    return xor(msg, ks[:len(msg)])    # decryption is the identical function

key = os.urandom(16)
# Two identical 16-byte blocks reveal ECB's pattern leak:
plain = b"YELLOW SUBMARINE" * 2
print("ecb:", ecb_encrypt(key, plain).hex())   # two halves IDENTICAL -> leak
print("cbc:", cbc_encrypt(key, plain).hex())   # halves differ; fresh each run
print("ctr:", ctr_encrypt(key, os.urandom(12), plain).hex())
\end{lstlisting}

Run it: the ECB output's two $16$-byte halves are byte-for-byte equal, while CBC and CTR show no such repeat and change on every run. That visible difference is exactly what an IND-CPA adversary exploits against ECB.
\end{implementbox}

\section{Where the modes actually live}

\begin{applicationbox}
\textbf{TLS.} TLS~1.0's CBC record layer used predictable chained IVs (enabling BEAST) and MAC-then-pad-then-encrypt composition -- computing a MAC on the plaintext, appending padding, and CBC-encrypting the bundle -- which exposed padding checks before MAC verification (enabling Lucky Thirteen and POODLE). TLS~1.2 added workarounds, and TLS~1.3 removed CBC entirely: it permits \emph{only} AEAD ciphers, and its two mandatory choices -- AES-GCM and ChaCha20-Poly1305 -- both generate a CTR-style keystream paired with an authentication tag. The evolution of TLS record encryption tracks the attacks in this chapter almost one for one.

\textbf{Disk and database encryption.} Full-disk encryption must read and write any $512$-byte or $4{,}096$-byte sector independently without decrypting earlier sectors, ruling out sequential modes like CBC. Disk sectors also have no spare room to store a fresh per-write nonce or MAC tag, so storage systems use \emph{tweakable} block-cipher modes such as XTS-AES (XOR-encrypt-XOR with ciphertext stealing), which mix a public ``tweak'' -- the sector number and block offset -- directly into each AES call.

\textbf{Wi-Fi.} Wi-Fi Protected Access~2 (WPA2) uses CCMP (\emph{Counter Mode with CBC-MAC Protocol}): AES in CTR mode for confidentiality paired with a CBC-based MAC for integrity. WPA3 adds GCMP (\emph{Galois/Counter Mode Protocol}), built on AES-GCM. By contrast, Wi-Fi's original 1999 standard, Wired Equivalent Privacy (WEP), paired the RC4 stream cipher with $24$-bit IVs that repeated every few thousand packets -- the same keystream-reuse failure as CTR nonce reuse.

\textbf{Signal, SSH, WireGuard.} Modern secure messaging, Secure Shell (SSH), and WireGuard VPN tunnels standardize on ChaCha20-Poly1305 or AES-GCM: a counter-driven keystream generator combined with an authentication tag, never an unauthenticated mode.
\end{applicationbox}

\begin{historybox}
In 1980, the U.S.\ National Bureau of Standards standardized four DES modes in Federal Information Processing Standard (FIPS)~81: ECB, CBC, CFB, and OFB. Whitfield Diffie and Martin Hellman had already described CTR mode in 1979, yet FIPS~81 omitted it; the National Institute of Standards and Technology (NIST) added CTR only in 2001 in Special Publication 800-38A alongside AES. Because of that two-decade gap, early internet protocols such as SSL/TLS and Internet Protocol Security (IPsec) standardized on CBC with a separate MAC. The wave of attacks that followed -- Vaudenay's 2002 PKCS\#7 padding-oracle attack, BEAST in 2011, Lucky Thirteen in 2013, and POODLE in 2014 -- drove the shift to unified AEAD constructions and later to \emph{nonce-misuse-resistant} modes (which derive the counter's starting state from both the nonce and a keyed hash of the message, so an accidental nonce repeat reveals only whether two messages were identical).
\end{historybox}

\section{Summary}

A block cipher encrypts one fixed-size block; a mode of operation extends it to messages of arbitrary length. ECB encrypts each block in isolation and fails IND-CPA immediately because identical plaintext blocks map to identical ciphertext blocks. CBC XORs each plaintext block with the preceding ciphertext block starting from an unpredictable $\mathit{IV}$; it achieves IND-CPA confidentiality, at the cost of sequential encryption, PKCS\#7 padding, and fragility when IVs are predictable or padding errors are observable. CTR evaluates $E_K$ on distinct nonce-and-counter blocks $N \concat i$ to produce a pseudorandom keystream; it is parallel in both directions, supports random access, needs no padding, and decrypts without $D_K$, subject to one strict rule: never reuse a $(K, T_i)$ pair. OFB and CFB are older feedback-based stream modes now largely replaced by CTR. None of these bare modes provides integrity on its own -- bit-flipping and padding-oracle attacks demonstrate why confidentiality without authentication is unsafe in deployment.

Closing that gap requires authenticating ciphertexts before decrypting them, and modern AEAD schemes build that check directly around CTR-style encryption. To construct those authenticators in Chapter~16, we first need two integrity tools: Chapter~14 introduces cryptographic hash functions (fixed-size fingerprints of arbitrary-length data), and Chapter~15 builds message authentication codes (MACs).

\section{Exercises}

\begin{exercise}
Using the $4$-bit toy permutation $E_K$ from the chapter (the $16$-entry table), encrypt the nibble stream $(\mathtt{2},\mathtt{6},\mathtt{2},\mathtt{6})$ in ECB mode. Identify the repeated ciphertext blocks and explain in one sentence what an eavesdropper learns.
\end{exercise}

\begin{exercise}
With the same toy $E_K$ and $\mathit{IV} = \mathtt{3}$, encrypt the nibble stream $(\mathtt{2},\mathtt{6},\mathtt{2},\mathtt{6})$ in CBC mode, showing each XOR and each table lookup. Confirm that the two identical plaintext blocks no longer produce identical ciphertext blocks.
\end{exercise}

\begin{exercise}
Prove formally that ECB is not IND-CPA secure by describing an adversary that wins the IND-CPA game with probability $1$ using a single challenge query. State exactly which two messages it submits and how it decides its guess.
\end{exercise}

\begin{exercise}
In CTR mode, suppose an implementer reuses the same nonce $N$ (under the same key) to encrypt two messages $m$ and $m'$ of equal length, producing $c$ and $c'$. Show that an attacker who sees $c$ and $c'$ can compute $m \xor m'$, and explain why this typically lets the attacker recover both messages if they are natural-language text.
\end{exercise}

\begin{exercise}
You are handed a CBC decryption service that returns ``ok'' if the PKCS\#7 padding of the decrypted message is valid and ``bad'' otherwise. Describe step by step how to recover the last byte of an unknown plaintext block, then sketch how the attack extends to the whole block. Approximately how many oracle queries does recovering one $16$-byte block require in the worst case?
\end{exercise}

\begin{exercise}
Explain why CBC encryption cannot be parallelized across blocks but CBC \emph{decryption} can. Then explain why CTR mode is parallelizable in both directions. Reference the exact recurrence relations.
\end{exercise}

\begin{exercise}
PKCS\#7 padding adds a full block of padding when the message length is already a multiple of the block size. Give a concrete example showing why omitting this rule -- i.e.\ adding no padding when the message is already block-aligned -- makes unpadding ambiguous, so the decryptor cannot always tell padding from data.
\end{exercise}

\begin{exercise}
Recall OFB's keystream recurrence $z_i = E_K(z_{i-1})$ with $z_0 = \mathit{IV}$. Argue that if the sequence $z_0, z_1, z_2, \dots$ ever revisits a previous value, the keystream becomes periodic from that point, and explain why that is a confidentiality problem. Why does CTR's counter-based keystream not suffer this issue?
\end{exercise}

\begin{exercise}
Consider CBC with a \emph{predictable} IV: before encrypting message $j$, the attacker can compute the IV that will be used. Construct the chosen-plaintext query that lets the attacker test whether an earlier secret first block equals a guessed value $g$, and explain why a freshly random per-message IV defeats the attack. (This is the BEAST setup.)
\end{exercise}

\begin{exercise}
A bare CTR-mode ciphertext is delivered to a receiver who decrypts and acts on the plaintext with no integrity check. The attacker knows that bytes $5$--$8$ of the plaintext encode a dollar amount and knows the original value. Show how the attacker can change that amount to any chosen value by XORing a known mask into the corresponding ciphertext bytes, \emph{without} knowing the key. What single countermeasure stops this entire class of attack?
\end{exercise}

\begin{exercise}
Modes leak the message length (CTR and CFB/OFB leak it to the byte; CBC and ECB to the block). Describe a realistic scenario -- for instance, encrypted web traffic or voice -- where leaking only the length still reveals sensitive information, and name one mitigation (hint: think about deliberately wasteful encoding).
\end{exercise}
