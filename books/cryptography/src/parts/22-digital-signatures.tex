\chapter{Digital Signatures}

In Chapter~21, we saw how elliptic curves make Diffie--Hellman fast and compact, while
leaving open how either party verifies who is on the other end of the connection. In the
symmetric setting, we solved message authenticity with a message authentication code (MAC, Chapter~15), which proves
that a message came from \emph{somebody who holds the shared key}. That suffices when Alice and Bob already share a secret and trust each other, but two limits appear as soon as strangers need to verify messages. First, the receiver can also \emph{produce} valid tags, because the same key both creates and checks them, so Bob cannot prove to a third party that Alice, rather than Bob himself, wrote the message. Second, Alice and Bob must already share a secret before exchanging their first authenticated message, which is the bootstrapping problem public-key cryptography was invented to solve.

A \emph{digital signature} fixes both problems. Alice signs with a \emph{private} key that only she holds; anyone with her \emph{public} key can verify. Because signing and verification use different keys, a verifier cannot forge. A valid signature is therefore publicly checkable evidence that the holder of Alice's private key endorsed this exact message. That capability is \emph{public verifiability}, and it brings \emph{non-repudiation}: Alice cannot later credibly deny having signed, because nobody else could have produced a signature that passes verification under her public key.

Signatures secure most everyday uses of public-key cryptography: web browsers check signed certificates (vouchers that tie a domain name to a public key, Chapter~24), phones check signed operating-system updates, SSH clients check a server's signed login proof, and payment networks check signed transactions. We now build these schemes from one-way trapdoors and discrete logarithms, examining what breaks naive constructions and what a valid signature actually proves.

\section{Signatures Versus MACs}
\label{ch22:sig-vs-mac}

Both a MAC and a signature attach a short tag to a message so the receiver can detect tampering and confirm origin. The difference is \emph{who can make a valid tag} and \emph{who can check it}.

\begin{itemize}
  \item \textbf{MAC:} one secret key $k$ does everything. Making a tag requires $k$, and verifying a tag also requires $k$. Sender and verifier are symmetric, so either can forge tags that pass the other's check.
  \item \textbf{Signature:} a key \emph{pair} $(pk, sk)$ consisting of a public verification key $pk$ and a private (``secret'') signing key $sk$. Only $sk$ produces signatures, while $pk$ only checks them. Signer and verifier are asymmetric: knowing $pk$ gives no ability to forge.
\end{itemize}

Figure~\ref{fig:ch22-mac-vs-sig} contrasts the two settings when a third party must decide who authored a message. That asymmetry gives signatures three capabilities that symmetric MACs lack.

\begin{itemize}
  \item \textbf{Public verifiability.} Anyone holding $pk$, which is public and can be posted openly, can check the signature. A MAC tag is checkable only by someone who holds the secret $k$.
  \item \textbf{No shared-secret setup.} The verifier needs only Alice's public key, which she can distribute over an unencrypted channel (provided its authenticity is established, Chapter~24). No shared secret is required before the first verified message.
  \item \textbf{Non-repudiation.} Because only Alice holds $sk$, she cannot plausibly deny a valid signature later. A MAC has no such property: since Bob also holds $k$, a tag ``from Alice'' could equally well have been made by Bob, so it proves nothing to a judge.
\end{itemize}

\begin{intuitionbox}
A MAC is a wax seal pressed with a signet ring that \emph{both} correspondents own. If you find a sealed letter, you know one of the two ring-holders made it, yet you cannot prove to an outsider which one, because you own an identical ring yourself.

A digital signature works like a signature backed by a public reference specimen: Alice alone can produce her mark (using $sk$), while \emph{everyone} carries a copy of the checker (her $pk$). Easy verification paired with infeasible forgery is what lets a stranger or a court rely on it.
\end{intuitionbox}

\begin{focusbox}
Non-repudiation is both a feature and a liability. Signatures are the wrong tool for a private conversation where you want plausible deniability later. Signal's messaging protocol (Chapter~27) uses shared-key MACs for per-message authentication and reserves signatures for the initial key-agreement step, so a leaked message log cannot prove to a third party who wrote what. ``Deniable authentication'' is a deliberate design goal, and per-message signatures would defeat it.
\end{focusbox}

\subsection{The syntax of a signature scheme}
\label{ch22:syntax}

\begin{definition}[Signature scheme]
\label{ch22:def-scheme}
A \emph{signature scheme} is a triple of algorithms $(\Gen, \Sign, \Vrfy)$:
\begin{itemize}
  \item $\Gen(1^n) \to (pk, sk)$: a randomized key-generation algorithm that takes the security parameter $n$ in unary ($1^n$, a string of $n$ ones, so ``polynomial time in the input length'' means polynomial in $n$) and outputs a public verification key $pk$ and a private signing key $sk$.
  \item $\Sign_{sk}(m) \to \sigma$: takes the private key $sk$ and a message $m$, and outputs a signature $\sigma$. Signing may be randomized or deterministic.
  \item $\Vrfy_{pk}(m, \sigma) \to \{0,1\}$: a deterministic algorithm that takes the public key $pk$, a message $m$, and a candidate signature $\sigma$, and returns $1$ (accept) or $0$ (reject).
\end{itemize}
\emph{Correctness:} for every $(pk, sk)$ output by $\Gen(1^n)$ and every message $m$,
\[
  \Vrfy_{pk}\!\bigl(m, \Sign_{sk}(m)\bigr) = 1.
\]
\end{definition}

\subsection{What ``secure'' means: existential unforgeability}
\label{ch22:euf-cma}

The security target mirrors the MAC game from Chapter~15, with one big change: the attacker is \emph{given the public key $pk$} at the start (Figure~\ref{fig:ch22-euf-cma}). She can run $\Vrfy_{pk}$ on her own as many times as she likes without asking an oracle. What she must not be able to do is produce a valid signature on any \emph{new} message, even after watching Alice sign messages of the attacker's choice.

\begin{formalbox}
\textbf{EUF-CMA (existential unforgeability under chosen-message attack).} Run $\Gen(1^n)$ to get $(pk, sk)$ and give $pk$ to the adversary $\Adv$. Give $\Adv$ access to a \emph{signing oracle} $\Sign_{sk}(\cdot)$, a black box holding $sk$ that takes any message $m_i$ chosen by $\Adv$ ($i = 1, \dots, q$) and returns $\sigma_i = \Sign_{sk}(m_i)$ without revealing $sk$. Eventually $\Adv$ outputs a candidate pair $(m^*, \sigma^*)$. She \emph{wins} if
\[
  \Vrfy_{pk}(m^*, \sigma^*) = 1 \quad\text{and}\quad m^* \notin \{m_1, \dots, m_q\}.
\]
The scheme is EUF-CMA secure if every probabilistic polynomial-time ($\PPT$) adversary wins with at most negligible probability $\negl(n)$ (shrinking faster than $1/n^c$ for every constant $c$, Chapter~8):
\[
  \Pr[\Adv \text{ wins}] \le \negl(n).
\]
\end{formalbox}

``Existential'' means the forgery can be on \emph{any} message $\Adv$ likes; even meaningless bytes count as a break. ``Chosen-message'' means she may first collect signatures on messages she picks. Demanding that she fail even after seeing signatures on millions of chosen documents sets a strict security bar that covers weaker real-world attacks automatically.

\begin{trapbox}
A stronger variant is \emph{strong existential unforgeability} (sEUF-CMA): $\Adv$ wins even if $m^*$ \emph{was} queried earlier, provided $\sigma^*$ is a \emph{new} signature ($\sigma^* \neq \sigma_i$). Plain EUF-CMA allows \emph{signature malleability}, turning one valid signature on $m$ into a second, different valid signature on the same $m$. That gap caused real damage in Bitcoin before 2017: each transaction's ID was computed by hashing the full transaction including its signature, so an attacker who altered the signature into an equally valid twin changed the transaction ID without invalidating the payment, confusing exchange accounting. Section~\ref{ch22:ecdsa} shows ECDSA's malleability directly.
\end{trapbox}

\section{RSA Signatures}
\label{ch22:rsa-sig}

RSA (Chapter~19) gives us a trapdoor permutation on $\Zns{N}$: raising to the public exponent $e$ modulo $N$ is fast for everyone, while inverting that map by raising to the private exponent $d$ is feasible only for whoever knows the prime factorization of $N$. Encryption used $e$ to lock and $d$ to unlock. Signing swaps the two exponents: the signer applies the \emph{private} exponent $d$, and anyone verifies by applying the \emph{public} exponent $e$.

\begin{historybox}
Diffie and Hellman named the goal -- a public-key signature whose forgery is as hard as
inverting a one-way function -- in their 1976 paper. Rivest, Shamir, and Adleman's
1978 paper gave the first construction alongside RSA encryption, observing that a message can be
``\emph{signed} by deciphering it with the secret deciphering key.'' Discrete-log
signatures followed with Taher ElGamal (1985) and Claus Schnorr (1989). Because Schnorr's
signature was covered by a patent until 2008, the 1991 U.S.\ federal standard from the
National Institute of Standards and Technology (NIST) -- the \emph{Digital Signature Algorithm}
(DSA), published in Federal Information Processing Standard (FIPS) 186 -- was designed to
avoid that patent; some cryptographers also criticized NIST and the National Security Agency (NSA)
for standardizing a signature-only design rather than RSA. Once
Schnorr's patent expired, a 2011 paper by Bernstein, Duif, Lange, Schwabe, and Yang
(``High-speed high-security signatures'') paired Schnorr's equation with the twisted Edwards curve
edwards25519 (Chapter~21) to create the Edwards-curve Digital Signature Algorithm (EdDSA) and its
standard instance Ed25519 (RFC~8032), now used across SSH, TLS~1.3, and Signal.
\end{historybox}

\subsection{Textbook RSA, and why it is broken}
\label{ch22:textbook-rsa}

The naive (``textbook'') scheme is the direct dual of textbook RSA encryption. The public key is $(N, e)$ and the private key is $d$, where $N = pq$ is a product of two distinct large primes and $ed \equiv 1 \pmod{\varphi(N)}$ with $\varphi(N) = (p-1)(q-1)$. For a message $m \in \Zns{N}$,
\[
  \Sign_{sk}(m) = m^{d} \bmod N, \qquad
  \Vrfy_{pk}(m, \sigma): \text{ accept iff } \sigma^{e} \equiv m \pmod N.
\]
Correctness follows from Euler's theorem (Chapter~4): writing $ed = 1 + k\varphi(N)$ for some integer $k$,
\begin{align*}
  \sigma^{e} &\equiv (m^{d})^{e} \pmod N \\
             &\equiv m^{1 + k\varphi(N)} \pmod N \\
             &\equiv m \pmod N \qquad\text{(since $m^{\varphi(N)} \equiv 1 \pmod N$).}
\end{align*}

\begin{example}[Textbook RSA signing by hand]
\label{ch22:ex-textbook}
Take $p = 61$ and $q = 53$, so $N = 3233$ and $\varphi(N) = 60 \cdot 52 = 3120$. Pick $e = 17$; then $d = 2753$, since $17 \cdot 2753 = 46801 = 15\cdot 3120 + 1$.

Sign the message $m = 100$. Using square-and-multiply (Chapter~3), the signature is
\[
  \sigma = 100^{2753} \bmod 3233 = 1391.
\]
To verify, anyone with the public key $(N, e) = (3233, 17)$ computes
\[
  \sigma^{e} \bmod 3233 = 1391^{17} \bmod 3233 = 100 = m,
\]
and accepts. Confirming $\sigma^e \equiv m \pmod N$ required only $(N, e)$, while finding $\sigma$ required $d$.
\end{example}

The scheme is correct, yet three elementary attacks break it completely.

\begin{attackbox}
\textbf{1. Existential forgery on a random ``message.''} A forger need not pick the message first. Choose any $\sigma \in \Zns{N}$, compute $m = \sigma^{e} \bmod N$, and output $(m, \sigma)$. Verification checks $\sigma^e \equiv m \pmod N$, which holds by construction. Although $m$ looks like random gibberish, EUF-CMA counts any valid pair $(m, \sigma)$ as a break, and protocols that treat raw integers as structured fields (an account ID, an amount) can be harmed directly.

\textbf{2. Multiplicative forgery.} Textbook RSA is \emph{multiplicatively homomorphic}, meaning the signature on a product equals the product of the signatures: $(m_1 m_2)^d \equiv m_1^d \cdot m_2^d \pmod N$. If Eve obtains Alice's signatures on $m_1$ and $m_2$, multiplying them gives a valid signature on $m_1 m_2 \bmod N$ that Alice never signed:
\begin{align*}
  \sigma_1 &= m_1^d \bmod N, \\
  \sigma_2 &= m_2^d \bmod N, \\
  \sigma_1\sigma_2 \bmod N &= (m_1^d)(m_2^d) \bmod N \\
  &= (m_1 m_2)^d \bmod N \\
  &= \Sign_{sk}(m_1 m_2 \bmod N).
\end{align*}
To forge on a \emph{chosen target} $m^*$, Eve splits $m^* \equiv m_1 \cdot m_2 \pmod N$ (for instance by picking a random invertible $m_1$ and setting $m_2 = m^* m_1^{-1} \bmod N$), asks Alice to sign the two harmless-looking pieces $m_1$ and $m_2$, and multiplies the returned signatures modulo $N$.

\textbf{3. Algebraic malleability across messages.} Because signing is a bare power modulo $N$, any multiplicative relation among signed messages carries directly over to their signatures.
\end{attackbox}

\begin{example}[Multiplicative forgery with tiny numbers]
\label{ch22:ex-mult-forge}
Continue with $N = 3233$, $e = 17$, and $d = 2753$. Eve wants a signature on $m^* = 4$, which Alice refuses to sign. Eve writes $4 = 2 \cdot 2 \bmod 3233$ and asks Alice to sign $m_1 = 2$:
\[
  \sigma_1 = 2^{2753} \bmod 3233 = 1027.
\]
Eve squares $\sigma_1$ modulo $3233$:
\[
  \sigma^* = \sigma_1^2 \bmod 3233 = 1027^2 \bmod 3233 = 1054729 \bmod 3233 = 771.
\]
Verification checks $771^{17} \bmod 3233 = 4 = m^*$. Eve forged a valid signature on $4$ from a signature on $2$ without knowing $d$.
\end{example}

\subsection{Hash-then-sign: the fix}
\label{ch22:hash-then-sign}

Every attack above exploited \emph{algebraic structure} in the input to $x \mapsto x^d \bmod N$. The fix is to destroy that structure before exponentiating: compress the message $m$ with a cryptographic hash function $\Hash$ (Chapter~14) and apply the RSA operation to the digest (Figure~\ref{ch22:fig-rsa-hash-vs-textbook}):
\[
  \Sign_{sk}(m) = \Hash(m)^{d} \bmod N, \qquad
  \Vrfy_{pk}(m, \sigma): \text{ accept iff } \sigma^{e} \equiv \Hash(m) \pmod N.
\]

\begin{whybox}
Hashing stops all three problems at once.
\begin{itemize}
  \item \textbf{Against the random-$\sigma$ forgery:} picking $\sigma$ first fixes a target $t = \sigma^e \bmod N$. Passing verification now requires finding a message $m$ with $\Hash(m) = t$, which means inverting the hash (finding a \emph{preimage}, infeasible for SHA-256). The forger can choose $\sigma$ or choose $m$, never both consistently.
  \item \textbf{Against multiplicative forgery:} the integer identity still holds modulo $N$, but exploiting it now requires finding messages $m_1, m_2, m^*$ whose digests satisfy $\Hash(m^*) \equiv \Hash(m_1)\cdot\Hash(m_2) \pmod N$. Because cryptographic hash outputs behave like uniform values in $\Zns{N}$, finding such a relation gives the attacker no advantage.
  \item \textbf{Arbitrary message length:} RSA operates only on integers below $N$. Hashing compresses a file of any length into a fixed-size digest first.
\end{itemize}
\end{whybox}

\begin{trapbox}
Placing a small 256-bit digest directly inside a 2048-bit modulus padded with leading zeros is still unsafe (for small $e$ such as $e = 3$, cube-root attacks remain possible if the block is mostly zeros). Real standards format a full-width block before exponentiating:
\begin{itemize}
  \item \textbf{RSASSA-PKCS1-v1\_5} (RSA Signature Scheme with Appendix, from Public-Key Cryptography Standards \#1 v1.5) places the digest inside a rigid byte layout (Figure~\ref{fig:ch22-pkcs1-v15}), read from most-significant (leftmost) byte to least-significant (rightmost) byte:
  \[
    \texttt{0x00} \concat \texttt{0x01} \concat \texttt{0xFF}\cdots\texttt{0xFF} \concat \texttt{0x00} \concat \texttt{ASN.1(hashID)} \concat \Hash(m),
  \]
  where enough $\texttt{0xFF}$ bytes fill the block so the digest sits flush against the rightmost byte, and $\texttt{ASN.1(hashID)}$ is a fixed byte sequence naming the hash function in Abstract Syntax Notation One (ASN.1, a standard binary encoding for structured fields).
  \item \textbf{RSA-PSS} (Probabilistic Signature Scheme, Chapter~19) mixes the digest with a fresh random byte string (a \emph{salt}) and stretches it across the full block with a hash-based mask. In the random-oracle model (treating the hash as an ideal random lookup table, Chapter~14), any successful PSS forger converts with almost no loss of success probability into an algorithm that inverts RSA.
\end{itemize}
Daniel Bleichenbacher's 2006 signature-forgery attack broke sloppy PKCS\#1 v1.5 verifiers when $e = 3$: a buggy verifier checked the left-hand prefix $\texttt{0x00 01 FF}\dots\texttt{00} \concat \texttt{ASN.1} \concat \Hash(m)$ and forgot to verify that no trailing bytes remained on the right. An attacker could then put that valid prefix in the most-significant bytes, fill the unchecked low-order bytes on the right so the whole integer was an exact cube $\sigma^3 < N$, and submit $\sigma$ without knowing $d$. Verification must check every byte of the format, and new designs should use RSA-PSS.
\end{trapbox}

\begin{applicationbox}
RSA signatures with $e = 65537$ remain widespread. Most web TLS certificates in deployment (Chapter~24) carry RSA signatures, as do Windows driver packages, many firmware images, Domain Name System Security Extensions (DNSSEC, which signs DNS records), JSON Web Tokens (JWT, web authentication tokens using \texttt{RS256}), and signed PDFs. Newer systems often choose smaller, faster Ed25519 keys (Section~\ref{ch22:eddsa}), while existing infrastructure keeps RSA verification universal. Certificate fields labeled \texttt{RSASSA-PSS} or \texttt{sha256WithRSAEncryption} refer to these two padding standards.
\end{applicationbox}

\begin{implementbox}
A toy hash-then-sign RSA implementation in Python. \textbf{For learning only -- never use in production.} It uses tiny primes, reduces a raw hash modulo a small $N$ without PSS padding, and relies on Python's variable-time integer arithmetic, which leaks secret key bits through execution timing (Chapter~37).
\begin{lstlisting}[language=Python]
import hashlib

# Toy keypair (textbook tiny primes -- NOT secure)
p, q = 61, 53
N = p * q                      # 3233
phi = (p - 1) * (q - 1)        # 3120
e = 17
d = pow(e, -1, phi)            # 2753

def H(msg: bytes) -> int:
    # Big-endian ("big"): first byte of digest is most significant.
    digest = hashlib.sha256(msg).digest()
    return int.from_bytes(digest, "big") % N

def sign(msg: bytes) -> int:
    return pow(H(msg), d, N)              # private op: ^d mod N

def verify(msg: bytes, sigma: int) -> bool:
    return pow(sigma, e, N) == H(msg)     # public op: ^e mod N

s = sign(b"Pay Bob 100")
print(verify(b"Pay Bob 100", s))          # True
print(verify(b"Pay Eve 9999", s))         # False -- different hash
\end{lstlisting}
Changing a single byte of the message produces an unrelated SHA-256 digest, so $\Hash(m)$ no longer matches $\sigma^e \bmod N$ and verification returns \texttt{False}.
\end{implementbox}

\section{Discrete-Log Signatures: DSA}
\label{ch22:dsa}

RSA signatures rest on the hardness of factoring. A second family rests on
\emph{discrete logarithms} (Chapter~20): given a generator $g$ and $g^x$ in a cyclic group, recovering
$x$ is hard. The Digital Signature Algorithm (DSA), standardized by NIST in 1991, brought
discrete-log signatures into federal standards and set the pattern for elliptic-curve variants.
Its signatures are much shorter than RSA's: two integers modulo a 256-bit prime $q$ (64 bytes total) rather than one integer modulo a 3072-bit modulus $N$ (384 bytes).

\subsection{Setup and the algorithm}
\label{ch22:dsa-algo}

DSA works in a prime-order subgroup of $\Zns{p}$. The public domain parameters are a large prime $p$ (say 3072 bits), a smaller prime $q$ (say 256 bits) dividing $p-1$, and a generator $g$ of the order-$q$ subgroup, so $\ord(g) = q$ and $g^q \equiv 1 \pmod p$. A user chooses a uniformly random private key $x \getsr \{1,\dots,q-1\}$ and publishes $y = g^{x} \bmod p$.

To sign a message $m$ with digest $h = \Hash(m) \bmod q$:
\begin{enumerate}
  \item Choose a fresh random per-signature secret $k \getsr \{1, \dots, q-1\}$. (Signature literature calls $k$ a \emph{nonce} -- a number used once -- though unlike an encryption nonce it must also stay strictly secret.)
  \item Compute $r = (g^{k} \bmod p) \bmod q$. If $r = 0$, draw a new $k$ and repeat.
  \item Compute $s = k^{-1}(h + x r) \bmod q$, where $k^{-1}$ is the modular inverse of $k$ modulo $q$. If $s = 0$, draw a new $k$ and repeat.
  \item Output the signature $(r, s)$.
\end{enumerate}

To verify $(r,s)$ on $m$ (with $h = \Hash(m) \bmod q$), reject unless $1 \le r < q$ and $1 \le s < q$; otherwise compute
\begin{align*}
  w &= s^{-1} \bmod q, \\
  u_1 &= h\,w \bmod q, \\
  u_2 &= r\,w \bmod q, \\
  v &= \bigl(g^{u_1} y^{u_2} \bmod p\bigr) \bmod q,
\end{align*}
and accept iff $v = r$.

\begin{whybox}
\textbf{Why verification works.} From step~3, $s \equiv k^{-1}(h + xr) \pmod q$ with $s \not\equiv 0 \pmod q$. Multiplying both sides by $k\,w \equiv k\,s^{-1} \pmod q$ gives
\begin{align*}
  k &\equiv s^{-1}(h + x r) \pmod q \\
    &\equiv w h + x (w r) \pmod q \\
    &\equiv u_1 + x u_2 \pmod q.
\end{align*}
Because $g$ has order $q$ modulo $p$, exponents of $g$ depend only on their residue modulo $q$:
\[
  g^{k} \equiv g^{u_1 + x u_2} \equiv g^{u_1}(g^{x})^{u_2} \equiv g^{u_1} y^{u_2} \pmod p.
\]
Reducing both sides modulo $q$ yields $r = v$. The secret key $x$ enters the right-hand side only through the public key $y = g^x \bmod p$, so anyone can verify without knowing $x$.
\end{whybox}

\begin{example}[DSA by hand with tiny parameters]
\label{ch22:ex-dsa}
Let $p = 23$ and $q = 11$ (note $11 \mid (23 - 1)$). To build an element $g$ of order $11$, pick $h_0 = 2$ and raise it to $(p-1)/q = 2$:
\[
  g = h_0^{(p-1)/q} \bmod 23 = 2^{2} \bmod 23 = 4.
\]
By Fermat's little theorem, $4^{11} = 2^{22} \equiv 1 \pmod{23}$, and since $11$ is prime and $4 \neq 1$, we have $\ord(g) = 11$.

Choose private key $x = 3$; the public key is $y = g^x \bmod 23 = 4^3 \bmod 23 = 64 \bmod 23 = 18$.

Sign a message whose digest is $h = 9$. First try nonce $k = 7$ (with $k^{-1} \bmod 11 = 8$, since $7\cdot 8 = 56 = 5\cdot 11 + 1$):
\begin{align*}
  r &= (4^{7} \bmod 23)\bmod 11 = (16384 \bmod 23)\bmod 11 = 8 \bmod 11 = 8, \\
  s &= k^{-1}(h + x r)\bmod 11 = 8\,(9 + 3\cdot 8)\bmod 11 = 8\cdot 33 \bmod 11 = 0.
\end{align*}
Because $33 \equiv 0 \pmod{11}$ makes $s = 0$, which would prevent inverting $s$ during verification, step~3 tells us to restart. Draw $k = 4$ instead (with $k^{-1} \bmod 11 = 3$, since $4\cdot 3 = 12 \equiv 1 \pmod{11}$):
\begin{align*}
  r &= (4^{4}\bmod 23)\bmod 11 = (256 \bmod 23)\bmod 11 = 3 \bmod 11 = 3, \\
  s &= 3\,(9 + 3\cdot 3)\bmod 11 = 3\cdot 18 \bmod 11 = 54 \bmod 11 = 10.
\end{align*}
The signature is $(r, s) = (3, 10)$.

\textbf{Verify.} Compute $w = s^{-1} \bmod 11 = 10^{-1}\bmod 11 = 10$ (since $10\cdot 10 = 100 = 9\cdot 11 + 1$):
\begin{align*}
  u_1 &= h w \bmod 11 = 9\cdot 10 \bmod 11 = 90 \bmod 11 = 2, \\
  u_2 &= r w \bmod 11 = 3\cdot 10 \bmod 11 = 30 \bmod 11 = 8, \\
  v   &= \bigl(g^{u_1} y^{u_2}\bmod 23\bigr)\bmod 11 = \bigl(4^{2}\cdot 18^{8} \bmod 23\bigr)\bmod 11.
\end{align*}
Modulo $23$, we have $4^2 = 16$, $18^2 = 324 \equiv 2 \pmod{23}$, $18^4 \equiv 2^2 = 4 \pmod{23}$, and $18^8 \equiv 4^2 = 16 \pmod{23}$. Hence
\[
  g^{u_1}y^{u_2} \bmod 23 = 16\cdot 16 \bmod 23 = 256 \bmod 23 = 3,
\]
so $v = 3 \bmod 11 = 3 = r$, and verification accepts.
\end{example}

\begin{trapbox}
DSA's security hangs on how the nonce $k$ is generated, and flawed nonce generation is the most common way deployed implementations fail. Each $k$ must be \emph{uniformly random} (or indistinguishable from it), \emph{secret}, and \emph{never reused}. Repeating $k$ even once, or letting a few bits of $k$ be predictable, exposes the long-term private key $x$, as Section~\ref{ch22:nonce-attack} shows.
\end{trapbox}

\section{ECDSA: DSA on an Elliptic Curve}
\label{ch22:ecdsa}

The \emph{Elliptic Curve Digital Signature Algorithm} (ECDSA) translates DSA from the multiplicative subgroup of $\Zns{p}$ to the additive group of points on an elliptic curve (Chapter~21). Because the fastest known discrete-log attack on a well-chosen curve of prime order $n$ is a generic square-root search taking roughly $\sqrt{n}$ group operations (Pollard's rho, Chapter~20), a 256-bit curve provides roughly 128-bit security. Matching that security with DSA over $\Zns{p}$ requires a 3072-bit prime $p$ and a 384-byte public key, whereas an ECDSA public key compresses to 33 bytes.

The public domain parameters are an elliptic curve $E$ over a prime field $\F_p$ and a base point $G \in E(\F_p)$ of large prime order $n$. The signer chooses a uniformly random private key $d \getsr \{1,\dots,n-1\}$ and publishes the point $Q = dG$ (scalar multiplication, the additive-group analogue of $g^x$). Figure~\ref{ch22:fig-ecdsa-pipeline} traces both signing and verification.

\textbf{Sign} a message $m$ with digest $h = \Hash(m) \bmod n$:
\begin{enumerate}
  \item Pick a fresh random secret nonce $k \getsr \{1,\dots,n-1\}$.
  \item Compute the curve point $(x_1, y_1) = kG$ and set $r = x_1 \bmod n$ (treating the field element $x_1 \in \{0,\dots,p-1\}$ as an integer). If $r = 0$, draw a new $k$ and restart.
  \item Compute $s = k^{-1}(h + d\,r) \bmod n$. If $s = 0$, draw a new $k$ and restart.
  \item Output the signature $(r, s)$.
\end{enumerate}

\textbf{Verify} $(r,s)$ on $m$: reject unless $1 \le r < n$ and $1 \le s < n$; otherwise compute
\begin{align*}
  w &= s^{-1}\bmod n, \\
  u_1 &= h\,w \bmod n, \\
  u_2 &= r\,w \bmod n, \\
  P &= u_1 G + u_2 Q.
\end{align*}
Reject if $P = \mathcal{O}$ (the point at infinity, acting as the curve's additive identity); otherwise write $P = (x_1', y_1')$ and accept iff $x_1' \bmod n = r$.

Correctness follows the same algebra as DSA: $k \equiv w(h + dr) \equiv u_1 + d u_2 \pmod n$, so
\[
  kG = (u_1 + d u_2)G = u_1 G + u_2(dG) = u_1 G + u_2 Q = P,
\]
and therefore $x_1' = x_1$, giving $x_1' \bmod n = r$.

\begin{example}[ECDSA on a tiny curve]
\label{ch22:ex-ecdsa}
Use the curve $E: y^2 \equiv x^3 + 2x + 2 \pmod{17}$ over $\F_{17}$. The base point $G = (5, 1)$ has prime order $n = 19$, so $19 G = \mathcal{O}$ and the group $E(\F_{17})$ has $19$ points.

Take private key $d = 7$. Using Chapter~21's point-doubling and point-addition formulas, $Q = 7G = (0, 6)$.

Sign a message with digest $h = 11$. Pick nonce $k = 3$; on this curve $kG = 3G = (10, 6)$, so $r = x_1 \bmod 19 = 10 \bmod 19 = 10$. Since $3\cdot 13 = 39 = 2\cdot 19 + 1$, we have $k^{-1} \bmod 19 = 13$, and
\begin{align*}
  s &= k^{-1}(h + d r)\bmod 19 \\
    &= 13\,(11 + 7\cdot 10)\bmod 19 \\
    &= 13\cdot 81 \bmod 19 = 13\cdot 5 \bmod 19 = 65 \bmod 19 = 8,
\end{align*}
using $81 = 4\cdot 19 + 5$ and $65 = 3\cdot 19 + 8$. The signature is $(r, s) = (10, 8)$.

\textbf{Verify.} Invert $s$ modulo $19$: $w = 8^{-1}\bmod 19 = 12$ (since $8\cdot 12 = 96 = 5\cdot 19 + 1$). Then
\begin{align*}
  u_1 &= h w \bmod 19 = 11\cdot 12 \bmod 19 = 132 \bmod 19 = 18, \\
  u_2 &= r w \bmod 19 = 10\cdot 12 \bmod 19 = 120 \bmod 19 = 6.
\end{align*}
Now compute $u_1 G + u_2 Q = 18G + 6Q$. Because $Q = 7G$, we can check this by hand as $(18 + 6\cdot 7)G = 60G = (3\cdot 19 + 3)G = 3G = (10, 6)$, giving $x_1' = 10$ and $x_1' \bmod 19 = 10 = r$, so verification accepts. (That $Q = 7G$ shortcut is only for checking on paper; an actual verifier computes $18G$ and $6Q$ directly from $G$ and $Q$ without knowing $d$.)
\end{example}

\begin{trapbox}
\textbf{ECDSA is malleable.} Whenever $(r, s)$ is a valid signature on $m$, its twin $(r,\, n - s)$ is also valid (Figure~\ref{fig:ch22-ecdsa-malleability}). Replacing $s$ by $-s \bmod n$ negates $w$, which negates $u_1$ and $u_2$ and sends the reconstructed curve point $P = (x_1, y_1)$ to its inverse $-P = (x_1, -y_1)$; both points have the \emph{same} $x$-coordinate $x_1$, so $x_1 \bmod n = r$ still holds. Bitcoin fixed the resulting transaction-malleability bug with a protocol rule (Bitcoin Improvement Proposal~62, the ``low-$s$'' rule) requiring a single standard form: verifiers accept only $s \le (n-1)/2$ and reject the upper half. EdDSA (Section~\ref{ch22:eddsa}) prevents this by hashing the nonce point directly into the challenge.
\end{trapbox}

\begin{applicationbox}
ECDSA over the NIST curve P-256 (and P-384) is the default signature in modern web TLS certificates and in the TLS~1.3 handshake's \texttt{CertificateVerify} message (where the server signs the handshake transcript to prove it holds the certificate's private key). It signs Apple and Android app packages, authenticates Bluetooth pairing, and -- over the curve \texttt{secp256k1} ($y^2 = x^3 + 7$, chosen for fast arithmetic) -- authorizes Bitcoin and Ethereum transactions. Its 64-byte signature at the 128-bit security level is why it displaced RSA where bandwidth or storage is tight. Its fragile spot is the nonce $k$, as the next section shows.
\end{applicationbox}

\section{The Catastrophic Nonce Attack}
\label{ch22:nonce-attack}

In both DSA and ECDSA, the secrecy of the \emph{long-term private key} depends on the per-signature nonce $k$ being unpredictable, secret, and never repeated (first previewed in Chapter~17). Violate any of those requirements and elementary modular algebra exposes the private key. We write the equations for ECDSA; DSA is identical with $G$ replaced by $g$ and $n$ by $q$.

\subsection{Reusing one nonce reveals the key}
\label{ch22:nonce-reuse}

Suppose Alice signs two distinct messages whose digests satisfy $h_1 \not\equiv h_2 \pmod n$, accidentally reusing the \emph{same} nonce $k$ for both. Because $r$ depends only on $k$ -- writing $kG = (x_1, y_1)$, both signatures have $r = x_1 \bmod n$ -- the repeated $r$ is visible in public. The two $s$ values are
\[
  s_1 = k^{-1}(h_1 + d\,r)\bmod n, \qquad s_2 = k^{-1}(h_2 + d\,r)\bmod n.
\]
Subtract the second congruence from the first so the unknown $d\,r$ term cancels (Figure~\ref{ch22:fig-nonce-reuse}):
\begin{align*}
  s_1 - s_2 &\equiv k^{-1}(h_1 - h_2) \pmod n, \\
  k &\equiv (h_1 - h_2)(s_1 - s_2)^{-1} \pmod n.
\end{align*}
(Since $n$ is prime and $h_1 \not\equiv h_2 \pmod n$, we have $s_1 \not\equiv s_2 \pmod n$, so the modular inverse $(s_1 - s_2)^{-1} \bmod n$ exists.) Once $k$ is recovered, rearrange the first signature equation and multiply by $r^{-1} \bmod n$ to solve for the private key $d$:
\begin{align*}
  s_1 k &\equiv h_1 + d\,r \pmod n, \\
  d &\equiv (s_1 k - h_1)\,r^{-1} \pmod n.
\end{align*}
Two public signatures, a subtraction, and two modular inverses (via the extended Euclidean algorithm, Chapter~4) hand the entire private key $d$ to any passive observer, who can then forge signatures on any message forever.

\begin{example}[Extracting the key from a reused nonce]
\label{ch22:ex-reuse}
Return to the tiny curve of Example~\ref{ch22:ex-ecdsa} over $\F_{17}$, where $n = 19$ and Alice's secret key is $d = 7$ (unknown to Eve). Suppose Alice reuses $k = 3$ (so $r = 10$ both times) on two messages with digests $h_1 = 11$ and $h_2 = 5$. From Example~\ref{ch22:ex-ecdsa}, $s_1 = 8$, and for the second message
\[
  s_2 = k^{-1}(h_2 + d\,r) \bmod 19 = 13\,(5 + 7\cdot 10)\bmod 19 = 13\cdot 75 \bmod 19 = 13\cdot 18 \bmod 19 = 6,
\]
since $75 = 3\cdot 19 + 18$ and $13\cdot 18 = 234 = 12\cdot 19 + 6$.

Eve observes $(r, s_1) = (10, 8)$ and $(r, s_2) = (10, 6)$ sharing $r = 10$. Since $s_1 - s_2 = 2$ and $2^{-1} \bmod 19 = 10$ ($2\cdot 10 = 20 \equiv 1 \pmod{19}$), she recovers the nonce:
\[
  k = (h_1 - h_2)(s_1 - s_2)^{-1} \bmod 19 = (11 - 5)\cdot 10 \bmod 19 = 60 \bmod 19 = 3.
\]
Next, using $r^{-1} \bmod 19 = 10^{-1} \bmod 19 = 2$ ($10\cdot 2 = 20 \equiv 1 \pmod{19}$), she recovers the private key:
\[
  d = (s_1 k - h_1)\,r^{-1} \bmod 19 = (8\cdot 3 - 11)\cdot 2 \bmod 19 = 13\cdot 2 \bmod 19 = 26 \bmod 19 = 7.
\]
Two public signatures yielded $d = 7$ by hand.
\end{example}

\begin{attackbox}
\textbf{The PlayStation~3 break (2010).} Sony signed PlayStation~3 firmware and games with ECDSA. The console's \emph{chain of trust} -- where each boot stage verifies a signature on the next stage before running it -- depended on a \emph{root of trust}: Sony's public key burned permanently into read-only hardware. At the 2010 Chaos Communication Congress (27C3), the group \texttt{fail0verflow} showed that Sony's signing tool used a \emph{constant} nonce $k$ instead of generating a fresh one per file. Every pair of signed updates shared the same $r$, and the two-line subtraction above revealed Sony's master private key.

Once $d$ leaked, anyone could sign custom software that every console accepted as genuine Sony code. No firmware update could revoke the compromised public key, because that key was hardwired into millions of shipped consoles.
\end{attackbox}

\begin{attackbox}
\textbf{Android Bitcoin wallet theft (2013).} A seeding flaw in Java's \texttt{SecureRandom} random-number generator (RNG) on several Android releases caused Bitcoin wallet apps to produce duplicate ECDSA nonces across separate transactions. Because Bitcoin records every signature permanently on its public transaction ledger (the blockchain), attackers scanned the ledger for pairs of signatures from the same address with matching $r$, ran Example~\ref{ch22:ex-reuse}'s arithmetic to compute the wallet's private key, and transferred the coins away.
\end{attackbox}

\begin{connectionbox}
Even a slight \emph{bias} in $k$, with zero exact repeats, leaks the private key. Suppose each nonce has its top byte fixed to zero, or is drawn from a slightly narrow interval. Then each signature equation $k_i \equiv s_i^{-1} h_i + (s_i^{-1} r_i)\,d \pmod n$ tells the attacker that a known multiple of $d$ modulo $n$ lands inside a smaller-than-usual range. Collecting a few hundred such equations turns finding $d$ into Boneh and Venkatesan's \emph{hidden number problem}, which is solved by finding an unusually short vector in a \emph{lattice} (a regular grid of integer linear combinations of basis vectors in $\R^m$) using the Lenstra--Lenstra--Lov\'asz (LLL) basis-reduction algorithm in polynomial time. Each biased nonce leaks a fraction of a bit of $d$, and a few hundred signatures expose the full key.
\end{connectionbox}

\subsection{The fix: deterministic nonces (RFC 6979)}
\label{ch22:rfc6979}

The cleanest defense removes run-time randomness from signing altogether. Instead of asking an RNG for $k$, RFC~6979 derives $k$ deterministically from the private key $d$ and the message digest $\Hash(m)$ using HMAC (Chapter~15) as a Deterministic Random Bit Generator (HMAC-DRBG, Chapter~17):
\[
  k = \operatorname{HMAC-DRBG}\bigl(d,\, \Hash(m)\bigr) \bmod n.
\]
Because $k$ is a function of $(d, \Hash(m))$, two messages with distinct digests get distinct nonces, preventing reuse across different messages, while signing the exact same message twice produces the exact same $(r, s)$ (so $s_1 = s_2$ and subtraction gives $0 \equiv 0$, leaking nothing). Because $d$ is secret, $k$ is unpredictable to outsiders, and because no RNG is called during signing, a faulty \texttt{SecureRandom} cannot cause a collision.

\begin{whybox}
Calling a deterministic nonce ``safe'' sounds contradictory after insisting $k$ be random. What the security proof requires is that each nonce be \emph{unpredictable to anyone without $d$} and \emph{independent-looking across distinct messages}. Applying a keyed pseudorandom function (PRF, Chapter~15) such as HMAC to the message satisfies both properties: without the key $d$, its outputs are computationally indistinguishable from uniform random integers, and distinct inputs map to unrelated outputs. Replacing a hardware RNG call at signing time with a keyed hash of $(d, \Hash(m))$ eliminates an entire class of implementation failures.
\end{whybox}

\section{EdDSA and Ed25519}
\label{ch22:eddsa}

EdDSA (Edwards-curve Digital Signature Algorithm), and its primary instance \emph{Ed25519},
is the default signature choice for new designs. Standardized in RFC~8032, it pairs Claus Schnorr's
linear signature equation with Daniel Bernstein's twisted Edwards curve edwards25519 (Chapter~21).
Its design eliminates the main implementation traps of DSA and ECDSA: nonces are deterministic by
construction, signing needs no modular inverse, and the curve's addition formula has no special-case
branches that leak secret bits through timing. SSH, TLS~1.3, Signal, and modern operating systems
use it by default.

\subsection{How Ed25519 signs}
\label{ch22:ed25519-algo}

The public parameters are the twisted Edwards curve edwards25519 over the prime field $\F_{2^{255}-19}$, a base point $B$ generating a subgroup of prime order $\ell \approx 2^{252}$ (the full curve has $8\ell$ points, cofactor $8$, Chapter~21), and the 512-bit hash function $\Hash = \text{SHA-512}$.

\textbf{Watch the letters.} Following RFC~8032, the letters $r$ and $k$ swap roles relative to ECDSA: here $r$ is the \emph{secret} nonce scalar and $k$ is the \emph{public} hash challenge, whereas in ECDSA $k$ was the secret nonce and $r$ was a public coordinate.

\textbf{Keys.} The private key is a uniformly random 32-byte seed. Hashing that seed with SHA-512 produces 64 bytes: the first 32 bytes -- clamped by clearing the bottom three bits and fixing the top two bits (Chapter~21) so the scalar is a multiple of the cofactor $8$ of fixed bit length -- form the secret scalar $a$, and the second 32 bytes form a secret nonce prefix $\mathrm{pre}$. The public key is the curve point $A = aB$, encoded in 32 bytes (its 255-bit $y$-coordinate plus one sign bit selecting between $\pm x$).

\textbf{Sign} a message $M$:
\begin{enumerate}
  \item Compute $r = \Hash(\mathrm{pre} \concat M) \bmod \ell$, the deterministic nonce scalar derived from the secret prefix and the message (no RNG call).
  \item Compute the commitment point $R = rB$.
  \item Compute $k = \Hash(R \concat A \concat M) \bmod \ell$, the challenge scalar binding $R$, the public key $A$, and the message $M$ (with points $R$ and $A$ serialized as 32-byte strings).
  \item Compute the response scalar $S = (r + k\,a) \bmod \ell$.
  \item Output the 64-byte signature $(R, S)$ (32 bytes for $R$, 32 bytes for $S$).
\end{enumerate}

\textbf{Verify} $(R, S)$ on $M$: reject if $S \ge \ell$ or if $R$ or $A$ fails to decode to a curve point; otherwise compute $k = \Hash(R\concat A\concat M)\bmod \ell$ and accept iff
\[
  S\,B = R + k\,A.
\]
(RFC~8032 also permits multiplying both sides by the cofactor $8$ -- checking $8 S B = 8 R + 8 k A$ -- so single-signature and batch verification agree on every point.)

\begin{whybox}
\textbf{Why verification works.} Since $S = (r + ka) \bmod \ell$ and $B$ has prime order $\ell$, scalar multiplication acts modulo $\ell$:
\[
  S\,B = (r + k\,a)B = rB + k(aB) = R + k\,A.
\]
The secret scalar $a$ appears on the right only inside the public key $A = aB$, so the verifier checks the equation using public values alone (Figure~\ref{ch22:fig-ed25519-flow}). This follows Schnorr's commit--challenge--response pattern: commit to $R = rB$, derive a hash challenge $k$ from $(R, A, M)$, and answer with $S = r + ka \bmod \ell$. Hashing $R$ and $A$ \emph{into} $k$ prevents malleability and avoids DSA and ECDSA's modular inverse $k^{-1}$.

Trace the same equation on the small curve of Example~\ref{ch22:ex-ecdsa} ($G = (5,1)$, prime order $n = 19$, secret $a = 7$, public $A = 7G = (0,6)$). Pick nonce $r = 3$, so $R = 3G = (10,6)$, and suppose the challenge hash evaluates to $k = 4$. Then
\[
  S = (3 + 4\cdot 7) \bmod 19 = 31 \bmod 19 = 12,
\]
with no modular inverse needed. The verifier checks $12G = (0,11)$ against $R + 4A = 3G + 4(7G) = 31G = 12G = (0,11)$, and accepts.

Why can't a forger fake $(R, S)$ without knowing $a$? If she chooses $R$ first, the hash fixes $k = \Hash(R \concat A \concat M) \bmod \ell$, and finding $S$ such that $SB = R + kA$ requires taking a discrete logarithm to base $B$. If instead she picks $S$ and $k$ first and sets $R = SB - kA$ so the curve equation holds, then $\Hash(R \concat A \concat M) \bmod \ell$ matches her chosen $k$ with probability only $1/\ell \approx 2^{-252}$.
\end{whybox}

\begin{focusbox}
What Ed25519 resolves compared with DSA and ECDSA:
\begin{itemize}
  \item \textbf{Deterministic nonce} ($r = \Hash(\mathrm{pre}\concat M) \bmod \ell$): no RNG is called at signing time, so the PlayStation~3 and Android Bitcoin failures cannot occur.
  \item \textbf{No modular inversion} in signing: $S = (r + ka) \bmod \ell$ needs only multiplication and addition modulo $\ell$, avoiding division-by-zero edge cases and simplifying constant-time code.
  \item \textbf{Complete addition formulas} on edwards25519 (Chapter~21): a single point-addition formula handles every pair of inputs without secret-dependent \texttt{if} branches that leak timing information.
  \item \textbf{Strong unforgeability (sEUF-CMA)}: hashing $R$ into $k$ binds the nonce point, and checking $0 \le S < \ell$ with canonical point encoding blocks ECDSA-style $(r, n-s)$ malleability.
  \item \textbf{High speed and batch verification}: a single laptop core signs and verifies tens of thousands of messages per second, and \emph{batch verification} -- checking many equations $S_i B = R_i + k_i A_i$ at once via a random linear combination -- runs faster still.
\end{itemize}
\end{focusbox}

\begin{applicationbox}
Ed25519 is the default host-key and user-key algorithm in OpenSSH (the standard SSH suite, via \texttt{ssh-keygen -t ed25519}); it signs long-term identity keys in Signal's Extended Triple Diffie--Hellman (X3DH) handshake (Chapter~27); it signs Git commits and tags, Linux package repositories, Certificate Transparency logs (public append-only ledgers of issued web certificates, Chapter~24), and DNSSEC zones; and it is built into TLS~1.3. Unless legacy compatibility or post-quantum resistance (resistance to future quantum computers, Chapter~35) dictates otherwise, Ed25519 is the standard choice for new systems.
\end{applicationbox}

\begin{implementbox}
A structural sketch of Ed25519 in Python. \textbf{For learning only -- do not use in production.} This outline omits bit clamping, curve-point encoding and validity checks, cofactor handling, and constant-time arithmetic; production code should call a vetted library such as \texttt{libsodium} or Python's \texttt{cryptography}.
\begin{lstlisting}[language=Python]
import hashlib

# Assume curve helpers exist: B (base point), L (subgroup order),
# point_mul(scalar, P), point_add(P, Q), encode(P) -> bytes, decode(b).
def H(b: bytes) -> int:
    # RFC 8032 uses little-endian ("little"): first byte is least significant.
    return int.from_bytes(hashlib.sha512(b).digest(), "little")

def sign(A_enc: bytes, M: bytes, a: int, prefix: bytes) -> bytes:
    r = H(prefix + M) % L                  # deterministic nonce -- no RNG
    R = point_mul(r, B)
    R_enc = encode(R)
    k = H(R_enc + A_enc + M) % L           # challenge binds R, A, M
    S = (r + k * a) % L                    # linear response: no inversion
    return R_enc + S.to_bytes(32, "little")

def verify(A, A_enc: bytes, M: bytes, sig: bytes) -> bool:
    R_enc, S = sig[:32], int.from_bytes(sig[32:], "little")
    if S >= L:
        return False
    R = decode(R_enc)
    k = H(R_enc + A_enc + M) % L
    return point_mul(S, B) == point_add(R, point_mul(k, A))
\end{lstlisting}
Note the range check \texttt{S >= L} in \texttt{verify}: rejecting non-reduced scalars $S + \ell$ preserves strong unforgeability.
\end{implementbox}

\section{What Signatures Guarantee -- and What They Do Not}
\label{ch22:guarantees}

A valid signature makes a precise, narrow claim, and most protocol bugs around signatures come from assuming it proves more than it does.

\textbf{A valid signature $\sigma$ on $m$ under $pk$ guarantees:}
\begin{itemize}
  \item \textbf{Authenticity:} someone holding the private key $sk$ paired with $pk$ produced $\sigma$ for this exact byte string $m$.
  \item \textbf{Integrity:} $m$ has not been altered since signing; flipping even one bit causes $\Vrfy_{pk}(m, \sigma)$ to reject.
  \item \textbf{Non-repudiation:} the holder of $sk$ cannot credibly claim a verifier fabricated $\sigma$ (unless $sk$ itself was stolen).
\end{itemize}

\textbf{It does \emph{not} guarantee:}
\begin{itemize}
  \item \textbf{Who owns $pk$.} A signature ties a message to a \emph{public key}, not to a \emph{person} or domain name. Binding keys to real-world identities is the job of digital certificates and public-key infrastructure (PKI, Chapter~24). If an attacker tricks you into verifying with the attacker's $pk$, every check passes cleanly for an impostor.
  \item \textbf{Confidentiality.} Signatures protect integrity and origin, not secrecy; $m$ is ordinarily sent in plaintext alongside $\sigma$. Keeping $m$ secret requires encryption as well (and careful composition; see below).
  \item \textbf{Freshness (replay protection).} A valid signature on ``Pay Bob \$100'' remains valid if an attacker replays the exact pair $(m, \sigma)$ tomorrow or next year. Preventing replay requires a unique request ID, counter, or timestamp \emph{inside} the signed bytes $m$ (just as with MACs, Chapter~15).
  \item \textbf{Human intent.} Signing proves the private key processed those bytes, not that a human read or understood them. ``Blind signing'' of raw digests has let phishing sites trick users into authorizing unintended cryptocurrency transfers on hardware key devices.
  \item \textbf{Safety after key compromise.} Once $sk$ leaks (as on the PlayStation~3 or affected Android wallets), an attacker can forge signatures indistinguishable from genuine ones. Limiting that damage requires short-lived keys, revocation mechanisms that cancel compromised keys (Chapter~24), and periodic \emph{key rotation} (retiring old keys in favor of fresh ones).
\end{itemize}

\begin{trapbox}
\textbf{Sign-then-encrypt, encrypt-then-sign, and surreptitious forwarding.} Composing public-key signing with public-key encryption without naming the parties inside the payload fails in both orders (Figure~\ref{fig:ch22-surreptitious-forwarding}). If Alice signs $m$ and encrypts the pair to Bob -- sending $\Enc_{pk_B}(m, \Sign_{sk_A}(m))$ -- Bob can decrypt with $sk_B$, keep Alice's valid pair $(m, \sigma_A)$, and re-encrypt it under Carol's public key $pk_C$. Carol decrypts, checks $\Vrfy_{pk_A}(m, \sigma_A) = 1$, and wrongly concludes Alice sent $m$ \emph{to Carol}. Reversing the order ($\Sign_{sk_A}(\Enc_{pk_B}(m))$) lets an outsider strip Alice's outer signature from the ciphertext and attach their own signature $\Sign_{sk_E}(\Enc_{pk_B}(m))$, claiming authorship of Alice's encrypted message. The fix is to bind both sender and intended recipient \emph{inside} what is signed and encrypted -- for example signing $\texttt{"from Alice to Bob:"} \concat m$ -- a lesson learned the hard way in early Pretty Good Privacy (PGP) email tools.
\end{trapbox}

\begin{figure}[htbp]
\centering

\begin{intuitionbox}
A \emph{digital certificate} is a signature whose message states ``public key $pk$ belongs to \texttt{example.com}'', signed by a certificate authority (CA). Signatures provide the mechanism; PKI (Chapter~24) uses them to link keys to names. Web HTTPS, operating-system code signing, and app-store verification all work by chaining such signed statements back to a root public key pre-installed on your device.
\end{intuitionbox}

The four schemes covered here trade off along four axes: underlying hard problem, key and signature byte sizes, nonce handling, and exposure to implementation mistakes (Table~\ref{ch22:tab-summary} and Figure~\ref{fig:ch22-size-comparison}).

The four schemes differ only in what the private operation is -- an $N$-modulus $d$-th power, a modular discrete-log equation, or a linear Schnorr response on an Edwards curve -- and in whether nonce safety relies on an external RNG or is built into signing itself.

With signatures in hand, two parties can verify who is speaking across an untrusted network.
Chapter~23 combines ephemeral Diffie--Hellman key exchange with digital signatures so that
sessions are both authenticated and protected by forward secrecy, keeping past traffic secret
even if a long-term signing key is later stolen.

\section{Exercises}
\label{ch22:exercises}

\begin{exercise}[MAC vs.\ signature, in court]
Alice sends Bob a money order authenticated with a shared-key MAC. Bob takes the tag to a judge as proof Alice authorized the payment. Explain precisely why the MAC tag is \emph{not} convincing evidence, and why a digital signature would be. Which exact property is doing the work?
\end{exercise}

\begin{exercise}[Textbook RSA forgery]
With $N = 3233$, $e = 17$, $d = 2753$ (Example~\ref{ch22:ex-textbook}), an attacker has obtained Alice's textbook-RSA signatures on $m_1 = 3$ and $m_2 = 5$. Produce, with no knowledge of $d$, a valid signature on $m^* = 15 \bmod 3233$. Show the arithmetic and verify your forgery passes $\sigma^e \equiv m^* \pmod N$.
\end{exercise}

\begin{exercise}[Why hashing stops the forgery]
Repeat the previous exercise but for \emph{hash-then-sign} RSA. Explain why the multiplicative trick now fails, and state precisely what computational problem the attacker would have to solve instead (name it, and say on which object -- message or digest).
\end{exercise}

\begin{exercise}[DSA verification by hand]
Using the DSA parameters of Example~\ref{ch22:ex-dsa} ($p=23$, $q=11$, $g=4$, $y=18$), verify the signature $(r,s) = (3,10)$ on a message with digest $h = 9$ by computing $w, u_1, u_2$, and $v$ independently, and confirming $v = r$.
\end{exercise}

\begin{exercise}[Sign with ECDSA]
On the curve of Example~\ref{ch22:ex-ecdsa} ($\F_{17}$, $G=(5,1)$, $n=19$, $d=7$, $Q=(0,6)$), sign a message with digest $h = 4$ using nonce $k = 5$. You are given $5G = (9, 16)$. Compute $r$, then $s$, and write the signature. (You will need $5^{-1}\bmod 19$.)
\end{exercise}

\begin{exercise}[Recover the key from reuse]
Continuing the previous setup, suppose Alice also signed a message with digest $h' = 13$ using the \emph{same} nonce $k = 5$, producing $s'$. Without using the known value $d=7$, set up the two-signature equations, solve for $k$, then for $d$, and confirm you recover $d = 7$. (Compute $s'$ first from the signing equation, then pretend you only know $r, s, s', h, h'$.)
\end{exercise}

\begin{exercise}[Spot the bad nonce]
You are auditing a batch of ECDSA signatures from one signer. Describe the single cheap check that detects same-nonce reuse across a corpus of signatures, why it works, and what an attacker who runs the same check can then do. Relate this to how the 2013 Android-wallet thefts were carried out on the public blockchain.
\end{exercise}

\begin{exercise}[ECDSA malleability]
Show that if $(r, s)$ verifies under public key $Q$ for message digest $h$, then $(r,\, n - s)$ also verifies. (Hint: trace what happens to $w = s^{-1} \bmod n$, then to $u_1$ and $u_2$, and finally to the recovered point's $x$-coordinate.) State the ``low-$s$'' rule on $\{1, \dots, n-1\}$ that removes the duplicate.
\end{exercise}

\begin{exercise}[Why no inversion in EdDSA]
EdDSA's response is $S = (r + ka) \bmod \ell$, with no $k^{-1}$, whereas ECDSA's is $s = k^{-1}(h + dr)\bmod n$. Give two concrete engineering advantages of avoiding the modular inverse (consider zero-divisor edge cases and constant-time execution against timing side channels), and explain why hashing $R$ into the challenge $k$ makes EdDSA strongly unforgeable (sEUF-CMA) whereas ECDSA satisfies only plain EUF-CMA.
\end{exercise}

\begin{exercise}[The narrow promise]
For each scenario below, state whether a valid signature defends against it, and if not, name the mechanism that does: (a) an attacker flips a byte of the message in transit; (b) an attacker replays last week's signed ``open gate'' command; (c) an attacker presents a valid signature under a public key that belongs to the attacker rather than the bank; (d) an eavesdropper reads the signed message's contents.
\end{exercise}

\begin{exercise}[Deterministic yet unpredictable]
RFC~6979 derives $k$ deterministically from the private key and the message digest. Argue that this satisfies the security requirement on the nonce even though $k$ uses no RNG at signing time, and identify which property of HMAC guarantees that two messages with distinct digests will not collide on the same $k$ in practice.
\end{exercise}

\begin{exercise}[Surreptitious forwarding]
Alice computes $\Enc_{pk_B}\bigl(m, \Sign_{sk_A}(m)\bigr)$ -- signing $m$ with her private key $sk_A$ and encrypting the message--signature pair under Bob's public key $pk_B$ -- and sends it to Bob, intending ``$m$, from Alice, for Bob.'' Show how Bob can make Carol believe Alice sent $m$ to \emph{Carol}. Then propose a change to what gets signed that defeats the attack, and explain why it works.
\end{exercise}
